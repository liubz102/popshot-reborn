# 会话 18 —— 拾取链与结算数值（2026-08-08）

## 用户报的两个现象

1. 路上打死的怪会掉武器、boss 也掉金币了，但**角色走过去捡不起来**。
2. 结算页面左上角已经是「完成」，但**经验 / 金币 / 分数全是 0**。

两个都查清并修好了，代码在 `server/gameserver.py`，硬事实在 FINDINGS §115–§116，
决策在 D053 / D054。**两个都做了实机验收。**

## 做了什么

### 一、捡不起来（§115，D053）

又是同一个形状：**判定在服务端，客户端报完就等着**，这次是第四条
（前三条是 §108 血量归零、§111 换图、§113 掉落物）。

`§113` 末尾那句「捡起掉落物不发任何包」**是错的，已勘误** —— 当时只扫了
`Item` 那一片地址的 `RawPacket::SetType` 调用点，而拾取包是 `Character` 发的。

链路：

```text
Character::CheckItemPickup 0x5154d3   碰撞成立 -> C→S 0x0407 {座位, 句柄}
                                      并且 [item+0x2a8] = 1  ★ 一件一局只报一次
   ★ 服务端回 0x0405 -> 0x551d35 -> Item::vf_d4 -> vf_11c 生效 + vf_20 删物件
```

`[item+0x2a8] = 1` 是关键：服务端不回，那件东西**彻底作废**，
反复走上去也不会再报第二次 —— 这就是用户说的「捡不起来」。

**定位手法**（新的一条，值得复用）：几个 Item 子类的**主 vftable 并排打印**，
只有 `+0x11c` 那一格逐类不同 → 那就是「拾取生效」的虚函数 → 反扫
`call [reg+0x11c]` 找到 `Item::vf_d4`(`0x51f447`) → 再反扫 `call [reg+0xd4]`
在包处理器那片命中 `0x551d89` → 它所在函数的唯一调用点在**跳表**
`0x54e5ae` 的第 0 项，跳表基址是 `opcode - 0x405`，**opcode 直接按下标数出来**。

修法同 D046：**原样回显**两个 int32。

### 二、结算数值全 0（§116，D054）

数值来自**两个不同的包**，这是之前一直没理清的地方：

| 界面行 | 包 | 业务值下标 |
|---|---|---|
| 分数 / 生命 | `0x0411 gspEndGame` | 5+6+7 之和 / 剩余生命（客户端本地） |
| 经验值 | `0x0309 gspRepGameResult` | 9 |
| 金币 | `0x0309` | 10 |
| 竞技场分数 | `0x0309` | 11 |

* 分数：`0x551804` 把包搬成 13 个 dword 的结算表 →
  `[GameContextQuest + 座位*0x34 + 0x3ec]`，`0x4a4e40` 把表[5]+表[6]+表[7]
  相加，用 `L"%d / %d"`（`0x668114`）和剩余生命一起画。
* 另外三行由**基类**画法 `GameContext::vf_44`(`0x48db6c`) 读
  `[ctx + 座位*4 + 0x2c / 0x44 / 0x5c]` 画成 `+%d`，
  标签串 `L"LADDER POINT"` / `L"PIXEL"` 就写在各自的画法旁边。
* ⚠ `0x0309` 的结构体里 `+0x24`/`+0x25` 是两个挨着的 1 字节 bool，
  所以从那儿之后「线序」比「结构体偏移」少 6 字节。

其余 20 个业务值继续填 0（D054）—— §100 那次一次全填会让客户端 20 毫秒内断链。

## 代码改动

* `OP_GET_ITEM`(0x0407) / `OP_PICKED_ITEM`(0x0405 服务端方向)、
  `parse_get_item` / `build_picked_item` / `GET_ITEM_FORMAT`。
* `Conn.on_get_item` —— 原样回显；`items_picked` 计数 + `reset_quest_state` 清理。
* `0x0407` 加进 `NOISY_OPCODES`（金币雨一局能上百件），首件照常记一行。
* `GAME_RESULT_EXPERIENCE/MONEY/LADDER_POINT` + `build_game_result_values`；
  `END_GAME_SCORE_PARTS` + `build_end_game_values(score=)`。
* `send_end_game` 填这四个数，日志行也把三格增量写出来。
* 控制通道新增 `pickup <句柄> [座位]`，`status` 增加 `items_picked`。
* 测试 156 → **176 项全过**（新增 20 项）。

## 实机验收

`start-debug.bat` 起，关卡「神秘岛 简单」，客户端 pid 23668。

* **拾取**：`drop 10101` 掉在角色脚下 → 客户端立刻发
  `0x0407 {0, 0x40000005}` → 服务端回 `0x0405` 同样两个字段。
  最硬的一发是红心：`probe_death.py` 读到 **HP 53 → 68**，
  说明 `vf_11c` 真的跑了，不只是包对上了。全程 **0 个 `0x0106 gcpReportHack`**。
* **结算数值**：本局分数 247，结算界面
  （`.claude/sessions/2026-08-08-18-result.png`）：

  ```text
  分数 / 生命    247 / 2
  经验值         +247
  竞技场分数     +0
  金币           +247
  ```

* 回房间后右上角数据栏也对得上（金币 7714 → 8068 = +354，正好是上一局的分数）。

## 遗留

1. 结算界面还剩**「合成材料」「称号卡片」两格**是空的。它们是**物件槽**
   （画的是图不是数字），不在这 24 个业务值里；`0x48e5a8` 起那段按房间类型
   分支去读 `[对象+0x24 + 下标*4 + 0x14/0x24/0x50]`，数据源还没跟到。
   `10103 ItemCard` 就叫「称号卡片」，多半能和 §113 的物件 id 对上。
2. **「真通关一次」的终验仍然没做**（会话 17 就欠着）。这次是用控制通道
   `endgame` 结算的 —— 走的是客户端发 `0x040f` 时的同一条 `send_end_game`，
   包字节完全一样，但「打死关底 → 金币雨 → 结算写完成 + 数值」这一整条
   还是没连着跑过。
3. `0x0309` 剩下 9 个业务值仍然不敢填（§100 的断链没查清）。

## 踩到的坑

* **结算界面是逐行动画展开的**（`0x4a4af5` 的 `[ebp+0x10]` = 展到第几行）。
  弹出后 6.4 秒才展到「金币」那一行 —— 第一次截图早了，以为金币还是空的。
  截结算页至少要等到 **+6.5 秒**，或者连拍几张。
* 第一次验拾取时在角色**旁边**掉了四件（间隔 40 单位）然后走过去，一发
  `0x0407` 都没有 —— 不是链路问题，是根本没碰上（掉落点 y 和角色走的
  地面高度差了近 100）。**验拾取要先 `probe_death.py` 读出角色坐标，
  直接掉在它脚下。**
