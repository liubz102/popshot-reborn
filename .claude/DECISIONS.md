## D061 战斗内同步方案 = **先探查再定**，不预先押注

- **决策**：里程碑 J 拆成 J.1 探查 → **J.2 停下来问用户** → J.3 实现。
  在 J.1 拿到实测结论之前，不写任何 UDP / 中继代码，也不预先承诺哪种架构。
- **理由**：
  1. 现有线索（FINDINGS §122）只够支撑「大概率是 P2P UDP + TCP 中继兜底」这个**推论**，
     没有一个字节的实测。押错方向的代价是整段白写。
  2. 两条路的工作量差一个数量级：P2P 只要服务端转发对端地址；
     TCP 中继要从零逆 `RelayConnection` / `rcpRegister` 那套帧格式。
  3. 这直接决定「云端联机到底能不能打」，是产品级取舍，应该由用户拍板而不是 agent 替他定。
- **被否**：直接实现服务端中继（可能白做）、直接做 P2P（云端可能不可用）。
- **反悔条件**：J.1 发现同步其实就在 gcp/gsp 里（比如 `0x040a`/`0x040b`/`0x040d`
  之一就是位置包），那这条决策自动作废，直接实现即可。
- **来源**：用户在 V0.2 会话 01 明确选择「先探查再定」。

## D062 服务端包 Windows / Linux **两边都自带独立 Python 运行时**

- **决策**：`tools/build-server-package.ps1` 产出的服务端包里同时带
  `runtime-win/python/`（复用现有 CPython 3.14.3 embeddable）和
  `runtime-linux/python/`（`python-build-standalone` 的 `x86_64-unknown-linux-gnu`）。
  `start.bat` / `start.sh` 各自挑对应的那份，**目标机什么都不用装**。
- **理由**：用户明确选择。开服的人不一定懂 Python 环境；云主机镜像自带的 python3
  版本参差（有的还是 3.6），而 `server/` 用了 `str | None` 这类新语法。
  自带运行时把「版本对不对、pip 装没装」整类问题一次消掉。
- **被否**：依赖系统 `python3`（包只有几百 KB，但要写版本检查和一堆报错提示）；
  只自带 Windows 那份。
- **反悔条件**：Linux 运行时体积或授权成为问题时，退回「优先用自带、找不到就用系统 python3」
  的双轨兜底 —— 但不能反过来（默认系统 python3）。
- **注意**：下载 `python-build-standalone` 时**必须记录 SHA-256** 并写进 FINDINGS，
  沿用 V0.1 D055 对内置 CPython 的做法；上游许可证随包保留。

## D063 单机模式的本地服务端也监听 `::`

- **决策**：客户端包里那个「单机游玩」用的服务端，和云端服务端**用完全相同的监听方式**
  —— `socket.create_server(('::', port), family=AF_INET6, dualstack_ipv6=True)`。
  不为单机单独做一套只绑 `127.0.0.1` 的分支。
- **理由**：
  1. 用户明确选择。
  2. 铁律 8 要求单机和云端共用同一套代码，**差异只能体现在配置上**。
     为单机加一个「只绑本机」的分支，就等于开了两套行为的口子。
  3. 顺带白送一个能力：想在局域网开黑的人不必去部署服务端包，
     直接让朋友填自己的内网 IP 就能连。
- **代价（要如实告诉用户，写进 README）**：玩单机时本机的 47611 / 27799 / 注册页
  三个端口对局域网开放。存的是明文密码，所以这不是零风险的。
- **被否**：只绑 `127.0.0.1`（最安全但和云端行为分叉）；
  加一个 `server.config` 开关（用户明确说监听地址「不用设置」）。
- **反悔条件**：用户改主意，或出现被局域网扫描骚扰的实际问题。

## D064 认证服和游戏服合并成**一个进程**（`server/app.py`）

- **决策**：`server/app.py` 是唯一入口，一个进程里起认证（47611）、游戏（27799）、
  注册网页、调试控制通道四个监听器。`authserver.py` / `gameserver.py` 降级为模块，
  它们的 `main()` 保留（单独调试时还能用），但监听逻辑抽成可被 `app.py` 调用的函数。
- **理由**：
  1. **票据必须跨这两个服务共享**。V0.1 靠往 `accounts.json` 里写 `active_account`
     绕过了这个问题，那只在「全世界只有一个玩家」时成立。多账号下要么合并进程，
     要么再造一套 IPC —— 后者纯属自找麻烦。
  2. 服务端包的启动脚本从「起两个进程还要各自看住」变成一行。
  3. 大厅 / 房间的共享状态（谁在线、有哪些房间）本来就该在一个进程里，
     跨进程还得同步。
- **被否**：保持两个进程 + 用文件或本地 socket 传票据（多一层故障面，且 Windows 上
  文件锁很难做对）；把认证服的功能塞进游戏服（端口和协议完全不同，混在一个类里更乱）。
- **反悔条件**：将来真的要把认证独立部署（比如多台游戏服共用一个账号中心）。
  那时 `AccountStore` 换成 HTTP 客户端即可，`app.py` 的结构不用动。

## D065 联机模式靠**本机 TCP 中继**接远端，不改客户端的 `connect` 目标

- **决策**：客户端包里带一个 `server/relay.py`，联机时
  `bshook` 把 `connect` 重定向到 `127.0.0.1:47621` / `127.0.0.1:27809`，
  由中继用 `getaddrinfo` 解析 `server.config` 里的地址再转发到远端的 47611 / 27799。
  中继**纯字节转发**，不碰协议。
- **理由**：
  1. 客户端是 2007 年的 32 位程序，`connect` 的参数是 `sockaddr_in`（**纯 IPv4**）。
     需求要支持 IPv6 和域名，在 hook 里没法表达 —— 除非在本机加一跳。
  2. 域名解析放在 Python 侧比在 C 的 hook 里做省事得多，且 `getaddrinfo`
     天然吃 IPv4 / IPv6 / 域名三种写法，需求一次满足。
  3. SnowCipher / SimpleCipher 都是**有状态的流密码**，中继只能整字节透传，
     绝不能拆包重组 —— 纯转发反而是最安全的形态。
- **被否**：在 `bshook` 里做 DNS 解析后填 IPv4（IPv6 无解）；
  改客户端命令行 `/serverip:`（V0.1 §14 提到有这个开关，但地址还是 IPv4 字符串，
  且改不了「按单选钮切换」的需求）。
- **反悔条件**：实测发现客户端还有别的出站连接没被 hook 覆盖（比如公告页用 wininet），
  那些不影响游戏，忽略即可。

## D066 单机 / 联机的区分靠**重定向到不同的本地端口**，不靠中继猜

- **决策**：`bshook` 的 `det_connect` 读登录框单选钮（`1011` 单机 / `1012` 联机）的状态：
  单机 → `127.0.0.1:47611` / `127.0.0.1:27799`（本地服务端）；
  联机 → `127.0.0.1:47621` / `127.0.0.1:27809`（中继）。
- **理由**：`connect` 发生在用户点「开始」之后，那一刻单选钮状态是**确定的**，
  判定没有竞态。若改成「中继和本地服务端都听同一个端口，由谁去猜模式」，
  就得引入模式文件或握手，凭空造一个时序 bug 出来。
  端口区分是零状态的，两个后端各管各的。
- **被否**：让 `launch.ps1` 提前问用户模式（用户要求在**登录界面**里选）；
  用文件传模式（有读写竞态）。
- **反悔条件**：客户端在别的时机建连（比如登录框出现前就连），
  那时改成「默认单机，切到联机后重连」。

## D068 登录框的注册链接**由我们接管**，不去猜原版怎么处理点击

- **决策**：给 `id=1010` 那条 Static 加 `SS_NOTIFY`、`SetWindowPos(HWND_TOP)`
  提到分组框上面、再子类化它的窗口过程，自己在 `WM_LBUTTONUP` 里
  `ShellExecuteW` 打开我们的注册页。同时保留 `ShellExecuteW/A` 的 hook
  （用于改写万一还有别的地方跳注册 URL，也用于日志）。
- **理由**：实测那条链接**在原版里就点不动**（FINDINGS §125）——
  没有 `SS_NOTIFY` 所以鼠标消息到不了它，而且 z 序上被分组框压着；
  真点上去**没有任何 `ShellExecute` 调用**。也就是说没有「原版行为」可以顺着改，
  只能自己造一个。子类化是最短的路径，且完全不碰游戏代码字节。
- **被否**：只 hook `ShellExecute`（客户端根本不调，白搭）；
  在内存里改那个已死的 tiancity URL 字符串（改了也没人去读它）。
- **反悔条件**：将来发现客户端在别的入口也会跳注册页，那时 hook 就派上用场了
  —— 两条路并存，互不干扰。

## D067 密码明文保存，但**日志里只打票据不打密码**

- **决策**：`accounts.json` 按用户要求明文存密码；但服务端日志（`logs/*.out`、
  每连接的 `game_*.txt`）**不打印密码**，登录相关只打用户名 + 票据前 8 位。
  注册页 / 登录页都要有明确的中文风险提示。
- **理由**：明文存盘是用户明确的产品决定（几十人规模、不用 DB），认了；
  但日志会被随手贴进 issue、发给别人排查，多一个泄漏面没有任何收益。
  V0.1 的 `authserver.py` 现在会把密码原样打进日志（`密码={p!r}`），**必须改掉**。
- **被否**：哈希存储（用户明确要求明文，且存档要能导出成人可读的 JSON）。
- **反悔条件**：无。这条只是把「明文」的范围限制在必要的地方。

## D069 登录失败的提示**用客户端自带的中文**，不自己造文案

- **决策**：认证服回 `20025`（不存在的帐号）/ `20026`（密码错误）这两个
  **客户端认识的 NMCO 错误码**，让它自己弹自己的中文框（FINDINGS §128）。
  不去 hook `MessageBoxW` 改写文案，也不在 hook 里另造一个提示窗。
- **理由**：
  1. 文案、字体、按钮全是原版的，和游戏里其它提示长得一模一样，
     玩家看不出这是我们加的东西 —— 复刻项目里这一点很值钱。
  2. hook 换文案要判「这个框是不是登录失败的那个」，还要知道**失败原因**；
     而原因只有服务端知道，联机时服务端还在另一台机器上，
     等于要为一句提示专门造一条旁路通道。回一个整数就没这些事。
  3. 翻译已经躺在 `Data/Chinese.ini` 里了，一个字都不用我们写。
- **被否**：bshook 换 `MessageBoxW` 文案（原计划 F.6，现作废）；
  在应答的字符串字段里塞中文（实测客户端**不显示**那两个字符串，
  `s2` 还被它当票据转发给了游戏服，§123）。
- **反悔条件**：将来要报的失败原因超出客户端那张表能表达的范围
  （比如「服务器维护中」「你被封号到 X 月 X 日」），那时再考虑自造窗口。

## D070 导入存档时**等级只能往上抬**

- **决策**：上传的存档里 `level` 比经验推出来的等级高 -> 把经验补到那一级的起点，
  让手改的等级真的生效；否则以**经验**为准（FINDINGS §131）。
  也就是说想降级必须把 `experience` 一起改小。
- **理由**：`level` 是派生字段（D024），两个字段打架时没法猜出玩家改的是哪一个，
  只能挑一个方向认。挑「往上抬」是因为：
  1. 玩家改存档十有八九是想变强，「把 level 改成 5」是最直觉的做法；
  2. 反过来认（level 永远说了算）会把「只改经验、不动 level」这种同样常见的
     改法**反向抹掉**，代价更大；
  3. 抬等级只动经验一个数，存档仍然自洽，读回来不会再变。
- **被否**：让 `level` 独立存储、不再由经验推（要动 D024 和结算/经验条整条链）；
  两个字段都照收（读一次就自相矛盾一次）。
- **反悔条件**：将来经验曲线变成分段/非线性，`(lv-1)*每级经验` 不再是那一级的起点。

## D071 被顶号回 `result=2`，其它票据失败仍回 `result=3`

- **决策**：`TicketStore` 记一张被作废票据的表；游戏服 `resolve()` 落空后再问
  `revoked_reason()`，**只有「被同账号的新登录顶掉」**这一种回
  `gspRepLogin(result=2)`（客户端弹「现有连接已断开。请重新尝试连接。」），
  其余（乱码票据、真的过期、从没签发过）仍然回 `result=3`（§132）。
- **理由**：
  1. 这两句话是**客户端自带的**，一个字都不用我们写，也不用改 bshook
     —— 和 D069「登录失败靠结果码说话」是同一条路子；
  2. 全都回 2 的话，一个乱码票据也会被告知「你的账号在别处登录了」，
     那是**在撒谎**，排查时会把人往错误方向带；
  3. 被顶号是**每次顶号必然发生**的一条路（客户端 9 毫秒后自动重连重放旧票据），
     不是边角情况，值得单独给一句对的话。
- **代价**：`TicketStore` 要多留一张表。已按同一个 TTL 过期，长期开服不会无限攒。
- **被否**：给旧连接发一个「你被踢了」的包再关（协议里没找到这么个包，
  而且客户端照样会重连重放票据，问题原样存在）；直接回 `result=1`
  （文案是「请重新确认帐号和密码」，账号密码根本没问题，更误导）。
- **反悔条件**：将来做「账号被封」「服务器维护」时需要更多种失败原因，
  客户端那三句话不够分，那时才谈自造窗口。

## D072 连接事件日志单独一个模块、单独一个文件，且和 `--verbose` 无关

- **决策**：新增 `server/eventlog.py`，统一前缀 `[online]` 打到 stdout，
  同时**追加**写 `logs/online.log`。认证 / 游戏服 / 注册页三处都往它记：
  谁认证通过、谁连上游戏服、谁登录成了、谁被顶号、谁断开（带 IP 和在线时长）。
- **理由**：
  1. 用户的需求是「谁连接了、谁断开了、IP 是什么」，这是**运营信息**，
     和逆协议用的逐包 dump 是两码事，不该被同一个开关关掉（§133）；
  2. 云服务端包要出**两套启动脚本**（精简 / debug），精简那套下这份流水
     就是唯一的排查依据，所以它必须在两套下都在；
  3. 另存一份文件是因为 `server.out` 每次启动被重定向覆盖。
- **被否**：把连接事件混进现有 `log()`（精简模式下也在，但会被逐包日志淹掉，
  且没法单独留档）；用 Python 的 `logging` 模块（要配 handler / formatter，
  比现在这三十行多，收益是零 —— 服务端全程只有一个进程、一个格式）。
- **反悔条件**：将来要按天切分 / 限制大小 / 输出 JSON 给别的工具吃，
  那时再换成 `logging` + `RotatingFileHandler`。

## D073 GameGuard 断点：等**目标指令解壳**，而不是等「主线程离开 APC」

- **决策**：采纳并合并 GPT-codex 给出的修法（`hook_merge\hook_DR0修改版\`）——
  武装 DR0 的判据从「主线程 EIP 不在那四个 DLL 里」换成
  「`0x54b0fc` 的 5 个字节已经是已知明文」，并加一条 10 毫秒的 DR0 守护回合。
  在它基础上我又改了三处：**保留 §124 的 2 秒余量**（GPT 版用满了整个超时，
  会和 bsloader 抢着报超时，DLL 的失败原因就写不出来）；
  `IsBadReadPtr` 换成 `VirtualQuery`；**加兜底武装**（详见 §134）。
- **理由**：旧判据在别人的电脑上 5 毫秒就成立，而那时主线程正落在
  **主模块自己的 ASProtect 壳**里（主模块不在排除表内），DR0 随即被壳的
  CONTEXT 恢复清掉 —— 日志写着「已武装」，断点永不命中。
  我这台机器不炸纯属采样时机的运气（§134）。
  新判据是「壳跑完了没有」的**直接证据**，不是对 EIP 的推测。
- **和 §124 的关系**：不推翻，两个坑叠在一起。§124 修的是「循环上限按次数算」，
  §134 修的是「判据本身错了」。合并后的代码两条都在。
- **被否**：只加守护、判据不动（能救回来，但每次都要先被清一次再补，
  且中间那段时间断点是失效的，一旦壳恰好在这窗口里执行到 `0x54b0fc` 就漏掉）；
  固定延时后再武装（V0.1 一开始就否掉的路子，机器快慢差几倍）。
- **反悔条件**：将来遇到按页惰性解壳的变体（`0x54b0fc` 直到被执行前一刻才明文），
  那时新判据永远等不到，会走兜底路径 —— 日志里会写「兜底已武装」，看到就来查这条。
