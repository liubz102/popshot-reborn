# DECISIONS — 关键决策与理由

> 只记「**为什么**这么选」。「是什么」记在 `FINDINGS.md`。
> 已定的方案不要无意义地推翻；要推翻请先读这里的理由，并在下面追加一条新决策说明改因。

格式：`## D<编号> 标题` + 决策 / 理由 / 被否方案 / 反悔条件

---

## D001 目标运行环境 = Win10 原生，不上虚拟机

- **决策**：客户端直接在用户这台 Win10 Pro 19045 x64 上跑。VM 只作兜底。
- **理由**：
  1. 用户明确选择"Win10 原生"。
  2. 用户报的失败是 **GameGuard 错误框**，说明 ASProtect 壳和 D3D9 在 Win10 上没问题
     —— 虚拟机能解决的那类兼容问题这里根本不存在。
  3. GameGuard 的更新服务器已停机 15 年，**在 XP 虚拟机里照样要停用它**，
     换环境并不能省掉这一步。
  4. 本机有 RTX 3070，原生跑图形性能远好于 VM。
- **被否**：XP 虚拟机、Win7 虚拟机。
- **反悔条件**：若阶段 2 发现 ASProtect 在 Win10 上存在无法绕过的行为差异
  （例如壳依赖 XP 时代的 ntdll 私有结构），再考虑 VMware + XP。

## D002 假服务端语言 = Python 3.14 + asyncio

- **决策**：`server/` 用 Python，优先零外部依赖（`struct` + `asyncio` 足够）。
- **理由**：协议逆向阶段需要**极高频的"改一版试一版"**，Python 的迭代成本最低；
  二进制解析用 `struct` 最直接；本机已装 Python 3.14。用户已确认。
- **被否**：Node+TS（能与用户之前的 Web 复刻同栈，但二进制处理啰嗦）、C#、Go。
- **反悔条件**：若最终发现性能瓶颈在服务端（几乎不可能，单机自用）。

## D003 脱壳策略 = 运行时 attach 转储，不硬啃 OEP

- **决策**：让客户端跑到 GameGuard 错误框（此时壳已解完、进程还活着），
  用 x32dbg attach + Scylla 转储，而不是从壳入口一步步跟到 OEP。
- **理由**：ASProtect 2.x 有大量 SEH 反调试和 stolen bytes，跟 OEP 很费时；
  而错误框给了一个**天然的、稳定的、壳已完全解开的暂停点**，白送的机会。
- **被否**：从 `EP=0x1000` 的 `push 0x7B2001` 开始跟 OEP（作为兜底保留）。
- **反悔条件**：attach 转储出来的镜像 Ghidra 认不出函数。

## D004 转储镜像只求可分析，不求可运行

- **决策**：`re\BigShot_dump.exe` 允许 IAT 有洞、允许跑不起来。
- **理由**：我们的目的是**读代码**（找 GameGuard 调用点、找协议），
  不是发布一个脱壳版。修 ASProtect 的 IAT 重定向到"能运行"的程度是数量级更大的工作量，
  且对目标毫无帮助 —— 真正运行的始终是原版 exe + 运行时 hook。
- **反悔条件**：若最终发现运行时 hook 路线完全走不通，才考虑做可运行脱壳版。

## D005 客户端修改方式 = 运行时注入，不静态改文件

- **决策**：所有对客户端行为的修改（GameGuard 绕过、网络重定向）都由
  `hook\bshook.dll` 在运行时打内存补丁 + API hook 完成，
  由 `hook\bsloader.exe` 拉起游戏并注入。`game_patched\BigShot.exe` **保持原样不改一个字节**。
- **理由**：exe 被 ASProtect 加密，静态改文件根本改不到真正执行的代码。
  运行时注入是唯一可行路径，而且改错了随时能撤，不会污染客户端。
- **推论**：patch 时机必须在**壳解完之后** —— DllMain 里起等待线程轮询特征字节，
  别在 DllMain 里直接写内存（那时目标位置还是密文）。

## D006 第一次运行前就把 GameGuard.des 改名

- **决策**：`game_patched\GameGuard.des` → `GameGuard.des.bak`，
  在**任何一次运行客户端之前**就改好。
- **理由**：2007 年的 nProtect GameGuard 会尝试安装内核驱动。
  没有任何理由往用户的日常工作机里塞一个 15 年前的、早已无人维护的 ring0 组件。
  反正它连不上更新服务器、也必然要被绕过，不如从一开始就不让它跑。
- **注意**：改名后游戏大概率还是会报 GameGuard 错误（游戏侧 npgl 模块自己会报），
  这不代表方案失败 —— 真正的解决在阶段 2 的运行时 patch。

## D007 不启动 NMService.exe / BsPatcherChn.exe

- **决策**：只跑 `BigShot.exe`，不跑 Nexon Messenger 服务和补丁器。
- **理由**：它们连的是 `platform.tiancity.com` / `ngm.nexon.net` 等已停机 15 年的地址，
  对进游戏毫无帮助，只会增加启动链上的失败点和排查噪音。
  `BigShot.exe` 只静态导入了 `nmcogame.dll` 的 `NMCO_MemoryFree`，
  真需要时用 stub DLL 顶替即可（见 `FINDINGS.md` §2.3 的 7 个导出）。

## D008 网络重定向用 API hook，不改 hosts / 不改 ini

- **决策**：在 `bshook.dll` 里 hook `connect`/`gethostbyname`/`getaddrinfo`/`WSAConnect`，
  把所有目标地址改写成 `127.0.0.1`（**端口保持不变**）。
- **理由**：
  1. `BigShotCN.ini` 是加密的，改不了；破解它的加密是纯粹的绕路。
  2. 服务器地址可能是**裸 IP**，那样改 hosts 根本不生效。
  3. hook 方案顺带免费得到"原始目标地址+端口"的日志，
     这正是我们判断有几个服务器、分别是什么角色所需要的信息。
- **被否**：改 hosts 文件、给回环网卡绑原服务器 IP、破解 ini 加密。

## D009 跨会话追踪体系放在 `.claude/`

- **决策**：`CLAUDE.md`（自动加载的入口）+ `.claude/{PLAN,PROGRESS,FINDINGS,DECISIONS}.md`
  + `.claude/sessions/`。每完成一小步立刻更新 `PROGRESS.md`。
- **理由**：用户明确要求全程由 AI 分阶段实施，单次会话上下文必然不够。
  `CLAUDE.md` 会被每个新会话自动加载，是唯一可靠的"入口指针"；
  把细节拆到 `.claude/` 下的专题文件，避免入口文件膨胀到没人读。
- **关键点**：`FINDINGS.md` 里**必须记录失败的尝试**（"死路清单"）。
  跨会话最大的浪费不是忘了成果，是重复踩同一个坑。

## D010 脱壳改用自写内存转储器，不用 Scylla

- **决策**：`tools/dump_process.py`（ctypes + ReadProcessMemory + 节表 PE 化），
  在客户端停在 GameGuard 错误框时转储。**不用 x64dbg + Scylla**。
- **理由**：
  1. Scylla 是 GUI 工具，本工程全程由 AI 分阶段实施，**无法脚本化 = 无法复现**。
  2. 目标只是「读代码」（D004），不需要能重新运行的脱壳版，
     那么原样倒内存 + 把 `PointerToRawData` 改成 `VirtualAddress` 就完全够用。
  3. GameGuard 错误框给了一个稳定、可重复、壳已完全解开的暂停点。
- **实测结果**：熵值 8.0 → 6.48/5.30/2.08，879 个 RTTI 类型名可读，**质量足够**。
- **保留**：x64dbg 仍留在 `tools/`，阶段 2 找 patch 点时做动态调试还用得上。

## D011 阶段 2 优先试命令行开关，其次才是内存 patch

- **决策**：先试 `BigShot.exe /serverip:127.0.0.1 /serverport:XXXX`
  （字符串证据见 `FINDINGS.md` §14），再考虑 hook `connect`。
- **理由**：官方自带的开关比我们打的补丁稳定得多，也不会被反作弊盯上。
  这可能让 D008（hook 重定向）整个变成不必要 —— 但 D008 的抓包价值仍在，
  所以 `bshook.dll` 的 send/recv 日志照做。
- **反悔条件**：实测开关无效，或只对部分连接生效。

## D012 bshook.dll 先做「只观测」版本，确认注入不被检测再动手改行为

- **决策**：第一版 `bshook.dll` 只记录模块/窗口/解壳时机，一个字节都不改。
- **理由**：ASProtect 2.x 有反调试反注入，先用最低风险的方式验证注入通道本身可用。
- **实测结果**：**注入完全没被检测**，客户端行为与不注入时一模一样
  （同样跑到 GameGuard 错误框）。通道可用，阶段 2 可以放心在上面加内存 patch。

## D013 阶段2 定位手法 = 动态 hook 错误框反推，不硬啃 Ghidra 静态

- **决策**：不导 Ghidra 手跟那坨混淆的 nProtect 代码，改用**动态**：在 `bshook.dll`
  里内联 hook `MessageBoxW`，等 GameGuard 错误框弹出时抓 `_ReturnAddress` + EBP 链回溯，
  直接拿到「谁决定弹这个框」的调用链，再用自写反汇编工具 `tools/re_bs.py`（capstone）
  静态确认校验条件。
- **理由**：
  1. `re_bs.py` 用 capstone/pefile（**本机其实已装**，FINDINGS §6 的「未装」作废），
     完全脚本化、可复现，比 Ghidra GUI 更契合「全程 AI 实施」。
  2. 校验主体（0x54b042）是重度混淆的 nProtect 代码，栈上还有构造出来的错误文本缓冲，
     纯静态从日志字符串往上爬极慢且易错；**从可观测行为（错误框）反推**一步到位。
  3. 事实证明：一次 hook 运行就拿到完整调用链 `0x5f7b9e→0x40a68e→0x40d039→0x54b042→弹框`，
     十几分钟定位到 5 字节 patch 点。
- **被否**：Ghidra headless + 脚本（保留备用，真要全量交叉引用时再上）。

## D014 GameGuard patch = 单点改校验取值，不动错误框/不动退出逻辑

- **决策**：只在校验点 `0x54b0fc` 把 `call 0x5611d0`（取 GameGuard 状态）替换成
  `mov eax,0x755`（成功码），5 字节等长替换。**不 hook 错误框、不改 ExitProcess、
  不 NOP 那个 je。**
- **理由**：
  1. 这是**最上游**的单点：状态一旦是 0x755，后面 `cmp/je` 自然走成功路径，
     错误框根本不会被调用，退出分支也不会进 —— 一改到位，副作用最小。
  2. `0x5611d0` 只是「状态取值器 + 打日志」，不是真正的 nProtect 初始化，
     跳过它无害（详见 FINDINGS §21）。等长替换不破坏后续指令边界。
  3. 比「hook 错误框返回 IDOK」稳：那条路错误框虽不显示，但校验仍返回失败、
     游戏仍会退出（FINDINGS §18 已证），治标不治本。
- **实测结果**：**patch 生效，无错误框，客户端进到「PopShot」登录界面**（会话02截图）。
- **反悔条件**：若后续发现别处还有 GameGuard 复检（如周期性心跳读同一状态），
  再补 patch 或改在 `0x5611d0`/状态全局 `[0x6e6624]` 上做。
- **注**：`bshook.dll` 仍保留 `MessageBoxW`/`MessageBoxA` 的 hook（现为观测+抑制），
  自动化跑测时防止任何模态框把无人值守的进程挂死；后续接入真实登录/对话框时需复核是否放行。

## D015 阶段4 解密路线 = 先动态拿标准答案，再回头校验静态实现

- **决策**：不追求"纯静态把算法读明白就直接用"，而是
  ①静态读出算法 → ②写 Python 实现 → ③**用客户端 hook 抓一组（密钥, 密文, 明文）三元组做标准答案** → ④逐位比对。
- **理由**：会话 03 里 `server/snow.py` 第一版看起来完全正确（表、轮函数、密钥装载都对得上论文），
  但拿它去解已抓到的登录包一直失败。**没有标准答案时，无法区分「实现有 bug」和「假设错了」**，
  会在两个未知之间反复空转。抓到三元组后一次比对就确认实现是对的，
  于是问题被干净地收敛成「假设错了」——登录包压根不是这个 cipher（FINDINGS §33）。
- **代价**：要给 detour 写完整包装（调原函数后再记输出），比只记入口麻烦一点。值得。
- **推论**：以后每逆出一个算法，都先找一组能观测到的输入/输出配对来钉死实现。

## D016 hook 时机 = 一律晚于 +2.5s，绝不"解壳完立刻打"

- **决策**：`bshook.dll` 的所有**游戏代码内存 patch**（GameGuard patch、SnowCipher hook 等）
  统一延后到进程启动 +2.5s 之后再打（`GG_PATCH_DELAY_MS`）。API hook（user32/ws2_32）不受此限。
- **理由**：ASProtect 有一条后台完整性校验线程（FINDINGS §32）。实测：
  - 打在 +0.7s（解壳一完成就打）：4 次里 3 次被抓，弹「Protection Error / Error: 15」卡死。
  - 打在 +2.5s：5 次全过。
  校验点 0x40d034 约 +5s 才执行，所以 2.5s–5s 是唯一安全窗口。
- **重要**：会话 01/02 的"成功"其实是 25% 的运气，当时没意识到。
  **这条不是优化，是修一个一直存在的间歇性 bug。**
- **反悔条件**：若发现校验时机随机漂移导致 +2.5s 也会被抓，
  改用**硬件断点（DR0 + VEH）**替代内存 patch —— 完全不改字节，CRC 校验看不见。

## D017 观测日志一律"连接后才开闸"

- **决策**：`bshook.dll` 里加解密的日志在 `connect` 到达之前**不落盘**，
  只把最近 16 把密钥存进环形缓冲；`connect` 一到就把它们倒出来并开闸全记。
- **理由**：启动时加载 `Pack\*.pkn` 会产生**上万次**解密调用，
  每条日志都 `FlushFileBuffers`，实测直接把游戏拖到 40s 都进不了登录界面。
  而网络用的 cipher 可能在 connect **之前**就构造好了，所以密钥不能不记 —— 环形缓冲两全。

## D018 认证协议改从 `nmconew.dll` 静态读，不再逆 `BigShot.exe`

- **决策**：47611 认证服这一跳的协议，一律以未加壳的 `game_org/Popshot/nmconew.dll`
  为权威来源做静态分析；**不再**在 `BigShot.exe` 的内存转储里找。
- **理由**：
  1. 客户端点「开始」时会**动态加载 `nmconew.dll`** 来做登录（bshook 日志实测），
     登录代码压根不在主模块里 —— 会话 03 在转储里搜 F 表搜不到，原因就是这个。
  2. `nmconew.dll` 未加壳，字段表、opcode、加解密全部可以直接读，
     而 ASProtect 的页级保护让"事后转储主模块"这条路根本拿不到东西（FINDINGS §37）。
  3. 实践对比很悬殊：会话 03 用差分反解只拿到「够解这一个包」的 64 字节表；
     会话 04 从 DLL 读，半小时就拿到**完整帧格式 + 16 个 opcode + 每个包的字段表**，
     而且能推广到任意长度和服务端→客户端方向。
- **代价**：多写一个 PE 工具 `tools/re_pe.py`（处理磁盘上 RAW≠VA 的正常 PE，
  `re_bs.py` 只能处理那份平坦转储）。很划算。
- **反悔条件**：下一跳（27799 游戏服）的协议不在 nmconew 里 —— 那一层是游戏自有的
  `gcp/gsp` + SnowCipher，**必然**要回到 BigShot.exe 上做（届时优先动态 hook，
  别指望静态转储，理由同上）。

## D019 假服务端一律「先按静态读出的字段表全填 0，再看客户端反应」

- **决策**：应答包不去猜"业务上正确的值"，先把字段按反序列化顺序填 0 / 空串发出去。
- **理由**：本会话实测三轮，`CULoginReplyPacket` / `CURequestOldFashionInfoReplyPacket` /
  `CULogoutReplyPacket` **全部字段填 0，客户端照单全收并推进到下一步**。
  结构对了就能往前走，语义可以后补 —— 这比一开始就纠结"结果码 0 是成功还是失败"快得多。
- **推论**：卡住时先怀疑**结构**（字段个数/类型/字节序），再怀疑取值。

## D020 游戏服和认证服拆成两个进程/两个模块

- **决策**：`server/authserver.py`（47611，NMCO）和 `server/gameserver.py`（27799，gcp/gsp）
  各自独立，各自监听、各自的协议模块（`protocol.py` / `simple.py`）。
  测试时起两个 Python 进程。
- **理由**：两层协议**没有任何共同点** —— 帧头、加密、字段编码、opcode 空间全不一样
  （NMCO 是 `0x18` tag + 大端 + 明文反馈异或；游戏服是 `0xFE/0xFF` + 小端 + SimpleCipher 流）。
  硬塞进一个 `main.py` 只会让两边互相污染。等两边都稳定了再在阶段 6 加一个一键启动脚本。
- **被否**：扩 `authserver.py` 的 `--port` 让它同时处理两种协议
  （会话 04 那版就是这么干的，只能收不能回，再往下走必然要拆）。

## D021 客户端在现代硬件上的兼容问题，优先改配置，不改代码

- **决策**：D3D 模式枚举死循环（FINDINGS §49）用改 `UserConfig.ini`
  （`FullScreen=1` + `ColorDepth=1`）解决，**不打内存补丁**。
  会话 05 曾按配置项名字把窗口模式记成 `FullScreen=0`；后续直接观察
  `D3DPRESENT_PARAMETERS.Windowed` 已确认这个老客户端的文件值语义相反，最终以动态参数为准。
- **理由**：
  1. 补丁点 `0x5bfb65` 在 ASProtect 的按页惰性解密区里，而这段代码**登录之后才第一次执行**
     —— 我们的 patch 线程在 +2.5s 那个安全窗口里根本读不到明文（FINDINGS §37 的页级保护）。
     要么写一个长期轮询的 patch 线程，要么冒险在运行中改内存，两个都比改一行 ini 贵得多。
  2. 配置解决是**可逆、可解释、用户自己也能改**的；补丁是隐性的，下个会话看不到。
  3. 这两个值本来就是游戏自己的设置项，改它不算「魔改客户端」。
- **代价**：`UserConfig.ini` 是客户端**登录成功那一刻才生成**的，
  所以「全新环境第一次跑」必然会中招一次。阶段 6 的一键启动脚本要**预置**这个 ini。
- **反悔条件**：以后想支持全屏或 16 位色 —— 那就 patch `0x5bfb65` 的 `76 49` -> `eb 49`
  （模式数为 0 时不进循环），并接受上面第 1 条的代价。

## D022 「客户端卡在哪」优先用外部线程采样，不再动辄重编 bshook

- **决策**：新增 `tools/thread_stacks.py`：64 位 Python 用 `Wow64GetThreadContext`
  拿 32 位进程每个线程的 EIP/EBP，再用 `ReadProcessMemory` 走 EBP 链。
  想读某个栈帧的局部变量也直接读（`probe_modeloop.py` 就是这么读出循环计数器的）。
- **理由**：
  1. D013 的「hook + EBP 回溯」很好用，但每次都要改 C、跑 `vcvars32` + `build.bat`、重启客户端，
     一个来回好几分钟；而且**只能观测你事先想到要 hook 的点**。
  2. 外部采样是**事后**的：客户端已经卡住了，直接问它「你现在在哪」，
     不需要预判。本次一次采样就定位到 `EnumAdapterModes`，再读两个局部变量就坐实了下溢。
  3. 完全脚本化、不改客户端一个字节，符合 D005 的精神。
- **保留**：需要**拦截行为**（改返回值、抑制弹框、抓加解密入参）时，还是 bshook 内联 hook。
  两者是观测 vs 干预的分工，不互相取代。

## D023 大厅/游戏内 UI 的自动化只能走真实鼠标

- **决策**：`tools/click.py` 用 `SetCursorPos` + `mouse_event` 点游戏画面上的按钮，
  截图用 `tools/screenshot.py`（BitBlt 屏幕 DC）。
- **理由**：登录框是真的 Win32 `#32770` 对话框（所以 `gui_probe.py` 的 `BM_CLICK` 有效），
  但**进大厅之后整套 UI 都是 D3D 自绘的**，`EnumWindows` 只看得到 `MoleWnd` 一个窗口，
  没有任何子控件可以发消息。想验证「点了这个按钮客户端会发什么包」，只能真的点。
- **注意**：会抢走鼠标焦点；而且游戏窗口失焦会自己最小化，
  所以两个工具都内置了 `IsIconic` -> `SW_RESTORE` -> 置顶 的前置动作。
- **被否**：`PrintWindow` 抓图（D3D 画面出来是全黑）、
  给 `MoleWnd` 直接 `PostMessage(WM_LBUTTONDOWN)`（没试，但 D3D 游戏通常读的是
  DirectInput/GetCursorPos，消息不一定管用；真鼠标一次就成功了，没必要再折腾）。

## D024 账号状态以 JSON 为真源，协议字段只做编码

- **决策**：在 `server/data/accounts.json` 持久化本地账号；对用户暴露语义清晰的
  `tutorial_completed: true/false`，由游戏服在组 `gspRepLogin` 时转换成客户端协议值
  `3/0`（精确字段与阈值见 FINDINGS §54）。
- **理由**：
  1. 用户明确希望以后能随时直接修改账号状态；JSON 对单机假后台最透明，且符合阶段 5
     原计划的 `save.json` 方向。
  2. 客户端内部用的是数值状态而不是单纯 bool。把魔数 `3` 封装在协议边界，能避免存档文件
     充斥难懂的逆向细节。
  3. 认证服与游戏服是两个进程（D020），认证服在收到用户名/密码后把当前本地账号写入同一份
     JSON；游戏服收到登录包时再读取。当前目标只有一个 localhost 客户端，这比继续猜 NMCO
     两个返回字符串中哪个会成为游戏票据更可靠。
- **约束**：每次游戏服登录都重新读取 JSON，使用户停服后或下次登录前手改状态即可生效；
  未知账号允许自动创建，保持现有假后台「任意本地账号可登录」的便利性。
- **反悔条件**：若以后支持多个并发客户端，则把根级 `active_account` 换成随机票据映射，
  通过认证应答传给游戏服，不能再依赖单一活动账号。

## D025 开局协议用显式单客户端状态机，不按 opcode 直接回显

- **决策**：`server/gameserver.py` 用 `StartGameHandshake` 依次管理
  `wait_start → wait_confirm → counting_down → preparing`；只在符合当前状态且载荷为空时推进。
- **理由**：
  1. 这套协议收发复用 opcode，但同号包结构不同：客户端空 `0x0400` 对应服务端
     `PrepareGame { int32 seed }`，空 `0x0402` 又同时承担成员确认和服务端同步通知。
     “收到什么就原样回什么”会让客户端反序列化错误或反复触发开局。
  2. 客户端代码已经给出严格顺序（FINDINGS §58）；显式状态能过滤网络重复包、提前包和
     带载荷的异常包，也让后续抓到新步骤时可以在一个位置扩展。
  3. 当前项目只服务一个 localhost 客户端，第二个 `0x0402` 就可视为全员确认；没必要先实现
     房间广播、超时和多人屏障。
- **随机种子**：`PrepareGame` 固定发 0，确保本地复现；不使用 `-1` 的客户端线程随机源。
- **反悔条件**：支持多人时，把状态机提升到 session 级，按账号/连接收齐每阶段确认后广播；
  不改变已确认的单连接包体和客户端顺序。

## D026 按“方向 + 房间类型”路由开局包，不为 `0x0416` 做猜测性应答

- **决策**：解析 `0x0201 gcpReqCreateSession` 中已确认的 `SessionDescriptor`，把
  `1 / 2 / 5` 分别记录为普通、闯关、天梯；每次建房重置 `StartGameHandshake`。
  type=2 的闯关房继续走 D025 的普通 `0x0402` 链；客户端空 `0x0416` 只标记为天梯请求，
  在响应语义查明前不回包。
- **理由**：
  1. 三个建房对话框的静态赋值已独立确认枚举（FINDINGS §59），不是根据 UI 文案猜测。
  2. 协议编号双向复用：客户端→服务端的 0x0416 是空载荷，而服务端→客户端同号包是
     `Packet_gspUpdateQuestDifficulty { int32, int32 }`。按 opcode 回显会让客户端读越界或误改任务状态。
  3. 解析并记录请求能让下一次实机验证直接确认是否进了 type=2 闯关房；建房时重置状态机，
     也避免同一连接第二局停留在 `preparing`。
- **兼容策略**：解析失败只写精确诊断，仍返回已经确认的最小成功应答；这样不会因为尚未见过的
  地区版本字段变体阻断当前复活主线。
- **反悔条件**：若未来要复活天梯玩法，先静态或实机确认空 0x0416 的真正服务端响应序列，
  再单独实现天梯状态机；不把它塞进普通/闯关状态机。

## D027 D3D9 显示拓扑恢复由用户手动完成，不自动禁用系统显示设备

- **决策**：当前不从脚本自动禁用 `Meta Virtual Monitor`、`GameViewer Virtual Display Adapter`
  或任何显示设备。请用户先退出对应虚拟显示/串流软件并用 `Win+P → 仅电脑屏幕` 做可逆切换；
  必要时只在设备管理器里临时禁用虚拟显示设备，绝不禁用 NVIDIA 实体显卡。
- **理由**：
  1. 32/64 位独立探针都确认 D3D9 直接枚举的是 RTX 3070，但同一 `DISPLAY1` 下同时有物理内屏
     `SHP14EC` 与虚拟目标 `XMD009A` 处于活动状态（FINDINGS §60）。这是强相关证据，尚未经过
     “切走虚拟目标后恢复”这一对照实验，不能把推测当成已证实根因。
  2. 自动禁用显示设备是工作区之外的系统级变更，选错对象可能让本地或远程画面消失；用户手动
     操作更容易看清对象并立即回退。
  3. `tools/d3d9_probe.exe` 可在几秒内给出客观验收结果，不需要用完整客户端做盲测。
- **验收门槛**：探针的
  `CheckDeviceType HAL/X8R8G8B8/windowed` 从 `8876086A` 变为 `00000000` 后，才重新跑约
  100 秒的完整登录/大厅流程，依次验收教程 flag、闯关建房与开局加载。


## D028 同号包按方向分别实现，成功路径绝不回显请求 opcode

- **决策**：`0x020b gcpReqMoveChannelByGameType` 的成功应答用 **`0x0701 gspRepMoveInto`**，
  同号的服务端 `0x020b` 一律不发。更一般地：这套协议收发共用 opcode 编号，
  但**同号不等于同结构、更不等于同语义**，实现任何应答前必须先读客户端那一侧的处理器。
- **理由**：
  1. `0x020b` 的客户端处理器 `0x54fbfa` 两条分支都是「移动到能玩该游戏的频道失败」，
     连 `result=0` 都是失败文案，回显会直接弹错误框（FINDINGS §62）。
  2. 这已经是第二次踩同一类坑：D026 里的 `0x0416` 也是「客户端发空包、服务端同号包
     完全是另一个结构」。把它上升成通则，别再一次次现踩。
- **推论**：新 opcode 的默认做法是「先找客户端处理器 → 读反序列化槽 → 再决定回什么」，
  不是「先回一个同号包看看反应」。

## D029 账号 JSON 的字段只有查明协议位置后才接线，但查明了就要立刻接

- **决策**：`level` 从「JSON 里存着但不发」改成「发到 `gspRepLogin` 第 1 个业务 int32」。
  新账号默认等级保持 1（`NEW_ACCOUNT_DEFAULTS`），因为闯关关卡记录的要求等级就是 1。
- **理由**：
  1. D024 定的是「JSON 是真源、协议字段只做编码」，D019 定的是「没查明就填 0」。
     等级的位置已经由两处独立证据钉死（建房四个下拉框的过滤 + 天梯标签页的 >=6 门槛，
     FINDINGS §63），继续填 0 就不是保守，而是**直接让闯关主线走不下去**。
  2. 等级 0 的表现是「任务下拉框空着、点了没反应」，很容易被误诊成 UI 或点击问题 ——
     实测已经在这上面绕了一圈。
- **注意**：其余 6 个业务 int32 语义仍未确认，继续按 D019 填 0，不要顺手一起猜。

## D031 包的**发送顺序**和字段值一样是协议的一部分，要从客户端处理器读出来

- **决策**：建房时服务端按 `0x0303`（Session）→ `0x0201`（建房结果）的顺序发，
  且 `0x0303` 的地图名留空；地图名等客户端发来 `0x0302 gcpChangeSession`
  之后再用第二个 `0x0303` 灌回去。
- **理由**：
  1. `0x0201` 的处理器 `0x54f747` 在**它自己内部**先读 `[LobbyStage+0x1c]` 决定
     建哪个房间面板（`0x54f875`），再读 `[LobbyStage+0x10]` 决定要不要干活
     （`0x54f835`，非空就直接 `ret`）。这两个字段都只能由 `0x0303` 写入。
     所以「先发哪个包」不是风格问题，是**能不能跑**的问题（FINDINGS §66、§67）。
  2. §65 留下的下一步写的是「在 `gspRepCreateSession` 之后补发」，按字面做修不好崩溃。
     这不是 §65 的静态分析错了，是**没读到应答处理器内部的时序**。
- **推论（对 D028 的补充）**：D028 说「实现任何应答前必须先读客户端那一侧的处理器」。
  再加一条：**读处理器时要一路读到底**，把它内部依赖的全局状态和读取顺序也记下来，
  而不是读到「哦它会反序列化成这几个字段」就停。
- **反悔条件**：支持多人房间时，`0x0303` 会变成房间广播，届时顺序约束依然成立
  （建房者那一份必须先于它的 `0x0201` 应答）。

## D032 描述符的收发用两张宽度表，不合并

- **决策**：`DESCRIPTOR_SENT_ARGUMENT_COUNTS`（抄 `0x557374` 序列化）只用于**解析**
  客户端发来的描述符；`DESCRIPTOR_READ_ARGUMENT_COUNTS`（抄 `0x557401` 反序列化）
  只用于**组**服务端下发的描述符，且**不含类型 3 / 4**。
- **理由**：类型 3 / 4 两侧不对称 —— 客户端写 1 个参数、读 2 个，而且读的第一个
  会写回 `+0x04` 把 type 字段自己覆盖掉（FINDINGS §69）。这是客户端的 bug。
  合成一张表必然要在某个方向上说谎；下发这两种类型则会让客户端的描述符错乱。
  宁可在服务端直接 `ValueError` 拒绝，也不要发一个已知会被读坏的包。
- **反悔条件**：查明类型 3 / 4 是什么玩法且确有需要时，按反序列化侧的读法构造，
  并在文档里写清「第一个参数会覆盖 type」这个坑。

## D030 画面验收安排在串流关闭的时段，不再尝试绕过

- **决策**：涉及游戏画面的验收，一律要求先退出 Sunshine / Moonlight，
  以 `tools/d3d9_probe.exe` 的 `CheckDeviceType ... hr=00000000` 为放行标准。
  不再尝试 REF / D3D9On12 / WARP 之类的回退路线。
- **理由**：
  1. 实测退出串流后 32/64 位、HAL/REF/9On12/WARP **全部**恢复成功（FINDINGS §61），
     说明这不是「老客户端不兼容」而是串流占用显示路径，没有可绕的余地。
  2. D027 原本还留了「必要时在设备管理器里临时禁用虚拟显示设备」这一步，
     实测**不需要**：虚拟显示器仍然挂在 `DISPLAY1` 上，探针照样成功。
     少一步不可逆风险更低。

## D033 房间座位用 `0x0300` 全量快照下发，不用 `0x0301` 逐座位事件

- **决策**：建房成功后服务端发一发 `0x0300`（房主座位号 + 6 个 `SessionSlot`），
  而不是给每个占用的座位各发一个 `0x0301`（action=0）。
- **理由**：
  1. `0x0300` 的处理器 `0x40637a` 是**幂等的整屋状态**：`0x556eec` 把 6 个座位
     一次性写完，空座位只占两个 int32。服务端不必维护「谁什么时候进来的」这种
     增量状态，单机自用场景下永远只有一份真相。
  2. `0x0301` 的载荷带一个 **action 码**（0 进房 / 1、2 / 3 离开 / 4 换角色），
     每个码都会往聊天框播一条消息、并触发不同的副作用
     （action 1/2 会 `0x405f8f` **销毁**座位的角色对象）。发错码的代价比发错
     字段大得多，而我们此刻并不需要任何一条「XX 进入房间」的播报。
  3. `0x0300` 顺带把 `LobbyStage+0x34`（房主座位）和每个座位的对端 IP
     （`0x0100007f`）一起设好，少一处要单独补的状态。
- **被否**：只发 `0x0301` action=0（更贴近「真服务器广播加入事件」的语义，
  但要自己拼房主座位号，且 action 的副作用面更大）。
- **反悔条件**：暂无。会话 09 一度怀疑 `0x0300` 没把座位的角色对象建出来
  （FINDINGS §82），但 `tools/probe_room_seats.py` 的采样证明它建得好好的
  （`0x3d1c8038`），崩溃是我们发 `0x0402` 的时机错了（§84/§85）。
  `0x0301` 的编码器（`build_session_member_update`）已经写好并有测试，
  真需要逐座位事件时直接用；目前主线用不上。

## D035 stage 切换类的包一次只推一个，且必须等客户端报到

- **决策**：`0x0400`（→ stage 6 加载）和 `0x0402`（→ stage 7 游戏）绝不同时下发。
  `0x0402` 一定要等客户端发来空 `0x0403`（加载 100% 的轮询）之后再发。
- **理由**：这两个 opcode 的处理器最后一句都是 `call/jmp 0x40e47f`（切 stage），
  **它们是命令不是应答**（FINDINGS §84）。会话 09 一口气发 `0x0402` + `0x0412`，
  客户端跳过 stage 6 的资源加载与对象重建直接进 stage 7，
  座位的角色对象正处在 NULL 窗口期，渲染路径立刻 `C0000005`（§82）。
  改成一次推一个之后，实机一路走到可玩的战斗画面。
- **推广**：这条不只适用于开局。**凡是发现某个「应答」的处理器结尾在切 stage /
  切对话框 / 重建对象，就要把它当成状态机转移来对待** ——
  先确认客户端已经进入前一个状态（通常表现为它开始轮询某个空包），再推下一步。
- **反悔条件**：若将来发现客户端在某个 stage 会等待多个包才继续，
  那就在该 stage 内按观测补齐，但「不跨 stage 抢跑」这条不变。

## D036 时序类 bug 用活进程采样定位，不用静态反汇编推

- **决策**：遇到「同一段代码有时对有时错」的现象（空指针、对象消失、状态错乱），
  先写一个带时间戳的活进程探针轮询相关内存，不要继续读反汇编。
- **理由**：会话 09 花了不少功夫静态推导「`0x405d8c(1)` 为什么没把角色对象建出来」，
  推不出结论 —— 因为它**建出来了**，只是随后被 stage 切换拆掉。
  `tools/probe_room_seats.py` 采样三行就把「没建成 / 建了又被销毁」这个
  二选一给出了答案，并顺带证明重建也会发生。
  静态分析能告诉你代码做什么，**告诉不了你它什么时候做**。
- **配套**：探针只在快照变化时打印一行，可以放心开长；
  Python 重定向到文件是块缓冲，**必须加 `-u`**，否则进程被杀时输出全丢。
- **已有探针**：`probe_session_desc.py`（描述符）、`probe_quest_list.py`（关卡目录）、
  `probe_room_seats.py`（座位 + 角色对象）、
  **`probe_room_ctx.py`（stage + 场景上下文 + World 已加载地图 + 六个座位，
  会话 13 靠它一次定位「房间纯黑」）**。新场景照抄一个即可。

## D034 UI 提示要按**韩文原串**反查，不按中文

- **决策**：想定位某个中文提示框背后的代码，一律先把它翻回韩文原文，
  再在 `re/BigShot_22524.img` 里搜 UTF-16。
- **理由**：中文文案在 `Pack\*.pkn` 的文本表里运行时替换，镜像里只有韩文原串
  （FINDINGS §74 已确认）。会话 09 用这条办法一次命中：
  「等级太低，无法选择任务。」→ `레벨이 낮아서 퀘스트를 선택할 수 없습니다`
  → `0x66a7fc` → 全镜像唯一引用 `0x4682d6` → 判定链 `0x468242`（§77）。
  而会话 08 顺着行为反推走了弯路，查到的 `0x465935` 根本是另一个函数。
- **配套技巧**：不知道确切原文时，搜**关键词**而不是整句 ——
  `레벨`（等级）/ `미션`·`퀘스트`（任务）/ `선택할 수 없습니다`（无法选择）
  三个词就能把二十多条相关文案连地址一起捞出来，再按语义挑。
- **反悔条件**：把 pkn 解开、拿到中韩文对照表之后，可以直接按中文查表定位，
  这条就退化成兜底手段。

## D037 战斗类应答用调试控制通道验证，不再依赖「把关卡真打完」

- **决策**：`server/gameserver.py` 常开一个控制端口（`--control-port`，默认 27800），
  配 `tools/gs_ctl.py`，可以在客户端处于任意状态时把任意游戏包推给它。
  验证战斗应答的标准做法从此是「进关卡 → 一行命令推包 → 截图 + 探针读内存」。
- **理由**：
  1. 会话 09 整整一个会话都没能实机验证 `0x0411 gspEndGame`，
     因为触发它的 `0x040f gcpEndQuest` 要客户端真把关打完/打输，
     而闯关模式有强制推进机制（不向前移动 15 秒就警告，§88），
     「挂机等 12:30」这条替代路线被堵死。
  2. 会话 10 用这个通道**一次就验完了**：包格式正确、客户端接受、
     四个全局逐字段对上（§93）。成本从「打完一整关」降到一行命令。
  3. 它同时解决了「怎么试错」的问题 —— `raw <op> <hex>` 能推任意 opcode
     任意载荷，配合 §88 的 `0x0106 gcpReportHack` 当反馈信号，
     可以低成本地逐个试探未知包，不必每次改代码重启服务端。
- **实现约束**：`Conn.send` 必须加锁。SimpleCipher 是逐字节推进的流密码，
  控制线程和收包线程交错加密会让整条流永久错位、客户端再也解不回来。
- **被否**：用 stdin 收命令（服务端是 `Start-Process -RedirectStandardOutput`
  起的，stdin 不通）；监视命令文件（要轮询，且没法回结果）。
- **反悔条件**：暂无。这是纯调试设施，`--control-port 0` 即可关掉；
  阶段 6 打包时默认关闭即可。

## D038 静态反推 UI 显示语义，性价比不如「发特征值 + 读内存」

- **决策**：想知道某个包的字段在客户端显示成什么，先用控制通道发一组
  可区分的特征值（`endgame-probe` 发 101..112），再用探针读客户端内存
  或直接截图，而不是从 UI 渲染代码往上爬。
- **理由**：会话 10 两条路都走了。静态那条：`0x4a4096` 只是把 13 个 dword
  存进 `GameContextQuest+0x3ec+seat*0x34`，真正读它的 `0x4a4b02` 是
  玩家标签渲染，中间隔着好几层虚调用，读了半天没结论。
  特征值那条：一发包 + 一次内存读，`105/102/104/103` 四个数直接把
  `pkt+0x1c / +0x10 / +0x18 / +0x14` 钉死（§93）。
- **配套**：`tools/probe_endgame.py` 就是为这个做的。新场景照抄一个
  （和 D036 的探针家族是同一套思路：**活进程采样 > 静态推导**）。
- **注意**：特征值不能乱选 —— `gspEndGame` 的 `pkt+0x1c` 在客户端是
  `[0x72e330] +=`（累加），同一个连接里发第二次会叠加。
  发之前先想清楚哪些字段有副作用。

## D039 `accounts.json` 是账户状态的唯一真源，协议字段只做编码

- **决策**：教程通过状态、经验、金币、等级全部以 `server/data/accounts.json`
  为准。客户端上报什么就存什么（`0x030f` 的教程进度、`0x0410` 的分数），
  下发时按存档重新编码。**没有任何一项写死在代码或协议默认值里。**
- **理由**：这是 D024 的延续，但会话 11 把它落到了全部四项。
  以前 `tutorial_completed` 是手工写死的 `true`，等级是手工填的，
  金币每次重登归零 —— 三者都不是「真实状态」。现在：
  1. 教程：初始 `false` → 客户端跑完教学发 `0x030f` → 自动置 `true`（§97）
  2. 经验/等级：结算入账 → 登录时经 `gspRepLogin` 下发（§95）
  3. 金币：结算入账 → 登录后和回房间后各补一发 `0x0600`（§96、§100）
- **`tutorial_completed`（布尔）压过 `tutorial_progress`（原始值）**：
  布尔是给人编辑的开关，置 `false` 就一定重跑教学，哪怕存档里还留着
  上次上报的 4/5。原始值只做保真记录，用于把客户端恢复到它自己报过的状态。
- **等级由经验推出，不独立存**：`login()` 会把手工改乱的 `level` 按经验校回来，
  避免 JSON 里两个字段互相打架。想调难度改 `EXPERIENCE_PER_LEVEL`。
- **反悔条件**：将来要支持多个并发客户端时，`active_account` 这个根级字段
  要换成票据映射（`AccountStore` 的模块注释已经写了这一点）。

## D040 未知字段一次全填特征值有风险，改逐字段试探

- **决策**：对没验证过的包，特征值探针要**逐字段**来，不要一次把所有字段
  都填成可区分的值。已知有副作用或会进入未走过分支的字段，单独试。
- **理由**：D038 说「发特征值 + 读内存」性价比最高，这仍然成立 ——
  `endgame-probe`（101..112）一次就解出了四个字段。但会话 11 对
  `0x0309 gspRepGameResult` 照做时，客户端**20 毫秒内主动断开了连接**
  （不崩、无崩溃报告，纯协议层拒绝，§100）。同一位置发全 0 则完全正常。
  也就是说特征值本身可能把客户端推进未走过的分支（`0x0309` 的
  `pkt+0x18` 非 0 就会进 `0x552170`），风险随字段数线性上升。
- **做法**：先全 0 确认包能被接受，再从**已知落位**的字段开始逐个给值。
  `0x0309` 就先只动 `values[9..11]`（它们落到 `GameContext + seat*4 + …`）。
- **反悔条件**：如果查明断链只由某一个字段引起，其余字段仍可批量试。

## D041 单机没必要的反挂机机制，改客户端而不是绕服务端

**背景**：房间里 90 秒没有鼠标/键盘动作就弹「90秒无任何动作，返回至游戏大厅。」
并发 `gcpLeaveSession(0x0203)`（FINDINGS §101）。打完一关回房间必然中招 ——
关卡本身就打了十几分钟，而计时器在 stage 7 里几乎不会被重置。

**为什么不用服务端解决**：这个计时器（`LobbyStage+0x3e8`）只有四个重置点，
全部是「窗口过程收到鼠标/键盘弹起消息」「`LobbyStage::ResetSession`」
「提示框自己重置」「战斗内 `0x4906ac`」——
**没有任何一个 opcode 的处理器会碰它**。唯一沾边的 `0x552943` 就是
`0x0203` 的成功应答，而那条路本身就是把玩家送回大厅。
也就是说服务端要么让玩家被踢，要么什么都做不了。

**为什么不直接把判定跳过**：`0x467635` 的 `jge` 改成 `jmp` 也能达到效果，
但那是删掉一个机制；改时长只是把窗口拉长，机制、日志、后续调用链全都原样。
出问题时把 `BSHOOK_KEEP_AFK_KICK=1` 一设就能对照原版行为。

**决定**：
1. `bshook.c` 在 GameGuard patch 之后紧接着 patch `0x4082ae` 的
   `push 0x15f90`(90000ms) → `push 0x40000000`（约 12.4 天）。5 字节换 5 字节。
   用 `0x40000000` 而不是 `0x7fffffff`，是为了让 `deadline = start + 时长`
   不至于溢出成负数（虽然 `IsExpired` 不看 deadline，但别给后面埋雷）。
2. **同时**在服务端实现 `0x0203` 的应答。这不是「顺带」——
   `0x0203` 是玩家主动退房用的同一个包，在这之前**玩家根本退不出房间**。

**约束**：以后再遇到「客户端等一个应答等到天荒地老」的现象，
先去 `0x54e036` 的 switch / `0x406332` 的跳表里查那个 opcode 有没有服务端方向，
有就照着处理器读出应答形状 —— 别急着推断成客户端 bug。

## D042 「未查明字段一律填 0」要加一条例外：**先确认 0 是不是合法值**

**背景**：`Session` 的第一个 int32（`+0x04`）在会话 08 建表时按 D019
（未查明 -> 填 0）填了 0，一直没人回头看。它其实是**房间状态**，
`2 = 待机中`，而客户端拿它决定房间里建哪个 3D 场景 ——
填 0 的后果是房间里建了个战斗上下文，背景全黑、角色不能走动
（FINDINGS §102）。这个 bug 在里程碑 B 就埋下了，一直被当成「客户端老游戏的毛病」。

**决策**：D019 保留，但补一条**验收动作**：填 0 之前先花两分钟找一处
**读这个字段的地方**，确认 0 落在它的合法取值里。找不到读点再填 0。

**为什么值得这么做**：这类字段的错误不会报错、不会崩、不会在日志里留痕，
只会让画面「看起来像原版就该这样」。会话 08~12 的五个会话都在这个房间里
跑来跑去，没有一个人怀疑过背景。**代价是几分钟，收益是不把 bug 当特性。**

**怎么找读点**（这次用的办法，可复用）：
1. 字段落在哪个对象的哪个偏移（`Session::Deserialize 0x556e80` 写 `this+4`）；
2. 全镜像搜该偏移的比较指令（`cmp dword ptr [reg+4], imm`）——
   这次一搜就撞上 `0x43e5de` 的 `cmp [session+4], 2`，两条分支分别推
   `'대기중'` 和 `'게임중'` 两个韩文串，语义当场坐实（D034 的老套路）。

**反悔条件**：无。这是 D019 的补丁，不是替代。

## D043 房间状态固定发「待机中」，不做「游戏中」广播

**决策**：`build_update_session` 的状态字段固定发 `SESSION_STATUS_WAITING = 2`，
开局时**不**改发「游戏中」。

**理由**：这个字段有两个消费者 —— 房间列表的「待机中/游戏中」标签，
和 `RoomStage` 的场景工厂。单机只有一个客户端，房间列表永远是空的，
第一个消费者根本不存在；而第二个消费者只在 RoomStage 构造时读一次，
那一刻永远是「玩家在待机房间里」。真要在开局时改成「游戏中」，反而会在
下一次进房间时把场景又建错。

**佐证**：客户端自己也是这么干的 —— `0x0403`（结算完回房间）的处理器
`0x551904` 直接 `mov [LobbyStage+4], 2` 硬写，不看服务端脸色。

**反悔条件**：将来真做多人房间列表时，列表条目里的状态要按房间实际状态发，
但下发给**房间里那个客户端**的 `0x0303` 仍应保持 2。

## D044 调试日志默认关，用两个启动脚本切换，而不是「留着反正能用」

- **决策**：客户端（`BSHOOK_VERBOSE_LOG`）和服务端（`gameserver.py --verbose`）
  的逐包 dump **默认关闭**。要看就跑 `start-debug.bat`，正常玩跑 `start.bat`。
- **理由**：
  1. 那套日志的真实代价被严重低估了 —— 实测**每条 2.0 毫秒**
     （`FlushFileBuffers` 同步刷盘），一次会话 9.6 万条 = **197 秒**纯等待（§105）。
     「启动慢」「玩着卡」两个用户可感的问题，根子全在这里。
  2. 它当初是**协议逆向期的刚需**（会话 03～13 全靠它）。现在
     `protocol.md` 该解的都解了，日常游玩一行都不看 —— 收益归零，成本照付。
  3. 关键事件（PATCH / HOOK / MSGBOX / WS2 / D3D / 崩溃）**两种模式都照记且照 flush**。
     排查「今天起不来了」这类问题该有的证据一条不少，只是没有了逐包字节。
- **实测之后的一条修正**：原本以为「详细模式必然慢」，实机跑下来**两种模式速度
  几乎一样**（登录到大厅 15.1 vs 14.6 秒）—— 因为那 100 秒的大头是 `FlushFileBuffers`，
  `bsvlog` 不刷盘之后详细模式一起受益了。
  所以这条决策的**真实理由收窄成**：默认精简是为了「日志可读 + 不白写几 MB 磁盘」，
  而不是「详细模式跑不动」。逆协议时开详细模式没有速度顾虑，放心开。
- **被否**：
  - **留着不动，靠加大缓冲/异步写来缓解**：治标。`SNOW_MAX_LOG_BYTES=256` 意味着
    一次解密最多 17 行，战斗中每个包都要走一遍格式化 —— 就算不刷盘也在做无用功。
    而且精简模式下 detour 本身也该省掉。
  - **做成运行时可切换（热键/控制通道）**：cipher hook 装了就没法干净卸载
    （inline hook 拆除要停所有线程），复杂度换不来什么。
    重启一次游戏 30 秒的事。
  - **默认开详细、让用户自己关**：默认值应该服务于「日常玩」这个主用途。
- **反悔条件**：如果后面要逆新的战斗包（`0x0408` / `0x0415` / `0x040c` 的语义），
  照样用 `start-debug.bat` —— 这不叫反悔，这就是它存在的理由。
  真要反悔的情形只有一个：发现精简模式漏掉了排查某类问题必需的日志，
  那就把那条日志从 `bsvlog` 提回 `bslog`，而不是把开关默认值翻回去。

## D045 启动脚本按「端口的 OwningProcess」判断服务端在不在跑，并记一个模式文件

- **决策**：`tools/launch.ps1` 用 `Get-NetTCPConnection -State Listen -LocalPort`
  查 47611 / 27799 有没有人监听来决定「要不要起服务端」，
  并把当前日志模式写进 `logs/.server_mode`。
  模式对得上就复用，对不上就先停再起。
- **理由**：
  1. 用户明确要求「不要重复启动后台服务器」。而端口被占是**唯一**真正要紧的判据
     —— `gameserver.py` 不开 `SO_REUSEADDR`，第二个实例会直接绑定失败退出，
     留下一个「看起来起来了、其实没有」的假象。
  2. 不能用「有没有 python 进程」判断：用户这台机器上还有别的 Python 活儿，
     误杀过一次（PROGRESS「测试前必读」）。按端口的 `OwningProcess` 精确定位，
     停的一定是我们自己的进程。
  3. 光判断端口还不够 —— 用 `start-debug.bat` 时如果沿用一个精简模式起的服务端，
     日志里就是没有 hexdump，而人会以为是代码坏了。所以要记模式并按需重启。
- **被否**：
  - **PID 文件**：进程被任务管理器杀掉后 PID 文件会留下来说谎，还得再查一次进程，
    不如直接查端口。
  - **互斥体**：得改 Python 代码，且跨语言拿 Windows 命名对象很啰嗦。
- **反悔条件**：将来服务端要监听动态端口时，这套判据要跟着改。

## D046 死亡/重生一律「原样回显客户端自报的内容」，服务端不自己算

- **决策**：
  - 收到 `0x0408`（HP 归零上报）→ 把**收到的 18 字节原样**当 `0x0406` 发回去。
  - 收到 `0x0413`（重生请求）→ 把**收到的 16 字节原样**当 `0x0419` 发回去。
  - 服务端不维护血量、不挑重生点、不判「谁杀了谁」。
- **理由**：
  1. **坐标只有客户端算得对。** 闯关是多场景推进的，重生点由
     `0x4fe70e` 按当前场景从 `[char+0x2b0]` 选出来。服务端手上没有地图数据，
     写死坐标就是会话 09 那个坑：角色被传到地图边缘卡住，客户端 23 毫秒后
     发 `0x0106 gcpReportHack` 告状（§88）。原样回显之后本次实机 **0 个 `0x0106`**。
  2. **句柄同理。** `0x0406` 的第一个字段是 `World::Find` 用的对象句柄，
     怪物每只一个。服务端没有对象表，只能回显。
  3. **真服务器在这一步做的也基本是转发** —— 它的额外职责是「广播给房间里其他人」
     和「反作弊校验」，单机假服务端两样都不需要。
  4. 回显天然正确，不会随关卡/版本漂移，也不用为每张地图维护出生点表。
- **被否**：
  - **服务端算血量**：`0x0408` 里根本没有伤害值，`0x0505 gcpAccumulatedWeaponDamage`
    是结算时才发一次的汇总。要算血量得把整套武器/怪物数值搬到 Python 来，
    收益为零（单机没有作弊动机）。
  - **只回 10 字节**（读侧只读这么多）：省不下什么，还得多写一个打包函数；
    原样回显更不容易出错。`build_broadcast_death()` 保留下来只给单元测试
    和控制通道 `kill` 用。
  - **继续用「静默 N 秒 = 死了」这个启发式**：已被证伪且有害（§88），
    连同 `--respawn-idle` 一起删了。
- **反悔条件**：将来要做多人（真广播）时，`0x0406` 得按房间里的所有连接分发，
  而不是只发回给报的人；那时这条决策要扩写，但「内容原样转发」仍然成立。

## D047 保留 `--no-death-reply` 开关，用来一键退回「坏掉的旧行为」

- **决策**：`gameserver.py --no-death-reply` 收到 `0x0408` 也不回死亡广播。
- **理由**：这个 bug 的表现（角色卡住不能操作）和「客户端卡死/掉线」很像。
  以后再有人报「角色动不了」，用这个开关跑一遍就能立刻分清是不是同一个问题
  —— 比翻日志找 `0x0408` 快。代价只有一个 if。
- **被否**：**直接删掉旧行为**。旧行为是唯一能复现用户原始现象的路径，
  留一个开关比留一段注释有用。

## D048 死亡广播「除死亡次数外原样回显」，并且只用一个格式串收发（D046 的修正）

- **决策**：D046 说的「原样回显 `0x0408` 的 18 字节」要改成
  **「把死亡次数那一格换成『收到的值 + 1』，其余原样」**；
  而且**重新 `struct.pack` 整个包**，不去对收到的字节做 `pack_into`。
- **理由**：
  1. 死亡次数那一格是**服务端的权威值**，客户端只是把自己的旧值报上来。
     照抄回去，`[char+0x600]` 永远不动，HUD 心形就永远是 3 颗（§109）。
     判负用的是另一份本地计数，所以「判负正常、心形不动」会同时出现 ——
     这正是用户报的现象，也说明「两份计数分家」不是理论风险而是实际后果。
  2. **不手算偏移**：线上是紧凑布局（死亡次数在偏移 6），客户端结构体里却在
     `+0x08`。按后者 `pack_into` 会写坏 X 并把死亡次数冲成六万多，
     客户端 `剩余生命 = 最大生命 - 死亡次数` 变负数，拿去当数组下标当场崩。
     用同一个格式串 `DEATH_REPORT_FORMAT` 解析 + 重新打包，这类错误在结构上不可能发生。
  3. 回归测试写成「把回包重新解析一遍，逐字段比对」，而不是「比对第 N 个字节」
     —— 后者会跟着同一个错误偏移一起错。
- **被否**：
  - **服务端自己维护每个角色的死亡次数**：怪物一场几十只，服务端没有对象表，
    维护它纯属自找麻烦；客户端报的值本来就够用。
  - **保留 `DEATH_COUNT_OFFSET` 常量但改成 6**：常量本身就是这次出错的载体。
    格式串是唯一真源，删掉更安全。
- **反悔条件**：将来做多人广播时，死亡次数要按「服务端维护的每角色计数」下发，
  那时才需要真的记账；但「用同一个格式串收发」这条永远成立。

## D049 顺手补上 `0x0410 -> 0x0415`（战绩面板的分数列）

- **决策**：收到 `0x0410 gcpUpdateQuestScore`（累计分数）就回一发
  `0x0415 gspUpdateQuestScore`（座位 + 同一个累计分数）。
- **理由**：查心形时发现分数列恒为 0 是**同一类问题** —— 客户端
  `GameContext::vf_1c()` 恒假，所以加分也不本地记，只发 `0x0410` 等服务端回
  （§109）。既然根因和修法都和心形一模一样，一起修比留个「已知坏掉的显示」更好；
  代价是三行代码 + 三条测试。
- **被否**：**顺便把分数改成服务端权威（自己算）**。`0x0410` 已经是累计值，
  服务端没有任何额外信息可加，改成自己算只会引入不一致。
- **注意**：`self.quest_score` 的语义（累计）没变，结算的经验/金币入账不受影响。

## D050 换图也走「原样回显 + 等客户端报到」，不在服务端维护地图表

**背景**：闯关走到地图边缘时客户端发 `0x0411 gcpReqChangeToNextMap`
等服务端回 `0x0417`，加载完再发 `0x0412` 等 `0x0418`（FINDINGS §111）。
两个都没接，玩家就卡在地图尽头、鼠标沙漏。

**决策**：
1. `0x0411` 里的地图名**原样回显**成 `0x0417`，服务端不查表、不校验。
2. `0x0418` **只在收到 `0x0412` 之后发**，绝不跟在 `0x0417` 后面一起发。

**理由**：
1. 第 1 条是 D046 的直接套用 —— 下一张地图叫什么只有客户端知道
   （它自己从 `[0x72e3d8]` 的地图目录查出来再填进请求包）。服务端要自己算，
   就得把每个关卡的地图链搬进 Python，一旦和 pkn 里的数据对不上，
   表现是「加载一张不存在的地图」，比现在的卡住更难查。
2. 第 2 条不是风格问题，是**会不会崩**的问题：客户端的加载循环
   （`0x47961d`）是**前置**判断，标志位在进循环前就为 1 的话，
   它会直接跳过整段等待，而后台加载线程还在跑。这就是 D035
   「一次只推一个 stage、必须等客户端报到」的原文场景，只是换了一对 opcode。
3. 保留 `maps_entered` 列表纯粹是为了日志和 `gs_ctl status`
   ——「这一局换了几次图、分别是哪张」是排查换图问题时最想先知道的一行。

**被否**：
- **在 `0x0417` 里回一个我们认为「正确」的地图名**：服务端没有地图数据，
  任何「正确」都是猜的。
- **收到 `0x0411` 就把 `0x0417` + `0x0418` 一起回**（少一个来回、看着更快）：
  见理由 2，会让客户端在地图没加载完时就进游戏。
- **给 `0x0412` 做状态机（没请求过换图就不回）**：`0x0418` 只是置一个
  在换图期间才有意义的标志，严格化只会在我们对触发条件理解有偏差时
  制造新的卡死。现在是「照样放行 + 日志记一行」。

**反悔条件**：将来做多人时，`0x0418` 要等房间里所有人都报了 `0x0412` 才广播
（这正是这个包在原版里存在的理由 —— 等齐所有玩家加载完）。

## D051 通关标志取客户端的 `0x0417`，不靠服务端自己判「有没有打完」

**背景**：结算界面的「完成 / 未完成」由 `0x0309` 尾部数组里自己那一格决定
（§112）。服务端得知道这一局到底通没通关。

**可选**：
1. 服务端自己判 —— 比如「分数超过某个阈值」「打死了某个句柄」。
2. 用客户端已经在发的 `0x0417 gcpMarkQuestSuccess`。

**选 2。** 理由：

* 服务端手上**没有关卡数据**（关底是谁、要打几只、地图有几张全在 pkn 的
  lua 脚本里），任何「自己判」的规则都是猜的，换一关就错。
* 客户端本来就在报，而且报得很准 —— 它就是关卡脚本调
  `GameContextQuest::vf_e4(1)` 发出来的。
* **时序天然对**（§112 的表）：打死关底那条路 `0x0417` 比 `0x040f` 早 30 秒；
  时间到/生命耗尽那条路 `0x0417` 反而晚 20 毫秒。所以「收到 `0x040f` 时
  `quest_success` 是不是真」正好等于「这一局通没通关」，
  既不用延后结算，也不用下一局补正。
* 和 D046（死亡/重生原样回显）、D050（换图原样回显）是同一条原则：
  **凡是只有客户端知道的事实，就让客户端报，服务端只做记账和放行。**

**代价**：客户端可以谎报通关。单机复活工程不在乎。

**必须记得清**：`quest_success` 要在离开房间 / 建房 / 结算看完回房间时
一起清掉（`Conn.reset_quest_state`），否则打通一次之后每一局都写「完成」。

## D052 掉落物也走「原样回显 + 服务端只补一个句柄」

**背景**：`0x0406 gcpCreateItem` 客户端每掉一件东西就发一次，等 `0x0404`
`gspCreatedItem`（§113）。服务端要回什么？

**选**：把客户端自报的 8 个字段**原样**发回去，前面只插一个服务端分配的
实例句柄。**不维护任何物件表、不做掉落随机、不校验坐标。**

理由和 D046 一模一样：

* 掉什么（物件 id）、掉在哪、初速多少，全是关卡的 lua 脚本算好的，
  服务端没有也拿不到这些数据。
* 客户端收到之后自己还会再夹一次地面高度、再找一次不卡地形的落点
  （`0x551a96` / `0x473969`），服务端算了也白算。
* 会话 09 那次「写死坐标把角色传到地图边缘 + `0x0106 gcpReportHack`」（§88）
  的教训：**只要服务端开始自己编坐标，就会和客户端的世界观打架。**

**句柄的取值**：从 `0x40000000` 开始自增。句柄落进 `[obj+0xd0]`，
`World::Add` 拿它当 map 的 key，**撞了会把已有物件覆盖掉**；
关卡自己的物件句柄实测在 `0x0010c9xx` 一带（死亡上报包里的 handle 就是
同一个字段），拉到 `0x40000000` 谁也够不着，而且还是正 int32、不等于 -1。

**不做**：不去模仿客户端 `0x513335` 那个 `[World+0x64]++` 的分配器 ——
那是客户端在 `[World+4]==0` 时给 `SpawningArea` 用的本地分配，
服务端读不到它的值，跟着它反而会撞。

## D053 拾取也走「原样回显」：`0x0407 -> 0x0405`

**背景**：会话 17 把掉落物做出来了，但走过去捡不起来。根因是
`0x0407 gcpGetItem` 没人应答（§115）。服务端要回什么？

**选**：把客户端那两个 int32（座位号 + 实例句柄）**原样**发回去。
**不查距离、不判归属、不看物件是什么、不管它值多少。**

理由和 D046 / D050 / D052 是同一条：

* 碰撞检测是客户端算的（`0x50f410`），服务端手上没有物件坐标、没有角色坐标
  （§113 之后我们连真正的角色位置同步包都还没找到），算了也算不对。
* 拾取效果也是客户端算的（`Item::vf_d4 -> vf_11c`：金币加钱、红心回血、
  武器换枪），服务端不需要知道这件是什么。
* 单机只有一个人在座位 0，「谁先碰到归谁」这种仲裁没有意义。

**这条比前几条更不能拖**：`Character::CheckItemPickup`（`0x5154d3`）发完包
就把 `[item+0x2a8]` 置 1，**一件东西一局只报一次**。服务端漏回一发，
那件东西就永远躺在地上 —— 不是「重试一下就好」，是彻底作废。
所以**绝不能加任何「看起来不对就不回」的过滤**（比如「句柄不在我发过的表里
就丢弃」）：关卡脚本自己摆的物件（句柄 `0x0010c9xx` 一带）也走这条链，
按句柄过滤会把它们全废掉。

**代价**：客户端可以隔着半张地图声称捡起任意句柄。单机复活工程不在乎。

## D054 结算界面只填**已经逐格验过**的四个数，其余继续填 0

**背景**：结算界面七行，会话 17 修好了「完成 / 未完成」，剩下六行还是 0 / +0。
两个包一共 24 个业务值可以填。

**选**：只填这四个，其余 20 个保持 0。

| 界面行 | 包 | 业务值下标 | 填什么 |
|---|---|---|---|
| 分数 | `0x0411` | 5（另两格 6/7 留 0，界面显示三者之和）| 本局分数 |
| 经验值 | `0x0309` | 9 | 本局分数 |
| 金币 | `0x0309` | 10 | 本局分数 |
| 竞技场分数 | `0x0309` | 11 | **0** |

**为什么不顺手把别的也填上**（这才是这条决策的重点）：
§100 实测 `gameresult-probe` 把 `0x0309` 的 12 个值一次全填 201..212，
客户端 **20 毫秒内主动断开连接**（不崩、无崩溃报告），至今没查出是哪一格干的。
所以这里的规矩是「**逐格查明语义 + 逐格实机验过，才允许非 0**」，
不许因为「多填几个看看效果」就整片开。这是 D019 在一个有明确反例的地方的收紧版。

**竞技场分数发 0 是有意的**，不是没查到：闯关模式本来就不涨天梯分，
发个假数字只会让人以为存档里真的记了这笔。

**经验 / 金币的数值口径**：沿用 D024 的「1 分 = 1 点经验 = 1 金币」。
`0x0309` 这三格是**本局增量**（界面写成 `+%d`），
`0x0411` 的经验三件套是**绝对累计值**（§94）—— 同一次结算里两种口径并存，
改数值时别改错地方。

## D055 便携发布先内置官方 Python embeddable，不先冻结服务端 EXE

**决策**：发布目录固定携带官方 CPython 3.14.3 x64 embeddable，
`tools\launch.ps1` 只按项目相对路径调用 `runtime\python\python.exe`，不回退到
系统 Python。先用 `tools\build-portable.ps1` 生成精简目录 / ZIP；暂不把两个
服务端分别打成 PyInstaller 单文件 EXE。

**理由**：

1. 生产服务端只有 Python 标准库依赖，官方嵌入式运行时已经足够，改动面最小。
2. `authserver.py` 和 `gameserver.py` 靠同一份 `server\data\accounts.json` 通信，
   日志也按 `__file__` 推导项目根。两个 PyInstaller onefile 会各自解压到不同的
   `_MEIxxxx` 临时目录，直接冻结会把存档拆成两份并把日志写到错误位置。
3. 不做系统 Python 回退，才能在开发机上发现便携运行时缺文件/缺模块；否则
   本机的 `C:\Python314` 会掩盖发布包问题。
4. Python 上游 `_pth` 隔离保留原样，不读取目标电脑的环境变量、注册表或
   site-packages，避免「在开发机能跑、换机器就加载到另一套包」。

**发布约束**：默认发布包不携带 `accounts.json`（可能含明文口令），也不携带
`logs`、`game_patched\Debug`、`game_patched\Dump`。个人迁移存档必须显式使用
`build-portable.ps1 -IncludeSave`，或手工复制这一份 JSON。

**反悔条件**：若以后确实需要隐藏 Python 源码或减少可见文件，再先统一持久数据
目录，然后做一个同时承载两套监听器的单一服务端 EXE；不能直接冻结现有两个入口。
