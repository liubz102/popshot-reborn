## 0. 怎么读这份表

### 0.1 可信度标记 —— ★ 请务必尊重它

| 标记 | 含义 |
|---|---|
| **✅实测** | 真客户端实机跑通过，字段值和屏幕上的现象逐条对上 |
| **🔍静态** | 逐指令读反汇编读出来的，没有实机验证，但字段位置/类型是硬事实 |
| **🤔推测** | 有间接证据（调用点、命名、相邻字段），**没有**直接证据 |
| **❓未知** | **不知道**。不要在这里填想当然的值，按 D019 一律填 0 / 空串 |

**「未知」就写未知。** 这份表宁可承认不知道，也不写猜的东西 ——
V0.1/V0.2 踩过的坑里有相当一部分就是「望文生义地按名字猜语义」造成的
（`0x0406` 被当成位置同步、`0x0301 action 3` 被当成离开、`0x040b` 被当成 u16……）。

### 0.2 三条铁律（先看这个，再看下面任何一条包）

1. **★ 同号反向是这套协议的常态。**
   同一个 opcode 在两个方向上语义**完全不同**，只能靠方向区分。
   已知的同号反向对见 [§1.5](#15-同号反向对照表-必查)。
   **加任何新应答之前先查那张表。**
2. **「返回值」在这套协议里几乎都是「另一个包」。**
   客户端的请求函数发完包就干等，**没有超时也没有本地兜底** ——
   服务端不回，玩家看到的就是「卡住 / 没反应 / 东西捡不起来 / 死不掉」。
   所以每条 gcp 都标了「**必须回什么**」。
3. **gcp 和 gsp 是两套独立编号。** `0x040f` 客户端方向是 `gcpEndQuest`，
   服务端方向是「同步数据下行」，两者毫无关系。

### 0.3 关于类名

- `Packet_gcp*` / `Packet_gsp*` / `Packet_rcp*` 这些名字**全部来自客户端自己的
  MSVC RTTI**（`re/rtti_types.txt`），是原作者写的名字，不是我们起的。
- **但不是每个 opcode 都有类。** 相当一部分包客户端是直接用 `RawPacket`
  拼出来的，没有专门的类，也就没有 RTTI 名字。这份表里这类包用
  `raw*`（我们自取的名字）标注，并写明「**客户端 RTTI 里没有这个类**」。
- 已确认**没有** RTTI 类、名字是本项目自取的：
  `gspRepListSession`(0x0200)、`gspRepCreateSession`(0x0201)、
  `gspRepLeaveSession`(0x0203)、`gspSession`/`gspUpdateSession`(0x0303)、
  `gspSetPlayerName`(0x0102)、`gcpReqLogin`(0x0100)、`gcpLeaveSession`(0x0203)。
  查 `re/rtti_types.txt` 可以自行复核。

### 0.4 vftable 槽位

`re/vftables.json` 的 key = **类的 vftable 首地址**：

```text
槽 0 (+0x00)  Serialize     （写包 = 发送方用）
槽 1 (+0x04)  Deserialize   （读包 = 接收方用）
槽 2 (+0x08)  析构
```

⚠ **相邻类的 vftable 是挨着排的**，肉眼按 3 个一组数很容易错一格。
要确认某个函数属于哪个类，拿它的 va 去镜像里搜 dword，看落在哪个 key 后面 4 字节
（V0.2 §136）。

⚠ `vftables.json` 里有 3 条 key 落在 `.text` 段里（`0x5b9f69`
`Packet_gcpMoveChannelTest`、`0x6150c4` `Packet_gspRepMoney`、
`0x5fd17f` `Packet_gspRespawnCharacter`），那是 RTTI 扫描的误命中
（代码里恰好有一个 dword 指向同一个 COL），**不是真的 vftable**。
真的分别是 `0x68c5a4` / `0x69185c` / `0x6916b0`。

## 1. 通用基础

### 1.1 三条链路

| 链路 | 端口 | 协议 | 加密 | 谁实现 |
|---|---|---|---|---|
| 认证服 | `47611`（客户端写死）| **NMCO**（Nexon 通行证，`nmconew.dll` 里）| 一次一密 XOR + 64 字节常量表 | `server/authserver.py` |
| 游戏服 | `27799`（客户端写死）| `RawPacket` + gcp/gsp opcode | **SimpleCipher** | `server/gameserver.py` |
| 原版 TCP 中继 | 服务端在 `0x0210` 里告诉客户端 | **rcp**（帧格式和 27799 逐字节相同）| SimpleCipher | `server/relayserver.py` |
| 玩家间 UDP 旁路 | 我们自己加的（`server.config` 可配）| **我们自己的** `PSU\x01` 协议 | 无 | `server/udpsync.py` + `bshook` |
| 客户端 P2P UDP | `7788`（客户端写死 bind）| `UdpPacket` 裸发 | 无 | **原版自带，我们管不着** |

### 1.2 游戏服 / 中继的帧格式

**握手（只有 27799 有，中继没有）**：

```text
客户端 connect 后裸发 4 字节 int32 版本号                ← ServerConnection::OnConnect 0x54d965
服务端回 0xFE 控制帧，载荷 = int32 结果码（+可选 wstr）   ← 槽12 = 0x54dbf6
        == 0  客户端接着发 0x0100 gcpReqLogin + 0x0103
        != 0  客户端再读一个字符串，走「升级 / 报错」分支并弹框
```

**版本号 int32 的两个取值来源（2026-08-22 起，V0.2 版本管理）**：

```text
原版客户端：   指令立即数写死 311 (0x137)
              0x54d98f  c7 45 f0 37 01 00 00   mov dword [ebp-0x10], 311
              （这 7 字节在整个已脱壳镜像里唯一，re/BigShot_*.img 核对过）

复活客户端：   bshook 启动时读包根 BUILD.ver 的 "version"（如 "V0.2.7"），
              把 0x54d98f 那条指令的立即数补丁成编码值 —— 仍是原样 4 字节，
              流布局不动（SimpleCipher 是有状态流密码，多一个字节全错位）。

编码（server/versioning.py 的 encode_wire/decode_wire，三处实现必须一致）：
              wire = major*1_000_000 + minor*1_000 + patch
              约束：major<=2146、minor/patch<=999；
              保留值 311（=0.0.311，打包时直接拒绝）；
              编码下限 1000（原版客户端版本号都在这个区间以下）。

服务端判定：   == 311        → 旧版客户端（没上报复活版本）
              1000..上限     → 解码出 V主.次.修订，记进 online.log
              其他（负数等） → 按旧版处理（日志带原始值）
门禁：         低于 server-ClientFilter.config（包根，热重载）里的最低版本、
              或旧版客户端且门禁开着 → 回 [int32 1 + wstr 升级提示]（上面的
              「升级/报错」分支），客户端不弹框也进不来：0x0100 gcpReqLogin
              在 on_game_login 里还有第二道拦截（回 result=2 + 断开）。

拒绝文案：     带服务器自身版本（gameserver.version_reject_message，读包根
              BUILD.ver），形如「…请更新到 V0.2.7 后再连接。」。★ 这句话
              是给机器读的协议：客户端更新器（updater\src\probe.c 的
              探针）连 27799 重演一次握手，按 [vV]数字.数字[.数字] 从文案
              里解析目标版本 —— 成对发布（D079）的客户端/服务器靠它对准
              批次。文案里的版本号格式被 server/test_update.py 钉住。

升级分支：     客户端拉起的 game_patched\BsPatcherChn.exe 已替换为自研更新
              引导器（tools/updater/updater.c，2026-08-22 起）—— 原版 NGM
              链（BsPatcherChn→NGMDll→platform.tiancity.com，停机多年）
              整条废弃。引导器只透传 -procid，其余 NGM 参数忽略，转手拉起
              updater（BsPatcherChn.exe，C 实现）完成下载/校验/应用/提示重启；与本表协议
              的交集只有上面这次 0xFE 拒绝帧（探针重演的也是它）。
```

**0xFE 控制帧**：

```text
+0  u8   0xFE
+1  u8   0
+2  u16  载荷长度
+4  ...  载荷
```

**0xFF 游戏帧（= `RawPacket` 的 10 字节头，写死在 `0x5bb9e7`）**：

```text
+0  u8   0xFF
+1  u8   0
+2  u16  载荷长度（= 总长 - 10）
+4  u16  0
+6  u16  标志（基类恒传 0）
+8  u16  ★ opcode
+10 ...  载荷
```

**加密**：`SimpleCipher`，两个方向的初值 `(0,1)` / `(5,3)`。
★★ 它是**逐字节推进的流密码** —— 发送中途超时 / 半发送会让密码状态前进而字节没送到，
**这条流从此对端再也解不开**（V0.2 §210）。所以发送必须带截止时间，失败就拆连接。

### 1.3 `UdpPacket`（玩家间同步数据）—— 和 `RawPacket` 是两个类

`UdpPacket`（vft `0x64dcf8`，构造 `0x5bbde5`）头 **12 字节**：

| 偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0` | u8 | 魔数，必须是 `0xFF`，否则 `0x4078ab` 直接丢 | 🔍静态 |
| `+1` | i8 | **发送方座位**，有效范围 -1..5（`0x4078c9` 是 signed 比较）| ✅实测 |
| `+2` | i8 | **目标座位**，`0xFF`(-1) = 广播。★ 上行**恒是广播**（91526/91526）；只有原版 UDP 直连在逐座位发送前才改写它 | ✅实测 |
| `+3` | u8 | **恒 0**（41 个语料文件 91526 发，0 例外；原来标 ❓未知，V0.3 §25） | ✅实测 |
| `+4` | u16 | ★★ **局号**（纪元号）。必须 == 收方的 `[GameSession+0x3c]`，**不等整包丢** | ✅实测 |
| `+6` | u16 | 校验和，`0x5bbdc1`：从 `+0x0c` 起、种子 `0x17` | 🔍静态 |
| `+8` | u16 | **序列号**，去重 / 排序用；★ 心跳(`0x4001`)时**恒为 0** | ✅实测 |
| `+10` | u16 | **内层 opcode**，见 [§5](#5-udppacket-的内层-opcode) | ✅实测 |
| `+12` | … | body | |

**局号（`+4`）的完整语义**（V0.2 §213 / §216 / §218，这是最容易踩的一条）：

| 事件 | 局号怎么变 |
|---|---|
| 登录成功 `0x0100`(result=0) | 复位成 **-1**（线上是 `0xFFFF`，和 u16 比永远不等 ⇒ 此时一发同步包都不收）|
| `0x0203`(result=0) 离开房间 | 同上，复位 -1 |
| 服务端发 `0x0400 gspPrepareGame` | **+1**，并 `ResetQueues` 清空六条收包队列 |
| 服务端发 `0x0403`（结算看完）| **+1**，同上 |
| 服务端发 `0x0303` 的包尾 u16 | ★ **直接设定成那个值** —— 客户端自己只会 `inc` 和「复位 -1」，**这是原版留给服务端的唯一「说几就是几」入口**，中途进房的人靠它对齐 |

**去重**在 `PktQueue::Insert`（`0x54bb8c`，队列在 `[session + 座位*0x24 + 0x2e4]`）：
`seq < base` 丢弃、`slots[seq-base]` 已占丢弃。**这就是「双通道同时投递同一个包」安全的唯一依据。**

### 1.4 流读写原语表（逆任何包的线格式先查这张表，V0.2 §136）

所有 `Serialize` / `Deserialize` 只调这十几个 helper（`ecx` = 流）。

**读**

| va | 读什么 | 落到 |
|---|---|---|
| `0x5d5942` | u8 | `al` |
| `0x5d5956` | int32 → bool | `al` |
| `0x5d596f` | **u16** | `ax`（调用方常跟 `movsx eax, ax`）|
| `0x5d5984` | int32 | `eax` |
| `0x5d5998` | float32 | st0 |
| `0x5d59c1` | n 个原始字节 | 指针参数 |
| `0x5d59d0` | 1 字节 | 指针参数 |
| `0x5d59de` | **int32 → bool**（线上 4 字节，内存 1 字节）| 指针参数 |
| `0x5d59f1` | 2 字节 | 指针参数 |
| `0x5d59ff` | 4 字节 | 指针参数 |
| `0x5d5a0d` | 8 字节 | 指针参数 |
| `0x5d5b3a` | **字符串** = `u16 字符数 + UTF-16LE` | 指针参数 |

**写**

| va | 写什么 |
|---|---|
| `0x5d5901` | 1 字节 |
| `0x5d5910` | 2 字节 |
| `0x5d591f` | 4 字节 |
| `0x5d592e` | 8 字节 |
| `0x5d5a4c` | 1 字节**零扩展成 4 字节**再写（★ 线上是 int32）|
| `0x5d5a5a` | 字符串（u16 字符数 + UTF-16LE）|

⚠⚠ **线偏移 ≠ 结构体偏移。** `0x5d59de`（bool）线上占 4 字节、结构体里只占 1 字节；
序列化器又是紧凑写的（没有对齐填充）。`gspRepGameResult` 从两个 bool 之后
「线序」比「结构体偏移」少 **6 字节**；`0x0408` 的死亡次数线偏移是 6、结构体里是 `+0x08`。
**收发一律用同一个格式串重新打包，不要手算偏移**（V0.2 §116、V0.1 §108 各踩过一次）。

### 1.6 绝对不要发的包

- **不要发 `0x0409`**：两条分支都是「开始失败」提示框（V0.1 §76）。
- **不要在客户端报 `0x0403` 之前发 `0x0402`**：空指针崩溃（V0.1 §82）。
- **不要发服务端方向的 `0x0408`**：那是「与 %s 的网络状态不佳」告警（V0.1 §89）。
- **不要在收到 `0x0412` 之前发 `0x0418`**：换图加载循环是**前置**判断。
- **不要在 `0x0300` 之前发 `0x030b`**：角色持有判定第一步查「座位已占用」。
- **不要用 `0x0416` 改难度解锁**：会弹一个没读过的通知窗（用 `0x020c`）。
- **不要给 `0x0407` 的应答加过滤**：漏回一发，那件掉落物**永久作废**。

### 2.1 系统段 `0x01xx`

#### `0x0100` gcpReqLogin —— 登录（**客户端 RTTI 里没有这个类**）

序列化 `0x558d34`（由 `ServerConnection` 虚表槽 15 = `0x54d520` 组包）。实测 34 字节。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | **wstring** | ★★ **票据**。认证服放进 `CULoginReplyPacket` 的**第二个字符串**（`s2`），客户端原样转发上来 | ✅实测（V0.2 §123）|
| 之后 | int32 数组 | 第 1 个 dword = **本机内网 IP**（按字节，实测 `c0 a8 0b d7` = 192.168.11.215）| ✅实测 |
| | | 随后 6 字节 **疑似网卡 MAC**（对应 `iphlpapi!GetAdaptersInfo`）| 🤔推测 |
| | | 再往后的 `0x1570d` 等值 | ❓未知 |
| 结尾 | functor | `this+0x10`（vft `0x6916a4`）写的尾部 | ❓未知 |

**必须回**：`0x0100 gspRepLogin`。
**服务端只需要读第一个 wstring**（票据），其余字段当前全部忽略。

★ 内网 IP 上报的用途：原版拿它做**客户端之间的 UDP 直连**目标（V0.2 §153）。
公网环境下这个地址基本发不到，靠 `0x040e` 那条通道兜底。

#### `0x0106` gcpReportHack（vft `0x65e118`）—— 客户端自己的作弊上报

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | **wstring** | 一行**给人看的**正文，由发现问题的那一处自己拼 | ✅实测 |

### 2.2 频道 / 房间列表段 `0x02xx`

#### `0x0200` gcpReqListSession（vft `0x6915f0`，Serialize `0x54c0e2`）—— 要房间列表

载荷 **12 字节**（V0.2 §139 / §170）：

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | u16 | **起始房间号** —— 分页锚点（当前列表里 index 0 的房间号）| 🔍静态 |
| `+0x02` | u16 | 恒 0 | ❓未知 |

| `+0x07` | u8 | 恒 0 | ❓未知 |

**必须回**：`0x0200`（服务端方向，房间列表）。

⚠ `+0x06` 那个字节以前被当成「未定字段」丢掉，于是大厅左下角「全部 / 待机」两个按钮
怎么点都没反应（§170）。

### 2.3 房间内段 `0x03xx`

#### `0x0301`（客户端方向）—— 改自己座位的某个字段（**无 RTTI 类**）

序列化 `0x558dcb`。★ **没有 action 字节**（服务端方向的同号包才有）。

| 顺序 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| 1 | int32 | **座位号** | ✅实测 |
| 2 | `SessionSlot` | 整个座位的副本，见 [§6.1](#61-sessionslot座位) | ✅实测 |

★★ **这个包有两个来源，载荷形状完全一样，只能靠「哪个字段变了」区分**（V0.2 §165）：

| 变的字段 | 来源 | 服务端要广播的 action |
|---|---|---|
| `character_id`（`+0x0c`）| 点「人物选择」的头像（`0x467050` / `0x4692d0`）| **4**（换角色）|
| `team`（`+0x08`，在 1 / 2 之间翻）| 点「变更队伍」（`0x469f95` / `0x46deaa`）| **3**（重建模型，不播提示）|

**必须回**：把 `0x0301`（服务端方向，带 action）广播回**全房间**（含发送者）。

#### `0x0302` gcpChangeSession（vft `0x691808`，Serialize `0x54c18c`）—— 提交房间设定

客户端在处理完 `gspRepCreateSession` 之后立刻发（`0x54f747` 结尾 `0x54fae9`），

| 1 | int32 | **自由座位数**（来自 `0x556f40`）| 🔍静态 |
| 2 | wstring | **房间标题**（回显 `LobbyStage+0x08`）| ✅实测 |
| 3 | wstring | ★ **地图名**（查表自 `0x40b6a2`）—— 建房后客户端就是靠这一发把地图名交上来的 | ✅实测 |
| 4 | int32（1 字节零扩展）| ★ **随机地图开关**（`[obj+0x10]`，来自 `[LobbyStage+0x14]`）| ✅实测 |

★★ **字段 4 必须原样回传**（V0.2 §228）：发送点 `0x54e5ea` 只推 5 个参数

`[LobbyStage+0x14]` 里的旧值。服务端不回传的话，紧接着那一发 `0x0303` 会把
`+0x14` 写成 0，**「随机」按钮当场弹回**（用户实机报的现象）。

二十多种值（`bug调查/6/server_logs/game_026_27799.txt`）。

#### `0x030f` gcpReqFirstUserResult（vft `0x69168c`，Serialize `0x404ee8`）—— 新手教程进度上报

载荷 **4 字节**：

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **新手教程状态**。客户端先自己写进 `[0x72e2a4]+0x64` 再原样发上来。已知三个调用点分别推 **5** / **4** / **4**，`>= 3` 都算完成 | ✅实测（V0.1 §97 / §54）|

**必须回**：**不用回**（客户端自己已经切回大厅了）。服务端只需要存进存档。
服务端方向的同号包有处理器 `0x4089c3`，但它**不读包体**，按 D028 不回显。

#### `0x0310` gcpStartTcpRelay（vft `0x65e0d4`，Serialize `0x4085a9`）—— 要一条中继通道

载荷 **8 字节**（V0.2 §152）：

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **我的座位号**（`0x409f7d` = `[[0x72e29c]+0x1cc]`）| ✅实测 |
| `+0x04` | int32 | **对方座位号** | ✅实测 |

发送节奏：进房后 `0x40591a` 每帧 tick 里，对**每个「不是我」且「有人」的座位**各发一发，
**每座位节流 10 秒**。所以「房里另外两个人 → 每 10 秒两发」是正常现象（§144）。

**必须回**：`0x0210 gspJoinRelay`（要中继）**或者什么都不回**（走 `0x040e` 回退路径）。

⚠⚠ **一条游戏连接只能回一次 `0x0210`**；重复请求是常态，**去重责任 100% 在服务端**（§159）。

#### `0x0311` gcpReqQuestRecord（vft `0x691644`）—— 要闯关 / PvP 记录

载荷 ❓未观测到有意义的字段（当前实现忽略）。

**必须回**：`0x0311 gspRepQuestRecordInPvp` = `int32 n + int32 records[n]`，**n 必须是 6**。

★ 六项是**六个座位**，不是「六种游戏类型」（V0.2 §161）。**每一项具体是什么数 ❓未知**
（落进 `[LobbyStage + 座位*4 + 0x1ac]`，纯表现层，多半是头顶的段位标记），
按 D019 全填 0，客户端照常工作。

### 2.4 战斗内段 `0x04xx`

> ★★ 这一段有一条贯穿全局的规律（V0.1 §108 / §111 / §113 / §115、V0.2 §191 / §194 / §200
> 一共六条同形状的链）：**客户端把「我想做什么」报上来就干等，真正让事情发生的是服务端的应答。**
> 不回 = 死不掉 / 换不了图 / 掉不了东西 / 捡不起来 / 用不了道具。

#### `0x0400` rawCountDownFinished（**无 RTTI 类**）

开局握手的一环。载荷 ❓未观测到有意义的字段。
处理见 [§3.4 的开局链](#开局链的顺序硬约束)。

#### `0x0402` rawCountGameReady（**无 RTTI 类**）

同上。⚠ **绝不能在客户端报 `0x0403` 之前发服务端方向的 `0x0402`**：空指针崩溃（V0.1 §82）。

#### `0x0403` rawLoadingDone（**无 RTTI 类**）—— 关卡加载完成

**必须回**：等房间里**所有人**都报完 `0x0403` 才发 `0x0402`（放行）。

#### `0x0405` rawLeaveGameResult（**无 RTTI 类**）—— 「结算界面看完了」

**空载荷**。客户端在结算界面上停留约 **9 秒**后发（会话 11 实测：`0x0411` 之后 9 秒整）。

**必须回**：`0x0403`（服务端方向）把它切回房间。
⚠ 这一发会让**局号 +1**（换代），见 [§1.3](#13-udppacket玩家间同步数据-和-rawpacket-是两个类)。
⚠⚠ **同号反向**：服务端方向的 `0x0405` 是**拾取放行**（两个 int32）。
判断时**必须**先确认「本局已经结算过」，否则会把拾取放行错当成「看完了」。

#### `0x0406` gcpCreateItem（vft `0x670c64`，Serialize `0x48c84f`，发送点 `0x493a57`）

**32 字节**。⚠ 这个包在 V0.1 §108/§109 里曾被错记成「位置同步」，§112 已勘误。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **物件 id**（`10101`=金币×1、`10202`=水炮…，见 [§6.5](#65-物件-id-表)）| ✅实测 |
| `+0x04` | float | **X** | ✅实测 |
| `+0x08` | float | **Y** | ✅实测 |
| `+0x0c` | float | **速度 X** | ✅实测 |
| `+0x10` | float | **速度 Y** | ✅实测 |
| `+0x14` | int32 | 实测**恒为 3** | ❓语义未知 |
| `+0x18` | int32 | 实测**恒为 -1** | ❓语义未知 |
| `+0x1c` | int32 | 实测**恒为 -1** | ❓语义未知 |

实测样本（怪物死后 62 毫秒）：`da 27 00 00 | 00 60 19 45 | 00 80 97 43 | 0 | 0 | 03 | -1 | -1`
= 物件 10202 水炮、x=2454.0、y=303.0。

**必须回**：★ **`0x0404 gspCreatedItem`**（在这 8 个字段前面插一个服务端分配的实例句柄）。
⚠⚠ **绝不能回显同号** —— 服务端方向的 `0x0406` 是**死亡广播**，回显 = 随机杀角色。

#### `0x0407` gcpGetItem（**无 RTTI 类**，Serialize `0x558e9a`，发送点 `0x493a99`）

**8 字节**。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **座位号**（= `[Character+0x2ac]`）| ✅实测 |
| `+0x04` | int32 | **实例句柄**（= `[Item+0xd0]`，就是服务端在 `0x0404` 里发下去的那个）| ✅实测 |

**必须回**：**服务端方向的 `0x0405`**（原样回显这两个 int32）。

★★ **不回的后果不是「这一次没捡到」，而是这件东西从此永远捡不起来**：
`Character::CheckItemPickup`（`0x5154d3`）发完就把 `[item+0x2a8] = 1`（防重发），
一件只报一次（V0.1 §115）。**所以绝对不要给这个应答加任何过滤。**

#### `0x0408` —— 「某个角色 HP 归零了」上报（**无 RTTI 类**，Serialize `0x558f16`）

**18 字节**。★★ **这是死亡判定的请求，不是遥测**（V0.1 §108）。

链路：`HP<=0`(`0x50f778`) → `Character::OnHpZero`(`0x4ffab0`) →
`GameContext::vf_1c()`(`0x46e188`) **恒返回 0**（所以客户端**不会自己判死**）→
`GameContext::ReportDeath`(`0x493855`) → 发本包 → **等服务端回 `0x0406`** 才真的倒下。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | u32 | **角色对象句柄**（`[char+0xd0]`），`World::Find` 用它找对象 | ✅实测 |
| `+0x04` | u8 | **座位号**（`[char+0x2ac]`）；怪物是 `0xFF`(-1) | ✅实测 |
| `+0x05` | u8 | 传给 `Character::Die()` 的参数（`[char+0x158]`，**疑似凶手 id**；实测怪物打死是 `0xFF`，掉岩浆 / 自杀是 `0x00`）| 🤔推测 |
| `+0x06` | int32 | ★ **死亡次数**（`[char+0x600]`，「我死之前已经死过几次」）| ✅实测 |
| `+0x0a` | float | **X** | ✅实测 |
| `+0x0e` | float | **Y** | ✅实测 |

⚠⚠ **线偏移 ≠ 结构体偏移**：死亡次数在**线上偏移 6**，在客户端结构体里是 `+0x08`
（中间两字节是对齐填充）。V0.1 会话 15 按 `+0x08` 就地改包 → 死亡次数变成六万多 →
`剩余生命 = 最大生命 - 死亡次数` 成大负数 → `0x472527` 拿它当数组下标 → C0000005。
**收发一律用同一个格式串（`<IBBiff`）重新打包。**

**必须回**：`0x0406`（服务端方向，死亡广播）。★ 里面的死亡次数必须是**收到的值 +1**，
照抄回去的话 HUD 上的心形永远是 3 颗（V0.1 §109）。

#### `0x040c` rawUseItem（**无 RTTI 类**，Serialize `0x559205`，发送点 `0x516335`）

**4 字节**。「按 Ctrl 用道具」。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **道具槽序号**。★ 客户端**恒发 0**（`RemoveItem` 会把后面的往前挪，所以「下一件要用的」永远在第 0 格）| ✅实测 |

客户端发完只放一声音效（id `0xd`）就等 —— **效果和扣道具全在服务端手上**（V0.2 §194）。

**必须回两发**：
1. `0x040c`（服务端方向，同号回显）**只发给他自己** → `Character::RemoveItem` 扣掉那一格；
2. `0x040a`（服务端方向，「某座位吃到某件道具的效果」）**广播全房间** → 每台机器都算上那个效果。

★ `RemoveItem` 在整个客户端里**只有那一个调用点**，不回 = 道具永远卡在槽里。

#### `0x040d` rawRemoveCharAttr（**无 RTTI 类**，Serialize `0x558f8e`，发送点 `0x509858`）

**8 字节**。「我身上那个道具效果结束了」（V0.2 §200）。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **座位号**。发送分支的前置判据就是「== 我的座位」，所以**只可能是发包人自己** | ✅实测 |
| `+0x04` | int32 | **属性号**（`Data/Status.ini` 的小节号，见 [§6.6](#66-角色属性号charattr)）| ✅实测 |

★ 只有**本机玩家自己的角色**才会发这一发（`Character::RemoveAttrEffect` `0x50982e` 里
`if ([char+0x2ac] == 我的座位)`）。

**必须回**：原样广播给房里**其他人**（发包人自己可以不发 —— 收侧 `0x551dfb` 开头
`if (座位 == 我的座位) return` 会丢掉）。
**不转发的后果**：三重射击 / 致命射击 / 毒弹这类「按弹数结束」的道具，
在别人屏幕上的模型 / 特效**永远变不回去**。

#### `0x040e` rawPeerData（**无 RTTI 类**，Serialize `0x5594be`）—— 玩家间同步数据上行

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | 字节流 | ★ **一整个 `UdpPacket`**（12 字节头 + body），见 [§1.3](#13-udppacket玩家间同步数据-和-rawpacket-是两个类) 和 [§5](#5-udppacket-的内层-opcode) | ✅实测 |

发送开关：`[GameSession+0x3e4]`，**默认 0，每次退房被清回 0**，
由服务端发 **`0x0410`（int32 1）** 打开。开关一开客户端立刻开始发（事件驱动，约 8 Hz）。

**必须回**：**原样**用 opcode `0x040f` 转发给同房间的其他人。
★ 转发时唯一要动的是 `UdpPacket` 头 `+4` 的**局号**（收件人可能在另一代，
见 `relayserver.restamp_peer_game_id`）。

## 3. 游戏服：服务端 → 客户端（gsp）

每条的格式：**opcode / 类名 / vftable / 反序列化点 / 处理器** → 参数表 → **客户端拿它干什么**。

★ 「返回值」在这个方向上 = **客户端的副作用**（改哪个全局、建哪个对象、切哪个 stage）。
所以这一节的每条都写了「落到客户端的什么地方」——排查「发了没反应」时先看这一列。

---

### 3.1 系统段 `0x01xx`

#### `0x0100` gspRepLogin（vft `0x6915d8`，Deserialize `0x54c35c`，处理器 `0x54f2cc`）

**48 字节起**（全填 0/空串时正好 48）。

| 顺序 | 类型 | 含义 | 落到客户端 | 可信度 |
|---|---|---|---|---|
| 1 | int32 | ★ **结果码**，见下表 | —— | ✅实测 |
| 2 | wstring | ❓未知 | 客户端没转发也没显示 | ❓ |

#### `0x0210` gspJoinRelay（vft `0x691814`，Deserialize `0x54d22f`，处理器 `0x55431c`）

**18 字节**（V0.2 §157）：

| 子对象 | 偏移 | 反序列化器 | 线格式 | 含义 |
|---|---|---|---|---|
| `NetAddress`（vft `0x68c580`）| `+0x04` | `0x4438dc` | `int32 ip` + `u16 port` | ★ **中继服务器地址** |
| `RelayAuthData`（vft `0x691580`）| `+0x10` | `0x54c47e` | `int32 a` + `int32 b` + `int32 c` | ★ **认证数据** |

- **`ip` 是网络字节序的原始 32 位**（`socket.inet_aton("127.0.0.1")` = `7f 00 00 01`
  直接当 4 字节写进去，**不要**再翻转）；**`port` 是主机序 u16**。
  证据：`Connect`(`0x5bc50d`) 里 `sin_addr` 原样写、只有 `sin_port` 过 `htons`。
- ★ **`RelayAuthData` 那三个 int32 客户端一个字节都不解释** —— 抄进
  `[RelayConnection+0x89c/0x8a0/0x8a4]`，之后原样抄回来发给中继。
  **所以它的语义完全由服务端定**（本项目拿它当「房间号 / 座位 / 一次性随机数」）。

⚠⚠ **两条铁律**（V0.2 §158 / §159）：
1. **一条游戏连接只回一次**。再回一发会让旧 `RelayConnection` 变成孤儿，
   等它收到 `FD_CLOSE` 时 `OnDisconnected` 照样触发，把**新**连接的全局指针清 0，
   再发一发 `0x0203` **把玩家踢出房间**。
2. 地址**必须是客户端一定连得到的**。连不上大概率同样走 `OnDisconnected` → 踢出房间。

#### `0x0211` —— 拆掉中继连接（处理器 `0x55437b`）

**载荷被无视。** `[0x72e290]` 非空就调它的 vft[0]（scalar deleting dtor）并把全局清零。
★ 走的**不是** `OnDisconnected`，所以没有「把玩家踢出房间」的副作用 ——
**这是唯一安全的拆连接方式**。

#### `0x0301`（服务端方向）—— 单个座位的变更事件（**无 RTTI 类**，Deserialize `0x40648d`）

| 顺序 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| 1 | **u8** | ★ **action**（`0x5d5942` 读 **1 字节**，不是 4）| ✅实测 |
| 2 | int32 | **座位号**，客户端校验 `0 <= n < 6`，**越界直接丢包** | ✅实测 |
| 3 | `SessionSlot` | 与 `0x0300` 里的每一项同格式 | ✅实测 |

★ **所有分支都先把 `SessionSlot` 反序列化进座位**，action 只决定「模型怎么动」：

| action | 分支 | 干什么 |
|---|---|---|
| `0` | `0x406691` | **进房**：清 IP/端口、**`0x405e1c` 建座位的角色对象**、`0x406f42`、刷 UI。★ 唯一会**建**角色对象的 |
| `1` / `2` | `0x406676` | **离开 / 被踢**：清 IP/端口 + `0x405f8f`（**销毁**角色对象并把 `[LobbyStage+0x1d0+i*4]` 清 0）。两个码在客户端里**完全等价** |
| `3` | `0x406628` | **按座位数据重建模型**（不销毁）。用于「变更队伍」「换模式重排」这类只改数据的场景 |
| `4` | `0x406520` | **换角色**：用 `seat+0x0c` 查角色名，播 `'%s님이 %s 캐릭터로 선택되었습니다.'`，然后落到 `0x406628` |

⚠⚠ **有人离开必须发 1（或 2），发 3 的话玩家列表里的名字没了、3D 模型却还杵着**（V0.2 §147）。
⚠ **服务端主动改一个座位**（V0.3 的房间 bot：换角色 / 换队 / 置准备）一律发 **3**，不发 4 ——
   4 会让客户端播那句韩文。3 走 `0x406628`，重建模型且**一个字都不播**，正是这种场景要的。
   反过来，**加一个座位只能发 0**：`0x405e1c` 是唯一会**建**角色对象的分支，
   发 3 的话玩家列表里有名字、天上却没有模型。
⚠ action `0` 会把 `seat[+0x14]`（对端 IP）和 `seat[+0x18]`（端口）清 0；
而 `0x0300` 的处理器会把「我」的座位 IP 写成 127.0.0.1 —— **两个包同发时 `0x0301` 要排在 `0x0300` 前面**。

### 3.4 战斗内段 `0x04xx`

战斗跳表 `@0x54e5ae` 覆盖 `0x0405`~`0x0413`（索引 = `opcode - 0x405`）；
另有 `GameContext` 自己的分发表 `0x493808`（战斗中**优先**于大厅/游戏跳表）。

#### 开局链的顺序硬约束

```text
房主按 F5        客户端 -> 0x0402（第 1 发，空载荷）
                 服务端 -> 0x0401 gspTriggerCountGame(int32 0)   ★ 广播给全房间
房主确认          客户端 -> 0x0402（第 2 发，空载荷）
                 服务端 -> 0x0400 gspPrepareGame(int32 seed)     ★ 广播，seed 必须相同
                           ↑ 切 stage 6（加载关卡）；**每个人的局号 +1** 并清空六条收包队列
加载到 100% 之后  客户端 -> 0x0403（空载荷，**每 5 秒**轮询一次「可以开始了吗」）
全员都报到之后    服务端 -> 0x0402（空载荷）→ 切 stage 7（游戏本体）
```

⚠⚠ **一次只推一个 stage。** 会话 09 实测：第二发 `0x0402` 一到就回 `0x0402`（而不是
`0x0400`），客户端被直接踢进 stage 7，房间的座位角色对象随之销毁，而开局数据从没下发 →
渲染路径解引用 NULL → `C0000005 @ 0x50a368`（V0.1 §82）。
⚠ `0x0400` 的 `seed` **必须全房间一致**，否则各人生成的关卡不一样。
⚠ 只认**房主**发的 `0x0402` —— 认了别人的就等于谁都能替房主开局。

★ 三个 opcode 都是**同号反向**：客户端方向的 `0x0400`/`0x0402`/`0x0403` 是
「我到这一步了」，服务端方向的是「命令你换 stage」（V0.1 §84）。

#### `0x0400` gspPrepareGame（vft `0x69165c`，处理器 `0x551605`）

| 顺序 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| 1 | int32 | **共享随机种子**（地图 / 刷怪点选择用）| ✅实测 |

★★ 副作用：`0x5517a3` → 局号 **+1**、`GameSession::ResetQueues`(`0x407678`) 清空六条队列、
阶段 4 / 切 stage 6。

★★ **seed 有两条硬约束**（V0.2 §228）：

1. **全房间必须是同一个数**，否则各人生成的关卡不一样；
2. **每局都要换一个**。它是 `0x40b6e5`（随机挑图）的第 5 个参数，
   `0x40b737` 判 `!= -1` 就拿它构造确定性随机源 —— **恒发 0 的话
   「随机地图」永远随到同一张**。取值范围用 `[1, 2^31-2]`：
   `-1` 是「改用线程本地随机源」的哨兵，发出去房里每人各随各的图。

★ 随机地图开着（`[LobbyStage+0x14] != 0`）且描述符 type 是 1 / 5 时，
处理器 `0x551605` 开头就先挑图、写 `[LobbyStage+0x10]`、往聊天框播
「已选择随机地图[%s]。」，最后**只有房主**（`0x551774` 比座位）回发一发
`0x0302` 把结果汇报给服务端。

#### `0x0401` gspTriggerCountGame（vft `0x65e0e0`，构造点 `0x4074de`）

| 顺序 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| 1 | int32 | **结果码**：`0` = 进正常的开局确认路径；`2` / `3` = 天梯维护错误 | 🔍静态 |

#### `0x0402` —— 「切到 stage 7（游戏本体）」（**无 RTTI 类**，处理器 `0x5517d0`）

**空载荷。** 记时间戳到 `[LobbyStage+0x3dc]`、清 `[0x72e2cc]+0xf7c` 的倒计时状态，
然后 `push 7 / jmp 0x40e47f` 切 stage。
★ 它**不是应答**，是「命令客户端换 stage」（V0.1 §84）。
★ `0x5517f9` 有 `cmp [stage+0x54], 7 / je` 的幂等保护，重复发不会出错，但没必要。

#### `0x0403` —— 结算看完 → 回房间（**无 RTTI 类**，处理器 `0x5518fb`）

★★ 副作用：`0x551900` → 局号 **+1**、阶段 2 / 切 stage 5，
并在 `0x551904` **硬写 `[LobbyStage+4] = 2`**（= 待机中，所以打完一关回来的房间背景是对的）。

#### `0x0404` gspCreatedItem（vft `0x69188c`，Deserialize `0x54c523`，处理器 `0x551a11`）—— 掉落物落地

#### `0x0405`（服务端方向）—— 拾取放行（处理器 `0x551d35`）

**原样回显客户端 `0x0407` 那两个 int32**：

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | **座位号** → `[LobbyStage + 座位*4 + 0x1d0]` 取角色对象 | ✅实测 |
| `+0x04` | int32 | **实例句柄** → `World::Find`(`0x474225`) + `dynamic_cast<Item*>` | ✅实测 |

两个都非空才 `item->vf_d4(角色)`（`0x51f447`）：
`if ([item+0x2a9] == 0) vf_11c(角色)`（当场生效：红心回血 / 武器换枪）
然后 `vf_20()` 把物件从世界里删掉。

★★ **对 17 个 PvP 道具来说这一发只是「抹掉箱子 + 放特效」** ——
它们建构时第 4 个参数是 1（`[item+0x2a9]`），当场生效那条分支**恒不成立**。
要让道具真的进道具栏，必须另发 `0x040b`（V0.2 §194）。

★★ **金币（10101 / 10102）会在客户端累加本局面额并显示累计值，但不会直接改
大厅账户金币。** V0.2 §230 的旧结论只跟到 `vf_11c` 前半段的音效 / 特效，
漏看了后半段，现以完整反汇编勘误：

- `CoinItem1::vf_11c`（`0x52156f`）在 `0x521689` 把常数 **1** 传给 `0x493d96`；
- `CoinItem5::vf_11c`（`0x521b2c`）在 `0x521c47` 把常数 **5** 传给同一函数；
- `0x493d96` 校验座位号后执行 `[当前战局对象 + 0x0c + 座位*4] += 面额`；
- 闯关模式下紧接着由 `0x493d76` 读回这一格，并交给物件的浮字函数
  `[vft+0xf4]`。所以连续捡 `CoinItem1` 显示 **1、2、3**，连续捡
  `CoinItem5` 才显示 **5、10、15**。它是**本局累计面额**，不是拾取序号，
  也不是每次只显示单枚面额。

这里累加的不是持久金币全局 `[0x72e330]`，而 `0x0405` 载荷又只有座位和实例
句柄，没有金额。因此服务端应按物件类型镜像记 **1 / 5**，结算时并进 `0x0309`
的值 10 和 `0x0411` 的 4 号位。通关金币雨在 `0x4a5552` 明确请求 `10101`
（×1），所以雨中正常看到 1、2、3；可破坏场景物在 `0x4faaad` 请求 `10102`
（×5），捡到它时才按 5 跳。

#### `0x0406`（服务端方向）—— 死亡广播（处理器 `0x4938d2`，`GameContext` 表 `0x493808`）

读侧只读 **10 字节**（写侧的 `0x0408` 是 18 字节；我们把收到的 18 字节里死亡次数 +1 后原样发回，
多出来的 X/Y 客户端不读）。

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | u32 | **角色对象句柄** → `World::Find`，找不到整包丢掉 | ✅实测 |
| `+0x04` | u8 | **座位号**；`0<=座位<6` 时给 `[ctx+0x384]` 的战绩表记一次死亡 | ✅实测 |
| `+0x05` | u8 | ★★ **凶手的座位号**（怪 / 环境是 0xff）→ `Character::Die(它)` = `[vft+0xdc]` = `0x4ffbb7`。**对战的记分全靠这一格** | ✅实测 |
| `+0x06` | int32 | ★★ **新的死亡次数** → `Character::vf_c4` = `[char+0x600] = n` | ✅实测 |

★★ `[char+0x600]` 就是 **HUD 上那排心形的数据源**：
`实心心形数 = GameContext::vf_a0(座位)（最大生命） - [char+0x600]`。
**必须是「客户端报上来的值 + 1」** —— 照抄回去等于告诉客户端「死亡次数没变」，
心形永远是 3 颗，而「死 3 次判负」照常生效（V0.1 §109，用户实机报过这个组合）。

★★ **`[char+0x600]` 跨换图不清零**（V0.2 §241，✅实测 + 静态复核）。
`0x47900a` 换图时把六个座位的角色**原样挂回世界**（同一批指针，`0x473e7c`），
不是卸掉重建；`[[0x72e2d4]+0x3c]` 起的 30 个 dword 还按 `max` 合并回去。
所以服务端的每句柄权威计数在换图时**只能清怪 / 物件那一份**，玩家的必须留着 ——
清了就会同时踩坏「心形不减」和「下一次死亡被判成重复上报、人躺着起不来」。

★★ **客户端有两个死亡计数器，都靠这一发喂，漏发一发两个都会歪**：

| 计数器 | 谁写 | 谁读 |
|---|---|---|
| `[char+0x600]` | 本包 `+0x06` → `Character::vf_c4` | HUD 心形（`0x4a49a4`）|
| `[vc + 座位*0x2c + 0x60]` | `0x48c942`，**每收到一发本包 `+= 1`**（不看 `+0x06` 的值）| 剩余生命 → `Die()` 在 `0x501976` 读，为 0 就把 `[char+0x2d8]` 写成 -1，**永不重生** |

`GameContext::vf_a0/vf_a4`（`0x4913aa` / `0x4913c6`）都转发给 `[ctx+0x384]`
的胜负条件对象；`[ctx+0x384]` 为 NULL（待机房间）时返回 `0x7fffffff` = 无限命。

| 胜负条件类 | vft | 最大生命 `vf+0x0c` | 剩余生命 `vf+0x10` |
|---|---|---|---|
| `QuestVictoryCondition` | `0x6935dc` | `0x55e095` = **`[vc + 座位*4 + 0x198]`（逐座位，来自关卡脚本，服务端拿不到）** | `0x55e0a3` = `最大生命 - [vc + 座位*0x2c + 0x60]`，负数截 0 |
| `SurvivalVictoryCondition` | `0x693624` | `0x55db69` = **写死 3** | 同上 |
| `DeathMatch` / `NewDeathmatch` / `TimeAttack` / `Debug` | —— | `0x55e0d1` = `0x7fffffff` | 同左（**无限命**）|

★★ **`Character::Die` 会自己给凶手记分，服务端必须用同一套口径**（V0.2 §224）。
它拿 `+0x05` 去 `0x404ff6`（座位 → 角色，**座位没人就是 NULL、一分不动**）之后三选一：

| 情况 | 调用 | 后果 |
|---|---|---|
| 凶手座位 == 受害者座位 | `Character::OnSuicide` `0x506eba` | **`[char+0x604] -= 1`**（下限 0）+ `AddScore(座位, -1)` |
| 组队战（`0x409df1(描述符+0x18)==1`）且两人同队（`0x40462c`）| 同上 | 同上 |
| 其余 | `Character::OnKill` `0x506e8c` | `[char+0x604] += 1` + `AddScore(座位, +1)` |

`[char+0x604]` = **屏幕上那个杀敌数**（`0x497536` 每帧读它画）；
`GameContext::AddScore`（虚表槽 `+0x100` → `0x48c98f`）写
`[victory + 座位*0x2c + 0x5c]` = **夺分胜负线比的那一格**（`0x55bf20`）。
两个数一起动 —— 所以服务端要是只加不扣，「玩家看见的」和「服务端判的」
就会越差越多（用户报过「HUD 说要 6 个，5 个就结算了」）。

#### `0x040a` —— 「某个座位吃到某件道具的效果」（Deserialize `0x5590d5`，处理器 `0x551d95`）

**16 字节 = 4 个 int32**。⚠ **字段顺序反直觉，别按直觉重排**：

| 线偏移 | 类型 | 含义 | 可信度 |

#### `0x040b` gspGiveItem —— 「往你的道具槽里塞一件」（处理器 `0x55206b`）

**4 字节**：

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | **int32** | **物件 id** | ✅实测 |

⚠ V0.2 §193 初记的「u16」**是错的**（§194 已更正）：处理器读字段用的是
`0x5d5984` = `Read(&buf, 4)`，是 int32。u16 的原语是 `0x5d596f`、u8 是 `0x5d5942`。

★★ **它认的是「收包这台机器上的本地玩家」，包里没有座位号** ——
所以**只能发给捡到东西的那个人**，广播出去等于人手一件。

`Character::AddItem`(`0x517037`) 做三件事：写进第一个空槽 `[Character+0x764+i*4]`、
建图标对象、起 3000 毫秒提示计时器。**4 格满了就整个函数什么都不做**，
所以服务端要自己卡住槽数上限，否则两边的槽会错位。

#### `0x040c`（服务端方向）—— 「把你的第 N 格拿掉」（处理器 `0x552089`）

**4 字节 int32 = 槽位序号**。同样按「收包的本地玩家」认人，**只发给用道具的那个人**。
★ `Character::RemoveItem`(`0x5170b4`) 在整个客户端里**只有这一个调用点**。

#### `0x040d`（服务端方向）—— 「某座位的效果结束了」（处理器 `0x551dfb`）

**8 字节 = 两个 int32**：`(座位号, 属性号)`。
处理器开头 `if (座位 == 我的座位) return`（自己那一发直接丢掉），
然后 `Character::RemoveAttrEffect`（拆模型 / 特效）+ `AttrList::Remove`。

#### `0x040f`（服务端方向）—— 同步数据下行（处理器 `0x4086b5` → `0x407869`）

载荷 = **一整个 `UdpPacket`**，把客户端 `0x040e` 上来的**原样**转出去即可。
客户端剥掉自己的 10 字节头（`0x55b9bc`）后交给 `0x407869` —— **和 UDP 收到的走同一个入口**。

#### `0x0410` gspToggleUdpClientCommunication（vft `0x65e194`，处理器 `0x408703`）

| 线偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+0x00` | int32 | ★ **同步通道 A 的总开关**（0/1）| ✅实测 |

处理器做两件事：
```text
[GameSession+0x3e4] = flag
setsockopt([0x72e30c]+8, IPPROTO_TCP, TCP_NODELAY, &flag, 4)   ; 顺手关 Nagle
```

★★ **默认 0，而且每次退房（`0x0203`）都会被清回 0** ⇒ **每次进房 / 每次开局都要重发**。
★★ **走原版中继也照样要先发这一发** —— 那个开关是两条路共同的总闸。

⚠ 客户端会**自己把它关掉**的情况见 V0.2 §209（表现为「我自己在动、别人看我一动不动」），
服务端不能只在「值变了」时才发。

#### `0x0411` gspEndGame（vft `0x691874`，Deserialize `0x54cea3`，处理器 `0x551804`）—— 关卡结束 + 结算

**14 个 4 字节字段**：

| 顺序 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| 1 | int32 | ★ **座位号**。必须等于客户端认为的自己的座位号，否则下面四个全局不更新 | ✅实测 |
| 2 | bool32 | **成功 / 失败**（线上 4 字节）。★ 和结算界面的「完成 / 未完成」标签**无关** | ✅实测 |
| 3..14 | int32 × 12 | 业务值，见下 | |

**12 个业务值里查明的**（索引从 0 起）：

| 索引 | 落到 | 含义 | 可信度 |
|---|---|---|---|
| **1** | `[0x72e33c]` | ★ **总经验**（绝对累计值）| ✅实测 |
| **2** | `[0x72e344]` | ★ **下一级所需总经验**（绝对值）| ✅实测 |
| **3** | `[0x72e340]` | ★ **本级起始总经验**（绝对值）| ✅实测 |
| **4** | `[0x72e330]` | ★ **金币** —— ⚠ 客户端是 **`+=`**，发的是**本局所得**，不是总额 | ✅实测 |
| **5,6,7** | 结算表 [5][6][7] | ★ **「分数 / 生命」那一行的分数**，界面显示的是**三格之和** ×系数。原版多半是「击杀分 / 时间分 / 收集分」之类的拆分 | ✅实测（V0.2 §116）|
| 0,8,9,10,11 | —— | ❓未知，一律填 0 | ❓ |

★ 经验三件套是**绝对累计值**，右上角数据栏自己做减法：
`当前经验 = 总经验 - 本级起点`、`升级所需 = 下一级所需 - 本级起点`。
填「本级内的差值」会让进度条错乱。

★★ **发给同一个人时，「他自己那份」必须排在最前**（V0.2 §178）：
处理**每一发** `0x0411` 都会走到 `0x5518e4 call 0x4913fc`（弹结算界面），
而真正把界面建出来的是**第一发**；只有座位号 == 自己时才更新的那四个全局在它**之前**写。
队友那几行是界面弹出来之后补进去的，照样显示得出来。

## 4. 原版 TCP 中继（rcp）

### 4.1 帧和加密 —— 和 27799 **完全相同**（V0.2 §156）

```text
帧      = RawPacket 10 字节头，逐字节相同
加密    = SimpleCipher，两个方向 (0,1) / (5,3)
开场白  = ★ 没有。ServerConnection 才发明文版本号，RelayConnection 上来就 rcpRegister
```

分发器 `RelayConnection::OnPacket` = `0x54bce1`，opcode = `word[包缓冲 + 8]`。

### 4.2 opcode 表（V0.2 §157，逐指令核对过）

**中继 → 客户端**

| opcode | 载荷 | 客户端做什么 | 可信度 |
|---|---|---|---|
| `0` | 一整个 `UdpPacket` | `0x54bd57`：`0x55b9bc` 剥掉 10 字节头 → `0x407869(0,0,0,&udp)`（**和 `0x040f` 同一个入口**）| ✅实测 |
| `1` | **0 字节** | ping → `0x54bdab` 回 opcode `1` | ✅实测 |
| `2` | **0 字节** | 「报一下身份」→ `0x54bd1b` 回 opcode `0`（`rcpRegister`）| ✅实测 |
| 其它 | —— | `0x54bcfa: xor al,al`（未处理）| 🔍静态 |

**客户端 → 中继**

| opcode | 类名 | vftable | 载荷 | 何时发 |
|---|---|---|---|---|
| `0` | `Packet_rcpRegister` | `0x691574` | **12 字节 = `RelayAuthData` 三个 int32**（就是 `0x0210` 里给它的那三个，**原样抄回来**）| 连上就发；收到 opcode 2 时再发 |
| `1` | `Packet_rcpRepPing` | `0x691568` | **0 字节**（`Serialize` = `0x470807` = `ret 4`）| 收到 opcode 1 时 |
| `3` | （无类名）| —— | 一整个 `UdpPacket`（`0x55b992`）| 有同步数据且中继已连上 |

★ 连上之后客户端会 `setsockopt(IPPROTO_TCP, TCP_NODELAY, 1)`。

### 4.3 通道 A 的选路（`0x408619`）

```text
if ([GameSession+0x3e4] == 0) return;                  ; ★ 0x0410 的总开关
if ([0x72e290] != 0 && [[0x72e290]+0x894] != 0)        ; 中继对象在且**已连上**
     0x54beb6(packet)   ; → rcp opcode 3
else 0x5594be(...)      ; → 0x040e 发给游戏服
```

### 4.4 ⚠⚠ 中继断线 = 玩家被自己的客户端踢出房间（V0.2 §158）

`RelayConnection::OnDisconnected` = `0x54be26`：

```text
[0x72e290] = 0
[this+0x894] = 0
if ([0x72e29c] != 0) 0x406191(GameSession)   ; ★★ 这不是「清标志」，是**退出房间**：
                                             ;    发 0x0203 gcpLeaveSession
                                             ;    + [GameSession+0x3e4] = 0（连回退路径都没了）
if ([0x72e2a4] != 0) 弹公告框（字符串 0x691588）
0x5bc41a(this)                               ; 关 socket
```

⇒ 实现上的硬要求：
1. **绝不能主动关**一条已注册的中继连接；
2. 要拆连接一律用 **`0x0211`**（走 dtor，不触发 `OnDisconnected`）；
3. **连不上也算数** —— 地址填错 → 连接失败 → 大概率同样走 `OnDisconnected`。

## 5. `UdpPacket` 的内层 opcode

内层 opcode 在 `UdpPacket +10`。分界线是 **`0x4000`**：

- `< 0x4000` → `0x407c01` 进每座位的 **`PktQueue`**：**可靠、按序，丢一发就永久错位**；
- `>= 0x4000` → `0x407918` 立刻处理（可丢）。

| 内层 opcode | 名字 | 来源 | 备注 |
|---|---|---|---|
| `0x0001` | `rpChangeWeapon` | `GameSession::ProcessReliableQueue`(`0x407c84`) 里的 switch 宽字符串字面量 | ★ 丢一发 → 收方的对象句柄分配器**永久错位** |
| `0x0002` | `rpFire` | 同上 | ★ **包里没有弹体句柄**，收方按同样顺序自己分配 |
| `0x0003` | `rpExplode` | 同上 | 句柄对不上就「打不死人」（V0.2 §216 / §217）|
| `0x0004` | `rpSplashDamaged` | 同上 | |
| `0x0005` | `rpSetOnFire` | 同上 | |
| `0x0006` | `rpJump` | 同上 | |
| `0x0007` | `rpDash` | 同上 | |
| `0x000B` | `rpCrouch` | 同上 | |
| `0x000C` | `rpRespawn` | 同上 | |
| `0x000D` / `0x000E` | `rpReqState` / `rpRepState` | 同上 | |
| `0x000F` | `rpReqDie` | 同上 | |
| `0x0011` | `rpAiMsg` | 同上 | 怪 AI 消息（只有控制者发）|

| `0x4002` | 讨重传 | 同上 | |

★★ **心跳里的 N 决不许越过还没转发的事件包**（V0.2 §216 / §217）：
收方拿 N 做 `FlushTo(N)`，`base` **只进不退**，之后 `seq < base` 的事件包被**静默丢弃**，
连讨重传都不会讨 ⇒ 那台机器上这个座位的句柄分配器永久错位 ⇒
伤害数字照出、血照掉一丝、**就是打不死**。

★ `UdpPacket +8` 的序列号对**心跳恒为 0**（实测 4527 发只有 1 个取值），
所以心跳没有任何可判新旧的原版字段 —— **下行绝不能双发**。

### 5.1 组包点：`push <内层opcode> ; call 0x5bbe1b`

`UdpPacket` 的构造函数是 **`0x5bbe1b(this, 内层opcode, 目标座位, 局号)`**，
内层 opcode 就是紧挨着它的那个 `push` 立即数。全镜像扫一遍就能一次拿到
**每个内层 opcode 的组包点**（V0.3 §23 有完整表格）：

| opcode | 组包点 | opcode | 组包点 | opcode | 组包点 |
|---|---|---|---|---|---|
| `0x0001` | `0x49313e` | `0x0007` | `0x492da3` | `0x0016` | `0x493507` |
| `0x0002` | `0x491e7a` | `0x0008` | `0x492e5b` | `0x0017` | `0x4935d7` |
| `0x0003` | `0x492577` | `0x0009` | `0x493023` | `0x0018` | `0x4936e6` |
| `0x0004` | `0x492b83` | `0x000b` | `0x492f13` | `0x0019` | `0x492f9e` |
| `0x0005` | `0x492402` | `0x0011` | `0x4933b3` | `0x001a` | `0x49402f` |
| `0x0006` | `0x492d19` | `0x0013` | `0x49348f` | `0x001b` | `0x494170` |
| `0x4001` | `0x405866` | `0x4002` | `0x407e03` | `0x4003` | `0x40804f` |
| `0x4005` | `0x40822e` | `0x0012` | `0x4674bd` | `0x0015` | `0x4930a9` |

**序列化写原语**（追加 N 字节，无编码）：`0x5d5901`=1、`0x5d5910`=2、

（`push ecx` 只是腾栈位，不是字段）。

角色状态结构由**一个虚函数**整块序列化（发侧 `[0x72e2dc]` 的 `vf+0xc0` =
`0x5040b0`，收侧 `vf+0xbc` = `0x5041e1`），走裸写 `0x5d593d(ptr, 0x18)`：

| body 偏移 | 类型 | 含义 | 可信度 |
|---|---|---|---|
| `+7..8` | i16 | ★★ **位置 X** —— 收方 `fstp [char+0x34]` | ✅实测 |
| `+9..10` | i16 | ★★ **位置 Y** —— 收方 `fstp [char+0x38]` | ✅实测 |
| `+11..12` | i16 | ★ **速度 X** = `[char+0x4c4] + [char+0x120]`，收方写回 `[char+0x120]`。和**下一发的 X 位移**同号率 95.5%、比值中位数 4.111；位置不变时恒 0 | ✅实测 |
| `+13..14` | i16 | ★ **速度 Y**，同上（`[char+0x124]`）| ✅实测 |
| `+15` | u8 | `[char+0x594]`（59117/67186 是 0）| 🔍静态 |
| `+16` | — | ★ **序列化器从没写过它**（栈残留，12 种取值）—— 收方不读 | ✅实测 |

和「包压根没发出去」长得一模一样。

★ 两处「从没写过的填充」说明收方不读它们 —— 填 0 也行。

### 5.6 ★★ 收方拿这个结构做什么（`0x5041e1`，V0.3 §25）

**位置默认是插值，不是硬置** —— 合成 bot 的心跳时这条决定观感：

```
if ([char+0x164] != 0)                        -> 整个位置更新跳过
else if ([char+0x128]==0 且 新包 bit2==1)      -> 硬置 [char+0x34]/[0x38]
else                                          -> [char+0x34] = 旧×0.6 + 新×0.4
                                                 [char+0x38] = 旧×0.6 + 新×0.4 + 0.5
```

（常数 `0x6937c4`=0.6 / `0x6937c0`=0.4 / `0x69371c`=0.5。）
真客户端的 `bit2` 绝大多数时候是 1 ⇒ **插值是常态**，约 5 发心跳收敛到位。

★ **`0x5f895c` 是朝零截断，不是四舍五入** —— 它是 MSVC 的 `_ftol2`
（`fistp` 之后用 `fsubp`+`adc`/`sbb` 掰回靠近零的一侧），等价于 C 的 `(int)`。
服务端合成时用 `int()`，别用 `round()`（差 1）。

### 6.1 `SessionSlot`（座位）

反序列化 `0x556d9d`（客户端方向的写侧 `0x556ccc`）。客户端内存里每项 **0x3c 字节**。

| 3 | **u8** | `+0x08` | ★ **队伍号**（⚠ `0x5d5942` 读 **1 字节**，不是 4）| ✅实测（V0.2 §165）|
| 4 | int32 | `+0x0c` | ★ **角色 id** | ✅实测 |
| 5 | int32 × n + int32(0) | `+0x1c` | **0 结尾的物品 id 列表** | ✅实测 |
| 6 | int32 | `+0x28` | ❓未知 | ❓ |
| 7 | u16 | `+0x2c` | ❓未知 | ❓ |
| 8 | **u16** | `+0x10` | ★ **等级** | ✅实测 |
| 9 | int32(bool) | `+0x2e` | ★ **准备状态** | ✅实测（V0.2 §165）|
| 10 | u16 | `+0x12` | ❓未知 | ❓ |
| 11 | wstring | `+0x30` | ❓未知 | ❓ |
| 12 | int32(bool) | `+0x34` | ❓未知 | ❓ |
| — | | | *以下无论占用与否都有* | |
| 13 | int32(bool) | `+0x01` | **关闭**（`0x556f40` 数 `+0x41 == 0` 的座位当空位）| 🔍静态 |

**`team`（`+0x08`）的完整语义**（`LobbyStage + 座位*0x3c + 0x48`，取值器 `0x40462c`）：

- 房间里角色模型站哪边：`0x405e5d` 把它当分组号交给 `0x473cb2`；
- 战斗里的友军伤害：`0x4fedfc` / `0x4ffec3` 比两边的队伍号，**相同就不结算伤害**；
- **只有组队模式才读**（三处读它之前都先判「描述符是组队」）；
- **取值 1 / 2**，`0` = 没分队。客户端的「变更队伍」只在 1 和 2 之间切。

⚠⚠ **服务端发出去的队伍号必须夹在 0..2**（V0.2 §212）：客户端的每队战绩数组只有两格，
`vf34`(`0x55c696`) 按 `this + 40*(队伍号-1)` 写、**没有上界检查** ——
发 `>= 3` 会踩掉别人的每座位战绩（死亡次数被越写越大 → 剩余生命归零 →
**活着进观战 / 死了永不重生**）。

**`ready`（`+0x2e`）**：

- 名字旁边那行「준비중 / 准备中」：`0x46c330`；
- 房主能不能按「开始」：`0x4696cd` 数已准备的人，**房主自己那格无条件算已准备**；
- 非房主的按钮在自己已准备时变灰（`0x46b5f9`）。

**`level`（`+0x10`）** 是「等级太低，无法选择任务。」那句话的真正来源（V0.1 §77）：
按 F5 时 `0x468242` 起拿**房主座位**的这个 u16 去和关卡要求等级比。
它和 `gspRepLogin` 下发、存在全局 `0x72e338` 的那个等级**是两回事**
（后者只管大厅 UI 和下拉框过滤）。

### 6.3 `Session`（房间）

对象 0x30 字节，构造 `0x4052ff`，Deserialize `0x556e80`
（★ 这个函数用**寄存器**传参：`esi` = this、`edi` = 流，不是标准 thiscall）。

| 顺序 | 类型 | 客户端偏移 | 含义 | 可信度 |
|---|---|---|---|---|
| 1 | int32 | `+0x04` | ★ **房间状态**：**`2` = 待机中**，其余一律「游戏中」| ✅实测 |
| 2 | wstring | `+0x08` | **房间标题** | ✅实测 |
| 3 | int32 | `+0x0c` | ★ `"%s(%d/%d)"` 的**第一个** `%d` = **当前人数** | ✅实测 |
| 4 | wstring | `+0x10` | **地图名** | ✅实测 |

★★ **状态字段同时决定房间里建哪个 3D 场景**（V0.1 §102，「待机房间背景纯黑」的真凶）：
工厂 `0x494509` 开头 `状态 == 2 / 5 / 6` → `GameContextWaitingRoom`（固定加载
`Maps/ReadyRoom.map`）；否则按 `descriptor.type` 建**战斗**上下文 —— 而战斗上下文
要靠 stage 6 的加载流程才能把场景铺起来，直接在房间里建出来就是一片黑。

★★ **`+0x14` 是「随机地图」开关**（V0.2 §228），两处独立读点：

```asm
; 开局校验 0x468176 —— 关就直接跳过随机分支
00468185  mov esi, [0x72e29c]        ; LobbyStage
0046818B  mov al,  [esi+0x14]
00468196  jz  0x468242

; 0x0400 gspPrepareGame 的处理器 0x551605 开头 —— 真正挑图的地方
00551628  mov eax, [0x72e29c]
0055162D  mov cl,  [eax+0x14]
00551632  jz  0x5517a3
```

打开之后，客户端用 `0x0400` 里那个 **seed** 调 `0x40b6e5`「按条件过滤地图目录
+ 随机取一张」：`0x40b737` 判 `seed != -1` 就拿它构造**确定性**随机源
（`0x5d8cb6`），所以**全房间算出来的是同一张图**。过滤条件也全是房间级的
（模式 / **房主**等级 `[LobbyStage+0x34]` 那个座位的 `+0x10` / 人数上限 / 任务 id）。
⇒ 服务端**不需要懂地图几何**，只要 ① 把这个开关原样回传、② 保证 seed
全房间一致**且每局重取**（恒 0 会永远随到同一张图）。

★ 房间列表的每一项也是这份布局（**没有** `0x0303` 结尾那个 u16 局号），
`+0x14` 同样要带上，否则列表和房间里看到的对不上。

## 7. 认证服（NMCO，端口 47611）—— **不在 `vftables.json` 里**

这一层的代码在**未加壳**的 `game_org/Popshot/nmconew.dll`（ImageBase `0x10000000`），
不是 `BigShot.exe`，所以 `re/vftables.json` / `re/rtti_types.txt` 里找不到这些类。
整理在这里是因为**它也是客户端和服务端之间的通信**。

### 7.1 帧格式（V0.1 §36）

```text
[0..1]   u16 BE  = NMCO 消息长度（= 总长 - 4）
[2..3]   u16 BE  = opcode
[4..]    NMCO 消息：
    [0]      0x18          固定 tag，客户端硬校验（0x1008bdb0）
    [1..3]   u24 BE = 载荷长 + 12
    [4]      flags         bit1(0x02)=加密  bit2(0x04)=分片续传
    [5..7]   u24 BE = 载荷长
    [8..11]  u32 BE 会话密钥（发送方随机；nmconew 用 GetTickCount ^ 0x5f54ca13）
    [12..15] u32 BE 消息 ID
    [16..]   载荷
```

**加密**：`C[i] = P[i] ^ P[i-1] ^ key ^ Fw[i&15]`（`0x1009f270` 加密 / `0x1009f2f0` 解密），
`F` = `0x100ef548` 处的 64 字节常量表（16 个**小端** dword）。
★ **只处理载荷前 `len//4*4` 字节**，尾部余数原样明文（V0.1 §34 记的「末尾 2 字节明文字段」
其实不是字段，就是这个余数）。分片阈值 1400 字节，目前用不到。

字符串编码同游戏服：`u16 小端字符数 + UTF-16LE`。整数是**小端**。

### 7.3 完整握手（V0.1 §39，实测跑通）

★ **每个请求各用一条新 TCP 连接**，服务端回完客户端就主动关闭。

```text
客户端 → 0x0f CULogin2Packet
    wstring 用户名 / wstring 密码 / wstring 空串
    + 12 字节 = 03 22 01 01 | 56 00 00 00 | 00 00 00 00   （3 个 int32，❓含义未知）
服务端 → 0x0c CULoginReplyPacket        （Deserialize `0x1002e910`）
    int32 结果码 / wstring s1 / wstring s2 / int32 / int32 / int32
客户端 → 0x2d CURequestOldFashionInfoPacket       （载荷 2 字节 = 一个空串）
服务端 → 0x2e CURequestOldFashionInfoReplyPacket  （Deserialize `0x10030c10`）
    int32 / wstring / wstring / wstring / int32 / u16 / u16 / int32 / int64 / int64
客户端 → 0x0d CULogoutPacket                      （载荷 2 字节 = 一个空串）
服务端 → 0x0e CULogoutReplyPacket                 （Deserialize `0x1002f160`）
    int32 结果码 / wstring
```

**除了下面两处，其余字段全填 0 / 空串客户端照单全收**（实测三轮）。

★ **实机带的都是票据，不是空串**（bug调查/11，✅实测）：登录拿到票据之后，
`0x2d` / `0x15` / `0x0d` 三个包的载荷都是一个 **wstring = 票据**（66 字节），
不是上面握手示例里的空串。⚠ **`0x0d` 的语义按 §238 勘误**：它是**退出登出**，
不是「重登第一步」——**没有任何一次**独立 0x0d 后面跟着 0x0f；正常退出时发
（客户端先关游戏连接、~1 秒后发 0x0d），**崩溃退出时也发**（主循环已死、
写完 mdmp 之后由退出路径发，之后进程终止）。服务端照旧回 `0x0e`
（int32=0 + 空 wstring，26 字节）即可，回不回都影响不了崩溃与否
（bug调查/11 定案：崩因在客户端脚本任务分发，见 §238）。
**看日志分型**：游戏连接「客户端先关」+ 上行到最后一刻 = 正常退出；
「连接随进程死亡」+ 上行在 0x0d 前停 >1 秒 = 崩溃遗言。

### 7.4 `CULoginReplyPacket`（`0x0c`）—— 两个真正有用的字段

| 字段 | 含义 | 可信度 |
|---|---|---|
| `int32 结果码` | ★★ **成功 = 0**；失败必须用**客户端认得的 NM 错误码**，见下表 | ✅实测 |
| `wstring s1` | ❓客户端**没有转发**（🤔多半是显示用的）| ✅实测（V0.2 §123）|
| `wstring s2` | ★★ **票据** —— 客户端把它原样填进游戏服 `0x0100 gcpReqLogin` 的第一个 wstring | ✅实测 |
| 其余 3 个 int32 | ❓未知，填 0 | ❓ |

**失败结果码**（V0.2 §128）—— 客户端自己会显示中文，**一行客户端代码都不用改**：

| 服务端回 | 客户端弹的框 |
|---|---|
| `20025` | 登录失败 / **`不存在的帐号 (20025)`** |
| `20026` | 登录失败 / **`密码错误 (20026)`** |
| 其它任何非零值 | 登录失败 / `认证服务器失败 (20000)`（一句没用的笼统话）|

★ 映射表在 `nmconew.dll` `0x10077000`；客户端再拿映射后的码去
`Data/Chinese.ini`（UTF-16LE 的韩→中对照表）查中文，最后
`MessageBoxW("<中文> (<码>)", "登录失败")`。
⚠ **不要用 1 / 2 这种自己编的码** —— 会全部落进 default 分支。
⚠ 映射表里 `20019` 会被映射成 **0（成功）**，别误用。

## 8. 我们自己加的 UDP 旁路（`PSU\x01`）—— **和游戏协议无关**

只在 `bshook` ↔ `server/relay.py` ↔ `server/udpsync.py` 之间用。8 字节头：

```text
+0  4  magic  b"PSU\x01"     最后一字节是版本号，改格式就 +1
+4  1  类型    HELLO / HELLO_ACK / DATA / PING / PONG
+5  1  份数    DATA 时 = 后面跟几组（含当前这一份）
+6  2  保留    0
```

| 类型 | 载荷 |
|---|---|
| `HELLO` | `u16 票据长度 + 票据(UTF-8)`。票据就是登录时那张，**不引入新的秘密** |
| `HELLO_ACK` | `u8 结果码 + u16 说明长度 + 说明(UTF-8)` |
| `DATA` | 份数 × (`u32 索引 + u16 长度 + 整个 UdpPacket`)，**索引升序** |
| `PING` / `PONG` | `u32 序号`（保活撑住 NAT 映射，顺带量 RTT）|

**铁律**（`server/udpsync.py` 顶部有完整论证）：

1. **只有位置走 UDP**：内层 `0x4001`（心跳）才双发；`< 0x4000` 的事件包和
   `0x4002`~`0x4005` **只走 TCP**。
2. **上行双发，服务端按索引去重** ⇒ UDP 完全不通 = 今天的行为，不需要 fallback 代码。
3. **心跳里的 N 决不许越过还没转发的事件包**（见 [§5](#5-udppacket-的内层-opcode)）。
4. **下行一个收件人同一时刻只有一条路**（心跳没有可判新旧的字段，双发必然乱序）。

## 9. 自己接着往下逆的方法

这份表里所有 ❓ 都可以用同一套手法补上（V0.1 §111 / V0.2 §136 用的就是它）：

1. **类名 → vftable**：`re/rtti_types.txt` 搜类名 → `re/vftables.json` 拿地址；
   或直接 `python tools/rtti_map.py Packet_`。
2. **vftable → Serialize / Deserialize**：槽 0 / 槽 1（见 [§0.4](#04-vftable-槽位)）。
3. **Deserialize → 线格式**：函数体里那串 `call 0x5d59xx` 就是字段表，
   对照 [§1.4 的原语表](#14-流读写原语表逆任何包的线格式先查这张表v02-136) 逐条读下来。
4. **找 opcode**：`python tools/re_bs.py xref <vftable>` 找建对象的地方，
   附近的 `push <imm>; call 0x5bba0a`（`RawPacket::SetType`）就是 opcode。
   客户端方向可以直接跑 `python tools/gcp_opcodes.py`（109 个调用点全量提取）。
5. **找处理器**：服务端方向从分发器入手 ——
   `0x54e036`（`ServerConnection` 槽 13，主分发）→
   `[0x72e29c]` 的 `0x4061e2`（大厅 / GameSession，跳表 `@0x406332`）→
   战斗跳表 `@0x54e5ae`（`0x0405`~`0x0413`）→ `GameContext` 表 `0x493808`。
6. **字段落到哪**：处理器里那串 `mov [全局], eax` / `mov [对象+off], eax`；
   再 `xref` 那个全局，看**谁读它**——读的地方才是「这个字段是什么意思」的答案。
7. **实机确认**：`tools/gs_ctl.py raw <op> <payload-hex>` 直接发任意包；
   `tools/fakeclient.py` 造第二个玩家；`--verbose` 打开逐包 hexdump。

⚠ 逆到的结论请**回填到这份文件**并同步更新 `.claude/FINDINGS.md`，
把可信度从 🔍 升成 ✅ 时**注明是哪次实机验证**。
