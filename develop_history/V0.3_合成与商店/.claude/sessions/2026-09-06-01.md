# 2026-09-06-01 · 物品库返工（用户验收退回）

## 用户报的四条

1. 合成配方页还有「等级」一栏，`recipe.json` 里也还留着 `level`。
2. 物品库按 材料 / 礼包 / 角色 / 消耗品 筛出来是 **0** 条，
   而「选择物品」弹窗里明明查得到。
3. 在商店上架、自动下架合成之后，页面报「shop：服务器内部错误，请看服务端日志」。
4. 物品库卡片上那行韩文名太长，把后面的上架信息挤没了。

## 查出来的根因

1. **只是数据没跟着改**。`SCHEMA["recipe"]` 里早就没有 `level` 了，但
   `restFields()` 有一道兜底：**文件里有、字段表里没有的键照样画出来**。
   `recipe.json` 是上一轮生成的，35 条里还带着 `level` ⇒ 画了 35 个怪框。
2. **D31 的范围定错了**。上一轮把「有没有等级 / 角色限定」和「收不收进物品库」
   当成了一件事，于是 `default_items()` 只收 `part_flag != 0` 的 734 件，
   `validate_items()` 还会**拒收**别的。用户原话说的是「不要那两个**输入框**」，
   不是「不要那一条」。⇒ 改成收全部 `ownable` 的 808 件。
3. **不是代码的错**：`server/data/shop.json` 正开在 サクラエディタ 里
   （独占打开），`os.replace` 撞 `PermissionError(13)`，被
   `web/server.py` 的通用兜底吞成了 500（§35）。
   ⚠ 但**顺序确实是错的**：上一版先存另一边，于是合成已经下架了、
   商店没存上 ⇒ 那件东西两头都没有（D33 改成先存自己）。
4. `metaLine()` 无条件画 `item.name_kr`，而 `.meta` 是单行 + 省略号，
   上架状态排在最后，一超长就被截掉。

## 顺手查出来的第五条（用户没报，但迟早会撞上）

上一轮把**中文名留在了 `shop.json` / `recipe.json`**，而物品库里又加了一份
可编辑的 `name` ⇒ 同一件东西**三份**名字，`item_info_records()` 优先取商店
那份 ⇒「在物品库里改了名字，游戏里还是老名字」。
这正是 D31 要消灭的那类错，换了个字段又犯了一遍。

## 改了什么

- `shopcfg.py`：`default_items` / `validate_items` 收全部 `ownable`；
  等级和角色只给 `part_flag != 0` 的，别的**丢掉不报错**。
  新增 `name_of()` / `item_name()`（查名字的唯一入口）。
  `validate_shop` / `validate_recipes` 丢掉 `name`；
  `default_shop()` 不再收材料和合成产物（86 条空壳）；
  `BACKFILL_KEYS` 加上 `items.json`。
- `shop.py` / `gameserver.py` / `web/admin.py`：所有取名字的地方改走物品库。
- `web/admin.py`：保存时自己接住 `OSError`，回一句人话（§35）。
- `web/admin.js`：物品库 = 全物品表（`fillItems()` 用目录补齐、
  抹掉穿不上身那些的 level/character），没有 ✕ 也没有「＋ 添加」；
  卡片上架状态排最前、不画韩文名；商店 / 合成两页的中文名变只读；
  角色筛选改按物品库那份（`character` 键删掉 = 不限，不再退回原版角色）；
  加 `ITEMS_BY_ID` 索引（808 条 × 每条筛一次 = 别现扫）；
  互斥保存改成先存自己（D33）。
- `server/data/`：手工迁移一次（脚本在临时目录，备份 `*.bak-20260906-013621`）。

## 结果

全量测试 **2722 项绿**。管理页的四个渲染函数 + 筛选 + 补齐逻辑在浏览器里
用假数据走了一遍，输出都对。**实机验收还没做**（要用户自己登管理页看）。

- `default_shop()` 现在只有 65 件武器 —— 要卖别的东西得在管理页
  「＋ 添加一条」，这一点没和用户确认过，他要是嫌麻烦就把材料收回去。
