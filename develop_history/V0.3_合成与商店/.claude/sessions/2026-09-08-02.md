# 2026-09-08 会话 16 —— 打包不再自动提取；五个 update bat 并成一个（D53）

## 题目

用户两句话，分两轮给的：

1. 「地形数据、武器表、角色属性表现在打包时会自动重新提取，我不希望每次打包都
   重新取，仅在需要的时候我手动提取就可以了。」
2. 「`update-shopdata.bat`、`update-shopicons.bat` 包括这两个，把所有更新用的都整合到
   一个里吧，其余的删掉。分的太多太乱了，分不清哪个是哪个。」

## 查明

- 自动提取来自 V0.3bot **D21**，实现在 `tools/build-common.ps1` 的三个 `Update-*`，
  由 `build-portable.ps1` 和 `build-server-package.ps1` 各调一次。它们探
  `Pack_decrypt\…` 和 `..\..\main\Pack_decrypt\…`，在 `main` worktree 里**素材总在**，
  所以每次打包都真的重提。商店那两份（`shopdata` / `shopicons`）从来不在这条路上。
- ★ 三个读取侧在 `format` 对不上时是**返回空表、不报错**的
  （`server/mapdata.py:660` `:707`、`weapondata.py:392`、`chrprops.py:348`）——
  这正是自动提取原本在挡的那个坑，去掉它就得另外补闸。
- 五个提取器的素材路径口径一致（都是 `Pack_decrypt\` 和 `..\..\main\Pack_decrypt\`
  两个候选），所以合并后只需吃**一个** `Pack_decrypt` 目录参数，其余由它派生。
- 图标图集要 Pillow：`C:\Python314` 有，便携运行时里没有（服务端只用标准库）。
  地形的 `--verify` 预览图也用 Pillow，但**缺了不算失败**（`write_preview` 返回 False）。

## 做法（D53）

| 文件 | 改动 |
|---|---|
| `tools/update-gamedata.bat` | **新增，唯一入口**。五步：地形 → 武器 → 角色属性 → 物品表 → 图标图集，每步「提取 + 立刻跑对应测试」，某步不过就停、后面不跑。可选参数 = `Pack_decrypt` 目录 |
| `tools/update-{mapdata,weapondata,chrprops,shopdata,shopicons}.bat` | **全部删除** |
| `tools/build-common.ps1` | 删三个 `Update-*` 函数 + 三个 `$script:*Updated`；新增 `Get-ServerFormatVersion`；三个 `Copy-*` 各加 format 校验；错误文案改指 `update-gamedata.bat` |
| `tools/build-portable.ps1` / `build-server-package.ps1` | 删三次 `Update-*` 调用，留注释指向新脚本 |
| `tools/shopicons.py`、`server/{test_botmove,test_mapdata,test_web_admin,web/admin}.py` | 提示文案里的旧 bat 名改成 `update-gamedata.bat` |

顺序有依赖：**[5] 图标必须在 [4] 物品表之后**（图集要读 `shop_items.json`）。
Pillow 探不到时不静默跳过：明说「前四份已更新、图标没重拼」并以 1 退出。
单独跑 / `--dump` 这类调试口没了，改成在成功尾巴上把五条 `python tools\xxx.py …`
原样打出来。

## 验证

- 三个 `.ps1` 过 `PSParser::Tokenize`；`Get-ServerFormatVersion` 实跑读出
  mapdata 6 / weapondata 11 / chrprops 2，四个 `Copy-*` 全过（178 个文件）。
- 反向：造 `format = 99` 的假产物，`Copy-ChrProps` 按预期中止并指名该跑哪个 bat。
- ★ `update-gamedata.bat` **整脚本非交互实跑**（`cmd /c "…bat" <nul`）：
  五步全绿、退出码 0 —— 这同时证明 `chcp 65001` 下这么长的中文 bat 没被截断。
  跑完 `git status server/` **改动数 0**：五份产物重新提取后和仓库里逐字节一致。
- **没跑整包打包**（用户此前说先不打包）。

## 坑（下次别再踩）

- ★ **别用 `sed -i` 改 `.ps1` / `.bat`**：这台机器的 Git Bash sed 会把 CRLF 吃成 LF，
  `build-common.ps1` 当场变成 BOM + LF（违反铁律 3）。已用 PowerShell 修回。
  改这两类文件一律走 Write / Edit 工具，改完 `file` 复核一次。
- ★★★ **`.bat` 里一个中文都不许有**（2026-09-09 定案，已写进全局
  `~/.claude/CLAUDE.md`）。`update-gamedata.bat` 第一版把中文全写在 bat 里，
  用户双击当场翻车：`echo   改了哪些文件看 git status；打包时…` 被从中间截断，
  报 `'us;' is not recognized`；**补了行尾空格再跑，变成指针倒退、`pause` 连弹两次**。
  机理：cmd 按**字节偏移**回读批处理，却把「消耗了多少**字符**」当「多少**字节**」
  写回指针，中文一个字 UTF-8 占 3 字节 ⇒ 每读一个中文少走 2 字节；
  到出事那行已累计 **724 字节**。
  ⚠ **行尾空格是错的**（我按用户说法试过，两次都翻）：空格 1 字节 + 1 字符，
  差值没变。判据是 `len(raw) - len(raw.decode('utf-8'))`，**纯 ASCII 时为 0**。
  ⇒ 现在是 `update-gamedata.bat`（纯 ASCII 壳，`file` 显示 `ASCII text`）+
  `update-gamedata.ps1`（全部逻辑和中文），同 `tools\build.bat` + `build-menu.ps1`。
  ⚠ 「跑通了」不是验收：同一个文件我 `cmd /c "…bat" <nul` 跑了三遍全好，用户双击就翻。
- 同类隐患还有两个**没动**（等用户发话）：`tools/quest-clear.bat`（26 行中文）、
  `hook/test-watchdog.bat`（5 行中文）。`start.bat` / `stop.bat` / `tools/build.bat` /
  `updater/build.bat` 本来就是纯 ASCII 壳，不受影响。
