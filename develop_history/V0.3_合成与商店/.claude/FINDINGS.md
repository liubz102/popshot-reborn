## §1 ★★★★★ 装备加成是**纯客户端算的**，服务端只需下发 itemId 列表

**结论**：服务端**不需要也没法**下发加成数值或公式。它只要通过**已经在跑的
`0x030b gspSlotEquippedList`** 告诉客户端「这个座位装备了哪些 itemId」，
客户端自己查本地 `Data/EquipBonus.ini` 就生效。
★ **2026-09-05 实机落锤，这一节已经是 ✅实测**（原为 🔍静态）—— 见 §16。

```
启动    0x40d68d push L"Data/EquipBonus.ini"(0x65f604) → 0x413ec9 从 pak 读
        → 0x413f60 解析成 INI 对象 [0x72e454] → 每个 section 建 EquipBonusEntry → map [0x72e440]
运行时  0x030b(座位, 3×掩码, itemId[]) → 处理器 0x406ea1 → EquipmentEx ctor 0x414d95
        → [GameSession + 0x250 + seat*4]
战斗    0x4070aa 读 [edi + esi*4 + 0x250] → 0x407014 GetEquipBonus(seat, index, key)
        → 0x4806bf 改伤害 / 0x50a09e 改 MaxHp / 0x5074f4 改移速
```

**关键佐证**：`0x406ea1`（`0x030b` 处理器）写的正是 `[GameSession + 0x250 + seat*4]`，
和 `0x4070aa`（所有战斗加成的读取点）读的是同一格。

**分桶规则**（`EquipmentEx::Equip` `0x414e43`）：`key = itemId/1000000 - 1`，
`itemId < 1e6` → `key = -1`（通用）。取值时 `0x41543e` 把**桶 -1 + 桶 key** 相加。
和 V0.1 §119 的角色持有判定是同一套规则。

**⚠ 三条限制**：

1. `EquipBonus.ini` 在客户端 pak 里（`0x413ef5` `PackHasFile` → `0x413f51` `PackReadFile`），
   **改数值要重打包 + 走 updater**，不能热下发。
2. `SetEquipBonusFunction` 在整个 exe 里**只有一个 C++ 调用点**（`0x41324d`），
   来自 INI 解析器，**没有任何网络包路径** ⇒ 服务端永远不能在运行时下发新公式。
3. 数值路径用 `_wtoi`（`0x413268`）⇒ **`Defense=5.0` 解析成 5，`Hp=0.5` 解析成 0**。
   服务端侧提取时也要用 `int()`，别用 `float()`。

**❓ 未验**：散文件能否覆盖 pak 里的 `Data/EquipBonus.ini`（`0x55e7f0`/`0x55e890` 没跟进去）。
真要改数值时先实测这条，能覆盖就省掉重打包。

## §2 ★★★★ `EquipBonus` 的 index 映射与各属性算法（**攻防只有 15% 概率触发**）

★ 「Attack 的 15% 概率门」和「`dmg = dmg*(100+x)/100` 朝零截断」**已实机落锤**，见 §16 ③。

**index 映射定死**（静态初始化器 `0x413096` 建的名字表 `0x732bfc..0x732c30`，
解析循环 `edi` 从 1 起）：🔍静态，与 14 个 `GetEquipBonus` 调用点的常数完全对上

| idx | 属性 | idx | 属性 | idx | 属性 |
|---|---|---|---|---|---|
| 1 | Attack | 6 | Sp | 11 | IncSplashRange |
| 2 | Defense | 7 | TeamDmg | 12 | DashAttack |
| 3 | Critical | 8 | SelfDmg | 13 | TeamReflection |
| 4 | MoveSpd | 9 | AntiGhostCnt | 0 | *(空串，保留未用)* |
| 5 | Hp | 10 | HeartBoost | | |

**算法各不相同**（常数：`0x693720=1.0f`、`0x693724=0.01f`、`0x6938cc=0.15f`）：

| 属性 | 读取点 | 算法 |
|---|---|---|
| **Attack** | `0x4807a5` | `dmg = dmg*(100+x)/100`，★ **前面有 `fcomp [0x6938cc]` ⇒ 只有 15% 概率生效** |
| **Defense** | `0x480906` | `dmg = dmg*(100−x)/100`，★ **同一个 15% 概率门** |
| **Hp** | `0x50a09e` | `MaxHp = 基础 + x`，**加法，100% 生效** |
| **Sp** | `0x50a0de` | `MaxSp = 基础 + x`，加法 |
| **MoveSpd** | `0x5074f4` | `speed *= (100+x)/100`，百分比，100% 生效 |
| **DashAttack** | `0x481e40` | `dmg *= 1 + x/100`，**没有 15% 门** |

**⚠ 「换弹速度」根本不在这 14 格里。** `ReloadTime` 只从武器 INI 读
（`0x489381`，默认 `0xc8`=200），**不经过任何装备加成** ⇒ 想让换弹变快
**只能换武器**（极速 R 系列 reload 700/680/660 vs 基础 720）。🔍静态

UI 提示串（`0x65fdac`~`0x65fee8`）自证这套算法：
`Attack %+d%%` / `Defense %+d%%` / `Speed %+d%%` / `HP %+d` / `SP %+d`。

**❓ 未查**：index 3 (Critical) 和 13 (TeamReflection) 在 `0x407014` 的调用点里
一次都不出现；`0x4070aa` 还有 7 个直接调用点没逐个查。

## §3 ★★★★★ 结算界面「合成材料」栏 = **`0x041c gspRewardReceived`**（纠正 V0.1 §99）

**结论**：那一栏有**专用包**，不是从 `0x0309` 里出来的。
**V0.1 §99 猜的 `0x48e5a8` 是错的** —— 那段在画角色立绘（`[ebp-0x20]` 比的
`0x66/0x68/0x69/0x6b/0x6c/0x6e` 是商城角色 id 102/104/105/107/108/110）。🔍静态

```
标签    0x48e7cd push L"ITEM_클리어리절트"(0x670f14) → 0x558916 翻译 → 画在 (161,465)
        （Chinese.ini：ITEM_클리어리절트=合成材料）
数据    0x48c9be(seat) → [GameContext + 0x74  + seat*20]   ← ★ 合成材料栏
        0x48c9dd(seat) → [GameContext + 0xec  + seat*20]   ← ★ 称号卡片栏
绘制    0x48b7a1 遍历（元素是指针数组，[+4]=itemId，[+8]=数量）
        itemId → [0x72e1dc] ItemDB(0x415a94) → +0x14 图标路径 → 0x5c5e14 载入贴图
写入    0x493ed1 ← 0x493808 的 opcode 链
```

**opcode 链**（`0x493808`，逐条算过）：`sub 0x406 / dec / sub 0xb / dec / dec / sub 8`
⇒ `0x0406`、`0x0407`、`0x0412`、`0x0414`、**`0x041c` → `call 0x493ed1`**。

**线格式**（Deserialize `0x54c5d0`，四发 `0x5d59ff`「读 4 字节」，无 bool
⇒ 线偏移 = 结构偏移 − 4）—— **body 16 字节**：

| 线偏移 | 类型 | 含义 |
|---|---|---|
| 0 | int32 | 座位号 |
| 4 | int32 | **槽类型**：`0` = 合成材料栏，`1` = 称号卡片栏 |
| 8 | int32 | 物品 id |
| 12 | int32 | 数量 |

**两条硬约束**：

1. `0x493f24` 是 `add [entry], count` ⇒ **同 itemId 发多次会累加**。
   服务端每种材料发一发即可，不用自己合并。
2. ★ **必须在 `0x0411 gspEndGame` 之前发** —— 它写的是 `GameContext`，
   关卡一结束就变 0（和 `0x0309` 同一个约束，V0.1 §99）。
   ⇒ 顺序：**`0x041c` × N → `0x0309` → `0x0411`**。
3. ★ **itemId 必须在 `ShopItem-Chn.ini` 里真有 `[Item-*]` 节**，否则 ItemDB
   查不到、图标画不出来。**已核对：全部材料都有**（见 §8）。

## §4 ★★★★ 商店 / 合成 / 仓库的协议全表（**上行四发已实测（§19），下行仍全是 🔍静态**）

分发器 **`ShopStage` vft `0x666164` 槽 `+0xc4`**，跳表 `@0x44434a`，
覆盖 `0x0500..0x050c` + `0x0604`。收发都在主连接 `[0x72e30c]` 上。

**★ 进商店时客户端连发四个请求**（ShopStage ctor 里 `0x444009`~`0x44402c` 顺序调用）：

| 顺序 | 发送函数 | opcode | 期望应答 |
|---|---|---|---|
| 1 | `0x44722b` | **`0x0704`（无正文）** | `0x0604 gspRepEquippedList`（处理器 `0x447278`） |
| 2 | `0x447467` | **`0x0605` gcpReqCompositionList**（★ 实测是 `u8+u16+i32+i32`，见 §19；这里原来写的 `u8+i32+u16+i32` 是错的） | `0x0505`（处理器 `0x4474e4`） |
| 3 | `0x44792d` | **`0x0607` gcpReqGiftList** | ❓（本版回空清单） |
| 4 | `0x5541c1` | **`0x0700`（无正文）** | ❓（V0.1 §50 记过大厅也在轮询它） |

**服务端 → 客户端**：

| opcode | 类 / vft | 线格式 | 处理器 |
|---|---|---|---|
| `0x0500` | `gspRepShopItemList` `0x666290` | `i32, i32, i32 n, n×Item@ShopStock{i32,i32,i32}`（步长 0x10） | `0x445ed9` |
| `0x0502` | `gspRepItemBuy` `0x666158` | `i32 ok, i32, i32` | `0x44615b` |
| `0x0505` | `gspRepCompositionList` `0x6662a8` | `i32, i32, i32 n, n×CompositionRule` | `0x4474e4` |
| `0x0506` | `gspRepComposeItem` `0x66623c` | 单 `i32` | `0x4476c4` |
| `0x0604` | `gspRepEquippedList` `0x666248` | 见下 | `0x447278` |
| `0x0503` / `0x0504` | ❓ | ❓ | `0x446700` / `0x446b62` |
| `0x0508`~`0x050c` | ❓（礼物 / 修理 / 丢弃一类） | ❓ | `0x44798d` `0x447c08` `0x448072` `0x4468bc` `0x448849` |
| `0x0501` / `0x0507` | 跳表指向 default ⇒ **客户端不处理** | — | — |

**客户端 → 服务端**（都是「无 RTTI 类」，用裸序列化函数发）：

| opcode | 线格式 | 发送点 | 语义 |
|---|---|---|---|
| `0x0602` | `i32 n, n×i32` | `0x446115` | **购买**（回应 `0x0502`）🔍 |
| `0x0603` | `i32` | `0x4466d2` | ❓（大概率回 `0x0503`）🤔 |
| `0x0604` | `i32, i32` | `0x446f5b`（`ret 8`） | **装备 / 卸下** 🤔 |
| `0x0606` | `i32` | `0x44765c` | 合成（回应 `0x0506`）🔍 |

**子结构**：`CompositionMaterial`（`0x666104`，Des `0x4438dc`）= `i32 itemId + u16 count`；
`CompositionRule`（`0x666254`，Des `0x44394d`）= `i32 + i32 + i32 n + n×Material + i32 + i32`。

**❓ 最大的残余不确定：货架目录到底走哪个 opcode。**
`0x0500` 的元素只有 3 个 int，装不下名字和价格；而 `ShopStock` 类
（`i32, wstr, i32, i32, i32, wstr, i32, vector`）才像货架目录。
`0x0503` / `0x0504` 的处理器没逆。**M4 必须实机落锤。**

**`0x0604` 处理器的一个细节**：它先建空 `EquipmentEx`（`0x414d27`），
对每个 itemId 查物品库 `[0x72e1dc]`（`0x415a94`），**只有 `flags & 8`（可装备）
的才 `Equip`**（`0x44736a: test byte ptr [eax+0x10], 8`）。

**★ `0x0604` 和 `0x030b` 是两条独立的路**：`0x0604` 落到 `[ShopStage+0x134/0x138]`
（只影响商店界面），`0x030b` 落到 `[GameSession+0x250+seat*4]`（战斗加成的唯一来源）。
⇒ **让加成生效必须发 `0x030b`**，发 `0x0604` 不够。

## §6 ★★★ 商店 id 编码 与「爆裂 / 极速 / 复合」三系列

**7 位 id = 角色(1) + 部位(2) + 序号(4)**。角色首位 `1`=泰尔 `2`=卡希尔 `3`=布洛克。

**部位 ↔ `PartFlag`（位掩码，共 16 位）**：

| 部位 | Flag | 部位 | Flag | 部位 | Flag |
|---|---|---|---|---|---|
| `01` 上衣 | 1 | `06` 突击技 | 32 | `12` 武器槽1 | 1024 |
| `02` 下装 | 2 | `07` 喷漆 | 64 | `12` 武器槽2 | 2048 |
| `05` 头/脸 | 4 | `11` 头饰 | 128 | `12` 武器槽3 | 4096 |
| `04` 鞋 | 8 | `08` 尾饰 | 256 | 称号 | 8192 |
| `03` 手套 | 16 | `09` 翅膀 | 512 | `13` 戒指 | 16384 |
| | | | | 宠物 | 32768 |

套装用**组合值**（实测出现过 9 / 11 / 19 / 23 / 31 / 539）。
`5x` 段（部位码 + 50）是**同一件外观的期限制售卖形态**，只有 `[Stock-]` 没有 `[Item-]`。
9 位 id（`101400001` 等）是**角色本体商品**，`account_store.character_item_id()` 已实现。

**★ 武器 id 规律**：`C 12 0 SS T` —— `SS`=`01~03`→**D 爆裂**（槽 1/2/3），
`04~06`→**R 极速**，`07~09`→**F 复合**；`T`=1/2/3 级。
`[Item-1120011] Tag=1000015.0` 里的 **`Tag` 就是 `weapon.ini` 的弹药 `Id`**。

**三系列的数值特征**（左轮 `Damage/ReloadTime`，基础 = `4/720`）：

| 系列 | 特征 | 1 级 | 2 级 | 3 级 |
|---|---|---|---|---|
| **D 爆裂** | 伤害↑、装填↑（更慢） | 4/720 | 5/740 | 6/760 |
| **R 极速** | 装填↓（更快），伤害不动 | 4/700 | 4/680 | 4/660 |
| **F 复合** | 两边各给一点，居中 | 4/710 | 4/710(头伤+1) | 5/710 |

D/R/F 只存在于 **ch00/ch01/ch02** 三个初期角色，每人 3 槽 × 3 系 × 3 级 = 27，共 81 条。

**⚠ 中文版砍掉了 18 件**：手枪 / 狙击的全部 3 级（D3/R3/F3），
只有榴弹系列（사과탄 / 화염탄 / 스크류런처）的 3 级留着。⇒ **上架前要按
`ShopItem-Chn.ini` 过滤**，中文版没有的 id 发下去客户端查不到图标。

**⚠ `weapon.ini` 里没有 SP 消耗字段** —— SP 消耗在 `GameProps.ini`
（`AssultSpCost=40` 等）和 `ChrProps.ini`（`Dash00-SpCost`）里。

## §11 有两批物品「只有货架、进不了背包」—— 判据是 `ownable`，不是 `timed`

### ③ ★ 「有时候 5 有时候 4」= `리핑체인 바지(1020062)` 的 `Attack=-1`

`0x4806bf` 里那一段（地址逐条对过）：

```text

004807fe  jp 跳过整段
00480800  test edi, edi ; jle       ; edi = GetEquipBonus(座位, 1=Attack, -1)
0048080d  mov [ebp-4], 0x10         ; ★ 正加成 -> flags |= 0x0010
00480825  jge 结束
```

## §18 难度号 ↔ 中文名（管理页的下拉框用它）

`1=简单 2=普通 3=困难 4=极限`。号码 → 难度是**客户端拼地图文件名**那一段定死的
（`mapdata.DIFFICULTY_SUFFIX`，出处 `0x405742` 的四发 `dec edi` →
`#Easy/#Normal/#Hard/#Extreme`）。

中文名取 `Chinese.ini` 的官方译法：`이지 모드=简单` / `노멀 모드=普通` /
`하드 모드=困难`（另一处 `EASY=简单` / `NORMAL=普通` / `HARD=困难` 互相印证）。

★ **难度 4 的中文名是我们自己拼的**：中文版把 `익스트림 모드` 原样留成了
`Extreme Mode`（没翻）。和第 7 关的名字（§15）是同一种情况。

写进 `shopcfg.DIFFICULTY_ZH`；`test_shopcfg` 卡死它和 `mapdata.DIFFICULTY_SUFFIX`
以及校验器上限（1..4）三处一致。

## §19 ★ 进商店那四发**实测对上了**，`0x0605` 的线格式要改（✅实测）

2026-09-04 实机点开界面。详见 `re/packet_api.md` §3.8（已改）。三条结论：

1. **四发的顺序就是 `0x0704 → 0x0605 → 0x0607 → 0x0700`**，同一毫秒发完；
   **服务端一发都不回，客户端不崩也不断线**（M4 的止损线没踩到）。
2. `0x0605` 的线格式是 **`u8 + u16 + i32 + i32`**（11 字节），
   §4 记的 🔍静态猜测 `u8 + i32 + u16 + i32` **是错的** ——
   按后者解，第 2 发会读出 `262144` 这种数。
3. **点界面里的小标签会重发 `0x0605`**（13 发里 11 发是点标签点出来的）
   ⇒ 它是**分页 / 分类列表请求**。❓ 哪个数对应哪个标签还没对上，
   下次实机**一次只点一个标签、记下点的是哪个**。

★ 顺带观测到 `0x0505 gcpAccumulatedWeaponDamage`（客户端→服务端，一局结束时）：
16 字节一条、末尾补零，键是 **`weapon.ini` 的 `ROH`**（`110001` 这种），
不是 itemId。本版用不上，记着免得下次重查。
