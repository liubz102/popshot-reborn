## §1 ★★★★★ 装备加成是**纯客户端算的**，服务端只需下发 itemId 列表

**结论**：服务端**不需要也没法**下发加成数值或公式。它只要通过**已经在跑的
`0x030b gspSlotEquippedList`** 告诉客户端「这个座位装备了哪些 itemId」，
客户端自己查本地 `Data/EquipBonus.ini` 就生效。
★ **2026-09-05 实机落锤，这一节已经是 ✅实测**（原为 🔍静态）—— 见 §16。

```
启动    0x40d68d push L"Data/EquipBonus.ini"(0x65f604) → 0x413ec9 从 pak 读
        → 0x413f60 解析成 INI 对象 [0x72e454] → 每个 section 建 EquipBonusEntry → map [0x72e440]
运行时  0x030b(座位, 3×掩码, itemId[]) → 处理器 0x406ea1 → EquipmentEx ctor 0x414d95
        → [GameSession + 0x250 + seat*4]
战斗    0x4070aa 读 [edi + esi*4 + 0x250] → 0x407014 GetEquipBonus(seat, index, key)
        → 0x4806bf 改伤害 / 0x50a09e 改 MaxHp / 0x5074f4 改移速
```

**关键佐证**：`0x406ea1`（`0x030b` 处理器）写的正是 `[GameSession + 0x250 + seat*4]`，
和 `0x4070aa`（所有战斗加成的读取点）读的是同一格。

**分桶规则**（`EquipmentEx::Equip` `0x414e43`）：`key = itemId/1000000 - 1`，
`itemId < 1e6` → `key = -1`（通用）。取值时 `0x41543e` 把**桶 -1 + 桶 key** 相加。
和 V0.1 §119 的角色持有判定是同一套规则。

**⚠ 三条限制**：

1. `EquipBonus.ini` 在客户端 pak 里（`0x413ef5` `PackHasFile` → `0x413f51` `PackReadFile`），
   **改数值要重打包 + 走 updater**，不能热下发。
2. `SetEquipBonusFunction` 在整个 exe 里**只有一个 C++ 调用点**（`0x41324d`），
   来自 INI 解析器，**没有任何网络包路径** ⇒ 服务端永远不能在运行时下发新公式。
3. 数值路径用 `_wtoi`（`0x413268`）⇒ **`Defense=5.0` 解析成 5，`Hp=0.5` 解析成 0**。
   服务端侧提取时也要用 `int()`，别用 `float()`。

**❓ 未验**：散文件能否覆盖 pak 里的 `Data/EquipBonus.ini`（`0x55e7f0`/`0x55e890` 没跟进去）。
真要改数值时先实测这条，能覆盖就省掉重打包。

## §2 ★★★★ `EquipBonus` 的 index 映射与各属性算法（**攻防只有 15% 概率触发**）

★ 「Attack 的 15% 概率门」和「`dmg = dmg*(100+x)/100` 朝零截断」**已实机落锤**，见 §16 ③。

**index 映射定死**（静态初始化器 `0x413096` 建的名字表 `0x732bfc..0x732c30`，
解析循环 `edi` 从 1 起）：🔍静态，与 14 个 `GetEquipBonus` 调用点的常数完全对上

| idx | 属性 | idx | 属性 | idx | 属性 |
|---|---|---|---|---|---|
| 1 | Attack | 6 | Sp | 11 | IncSplashRange |
| 2 | Defense | 7 | TeamDmg | 12 | DashAttack |
| 3 | Critical | 8 | SelfDmg | 13 | TeamReflection |
| 4 | MoveSpd | 9 | AntiGhostCnt | 0 | *(空串，保留未用)* |
| 5 | Hp | 10 | HeartBoost | | |

**算法各不相同**（常数：`0x693720=1.0f`、`0x693724=0.01f`、`0x6938cc=0.15f`）：

| 属性 | 读取点 | 算法 |
|---|---|---|
| **Attack** | `0x4807a5` | `dmg = dmg*(100+x)/100`，★ **前面有 `fcomp [0x6938cc]` ⇒ 只有 15% 概率生效** |
| **Defense** | `0x480906` | `dmg = dmg*(100−x)/100`，★ **同一个 15% 概率门** |
| **Hp** | `0x50a09e` | `MaxHp = 基础 + x`，**加法，100% 生效** |
| **Sp** | `0x50a0de` | `MaxSp = 基础 + x`，加法 |
| **MoveSpd** | `0x5074f4` | `speed *= (100+x)/100`，百分比，100% 生效 |
| **DashAttack** | `0x481e40` | `dmg *= 1 + x/100`，**没有 15% 门** |

**⚠ 「换弹速度」根本不在这 14 格里。** `ReloadTime` 只从武器 INI 读
（`0x489381`，默认 `0xc8`=200），**不经过任何装备加成** ⇒ 想让换弹变快
**只能换武器**（极速 R 系列 reload 700/680/660 vs 基础 720）。🔍静态

UI 提示串（`0x65fdac`~`0x65fee8`）自证这套算法：
`Attack %+d%%` / `Defense %+d%%` / `Speed %+d%%` / `HP %+d` / `SP %+d`。

**❓ 未查**：index 3 (Critical) 和 13 (TeamReflection) 在 `0x407014` 的调用点里
一次都不出现；`0x4070aa` 还有 7 个直接调用点没逐个查。

## §3 ★★★★★ 结算界面「合成材料」栏 = **`0x041c gspRewardReceived`**（纠正 V0.1 §99）

**结论**：那一栏有**专用包**，不是从 `0x0309` 里出来的。
**V0.1 §99 猜的 `0x48e5a8` 是错的** —— 那段在画角色立绘（`[ebp-0x20]` 比的
`0x66/0x68/0x69/0x6b/0x6c/0x6e` 是商城角色 id 102/104/105/107/108/110）。🔍静态

```
标签    0x48e7cd push L"ITEM_클리어리절트"(0x670f14) → 0x558916 翻译 → 画在 (161,465)
        （Chinese.ini：ITEM_클리어리절트=合成材料）
数据    0x48c9be(seat) → [GameContext + 0x74  + seat*20]   ← ★ 合成材料栏
        0x48c9dd(seat) → [GameContext + 0xec  + seat*20]   ← ★ 称号卡片栏
绘制    0x48b7a1 遍历（元素是指针数组，[+4]=itemId，[+8]=数量）
        itemId → [0x72e1dc] ItemDB(0x415a94) → +0x14 图标路径 → 0x5c5e14 载入贴图
写入    0x493ed1 ← 0x493808 的 opcode 链
```

**opcode 链**（`0x493808`，逐条算过）：`sub 0x406 / dec / sub 0xb / dec / dec / sub 8`
⇒ `0x0406`、`0x0407`、`0x0412`、`0x0414`、**`0x041c` → `call 0x493ed1`**。

**线格式**（Deserialize `0x54c5d0`，四发 `0x5d59ff`「读 4 字节」，无 bool
⇒ 线偏移 = 结构偏移 − 4）—— **body 16 字节**：

| 线偏移 | 类型 | 含义 |
|---|---|---|
| 0 | int32 | 座位号 |
| 4 | int32 | **槽类型**：`0` = 合成材料栏，`1` = 称号卡片栏 |
| 8 | int32 | 物品 id |
| 12 | int32 | 数量 |

**两条硬约束**：

1. `0x493f24` 是 `add [entry], count` ⇒ **同 itemId 发多次会累加**。
   服务端每种材料发一发即可，不用自己合并。
2. ★ **必须在 `0x0411 gspEndGame` 之前发** —— 它写的是 `GameContext`，
   关卡一结束就变 0（和 `0x0309` 同一个约束，V0.1 §99）。
   ⇒ 顺序：**`0x041c` × N → `0x0309` → `0x0411`**。
3. ★ **itemId 必须在 `ShopItem-Chn.ini` 里真有 `[Item-*]` 节**，否则 ItemDB
   查不到、图标画不出来。**已核对：全部材料都有**（见 §8）。

## §6 ★★★ 商店 id 编码 与「爆裂 / 极速 / 复合」三系列

**7 位 id = 角色(1) + 部位(2) + 序号(4)**。角色首位 `1`=泰尔 `2`=卡希尔 `3`=布洛克。

## §11 有两批物品「只有货架、进不了背包」—— 判据是 `ownable`，不是 `timed`

```text
004807fe  jp 跳过整段
```

## §20 ★★★★★ **货架目录请求是 `0x0600`**（同号反向！）—— M4 最大的未知落锤了

**结论**：客户端**要**货架目录，走的是 **`0x0600`（客户端 → 服务端）**，
服务端回 `0x0500 gspRepShopItemList`。⇒ §4 那句「货架目录到底走哪个 opcode
仍然没落锤」**作废**，也不用再去逆 `0x0503` / `0x0504` 了。

⚠⚠ **`0x0600` 是同号反向**：服务端方向的 `0x0600` 是 `gspRepMoney`
（右上角数据栏，`send_rep_money`）。**收到 `0x0600` 千万别当 money 处理。**

**为什么以前没看见**：会话 03 的 `SHOP_PROBE_OPCODES` 里没有 `0x0600`，
监听器不认它 —— 但**通用包日志早就记下来了**。
`logs/server-20260904-223901.out:186`（就是那次实机）：

```text
[22:13:12.181] #2 ★ 游戏包 opcode=0x0600 (?) 载荷 11 字节
    0000  00 02 00 00 00 00 00 00 00 00 00
```

**发送点**：`0x445e40 ReqShopItemList(this=分类id, u8 角色, u16 页号, u8 标志)`
→ 组包 `0x5592da`（`push 0x600`）。ShopStage ctor `0x444009` 调一次，
换分类 / 翻页各调一次（`0x44869f` / `0x44871d` / `0x45b5b2`）。

**线格式 = `u8 + i32 + u16 + i32`（11 字节）**，和 `0x0605` 一模一样：

| 线偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u8 | **角色过滤**：当前预览角色 id（0/1/2）；分类高半字 == 3（용병 雇佣兵）时客户端强制填 `0xff` |
| 1 | i32 | **分类 id**（`(组<<16)\|序号`，见 §22）|
| 5 | u16 | **页号**，从 0 起 |
| 7 | i32 | ❓ 标志，取自 `[面板+0x160]`，实测恒 0（客户端按 u8 零扩展成 4 字节写）|

★ **10 秒节流**：`[ShopStage+0x144]` 是个 `0x2710`ms 定时器，**收到 `0x0500`
才清掉**（处理器第一句 `0x445ef1`）。⇒ 不回包的话客户端每 10 秒重发一次
—— 那三发 `0x0600`（22:13:12 / 23.354 / 33.744）就是这么来的。

### ★ 顺带把 `0x0605` 的线格式改回来：**`u8 + i32 + u16 + i32`**

§19 那条「实测纠正」是**错的**。三条独立证据：

1. `Serialize 0x443a38` 逐句写 1 / 4 / 2 / 4 字节（`0x5d5901` / `0x5d591f` /
   `0x5d5910` / `0x5d591f`），`Deserialize 0x443a74` 按同样顺序读 —— 两边对上；
2. 合成面板 ctor `0x45e0a3` 把「当前分类」初始化成 **2**，而进界面那一发的
   `bytes[1:5]` 正好是 `02 00 00 00`；按错误格式解，这个 2 会跑到 u16 那一格；
3. 同形状的 `0x0600` 实测到 `00 | 00 00 06 00 | ...` = 分类 `0x00060000`
   = **组 6（무기 武器）的父标签**，和 §22 的标签树严丝合缝；
   按错误格式解则是「u16=0, i32=6」，和标签树对不上。

⇒ 原来那条推理链的漏洞是：`0x50003` 这种数**看着不像 id 所以判成解错了**，
其实它就是 id（§22 的 `(组<<16)|序号` 编码）。**「这个数不好看」不是判据。**

## §21 ★★★★★ `0x0500 gspRepShopItemList` 的完整线格式（✅ **实机货架画出来了**）

**2026-09-05 实机落锤**：商店界面的 8 个格子里出现了图标 + 中文名 + 价格 +

⇒ 下面这份线格式和「itemId / 名字 / 价格 / 货币」四个字段的语义**从 🔍静态
升成 ✅实测**（其余三格仍是 ❓）。

**三条顺带被实机证实的**：

1. **总页数 / 当前页那两格是真的**：泰尔的武器 20 件 → 界面显示 `1 / 3`，

价格」是把中间那层 `ShopStockGroup`（只有一个 vector）当成了叶子。

```text
gspRepShopItemList (Des 0x4439cc)
    i32   总页数        -> 面板 +0x14c（0x45b300：当前页 >= 它就跳回第 0 页）
    i32   当前页        -> 面板 +0x148（0x45b2be：夹到 [0, 总页数-1]）
    i32   n                                     ★ 一页最多 8 项（面板只有 8 个格子）
    n × ShopStockGroup (Des 0x4437fe，步长 0x10)     = 货架上的一个格子
          i32 m
          m × ShopStockGroupItem (Des 0x4436c7，步长 0x34)  = 这个格子的一档买法
                wstr  ❓（档位名？「7일」这类）
                ShopStock (Des 0x44360a)
                    i32   物品 id      ← 图标就是拿它查 ItemDB 的
                    wstr  **商品名**（画在格子上）
                    i32   **价格**     ← 旁边的标签是 `가격`
                    i32   ❓
                    i32   **货币**：0 = 픽셀（中文版叫「金币」）/ 非 0 = 캐시（「游戏币」）
                    wstr  ❓
                    i32   ❓
                    i32   k
                    k × Item@ShopStock（步长 0x10）：i32 物品 id + 2 个 ❓ int
```

**字段语义的出处**（`0x45bc93` 刷新一个格子）：`+0x14`→`가격` 标签
（`0x45bdde`）、`+0x1c`→在 `픽셀`/`캐시` 之间二选一（`0x45be0b`）、
`+0x10`→设进文字控件、`+0x0c`→`0x4169e9` 查图标。
★ **角色限定 / 修理次数是客户端自己从 ItemDB 查的**（`타이 전용` 等串在
`0x45c025`~`0x45c0d3`），**不在包里** ⇒ 服务端不用管。

⚠ **未知 itemId 会走告警路径**：处理器 `0x445f8c` 对每个 `Item@ShopStock`
查 ItemDB，查不到就收集起来，循环完弹提示（`0x445fe5`）。
⇒ **发下去的 id 必须过 `shopdata.ownable()`**（§11）。

## §24 ★★★★★ 穿 / 脱装备是 **`0x0702` / `0x0703`**，`0x0604` 上行其实是「修理」

**结论**（🔍静态，逐个按钮跟出来的）：

| 上行 opcode | 线格式 | 语义 | 组包点 |
|---|---|---|---|
| **`0x0702`** | 单 `i32` itemId | **穿上** | `0x559464` ← `0x554393` |
| **`0x0703`** | 单 `i32` itemId | **脱下** | `0x55949e` ← `0x55441c` |

两发**都回 `0x0604 gspRepEquippedList`**（没有专用应答）。

### ⚠⚠ **每一发都必须回，一发不落** —— 客户端拿应答当计数器

仓库里点「착용 穿上」时，客户端先把**冲突的旧装备逐件发 `0x0703`**，
每发一件就 `inc [ShopStage+0x13c]`（`0x4459da`），最后发一发 `0x0702`。
`0x0604` 的处理器结尾（`0x4473e0`）是：

```text
if ([ShopStage+0x13c] > 0) { 减一; 不刷新界面 }
else                       { 调 0x44e103 刷新仓库界面 }
```

⇒ 换一件抢两个槽的装备 = 3 发请求，服务端**少回一发**，计数器就停在 1，
**界面永远不刷新**（玩家看到「点了没反应」）；**多回一发**则会提前刷新一次。

### ★ `0x0604` 上行不是装备 —— 是「用扳手修理」

`0x446f2e` 唯一的调用点 `0x45087d` 写死第二个参数 `0x33453` = **210003**
（스패너 扳手，§8 那批商城消耗品之一），调用点是「수리하시겠습니까 要修理吗」
确认框的确定键。⇒ §4 / packet_api 里那句「`0x0604` = 装备 / 卸下 🤔」**是错的**。

### ★ 顺带把商店段剩下的上行全对上了（每个都只有一个调用点）

| opcode | 语义 | 判据 |
|---|---|---|
| `0x0601` | **「这些 itemId 我不认识，给我定义」** | 调用点全在各处理器的「查不到 id」分支（`0x445fe5` / `0x447426` / `0x493f51`…）|
| `0x0602` | **买**（购物车里每个 `ShopStock+4` 的 itemId 列表）| 空购物车时弹 `구입하려는 물품이 없습니다` |
| `0x0603` | **卖**（单 itemId）| 调用点是 `되팔기 转卖` 对话框的确定键 |
| `0x0604` | **修**（itemId + 210003 扳手）| 见上 |
| `0x060b` | **用**（`gcpReqItemUse`，单 itemId）| 调用点是 `전적 초기화 战绩重置` 确认框 |

★ **`SessionSlot` 里那串 `item_ids` 不是装备上报**：客户端序列化器
`0x556ccc` 原样写 `[slot+0x1c]`，那一格是服务端 `0x0300`/`0x0301` 发下来的
快照。**客户端改一份副本发回来，不是新信息** ⇒ 别指望从 `0x0301` 读装备。

### ★ 教训：**机械扫 `SetType` 会漏**

`tools` 里那套「扫 `push imm` + `call 0x5bba0a`」的办法**没扫到 `0x0702`/`0x0703`**
（线性反汇编在 `.text` 里的数据处失步了）。这两发是**顺着 UI 按钮一路跟**
才找出来的：`착용` 串 `0x668094` → 按钮存 `[obj+0xac]` → 分发 `0x45270a`
→ `0x445703` → 检查全过之后 `0x554393`。
⇒ **要确认「某个功能到底发不发包」，跟按钮比扫 opcode 可靠。**

## §25 ★★★★★ `0x0600` 最后那个标志位 = **右下角的排序开关**（✅实测触发）

**用户 2026-09-05 报的现象**：商店右下角有「基本顺序 / 上市顺序」两个按钮，
**点了没反应**。根因是服务端把请求里那个标志位读出来就扔了。

```text
0x45b5be  点按钮：== [面板+0x154] -> 标志 = 0
                  == [面板+0x15c] -> 标志 = 1
                  其余             -> 取反
          标志存在 [面板+0x160]（1 字节），然后触发一次货架重发
0x45b59b  组包时 `mov al, byte [esi+0x160]` push 进 0x0600 的第 4 格
```

* **`0` = 基本顺序**（进商店的默认值 —— 实机日志里进商店那一串全是 `标志=0`），
  `1` = 上市顺序。
* 线上那一格是 **int32**，内存里才是 1 字节（和 `0x0502` 的 bool 同款）。
* ★ **排序只能在服务端做** —— 一页只发 8 件，客户端手里没有全表。

**「上市顺序」按什么排**：原版的上市日期随 2009 年停服的服务端 DB 一起没了。
唯一不用自己编的近似是 **`ShopItem-Chn.ini` 的行序**（`shop_items.json` 的
`items` 保序 ⇒ `shopdata.catalog_index()`），**倒过来**用 = 新的在前。
实测在真实货架上两种顺序差别明显（武器 1 页：`1120011…` ↔ `1120083…`）。

## §26 ★★★★ 探针轮**负结果**：`ShopStock` 剩下三格，商店面板一个都不读

2026-09-05 开着 `shelf-probe on` 让用户把能点的标签全点了一遍，
**界面上 777 / 888 / ※探针※ 一个都没出现**。日志确认探针**确实在包里**
（`0x0500` 的 hex 里有 `09 03 00 00` / `78 03 00 00` / `04 00 3b 20 a2 63 88 94 3b 20`）。

静态复核对上了：格子刷新 `0x45bc93` 从头到尾**只读 4 格** ——
`+0x0c` 图标 id、`+0x10` 名字、`+0x14` 价格、`+0x1c` 货币
（这些偏移是**相对 `ShopStockGroupItem`**，比 `ShopStock` 自己的偏移大 8）；
购物车 `0x456923` 只取 `ShopStock+4` 的 itemId。
⇒ **`ShopStock` 的 `+0x10` / `+0x18`(wstr) / `+0x1c` 三格在商店面板上是死字段**，
填 0 / 空串即可，别再花时间找。（礼物 / 合成面板会不会读，没查。）

**内存布局**（Des `0x44360a`，大小 `0x2c`，`+0` 是 vftable 不上线）：

```text
+0x04 i32 物品id   +0x08 wstr 名字   +0x0c i32 价格   +0x10 i32 ❌死
+0x14 i32 货币     +0x18 wstr ❌死   +0x1c i32 ❌死   +0x20 vector<Item>
```

★ 教训：**探针法的负结果也是结果**，但它只证明「这个面板不画」，
不证明「谁都不读」—— 结论要写清楚是在哪个界面上试的。

## §27 ★★★★ 合成段的线格式全逆出来了（🔍静态，M7 直接照做）

**`CompositionRule`**（Des `0x44394d`，内存步长 `0x20`，`+0` 是 vftable）：

```text
i32   产物 itemId    ← 图标/名字都用它查 ItemDB；★ 0x0606 发回来的就是它
i32   合成费用       ← 「조합비용」标签（0x45fa4c 读 rule+8）；货币写死 픽셀 金币
i32 m + m×材料       ← 材料 = { i32 itemId, **i16** 数量 }，内存步长 0xc
i32   产物有效天数   ← >0 显示「기간:%d일」；<=0 走 ItemDB 的修理次数显示
i32   ❓             ← 五个消费点一个都没读它（同 §26），填 0
```

**判据出处**：`0x4474e4`(处理器，步长 0x20 + 拿 `rule+4` 查 ItemDB)、
`0x45f99f`(格子刷新，费用/天数)、`0x45d361`~`0x45d708`(确认框：
`cmp [余额 0x72e330], [rule+8]` 判买不买得起、遍历材料 `[rule+0xc]..[rule+0x10]`)。

★ 客户端**自己算得起买不起**（拿 `[0x72e330]` 比 `rule+8`）—— 费用要如实发，
乱填会让「明明够钱却点不动」。等级 / 角色限定 / 修理次数**全是 ItemDB 查的**，
不在包里（和货架同款，§21）。

### ⚠⚠ `0x0606` 认的是**产物 itemId**，不是配方号

`0x45d738: push [rule+4]` → `0x44765c` 组 `0x0606`（单 i32）。
⇒ **一个产物只能有一条配方**，否则服务端分不清玩家点的是哪条。
`recipe.json` 里 `result` 撞车时必须拒收（M7 的校验要加这条）。

**`0x0505 gspRepCompositionList`**（Des `0x443ae1`）= `i32 总页数 + i32 当前页
+ i32 n + n×CompositionRule`，和 `0x0500` 一个骨架；请求 `0x0605` 的线格式
和 `0x0600` **完全相同**（含 §25 那个排序位）。

## §28 ★★★★★ **客户端的物品定义表是空的，全靠服务端喂** —— `0x0601` ⇄ `0x0501`

**这一条解释了 2026-09-05 实机报的四个 bug 里的三个**（购买提示「无法从服务器
读取道具信息」、仓库空的、左侧人物模型不显示装备）。

客户端有**两张**物品表，以前一直把它们当成一张：

| 全局 | 内容 | 谁填的 |
|---|---|---|
| `[0x72e1e0]` | 图标路径 + `PartFlag` | **本地** `ShopItem-Chn.ini`（`[Item-*]`/`[Stock-*]` 节）|
| `[0x72e1dc]` | **`ItemInfo`**：名字 / 部位 / 形态标志 / 等级 / 角色限定 / 耐久 | ★ **只有服务端能填** |

⇒ 货架能画出图标和名字（名字在 `0x0500` 包里、图标查本地表），但**凡是要问
「这件东西是什么」的地方全废**：穿装备、买东西、仓库列表、左侧人物模型。

### 协议：同号反向的一对（又一次）

| 方向 | opcode | 载荷 |
|---|---|---|
| 客户端 → 服务端 | **`0x0601`** | `i32 n + n×i32 itemId + **u8 用途标志**`（Ser `0x559318`，发送函数 `0x55403a`）|
| 服务端 → 客户端 | **`0x0501`** | `i32 n + n×ItemInfo + **u8 用途标志**`（Des `0x559357`，处理器 `0x554136`）|

★ 服务端方向的 `0x0601` 是**持有物清单**（见 §29），**不是**物品定义。

**处理器 `0x554136`**：逐条 `0x415aab` 插进 `[0x72e1dc]`（key = `ItemInfo+4`），
然后调 `当前Stage->vft[0xb4](清单, 用途标志)`。

### ⚠⚠ 用途标志必须**原样回**

`ShopStage::vft[0xb4] = 0x44602a` 第一句就是 `cmp byte [ebp+0xc], 2` ——
**只有标志 == 2 才重建左侧人物模型**（`[ShopStage+0x134]` 那个 `EquipmentEx`），
其余值直接 return。客户端发请求时按用途填：

| 标志 | 谁发的 | 发送点 |
|---|---|---|
| `0` | 货架 `0x0500` 里有不认识的 id | `0x445fd3` |
| `1` | 持有物清单 `0x0601` 里有不认识的 id | `0x5542ac` |
| **`2`** | 装备清单 `0x0604` 里有不认识的 id ⇒ **回来要重建人物模型** | `0x44740c` |
| `5` | 结算界面 | `0x493f3e` |

★ 实机日志对得上：进商店后第一发 `0x0601` 尾字节是 `02`（6 件穿着的），
第二发是 `00`（8 件货架的）。

### `ItemInfo` 线格式（Des `0x5586a6`，内存大小 `0x38`，`+0` 是 vftable）

| 线序 | 结构偏移 | 类型 | 含义 | 出处 |
|---|---|---|---|---|
| 1 | `+0x04` | i32 | **itemId**（就是 map 的 key）| `0x554168` |
| 2 | `+0x08` | i32 | ❓ 全镜像找不到消费点 ⇒ 填 0 | |
| 3 | `+0x0c` | i32 | **`PartFlag` 部位掩码** | `0x4152ed: test [槽掩码], eax` |
| 4 | `+0x10` | i32 | **形态标志**（见下）| `0x443444` / `0x44736a` |
| 5 | `+0x14` | wstr | **物品名** | `0x552602`「%s의 내구도…」、`0x45238d` 提示框标题 |
| 6 | `+0x18` | wstr | ❓ 无消费点 ⇒ 填空串 | |
| 7 | `+0x1c` | i32 | ★ **等级要求** | `0x445817: cmp eax, [0x72e338]` |
| 8 | `+0x20` | i32 | ❓ 无消费点 ⇒ 填 0 | |
| 9 | `+0x24` | **i16** | ★ **角色限定**：`-1` = 不限，`0/1/2` = 泰尔/卡希尔/布洛克 | `0x44e1b8: cmp ax, 0xffff` |
| 10 | `+0x28` | i32 | ❓ 无消费点 ⇒ 填 0 | |
| 11 | `+0x2c` | i32 | ❓ 无消费点 ⇒ 填 0 | |
| 12 | `+0x30` | i32 | **最大耐久**（`0` 时客户端跳过百分比计算）| `0x5525dd` |
| 13 | `+0x34` | i32 | **修理次数上限**，`< 0` = 不限 | `0x412934` |

**形态标志 `+0x10` 的位**（`0x443444` 按位挑提示文案）：

| 位 | 含义 | 界面表现 |
|---|---|---|
| `0x01` | 计数持有 | 提示框写「소지개수 : %d개」，数字取**持有物条目 +0x08** |
| `0x02` | 期限持有 | 写「%d일」，天数取**持有物条目 +0x0c** |
| `0x08` | ★ **可装备** | `0x0604` 的处理器**只有这一位为 1 才 `Equip`** |
| `0x10` | 和 `0x02` 一起 = 「100%」 | |
| `0x20` | ❓ 仓库格子上多画一个标记 | |
| `0x40` | 按局数 | 写「%d게임」 |

⇒ 本版：**装备发 `0x08`，材料发 `0x01`，一件都不发 `0x02`**（不做期限售卖），
标志全 0 的话提示框写「기간제한없음」。

★ **两条硬约束**（发错了玩家点了没反应，而且客户端不说为什么）：
1. **等级要求必须 ≤ 玩家等级**，否则「착용 穿上」按钮直接弹框拒绝（`0x445817`）；
2. **角色限定要和 id 对上** —— `-1` 才是「不限」，`0` 是「泰尔专用」。

## §29 ★★★★★ **仓库列表 = 服务端方向的 `0x0601`**，请求是 `0x0700`

**`0x0700`（上行，无正文）不是「进商店了」—— 它是「给我持有物清单」。**
⇒ §3.8 里那句「❓语义未查明，不是商店专用」作废；大厅 / 房间也发它正是
因为哪儿都要用持有物。发送函数 `0x5541c1`，6 个调用点（ShopStage ctor
`0x44402c`、大厅 `0x43b5c4` / `0x4692c2`、`0x0609` 和 `0x0701` 的处理器尾巴）。

**应答 = 服务端方向的 `0x0601`**（处理器 `0x55420e`，Des `0x559413`，
条目 Des `0x412621`，内存步长 `0x20`）：

```text
i32 n
n × 持有物条目：
      i32   物品 id
      i32   数量 / 剩余局数        -> 条目 +0x08
      f64   剩余分钟数（0 = 永久） -> 条目 +0x10 ★ 8 字节 double
      i32   已修理次数             -> 条目 +0x18
```

处理器把它整份换进全局背包 `[0x72e41c]`（`0x4126cb`），再调
`当前Stage->vft[0xb8]`；`ShopStage` 的是 `0x446f8a` = **刷新仓库面板
`[ShopStage+0x108]`** ⇒ 这一发不发，仓库界面就是空的。

⚠ **顺序**：`0x0501`（定义）必须排在 `0x0601`（持有物）**前面** ——
仓库面板是在收到 `0x0601` 的那一刻建的，那时 ItemDB 还空着就建成空的，
而补发的 `0x0501` 标志位不是 2，`ShopStage` 不会再刷一次。

### ★ `0x0604` 发的是**穿着中**，不是「我拥有的全部」

处理器 `0x447278` 把清单里每个 `flags & 8` 的条目 `Equip` 进
`[ShopStage+0x134]`（左侧人物模型的数据源）—— 发全部持有物的话，
玩家会看到自己**同时穿着所有装备**。⇒ 只发 `equipped_items()`。

### ★ 客户端自己会在两个时机重新要一次持有物

`0x0701 gspRepMoveInto`（换频道结果，我们本来就在发）的处理器 `0x552b47`
处理完发一发 `0x0700`（`0x552d31`）；`0x0609`（耐久更新）的处理器
`0x552593` 尾巴上也发一发（`0x552794`）。**买东西之后它不发**
（`0x44615b` 里没有 `0x5541c1` 的调用点）⇒ 买完那一发只能服务端主动推。

## §30 ★★★★★ `0x0502` 第二格是**失败原因码**；买完那四发的**顺序**是硬要求

**§24 里那句「失败时客户端什么都不显示」是错的**（2026-09-05 实机推翻）：
失败会弹一个「购买失败」框，正文就是拿包里第二格查表。

### ① 失败原因码（`0x0502` 的 `+8`）—— `switch` 在 `0x45915f`

弹窗构造函数 `0x4586e1(this, ok, **原因码**, ?, 差额)`；组包点 `0x4461f8`
把包里的第二个 i32 当第二个参数递进去。分支表：

| 码 | 韩文串 | 中文版文案 |
|---|---|---|
| 1 | `%d 픽셀이 모자랍니다.` | 还缺少 %d 金币 |
| 2 | `%d 캐시가 모자랍니다.` | 还差 %d 游戏币 |
| 3 | `레벨이 낮습니다.` | 等级太低。|
| 4 | `레벨이 높습니다.` | 等级太高。|
| 5 | `인벤토리가 꽉 찼습니다.` | 购物车已满。|
| 6 | `내부 오류입니다.` | 内部错误。|
| 7 | `이미 소지한 아이템입니다.` | 已拥有的道具。|
| 其余（**含 0**）| `정의되지 않은 오류입니다` | 未定义的错误。|

★ 1 / 2 里那个 `%d` **不在包里** —— 客户端自己拿购物车总价减余额算
（`0x457dae`，`0x4461da` 处取）。⇒ 服务端只发码，不发金额。
★ **兜底不能填 0**：0 = 「未定义的错误」，等于我们知道原因却不说。

### ② ⚠⚠ 买完那四发：**仓库必须排在购买结果前面**

买成功之后客户端会弹「구입하신 아이템을 착용하시겠습니까?（要不要直接穿上
刚买的这件）」，条件是**购物车正好一件**且它 `PartFlag != 0`
（`0x44625d: cmp eax,4` / `0x446268: cmp [eax+0xc],0`）。
点「确定」（`0x4463e3: cmp edi,5`）之后：

```text
0x4463e8  push [ItemInfo+4]        ; 刚买的 itemId
0x4463eb  mov eax, 0x72e41c        ; ★ 全局背包（0x0601 灌进去的那份）
0x4463f0  call 0x412742            ; 在背包里找它
0x4463f7  je  0x446400             ; ★★ 找不到 -> 什么都不做，一声不吭
0x4463fb  call 0x445703            ; 找到了才走「穿上」（发 0x0703×N + 0x0702）
```

⇒ **`0x0502` 到达时背包里必须已经有这件东西**，否则「选了装备却没装上」
（2026-09-05 实机现象；日志里买完到手动装备之间一发上行包都没有）。
`0x424b13` 那个确认框是**阻塞**的，排在 `0x0502` 后面的包要等玩家点完才处理。

**⇒ 服务端买完的发包顺序钉死为**：
`0x0501` 定义 → `0x0601` 持有物 → `0x0604` 穿着 → `0x0600` 数据栏 →
**`0x0502` 购买结果（最后）**。

### ③ ★ 不许按「玩家当前是哪个角色」拦购买

实机：泰尔（`player_character = 0`）买布洛克的 `3120031 火箭筒 爆裂1` 被
服务端拒了。商店上方那排角色箭头本来就是给「替别的角色买」用的 ——
货架已经按**预览角色**过滤了（`0x0600` 的第一个字节，§20），
再按当前角色拦一道是我们自己加的规矩。**原版没有。**

## §31 ★★★★★ 三处「被判成死字段」的格子其实都有人读

2026-09-05 第三轮实机推翻了 §23 和 §26 各一条结论。**通则**：
「某个面板不读」≠「谁都不读」—— §26 结尾自己写过这句，这次就栽在上面。

### ① ⚠⚠ `Equipment` 头上那 12 字节 = **每个角色的槽位掩码**（§23 那句作废）

**实机现象**：房间（待机房间）下面的仓库格子里点「卸下」，弹「已卸下。」
（韩文 `이미 아이템을 착용하고 있지 않습니다` = 「你根本没穿这件」），
**而且一个包都不发**，界面上那件还标着「使用中」。

**判定函数 `0x5584ab(ecx=ItemInfo, eax=EquipmentEx)`**：

```text
si = [ItemInfo+0x24]                        ; 角色限定
if (0 <= si < 3):
    if ((EquipmentEx[0xc + si*4] & [ItemInfo+0xc]) != [ItemInfo+0xc])
        return false                        ; ★ 掩码里没有这个部位 -> 「没穿」
return  itemId 在 [EquipmentEx+0x18..0x1c) 的 vector 里
```

⇒ 掩码全 0 ⇒ 凡是**有角色限定**的装备一律判成「没穿」。

**客户端自己怎么维护它**（`Equipment::Equip 0x5583d3`）：

```text
ax = [ItemInfo+0x24]
0 <= ax < 3  ->  [Equipment + 0xc + ax*4] |= [ItemInfo+0xc]      ; 只点亮那一个
ax == -1     ->  三个掩码全部 |= [ItemInfo+0xc]                   ; 不限角色
然后 itemId push 进 [Equipment+0x18]
```

**为什么只有房间里出问题**：`0x0604` 的处理器是**先建空的再逐件 `Equip`**

★ 战斗加成不受影响（`0x55853c` 只遍历 id vector，不看掩码）——
所以 §16 那轮实测在掩码全 0 的情况下也是对的。

⇒ **`0x0604` 和 `0x030b` 都按 `shop.equipment_slot_masks()` 算着发。**

### ② `ShopStock+0x10` = **划线原价**（§26 判它「死」，只对货架格子成立）

### ③ `ShopStock+0x18`（wstr）和 `ItemInfo+0x18`（wstr）= **物品说明**

## §33 ★★★★★ 合成段剩下的三件事：`0x0506` 结果码 / 标签树只有 8 个 / 一页 8 条

M7 动手前补的一轮（🔍静态，判据全在脱壳镜像上）。§27 只逆出了**列表**那一半，
这一节补齐**结果**那一半，外加两个「不看就会白做」的边界。

### ① `0x0506 gspRepComposeItem` 的那一个 i32 = **结果码**（处理器 `0x4476c4`）

`0x44771b: cmp [ebp-0x2c], 0` 挑标题（`0` = `조합하기 성공`，非 0 = `실패`），
`0x44777a` 起的 `sub eax,0 / dec eax` 链挑正文：

| 码 | 界面文案 |
|---|---|
| **0** | 合成成功 ——「请在我的仓库里装备道具」；**选中那条配方的 `rule+0x18` 天数非 0** 时换成带「(사용기간 : %d일)」的那句（`0x44785f` 读 `[面板+0x594]->[+0x18]`）|
| 1 | `픽셀이 부족합니다` 金币不足 |
| 2 | `재료가 부족합니다` 材料不足 |
| 4 | `이미 소지하고 있습니다` 已拥有 |
| 其余（**含 3**）| `알 수 없는 오류` 未知的错误 |

⚠⚠ **和 `0x0502` 极性相反** —— 那一发填 0 是「未定义的错误」，
**这一发填 0 是「合成成功」**。拒绝时兜底填 0 = 玩家看到「合成成功」，
然后发现仓库里什么都没有。

⚠⚠ **没有「等级太低」这一档** ⇒ 等级不能拿来在合成上拒绝，只能当列表过滤（D27）。

★ 处理器**只弹个框，什么都不刷**（函数体里既没有 `0x5541c1` 要持有物、
也没有 `0x447467` 要配方列表的调用点）⇒ 仓库 / 金币 / 配方页全靠服务端主动推。

### ② 合成界面的标签树：**5 个顶级 + 7 个子标签**（✅ 2026-09-06 实机确认）

**顶级标签**在 `0x45e2f0` 那张表里，一行一个「标签名索引」：

```text
[ebp-0x40]=0 신상품 新商品   [ebp-0x3c]=1 아이템 道具   [ebp-0x38]=2 의상 装备
[ebp-0x34]=8 타이틀 称号     [ebp-0x30]=9 이벤트 活动
```

索引查的是**全局名字表 `0x72e6a0`**（10 个 `std::wstring`，`0x635389` 一次性
填好）：`0 신상품 / 1 아이템 / 2 의상 / 3 스킬 / 4 캐릭터 / 5 무기 /
6 받은선물 / 7 수집품 / 8 타이틀 / 9 이벤트`。
建标签的公共函数是 `0x44f451`（`lea eax,[eax*4+0x72e6a0]`），
仓库 / 商店 / 合成各调一次（`0x452e4e` / `0x45a4e6` / `0x45e367`）。

**子标签**（`0x45e42f` 起，一路 `push 标签名` + `mov 槽位, id`）：
装备下面 `0x10005` 머리 / `0x10001` 상의 / `0x10002` 하의 / `0x10003` 장갑 /
`0x10004` 신발；道具下面 `0x40001` 치장 / `0x40002` 기타；
新商品自己一格 `2`。**称号和活动没有子标签**。

⚠⚠ **没有武器、没有套装**（商店那棵树有 `0x60000` 武器和 `0x10006` 套装，
这棵没有）⇒ 产物归在那两类的配方，在「装备 / 道具」下面**永远点不到**
—— 现在靠「新商品」兜住（`shop.CATEGORY_NEW` 收全部，D32）。

★ 教训：**只读到叶子就以为读全了**。我第一版只扫到 `0x45e42f` 起的那 8 个
子标签，就写成「合成界面只有 8 个标签」；用户实机看到的是 5 个顶级标签，
名字一个都对不上。顶级那一层在**另一个函数、另一张表**里，
而且是「索引 → 全局名字表」的间接寻址，按字符串搜搜不到。
⇒ 逆界面结构时，**先找到「建一个标签」的那个公共函数**，再看谁调它、传了什么。

★ 和货架同样的坑：**分类 `0` 不是通配**，它是「人物 → 英雄」标签的真 id（§22）。

### ③ 一页 **8 条**，和货架一样

`0x45f011`（配方列表 setter）的循环走 `[ebp-8] = 0 .. 0x100` 步长 `0x20`
（一条 `CompositionRule` 的内存大小）⇒ 面板只有 8 个格子。
总页数写 `[面板+0x144]`、当前页写 `[面板+0x140]`，客户端自己会把当前页
夹到 `[0, 总页数-1]`（`0x45efb9` 的 `dec ecx`）⇒ **一条配方都没有也要报 1 页**。

### ④ `0x0505` 的处理器会把**产物和每一种材料**都拿去查 ItemDB

`0x447575` 查 `rule+4`（产物）、`0x4475ad`~`0x4475bf` 遍历
`[rule+0xc]..[rule+0x10]` 步长 `0xc` 查 `mat+4`（材料），查不到的攒起来
发一发 `0x0601`，**用途标志是 `3`**（`0x447603: push 3` —— 用途标志表里
原来缺的那一档）。⇒ 服务端要在 `0x0505` **之前**把两批 id 的定义都喂下去，
否则四个材料槽是没名字的空格子（和 §28 同一条道理）。

### ⑤ 「持有量」是**现场读背包**的，不是包里带的

按 §32 那套「全扫地址字节」的办法扫背包全局 `[0x72e41c]`，22 处引用里
落在合成面板范围（`0x45c000`~`0x45f000`）的有四处：`0x45d271` / `0x45d57b` /
`0x45db08` / `0x45dcb5`，全在**确认框和材料槽刷新**里 ⇒ 合成完推一发 `0x0601`
就能让「持有量」变对。⚠ 但**面板不会自己重画** —— 所以我们额外把客户端
最后一次发过的那发 `0x0605` 原样重放（D28）。

★★ **2026-09-05 晚实机全部通过**（✅实测）：合成成功、材料和金币照扣、
**「持有量」当场就变**（⇒ D28 那一发重放是有效的，不是白发）、
「材料不足」/「金币不足」的失败框文案也都对上了。

### ⑥ 合成面板**没有购物车**，这是原版设计

用户 2026-09-05 报「商店里点一下会自动加购物车，合成里点了只预览」。
判据是协议的形状，不是界面：`0x0606` 的载荷是**单个 i32**，而按下
「조합」的那一句是 `0x45d738: mov eax,[esi+0x594] / push [eax+4]`
—— push 的是**当前选中的那一条规则**的产物 id，不是某个清单。
⇒ 合成一次只处理一件，服务端也没有任何包能让格子「攒起来」。

## §35 ★★★ 管理页「服务器内部错误」十有八九是**编辑器把 json 独占打开了**

**结论**：`POST /admin/api/config/*` 回 500、日志里写
`PermissionError(13, '拒绝访问。')`，原因不是代码，是 **`server/data/*.json`
正开在 サクラエディタ 里**（它默认独占打开），`write_json` 的
`os.replace` 撞上 Windows 的共享冲突。关掉编辑器里那个文件就好了。

**怎么确认是哪个进程占着**（不用装 Sysinternals）：PowerShell 里调
Restart Manager（`rstrtmgr.dll` 的 `RmStartSession` /
`RmRegisterResources` / `RmGetList`），它直接回进程号 + 程序名。
.NET 的 `[System.IO.File]::Open($p,'Open','ReadWrite','None')` 只能告诉你
「被别的进程占着」，说不出是谁。

**改了什么**：`_admin_config_post` 现在自己接住 `OSError`，回一句
「写不进 xxx.json（…），这个文件多半正被别的程序占着（编辑器打开了它？）」。
兜底那层 `except Exception` 只会打一行日志 + 回「请看服务端日志」——
用户根本猜不到要去关编辑器。

★ **教训**：凡是「写文件」的接口，`OSError` 都该有一句自己的话。
把它交给通用兜底 = 把一个**用户能自己解决**的问题变成一个要看日志的问题。

## §40 ★★★ 数据备份要知道的五件硬事（2026-09-07，D46）

1. **`server.config` 原本只有读没有写回**：`config.parse_text` / `load`，

   ⚠ `parse_text` 同键取**最后一次** ⇒ 写回时同键出现几次就全换。
2. **`web/admin._config_locks` 只护管理页保存那条路**；`ensure_files` /
   `backfill_defaults` / 外部脚本都不持锁；存档另有 `AccountStore._lock`（RLock）。

   存档锁）拿两套不会死锁。
3. **Windows 上读文件会挡住别人的 `os.replace`**（Python `open()` 无 FILE_SHARE_DELETE）

   和 §35 编辑器独占是同一个物理现象。
4. **回滚一份等大小的旧文件会骗过 `shopcfg` 的热重载**（缓存键 `(st_mtime_ns, st_size)`）
   ⇒ 回滚后必须 `shopcfg.invalidate()`（`test_backup.RestoreTests` 钉住）。
   `accounts.json` 存储层零缓存（每次操作现读盘），但 `Conn.account` 是登录时抓的
   **视图**，写盘不会把它盖回去，只是玩家看到的数过期 ⇒ 回滚后 `reload_account`
   + `_push_account`。
5. **管理员账号在 `accounts.json` 的 `admin_accounts` 段里** ⇒ 回滚老存档能把自己锁在
   管理页外面（更老的连这一段都没有）；`databackup.admin_survives` 在写盘前拦，
   回滚后再跑一遍 `ensure_item_fields` + `realign_levels`（启动那两步，幂等）。

**打包**：自检真跑一次包内 `app.py`，`build-common.ps1` 的 `$argList` 加了 `--no-backup`
（照 `--no-log-cleanup`），否则备份会被打进发布包。`.gitignore` 加了

## §46 ★★★★★ 装备槽是**每个角色一套**；服务端曾按整个账号一套算 —— 一人穿铠甲另两人被脱光（✅实测 + 🔍静态）

**现象**（2026-09-09 用户在 `dist/…V0-3-0 - 副本` 实机，`logs/server.out` 01:00:41）：
泰尔穿上 `1010052`，服务端日志「顶掉 [2020023, 2010047]」—— 那是卡希尔的两件；
`3120011`（布洛克武器槽 1）同样顶掉了 `1120042`（泰尔武器槽 1）。
整局客户端**一发 `0x0703` 都没发** —— 它根本不认为这些是冲突。

**根因**：`shopdata.resolve_equipped()` 用**一个**总掩码收敛整份 `equipped`，
「同 `part_flag` 即冲突」不看角色。客户端是三个掩码、一个角色一个（§31 ①）：

| 客户端 | 地址 | 规则 |
|---|---|---|
| 穿上前的预检 | `0x55832c(ItemInfo, Equipment, 0)` | 角色限定 0/1/2 → 只查 `掩码[角色] & PartFlag`；`-1` → 三个掩码都查 |
| 收集要先脱的旧件 | `0x415304(Equipment, &out, 角色, PartFlag)` | 穿着中的每件：`(旧.角色 == 新.角色 ‖ 旧.角色 == -1) && (旧.PartFlag & 新.PartFlag)` 才进清单（逐件发 `0x0703`）|

⇒ 同一个部位、不同角色，客户端**从不认为冲突**；服务端一「顶掉」，回的 `0x0604`
少了那几件，客户端整份重建（先建空再逐件 `Equip`，§31），另两个角色就光了。

**受影响的**：凡是角色限定的装备全中 —— 铠甲各部位 / 套装、武器三个槽、
突击技（`part_flag` 32）、喷漆（64）、戒指（16384）。不限角色的只有称号（8192）
和宠物（32768），它们和角色装备没有共用的 `part_flag`，所以没被殃及。

**修法**（D54）：`shopdata.slot_owners(item)` 一处定「这件点亮哪几个掩码」
（照 `Equipment::Equip 0x5583d3`），`resolve_equipped` / `conflicts` /
`shop.equipment_slot_masks` 共用；收敛时三个掩码各算各的。
存档不用迁移：被错顶的装备只是从 `equipped` 掉出来，`inventory` 还在，重穿即可。

⚠ 客户端那条收集规则是**不对称**的：新件不限角色（-1）、旧件角色限定时，
`0x415304` 不收旧件（只匹配 `旧 == -1`），预检 `0x55832c` 却会判「占着」。
服务端按掩码模型（对称）收敛，这种情况会替它顶掉旧件；现在的物品表里没有
这种同槽组合，`test_shopdata` 里那件合成的「不限角色上衣」只是为以后钉规则。

## §54 ★★★★★ `0x0103` **本身就是崩溃报告包**，而且客户端上报完会**把文件删掉**（✅实测，2026-09-09）

（V0.1 §44）。**不对。** `0x0103` 自己就是那一发：

```text
int32  有没有报告：0 = 没有，1 = 有
int32  正文字节数
byte[] Dump\LastCrashReport.txt 的正文，原样字节
```

证据（`logs/server-20260909-122222.out`）：12:09 那次登录的 `0x0103` 载荷 **1890 字节**
= `int32(1) + int32(0x756=1878) + 正文`，而 1878 正是当时那个文件的大小；
其余每次登录都是 **8 字节** 的 `int32(0)+int32(0)`。

★★ **上报完客户端就把 `Dump\LastCrashReport.txt` 删了** —— 12:09 之后文件消失，

`crashwatch` 因此在**客户端进程退出的那一刻**就把它读进内存（`read_crash_report`），

## §56 ★★★ 认「哪个进程是本次客户端」和「它死了没有」，事件都是现成的

* **PID**：中继 `accept` 到 `127.0.0.1:<peer>` 的连接后，`GetExtendedTcpTable`
  (`AF_INET=2`, `TCP_TABLE_OWNER_PID_ALL=5`) 按 (本地口=peer, 远端口=中继监听口)
  查 owning PID。表里端口是**网络字节序塞在 DWORD 低 16 位**。
* **死了没有**：`OpenProcess(SYNCHRONIZE|PROCESS_QUERY_LIMITED_INFORMATION)` +
  `WaitForSingleObject(INFINITE)`。ctypes 调用期间放开 GIL，干等着不挡别的线程。
* **会话起点**：同一个句柄 `GetProcessTimes`，FILETIME 减 `116444736000000000`
  再除 `1e7` = Unix 时刻。**挑「本次运行的日志」的那条边界就是它**，不是拍的时间窗。
* **退出码**：同一个句柄 `GetExitCodeProcess`（崩溃时是 `0xC0000005` 之类）。

★★ **进程对象被置位 ⇒ 进程已完全终止 ⇒ 它所有文件句柄都被 OS 关闭**
⇒ `.mdmp` / `.rpt` / `LastCrashReport.txt` 必定写完且没被占着。
**这条排除了「读到半截文件」的竞态，所以整条链上一个 `sleep` 都不需要。**

`hook/bsloader.c:383` 早就在做同一件事（`WaitForSingleObject` + `GetExitCodeProcess`），
但它把结果只打进 `logs/bsloader.out`，没人读。

`0x417a76` map.find → 查得到才 `0x4136af` 格式化。⇒ **服务端一个字都改不了。**

### ② ★★ **有两个生成器**，五个消费点（2026-09-09 实机订正）

第一版只找到 `0x414128`，堵完用户报「商店浮窗里还有绿字」—— 商店走的是**另一个**。

| 生成器 | 参数 | 消费点 | 界面 | 绿色怎么设 |
|---|---|---|---|---|
| **`0x414128`** | 单件 `itemId` | `0x455628` | `UiCabinetToolTip` ★ **一个类被大厅仓库 / 房间内背包 / 商店页里的仓库格共用**（§31 那批调用点）| `0x4556ce push` |
| | | `0x460059` | `UiCompositionToolTip`（合成）| `0x4600ff push` |
| | | `0x450614` | `Data/Ui/RepairItemUI.ui` 的 `ItemEffectText` | `0x45067d mov [eax+0x4c],` ★ 不是 push |
| | | `0x45078d` | 同上，`DlgRepairItem` 虚表槽 `+0x4` | — |
| **`0x4141AC`** | **id 列表**（把多件的加成**累加**起来）| `0x45c5fa` | ★ **`UiShopToolTip`（商店）** | `0x45c69b push` |

**商店那条**：`0x45c59a` 先把 `ShopStock+0x20` 的「买了会得到什么」列表（每元素 16 字节、
取 `[+4]` = itemId）收集出来，再交给 `0x4141AC` 求合计加成。⇒ 礼包 / 套装那种
「一件商品给你好几样」的合计属性。**我们没填 `+0x20`，但商品自己那一件在列表里**，
所以照样有绿字。

★ 另有 `0x45d1BF` 直接调格式化器 `0x4136AF`，输出进 `[UiComposition+0x57c]` 一个标签
（合成**面板**自己的，**不是绿字**）—— 没动它。

⇒ 全查法：绿色常量 `0xFF22C701` 在代码段出现 **7 处** —— 3 处是三个提示框构造函数里的
默认色（`0x4549C9` / `0x45BBB9` / `0x45F828`，`mov eax,` 形式），3 处是提示框绘制
（`push` 形式），1 处是修理界面（`mov [eax+0x4c],` 形式）。**按 `push` 扫会漏掉后者。**

### ③ 绿字自带三个原版缺陷，**全在 pak 里，服务端改不了**

| 现象 | 根因 |
|---|---|
| 「速度+d%」 | `Chinese.ini` 错字：`Spd%+d%%=速度+d%%`，**漏了 d 前面的 `%`**（长格式 `Speed %+d%%=速度 %+d%%` 是对的，短格式坏了）|
| 称号上出现「Team 5% Down」 | `Chinese.ini` **漏翻 3 条**：`Team %d%% %s` / `Self %d%% %s` / `Down`（只翻了短格式 `Team%d%% %s=团队…` 和 `Dn=降低`）|
| 换行溢出到下面的框 | `ItemInfo2Txt` 在 `.ui` 里只有 **240×14 = 一行**，属性一多就换行顶出去 |

### ④ 「绿字错位到下面」不是错位 —— 三个框的位置本来就是这样

`ShopToolTipNewUI.ui` 里写死：第 1 段 `ItemInfo0Txt` y=165(h88) →
**绿字 `ItemInfo2Txt` y=256(h14)** → 第 2 段 `ItemInfo1Txt` y=274(h51)。
绿字永远夹在两段中间；第 2 段空着时看上去就像「掉到下面去了」。

### ⑤ ★★ `.ini` 加载器**只读 pak，散文件不生效**（把 §1 那个 ❓ 结掉）

```
0x413ef5  call 0x55e7f0      ; 这个文件在 pak 里吗
0x413efa  ...neg/sbb/inc...  ; bl = 不在 pak 里 ? 1 : 0
0x413f13  jne 0x4140d2       ; ★ 不在 pak 里 -> 0x4140d2 = **函数尾，直接 return**
```

⇒ 往 `game_patched/Data/` 放一份改过的 `Chinese.ini` / `EquipBonus.ini` **没有任何效果**，
要改只能重打 `.pkn`（项目里没有打包工具）。**§1 结尾那条「真要改数值时先实测散文件能否覆盖」
到此有答案：不能。**

### ⑥ 处理：**两处各一个字节**关掉绿字（D65）

打在**两个生成器**上，不是五个绘制点上。两处的循环体一模一样
（`map.find(itemId)` → `test` → `je 跳过`），把 `je` 改成 `jmp` 即可：

| 补丁点 | 原字节 | 改成 | 效果 |
|---|---|---|---|
| `0x41415E`（`0x414128` 里）| `74 20` | `EB 20` | 永远返回**空表** |
| `0x414208`（`0x4141AC` 里）| `74 07` | `EB 07` | 永远**不累加** ⇒ 累加器保持全 0 |

后者要成立还得有一条：`0x4136AF` 对**每一项都判零**才输出
（短格式 `0x41379D` 那一串、长格式 `0x413A7F` 那一串，两条分支都判）
⇒ 累加器全 0 时一条都不输出，同样是空表。✅ 已逐条核对。

★ 这两刀几乎零风险：走的就是**原版每天都在走**的那条路 —— 武器 / 材料 / 纯外观装备
在 `EquipBonus-Chn.ini` 里都没有条目，本来就走 `je` 这一支；SEH 状态 `[ebp-4]`
两条路完全一样，vector 的构造 / 拷贝 / 析构一步不少。
`hook/bshook.c` 的 `try_patch_hide_client_bonus_text()`（一张两条的表，
**两处都打中才算成功**），`BSHOOK_KEEP_CLIENT_BONUS_TEXT=1` 可回到原版。

### ⑦ 教训：**「按 push 扫常量」和「找到一个生成器就收工」都会漏**

第一版只扫 `push 0xFF22C701` ⇒ 漏了修理界面那处 `mov [eax+0x4c],`；
只跟到 `0x414128` ⇒ 漏了商店走的 `0x4141AC`，用户实机一眼就看见了。
⇒ 以后堵这类「同一份信息有多个入口」的东西，判据要落在**数据源**
（这里是 `[0x72e440]` 那张表：`xref` 出 11 个引用，逐个分类），别落在「我找到的那个入口」。

写备份」）—— 但 `ensure_files` 那时没有出口，`app.py` 压根没有 `--data-dir`。

**判据（怎么分清「拷进去的」还是「跑出来的」）**：把包里的 `server\` 拷到临时目录、

**教训**：凡是挂在服务端**启动路径**上的「缺文件就生成一份」「到点写一份」，

## §63 ★★★★★ 装备**外观**也走 `0x030b`，而且是**按座位**的 —— 服务端只发给本人 ⇒ 别人全看不见（✅静态落锤 + 🔍代码，2026-09-09）

**用户现象**：自己穿的装备，房里 / 局里别人看不见。

**根因一句话**：`0x030b` 全服务端**只有一个发出点**，而它永远是
`座位 = self.my_seat`、`清单 = self.account`、`收件人 = self`
（改前 `gameserver.py:6570` 那一句 `self.send(...)`）。
⇒ 每个客户端手里只有**自己那一格**的清单，别人那五格恒空 = 没穿装备的样子。

### 外观这条路（这一节新查明的部分）

```
0x030b(座位, 掩码×3, itemId[]) → 处理器 0x406ea1
    ├ 写 [LobbyStage + 座位*4 + 0x250]        ← 加成读的也是这一格（§1）
    └ 0x406f42(座位, LobbyStage)
         ├ 0x404ff6 → [LobbyStage + 座位*4 + 0x1d0]   该座位的 3D 角色对象
         ├ 0x506251 清掉它身上已挂的装备（+0x2e4 / +0x348 / +0x3ac / +0x3b0）
         └ 逐件 0x505bb9(itemId)  →  0x5059c0 真的挂上去
```

**`0x505bb9` 查的是 `[0x72e1e0]`，不是服务端喂的 ItemDB `[0x72e1dc]`（§28）。**
`[0x72e1e0]` 由 `0x41652d` 在**启动时**从 pak 里的 `ShopItem-Chn.ini` 读进来
（文件名串 `0x6602a8`，经 `0x55e7f0` 那个 pak 加载器），键是 itemId、
挂着 `Tag`（角色网格路径，§51）。
⇒ **服务端只要给 itemId 就够**，不用也没法下发模型路径；
⇒ 观察者的客户端**不需要**先查过这件物品的定义（`0x0501`），外观照样出得来。

角色限定在 `0x505bb9` 里现算：`key = itemId/1e6 - 1`，`-1` 或等于
`[角色+0x2b0]` 才挂 ⇒ 一次把某人三个角色的装备全发过去是安全的，
客户端自己按那一格当前的角色挑。

**战斗里同一份**：`0x493258` 建完座位角色紧接着就是 `0x406f42`
（`0x49325d` 起，全局 `[0x72e29c]`）⇒ 房间里对了，进图也就对了。

### ⚠ 座位清单是**跨房间活着的全局**

`LobbyStage`（`[0x72e29c]`）不随房间销毁，`[+0x250+座位*4]` 里那份清单
**没人覆盖就一直在**。而 `0x0301` action 0（`0x4066a5` 建 3D 角色 →
`0x4066ae` 调 `0x406f42`）会立刻拿那一格的清单去挂装备。
⇒ **每次某一格换人都必须重发一次，bot 那一格也要发（空清单）**，
否则 bot / 新人会穿着**上一个坐这儿的人**的装备站在那儿。

### 结论：要发的时机（改后全在 `gameserver.py`）

| 时机 | 发给谁 | 函数 |
|---|---|---|
| 进房 | 只给进房的人，**每个有人的座位各一发** | `send_room_equipped_lists()` |
| 有人进房 | 广播给房里其他人（排在 `0x0301` action 0 **之后**）| `announce_join()` |
| 穿 / 脱（`0x0702` / `0x0703`）| 本人 + 广播 | `on_req_equip_item()` |
| bot 坐进某格 | 全房间（含房主），**空清单** | `bot._add_one_bot()` |
| 结算看完回房间（`0x0405`）| 只给自己，**每个有人的座位各一发** | `leave_game_result()` |
| 调试 `equip` / `unequip` / `sync-account` | 本人 + 广播 | `handle_control_command()` |

★ 客户端**不校验**「这个座位号是不是我自己」—— 处理器直接拿包里的座位号
算 `0x250` 的下标，所以六格都能发。

## §65 ★★★★★ **崩溃报告器自己会崩** —— 出错地址不在任何已加载模块里就死在 `0x5D76CD`（✅本机 A/B 逐字节实证，2026-09-10）

**先说后果**：这一条不是「又一个闪退」，是**我们为什么看不见闪退**。
bug调查/17 收到的 5 份线上现场里有 **3 份**报告只有开头四行、`.mdmp` 根本没生成 ——
不是上传丢了，是客户端**没写出来**。

**根因**（写报告的 `0x5d7b90` → 找模块的 `0x5d7695`）：

```text
005d76a6  VirtualQuery(出错地址, &mbi, 0x1c)      ; 失败 -> 返回 0
005d76b8  edi = mbi.AllocationBase
005d76bf  GetModuleFileNameA(edi, 名字缓冲区, 0x104)  ; 失败 -> 返回 0
005d76cd  eax = [edi+0x3c]                        ; ★ edi == 0 时读空指针
```

出错地址落在**未提交 / 已释放**的页上（= 通过野函数指针 `call` 跳飞，最常见的崩法）
⇒ `AllocationBase == 0`，而 `GetModuleFileNameA(NULL, …)` 按 Win32 语义返回的是
**主模块路径、非 0**，判断被骗过去，`[0+0x3c]` 当场再崩一次。崩在异常过滤器里
⇒ 报告写到一半停住、`MiniDumpWriteDump` 压根没轮到。

**断点是确定的**：报告的最后一行永远是 `Exception code: …\r\r\n`，
因为那之后到 `Fault address:` 之间**只有 `call 0x5d7695` 这一个调用**。
三份线上现场（238 / 268 / 285 字节）全断在这里，一个字节不多。

**顺带第二个毛病**：三个出参（模块名 / 节号 / 节内偏移）原版**从不初始化**，
两条失败路径都直接 return，调用方照样打 ⇒ `4DB8E501 00:00C5022C \x02` 这种栈上垃圾。

**A/B 实证**（本机 2026-09-10，`CreateRemoteThread(起始地址=0)` 造一次 EIP=0 的崩溃）：

| | `LastCrashReport.txt` | `.mdmp` |
|---|---|---|
| `BSHOOK_KEEP_RPT_CRASHES=1`（原版） | **238 字节，断在 `Exception code` 后** | **没生成** |
| 打了补丁 | 982 字节，寄存器 + 完整调用栈齐全 | 12.6 MB 已生成 |

**修**（`hook/bshook.c` `try_patch_crash17_guards()`，偷 `0x5d76b4` 起 7 字节）：
① 先把三个出参填成「不在模块里」的合法值（名字 = 空串、节号 = 0、偏移 = 地址本身），
之后**任何**一条失败路径打出来的都是 `<地址> 00:<地址>`；
② `AllocationBase == 0` 直接走原版失败出口 `0x5d76c9`。

★★ **推论**：那 3 份断头现场 = **出错地址在未映射页** = 通过野指针 call 过去的，
和 §66 那次 `PRIV_INSTRUCTION` 是同一族（跳进堆里执行垃圾 = 特权指令，
跳进未提交页 = 访问违例）。⇒ 5 次线上闪退里 **4 次是同一类**。

## §70 金币 / 经验原来是怎么算的（搬进配置前的基线，2026-09-10）

搬走之前 `gameserver.py` 里那两个纯函数就是全部：

```text
闯关  经验 = int(基数经验 × 系数) + 本局分数 // 20      基数经验 = 20 + 10×(关卡-1)
      金币 = int(基数金币 × 系数)                       基数金币 = 100 + 50×(关卡-1)
      系数 = 难度加成 {1:1.0, 2:1.6, 3:2.5}，没通关再 ×0.3
对战  经验 = 10 + 杀敌×3 + (赢 ? 15 : 0)
      金币 = 30 + (赢 ? 50 : 0)
```

★ **对战八种组合（生存/夺分 × 道具战 × 个人/组队）给的钱一模一样** ——
`pvp_reward(score, seat_cleared)` 只有这两个入参，模式 / 道具 / 队伍一个都没进去。

★ **金币不吃分数 / 杀敌数**（D152），只有经验吃；**地上捡到的金币另加**
（`quest.coins_of(seat)`，在 `send_end_game` 里加，不走公式）。

★ 三个界面数字的落点（`re/packet_api.md` §3.3 / §3.4，协议这次一个字没动）：
`0x0309` 的值 9 = 经验 +N、值 10 = 金币 +N、值 11 = 竞技场分数 +N（本局增量）；
`0x0411` 的 1/2/3 号位是**经验三件套绝对值**、4 号位是本局金币（客户端 `+=`）。

**怎么保证搬家后一分钱不变**：默认表用**同一个表达式**展开
（`shopdefaults.build_rewards()`），`test_shopcfg.RewardDefaultsTests`
把上面这段公式原样抄成第二个实现逐格比对。⚠ 别手抄成数字表：`int()` 向零取整，
`int(150 × 2.5 × 0.3)` = **112 不是 113**。

| 组队战 | `Conn.battle_teams()` 的第二个返回值 | `team_layout == TEAM_LAYOUT_TEAMS` |

★ **中国区玩家只选得到生存(0) 和 夺分(3)**：低等级号选生存还会被客户端自己改回夺分
（`0x465338` / `0x465a2c`，hook 的 `try_patch_player_level_gate` 第 3 / 4 处就是解它）。
⇒ 奖励表只放这两行，剩下两个号由 `gameserver.PVP_MODE_ROW` 按**引擎里的胜负条件**
归档（2 和 0 共用 `SurvivalVictoryCondition` ⇒ 归生存；1 和一切没见过的归夺分）。

★ **天梯房 / 练习房（`session_type` 5 / 6）也走对战那条结算路**
（`quest_mode()` 只认 type 2），它们的 `arguments` 不是对战那套含义 ——
落到 `PVP_MODE_ROW` 的兜底，按夺分那一行发钱。要给天梯单独定价，
得先让描述符把「这是天梯」传下来，别在发钱那一步猜。

★ **平局按「输」算**：尾部数组那一格是 `1` 才是赢，`0`（谁都不判）和 `-1` 都走输那一列。

## §72 等级曲线是我们自己定的，只有一处定义（2026-09-10）

```text
升 L → L+1 需要        = 100 × L                （`EXPERIENCE_STEP`）
到达 L 级的累计经验    = 100 × L × (L-1) / 2 = 50·L·(L-1)
满级                   = 60（`LEVEL_MAX`）      到 60 级累计 177000
```

★ **不是从客户端逆出来的**：客户端只按 `gspEndGame` 下发的三个绝对值
（总经验 / 下一级所需 / 本级起点）做减法画进度条（§94），它不知道曲线长什么样。
60 这个上限倒是**物理的** —— `Images/General/LevelMark.smf` 只有 60 帧，

（原版实际内容只铺到 21 级，`map.ini` 的 `MinLevel` 最高就是 21。）

`experience_for_level(61)` 存在，但只给 `experience_bounds()` 在满级时当
**除法分母**用（两个数一样客户端就要除以 0，那是没验过的行为）——
**别把它当成「还能再升一级」显示出来**（D72a）。

★ 管理页那张参照表照 `account_store.level_table()` 画，**前台不自己套公式**：
曲线只有 `account_store` 一处定义，`test_account_store` 把表和
`experience_for_level` / `level_for_experience` 逐级对死。

## §73 V0.3.0 的服务端升到「多一份配置」这一版，升级路径是干净的（2026-09-10 实测）

线上已经发布过 V0.3.0，那些服务器的 `server/data/` 里只有**四份**配置。
这一版多了 `rewards.json`。**三条路都实测过**（不是读代码推的）：

| 时刻 | 会发生什么 | 靠谁保证 |
|---|---|---|
| 启动、`ensure_files` 之前就有人打完一局 | 照内置默认值发钱（第 7 关困难 = 经验 200 / 金币 1000），日志里一行警告 | `shopcfg._USE_DEFAULT` → `_load` 的 `fallback()` |
| 启动时 `ensure_files()` | **只新建 `rewards.json`**；老四份逐字节没动，运营手改过的价原样在 | 它逐份看 `os.path.exists`，「已存在一律不覆盖」（D7） |
| 回滚到 V0.3.0 那会儿做的备份 | 回滚框那一格**只列备份里真有的四份**，并写「备份里没有 金币 / 经验获取，它保持现状」；回滚下去不报错，现在这份 `rewards.json` 不动 | `databackup.groups_of()` 取的是 `config_filenames() ∩ 备份里有的`；`check_selection` 也按这个交集判 |

★ **协议一个字节没改** ⇒ **老客户端（V0.3.0）连新服务端照常玩**。
`0x0309` 的值 9 / 10 和 `0x0411` 的经验三件套 / `money_gained` 语义全没动，
改的只是「那几个数从哪儿来」。要不要抬版本号是发版的决定，不是兼容性要求。

★ **写盘失败也不拦着开服**：`app.py._report_shop_config` 把 `ensure_files`
包在 try 里；那种情况下奖励表一直读不到，就一直用内置默认值 ——
最坏是「管理页改不了数」，不会是「打完一局一分钱不给」。

★ 两条回归用例钉着，**都不写死文件名**（拿「`_SPECS` / `config_filenames()`
的最后一份」当新加的那份），所以**下次再加第六份配置时自动跟着走**：
`test_shopcfg.test_an_old_data_dir_only_gets_the_files_it_is_missing`、
`test_backup.test_an_old_backup_without_the_newest_config_still_rolls_back`。

## §74 ★★ `$ErrorActionPreference='Stop'` 下，裸奔的 `Stop-Process` 会把「杀不掉一个进程」升格成「整个启动中止」（2026-09-10 玩家实机）

**现场**：玩家跑 `start.bat`，服务端和中继都起来了，最后一句
`[启动失败] Cannot stop process "BigShot (43000)" ... Access is denied.` +
`ProcessCommandException`，游戏没起来。

**这跟执行策略没关系**（第一反应会往那儿想）。`start.bat` 一直带
`-ExecutionPolicy Bypass`；真被策略拦住的话第一行就报「禁止运行脚本」，
屏幕上不会有任何游戏输出。这里的 `Access is denied` 是 Win32 的
`ERROR_ACCESS_DENIED`——拿不到那个进程的 `PROCESS_TERMINATE`。

**放大机制**：`Stop-Process` 的失败本来是**非终止**错误，可以接着往下走；
但 `launch.ps1` 开头是 `$ErrorActionPreference = 'Stop'`，于是它被升格成终止
错误，直接落进 trap → `exit 1`。**全库唯一一处没包 try/catch 的 Stop-Process**，
其余四处（`launch.ps1` 的 `Stop-ListenerOn`、`shutdown.ps1` 两处、
`build-common.ps1`）都包了 ⇒ 是漏网，不是设计。

★ **教训**：本仓库任何 `.ps1` 里的 `Stop-Process` / `Remove-Item` / `Start-Process`
这类「失败很正常」的命令，都必须自己接住错。`$ErrorActionPreference='Stop'`
是个**全局**开关，它把「这一步没成」和「这次跑不下去了」变成了同一件事。

**「拒绝访问」有四种来源，脚本判断不了，只能把事实摆给玩家**：
① 残留进程是提权跑的而当前不是；② 属于另一个用户账户；③ 安全软件拦着；
④ GameGuard 驱动在保护它（玩家点了开始菜单那份**只读原版**的快捷方式——
`Get-Process BigShot` 是按**进程名**匹配的，原版那个 exe 也叫 BigShot，会被
一起捞进来；而铁律 2 的自检只看 `game_patched\GameGuard.des`，管不到玩家
自己那份原版）。分辨这四种的事实只有两个：**进程属主 + exe 完整路径**。
⇒ `wincompat.ps1` 加了 `Format-ProcessIdentityText`。

★ 拿属主/路径**别用 `$proc.Path`**：那个访问器走 `MainModule`，要
`PROCESS_QUERY_INFORMATION | VM_READ`——「进程提权了而我们没提权」时它自己
就抛「拒绝访问」，**而那恰恰是唯一需要它的场景**。`Get-WmiObject Win32_Process`
的 `ExecutablePath` / `GetOwner()` 走 WMI（服务是 SYSTEM 在跑），同样的场景
读得到。（`Get-CimInstance` 是 PowerShell 3.0 才有的，Win7 上没有。）

★ **别把「用管理员身份运行 start.bat」当解法**：情况 ③④ 根本不管用
（GameGuard 是内核层剥权限，SYSTEM 一样被拒）；就算是情况 ①，提权拉起来的
新 BigShot **也是管理员权限的**，玩家下次正常启动照样卡在这儿——
等于把毛病焊死，从此必须一直提权跑。正确的解法是**用管理员的任务管理器
结束那个进程**（不改变新游戏的权限级别），再正常启动；再不行重启电脑。

**判据用「还在不在」，不是「Stop-Process 报没报错」**：报了错却自己退了、
没报错但还在，两种都见得到。杀完等的是 `WaitForExit()` 这个**事件**
（`Stop-Process` 只是发出终止请求就返回，互斥体那会儿可能还没放），
上面那个 10 秒不是判据、是防挂死的兜底，真正的判据是重新 `Get-Process` 复核。
