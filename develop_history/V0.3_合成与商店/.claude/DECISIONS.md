# V0.3 后半 DECISIONS —— 为什么这么选

**编号从 D1 起**，和 V0.1 / V0.2 / V0.3bot 相互独立。引用旧版一律写全「V0.2 D103」。

**只记「为什么」，不记「是什么」**（「是什么」在 FINDINGS 和代码注释里）。
一条选择一节，写清**被否掉的方案**和**否掉的理由** —— 那才是防止后人推翻的东西。

---

## D1 · 只做**原生游戏内 UI**，不做网页商店（用户 2026-09-03 拍板）

**选**：商店 / 合成 / 仓库全部走客户端原版的 `ShopStage`，
服务端逆通 `0x05xx` / `0x06xx` / `0x0704` 那一套包。

**否掉的方案**：① 网页商店（玩家在浏览器里买 / 合成 / 装备，游戏内靠 `0x030b` 生效）；
② 先网页保底、再攻原生。

**理由**：这是**复活工程**，原版界面本来就完整存在（`ShopStage` 跳表覆盖
`0x0500..0x050c`，进商店会连发四个请求），只是从没被喂过数据。
用网页替代等于把原版最完整的一块 UI 扔掉，体验出戏。

**代价（要认）**：整套协议**一发都没在线上观测过**，全是静态反汇编结论，
其中「货架目录到底走哪个 opcode」还有残余不确定（FINDINGS §4）。
⇒ **M4 是一个 spike，必须尽早跑**；走不通要**停下来找用户重新拍板，不要硬凑**。

---

## D2 · 合成配方**自己设计**，存 `recipe.json`，管理页可改（用户 2026-09-03 拍板）

**选**：我按原版材料的主题和稀有度分档设计初稿（珠子=基础 / 铁矿石·水管·青铜管=中级 /
不死鸟之羽泪·太阳碎片·龙之泪=高级），产物优先用原版**「有图标但没上架」**的那批装备
（FINDINGS §7）。全部写进 `server/data/recipe.json`，用户在 `/admin` 里随时改。

**否掉的方案**：① 极简统一规则（一律「N 颗珠子 + 金币 = 一件装备」）——
没有原版味道；② 等用户提供配方 —— 用户明说「你先设计，我试用后再调」。

**理由**：原版配方随 2009 年停服的服务端 DB 一起消失，客户端里**彻底不存在**
（找过的地方见 FINDINGS §7，别再找第二遍）。既然只能造，就造得**可改**：
配方是玩法平衡参数，第一版一定不对，重点是让用户改起来不用改代码、不用重启。

**约束**：一条配方**最多 4 种材料**（合成界面只有 4 个槽），**没有成功率**
（原版 UI 上没有任何概率控件）—— 这两条是原版事实，不是我们的选择（铁律 12）。

## D3 · 管理员密码**明文**，和玩家账号一个口径（用户 2026-09-03 拍板）

**选**：`accounts.json` 顶层 `admin_accounts` 段存明文密码，
初始 `admin` / `Admin123`。

**否掉的方案**：PBKDF2 哈希（标准库 `hashlib.pbkdf2_hmac`，零依赖）。
我推荐过这条，用户选了明文。

**理由（用户的）**：和铁律 9 一致，且可以**直接手改 JSON 改密码**。

**⇒ 必须做的补偿**（因为管理页公网可达 + 弱默认密码）：
① 登录**按 IP 限速**（照 `RegisterRateLimiter`）；
② 页面上明确提示「**请立刻改掉默认密码**」；
③ 日志里**不要打印密码**（铁律 9）。

---

## D4 · 材料掉落 = **原版基线 + 可配置扩展表**（用户 2026-09-03 拍板）

**选**：`drops.json` 里既有原版 `Promotion.ini` 的 4 条固定奖励
（Lv15/19/26 青铜管、Lv24 浮游石），也有我们加的扩展
（任务模式按关卡+难度掉珠子，难度越高越好；对战模式给少量）。
**扩展表也要能在管理页里改**（用户特别要求）。

**否掉的方案**：① 严格照原版 —— 只有 4 关掉 2 种材料，合成系统几乎转不起来；
② 全任务必掉、掉率给高 —— 好测试但破坏平衡。

**理由**：原版珠子类材料主要来自**对战模式**（FINDINGS §9），
但用户的记忆和期望是「打任务掉材料」，而且任务模式是现在唯一稳定跑得通的 PVE 内容。
折中就是「基线忠实 + 扩展可调」，把平衡权交给用户而不是写死在代码里。

---

## D5 · 存档新字段走「**读盘时按默认值补齐**」，**不动 `schema_version`**

**选**：把 `inventory` / `equipped` / `materials` 加进 `NEW_ACCOUNT_DEFAULTS`，
靠现成的 `_merged_account()` 在每次读写时自动补齐；
另加一个**幂等**的 `ensure_item_fields()` 在启动时跑一遍（照 `realign_levels()`）。

**否掉的方案**：写一个「版本号驱动的 migration」（`if schema_version < 3: ...`）。

**理由**：① 本仓库现有的设计就是 defaults-merge，加 migration 等于引入第二套机制；
② **版本号驱动的迁移只跑一次，跑坏了没有第二次机会**；defaults-merge 是
「每次读都补」，**天然幂等**，反复启动不会破坏也不会回滚数据（铁律 11）。
`realign_levels()` 的自述就是这个道理：「幂等，所以每次启动都可以跑，不需要 schema 版本号」。

**⇒ 启动时的补齐必须做到「没有账号需要改时不写盘」**，否则每次启动都重写
生产数据，白白增加写坏的机会。

---

## D6 · `equipped` 存 **itemId 列表**，不存「部位 → itemId」字典

**选**：`"equipped": [1010015, 1120041]`。服务端保证列表内两两 `part_flag`
按位与为 0（不冲突）。

**否掉的方案**：`{"1": 1010015, "1024": 1120041}`（PartFlag 当键）。

**理由**：`0x030b` 的线格式本来就是「一个 itemId 列表」（FINDINGS §1），
客户端拿它直接建 `EquipmentEx`。存成字典就要在每次下发时拼回列表，
多一层无意义的转换；而且**套装的 `PartFlag` 是组合值**（1+2+4+8+16=31 全身），
字典模型下一件套装要占好几个键，反而更难维护。
按位与为 0 这一条规则同时覆盖单件和套装。

## D7 · 三份配置放 `server/data/`，**不进 git**，首次启动自动生成

**选**：`server/data/{shop,recipe,drops}.json` —— 和 `accounts.json` 同目录，
`.gitignore` 排除，服务端启动时不存在才从内置 `DEFAULT_*` 生成，
**已存在一律不覆盖**。打包只建空目录（现状）。

**否掉的方案**：放 `server/` 根（和 `bot_weapons.json` 同级）随包发布。

**理由**：用户明确要求 `server/data/shop.json` 这个路径，而且它们是
**用户会手改的运行时状态**，语义上和 `accounts.json` 是一类，不是随包发布的产物。
随包发布的后果是**每次升级都会覆盖用户手改的价格和配方** —— 这正是要避免的。

**⚠ `.gitignore` 里的规则是逐文件写的**（`/server/data/accounts.json`），
不是整个目录 ⇒ **三份新 json 必须各补一行**，否则会被 git 追踪。

**对照**：`server/shop_items.json`（从原版 ini 提取的**只读镜像**）是产物，
**要进 git、要进包**，和这三份是两回事。

---

## D8 · 装备的属性数值**照原版不动**，我们只决定「谁能拿到哪件」

**选**：`EquipBonus.ini` 的 633 条加成原样用，商店 / 合成只控制
「上不上架、卖多少钱、要什么材料」。

**否掉的方案**：调整装备数值让手感更好。

**理由**：加成表在**客户端 pak 里**，客户端启动时自己读（FINDINGS §1）。
改它要重打客户端包 + 走更新器分发，**服务端无论如何下发不了**
（`SetEquipBonusFunction` 全 exe 只有一个调用点，来自 INI 解析器，没有网络路径）。
⇒ 这不是「我们选择不改」，而是**改不了**。真要改时先实测「散文件能否覆盖 pak」。

**同理，这三条也是既成事实，不是 bug**（写进 PLAN，防止以后当 bug 查）：
攻防加成**只有 15% 概率触发**；**换弹速度不受装备加成影响**（只能换武器）；
HP/SP 是加法、攻防移速是百分比。

## D9 · 三份配置的默认内容**程序化生成**，不写死几百行字面量

**选**：`shopcfg.default_shop()` / `default_recipes()` / `default_drops()` 从
`shop_items.json` **算**出来（价格按级别档、配方按套装 × 加成大小缩放、
掉落按难度分档），只有一张「韩文名 → 中文名」的小表是手写的。

**否掉的方案**：把 141 件商品 + 35 条配方直接写成 Python 字面量。

**理由**：① 手写 141 条一定会和原版数据脱节（比如中文版砍掉的那 18 件武器，
手写时很容易漏掉）；② 生成逻辑本身就是**设计意图的表达** ——
「1/2/3 级卖 3000/8000/18000」比 63 行价格表更容易看懂也更容易改；
③ 生成只在**文件不存在时跑一次**，之后用户改的是 JSON，代码怎么写不影响他。

★ 配套的护栏：`test_every_recipe_material_can_actually_drop` ——
**配方要的每一种材料都必须有掉落规则**。会话 01 就是被它抓出来的：
配方要铁矿石 / 水管 / 不死鸟之羽，掉落表里只有珠子和青铜管，
那三条产线永远合不出来。生成式默认值最容易犯的就是这种「两张表各自对、
合起来不成立」的错，所以这条断言必须留着。

---

## D10 · 配置读坏了**保留上一份好的、绝不回写**

**选**：`shopcfg._load()` 遇到 JSON 解析失败或校验不过时：
① 有上一份好的 → 用它，只记警告；② 一次都没读成功过 → 返回**空目录**；
③ **任何情况下都不写文件**。生成只发生在 `ensure_files()` 那一次。

**否掉的方案**：① 读坏了就退回**内置默认值** —— 「商店突然多出一堆用户
没上架的东西」比「商店空着」难查十倍，而且会掩盖「用户的文件坏了」这个事实；
② 读坏了自动修复并回写 —— 用户很可能**正编辑到一半**，回写等于把他没存完的
内容盖掉。

**理由**：这三份是用户随时手改的运营数据，热重载意味着**每次读都可能撞上
半个文件**。判据是「哪种失败模式最好查」：空商店一眼看得出来，
日志里还有具体是哪一行不对。
