# V0.3 后半 DECISIONS —— 为什么这么选

**编号从 D1 起**，和 V0.1 / V0.2 / V0.3bot 相互独立。引用旧版一律写全「V0.2 D103」。

**只记「为什么」，不记「是什么」**（「是什么」在 FINDINGS 和代码注释里）。
一条选择一节，写清**被否掉的方案**和**否掉的理由** —— 那才是防止后人推翻的东西。

---

## D1 · 只做**原生游戏内 UI**，不做网页商店（用户 2026-09-03 拍板）

**选**：商店 / 合成 / 仓库全部走客户端原版的 `ShopStage`，
服务端逆通 `0x05xx` / `0x06xx` / `0x0704` 那一套包。

**否掉的方案**：① 网页商店（玩家在浏览器里买 / 合成 / 装备，游戏内靠 `0x030b` 生效）；
② 先网页保底、再攻原生。

**理由**：这是**复活工程**，原版界面本来就完整存在（`ShopStage` 跳表覆盖
`0x0500..0x050c`，进商店会连发四个请求），只是从没被喂过数据。
用网页替代等于把原版最完整的一块 UI 扔掉，体验出戏。

**代价（要认）**：整套协议**一发都没在线上观测过**，全是静态反汇编结论，
其中「货架目录到底走哪个 opcode」还有残余不确定（FINDINGS §4）。
⇒ **M4 是一个 spike，必须尽早跑**；走不通要**停下来找用户重新拍板，不要硬凑**。

---

## D2 · 合成配方**自己设计**，存 `recipe.json`，管理页可改（用户 2026-09-03 拍板）

**选**：我按原版材料的主题和稀有度分档设计初稿（珠子=基础 / 铁矿石·水管·青铜管=中级 /
不死鸟之羽泪·太阳碎片·龙之泪=高级），产物优先用原版**「有图标但没上架」**的那批装备
（FINDINGS §7）。全部写进 `server/data/recipe.json`，用户在 `/admin` 里随时改。

**否掉的方案**：① 极简统一规则（一律「N 颗珠子 + 金币 = 一件装备」）——
没有原版味道；② 等用户提供配方 —— 用户明说「你先设计，我试用后再调」。

**理由**：原版配方随 2009 年停服的服务端 DB 一起消失，客户端里**彻底不存在**
（找过的地方见 FINDINGS §7，别再找第二遍）。既然只能造，就造得**可改**：
配方是玩法平衡参数，第一版一定不对，重点是让用户改起来不用改代码、不用重启。

**约束**：一条配方**最多 4 种材料**（合成界面只有 4 个槽），**没有成功率**
（原版 UI 上没有任何概率控件）—— 这两条是原版事实，不是我们的选择（铁律 12）。

## D3 · 管理员密码**明文**，和玩家账号一个口径（用户 2026-09-03 拍板）

**选**：`accounts.json` 顶层 `admin_accounts` 段存明文密码，
初始 `admin` / `Admin123`。

**否掉的方案**：PBKDF2 哈希（标准库 `hashlib.pbkdf2_hmac`，零依赖）。
我推荐过这条，用户选了明文。

**理由（用户的）**：和铁律 9 一致，且可以**直接手改 JSON 改密码**。

**⇒ 必须做的补偿**（因为管理页公网可达 + 弱默认密码）：
① 登录**按 IP 限速**（照 `RegisterRateLimiter`）；
② 页面上明确提示「**请立刻改掉默认密码**」；
③ 日志里**不要打印密码**（铁律 9）。

## D4 · 材料掉落 = **原版基线 + 可配置扩展表**（用户 2026-09-03 拍板）

**选**：`drops.json` 里既有原版 `Promotion.ini` 的 4 条固定奖励
（Lv15/19/26 青铜管、Lv24 浮游石），也有我们加的扩展
（任务模式按关卡+难度掉珠子，难度越高越好；对战模式给少量）。
**扩展表也要能在管理页里改**（用户特别要求）。

**否掉的方案**：① 严格照原版 —— 只有 4 关掉 2 种材料，合成系统几乎转不起来；
② 全任务必掉、掉率给高 —— 好测试但破坏平衡。

**理由**：原版珠子类材料主要来自**对战模式**（FINDINGS §9），
但用户的记忆和期望是「打任务掉材料」，而且任务模式是现在唯一稳定跑得通的 PVE 内容。
折中就是「基线忠实 + 扩展可调」，把平衡权交给用户而不是写死在代码里。

---

## D5 · 存档新字段走「**读盘时按默认值补齐**」，**不动 `schema_version`**

**选**：把 `inventory` / `equipped` / `materials` 加进 `NEW_ACCOUNT_DEFAULTS`，
靠现成的 `_merged_account()` 在每次读写时自动补齐；
另加一个**幂等**的 `ensure_item_fields()` 在启动时跑一遍（照 `realign_levels()`）。

**否掉的方案**：写一个「版本号驱动的 migration」（`if schema_version < 3: ...`）。

**理由**：① 本仓库现有的设计就是 defaults-merge，加 migration 等于引入第二套机制；
② **版本号驱动的迁移只跑一次，跑坏了没有第二次机会**；defaults-merge 是
「每次读都补」，**天然幂等**，反复启动不会破坏也不会回滚数据（铁律 11）。
`realign_levels()` 的自述就是这个道理：「幂等，所以每次启动都可以跑，不需要 schema 版本号」。

**⇒ 启动时的补齐必须做到「没有账号需要改时不写盘」**，否则每次启动都重写
生产数据，白白增加写坏的机会。

---

## D6 · `equipped` 存 **itemId 列表**，不存「部位 → itemId」字典

**选**：`"equipped": [1010015, 1120041]`。服务端保证列表内两两 `part_flag`
按位与为 0（不冲突）。

**否掉的方案**：`{"1": 1010015, "1024": 1120041}`（PartFlag 当键）。

**理由**：`0x030b` 的线格式本来就是「一个 itemId 列表」（FINDINGS §1），
客户端拿它直接建 `EquipmentEx`。存成字典就要在每次下发时拼回列表，
多一层无意义的转换；而且**套装的 `PartFlag` 是组合值**（1+2+4+8+16=31 全身），
字典模型下一件套装要占好几个键，反而更难维护。
按位与为 0 这一条规则同时覆盖单件和套装。

## D7 · 三份配置放 `server/data/`，**不进 git**，首次启动自动生成

**选**：`server/data/{shop,recipe,drops}.json` —— 和 `accounts.json` 同目录，
`.gitignore` 排除，服务端启动时不存在才从内置 `DEFAULT_*` 生成，
**已存在一律不覆盖**。打包只建空目录（现状）。

**否掉的方案**：放 `server/` 根（和 `bot_weapons.json` 同级）随包发布。

**理由**：用户明确要求 `server/data/shop.json` 这个路径，而且它们是
**用户会手改的运行时状态**，语义上和 `accounts.json` 是一类，不是随包发布的产物。
随包发布的后果是**每次升级都会覆盖用户手改的价格和配方** —— 这正是要避免的。

**⚠ `.gitignore` 里的规则是逐文件写的**（`/server/data/accounts.json`），
不是整个目录 ⇒ **三份新 json 必须各补一行**，否则会被 git 追踪。

**对照**：`server/shop_items.json`（从原版 ini 提取的**只读镜像**）是产物，
**要进 git、要进包**，和这三份是两回事。

## D8 · 装备的属性数值**照原版不动**，我们只决定「谁能拿到哪件」

**选**：`EquipBonus.ini` 的 633 条加成原样用，商店 / 合成只控制
「上不上架、卖多少钱、要什么材料」。

**否掉的方案**：调整装备数值让手感更好。

**理由**：加成表在**客户端 pak 里**，客户端启动时自己读（FINDINGS §1）。
改它要重打客户端包 + 走更新器分发，**服务端无论如何下发不了**
（`SetEquipBonusFunction` 全 exe 只有一个调用点，来自 INI 解析器，没有网络路径）。
⇒ 这不是「我们选择不改」，而是**改不了**。真要改时先实测「散文件能否覆盖 pak」。

**同理，这三条也是既成事实，不是 bug**（写进 PLAN，防止以后当 bug 查）：
攻防加成**只有 15% 概率触发**；**换弹速度不受装备加成影响**（只能换武器）；
HP/SP 是加法、攻防移速是百分比。

## D9 · 三份配置的默认内容**程序化生成**，不写死几百行字面量

**选**：`shopcfg.default_shop()` / `default_recipes()` / `default_drops()` 从
`shop_items.json` **算**出来（价格按级别档、配方按套装 × 加成大小缩放、
掉落按难度分档），只有一张「韩文名 → 中文名」的小表是手写的。

**否掉的方案**：把 141 件商品 + 35 条配方直接写成 Python 字面量。

**理由**：① 手写 141 条一定会和原版数据脱节（比如中文版砍掉的那 18 件武器，
手写时很容易漏掉）；② 生成逻辑本身就是**设计意图的表达** ——
「1/2/3 级卖 3000/8000/18000」比 63 行价格表更容易看懂也更容易改；
③ 生成只在**文件不存在时跑一次**，之后用户改的是 JSON，代码怎么写不影响他。

★ 配套的护栏：`test_every_recipe_material_can_actually_drop` ——
**配方要的每一种材料都必须有掉落规则**。会话 01 就是被它抓出来的：
配方要铁矿石 / 水管 / 不死鸟之羽，掉落表里只有珠子和青铜管，
那三条产线永远合不出来。生成式默认值最容易犯的就是这种「两张表各自对、
合起来不成立」的错，所以这条断言必须留着。

## D10 · 配置读坏了**保留上一份好的、绝不回写**

**选**：`shopcfg._load()` 遇到 JSON 解析失败或校验不过时：
① 有上一份好的 → 用它，只记警告；② 一次都没读成功过 → 返回**空目录**；
③ **任何情况下都不写文件**。生成只发生在 `ensure_files()` 那一次。

**否掉的方案**：① 读坏了就退回**内置默认值** —— 「商店突然多出一堆用户
没上架的东西」比「商店空着」难查十倍，而且会掩盖「用户的文件坏了」这个事实；
② 读坏了自动修复并回写 —— 用户很可能**正编辑到一半**，回写等于把他没存完的
内容盖掉。

**理由**：这三份是用户随时手改的运营数据，热重载意味着**每次读都可能撞上
半个文件**。判据是「哪种失败模式最好查」：空商店一眼看得出来，
日志里还有具体是哪一行不对。

---

## D11 · `materials` 和 `inventory` 分两张表，不合成一个背包

**选**：存档里 `inventory`（`{id: {count, expires}}`）和
`materials`（`{id: count}`）各是一个字典。

**否掉的方案**：一张统一背包表，靠 `shopdata.kind()` 区分是不是材料。

**理由**：客户端就是分开的 —— 材料只出现在**结算界面那一栏**（`0x041c`，§3）
和**合成界面的材料槽**里，装备只出现在**仓库和 `0x030b`** 里，两条链一次都不交叉。
合成一张表以后，每个下发点都要先按 `kind` 过滤一遍，等于把客户端的区分
重新在服务端实现一遍，还多一次「过滤漏了」的机会。

**代价**：万一以后原版有「既是材料又能装备」的东西，要挪。查过了：没有
—— 材料的 `PartFlag` 全是 0（§8）。

---

## D12 · 「id 客户端不认识」时，`add_item` **抛**、`add_materials` **跳过**

**选**：两个入口对同一件事故意给两种反应。

**理由**：判据不是「哪个更严格」，而是**各自调用点的失败模式哪个更好查**。

- `add_item` 的调用点是**买 / 合成** —— 玩家主动发起的单笔交易，请求处理器
  本来就要回一个失败码。静默跳过会变成「钱扣了东西没有」，是最难查的那种账。
- `add_materials` 的调用点是**结算发奖**，规则来自用户手改的 `drops.json`。
  抛异常会把整局的 `gspEndGame` 打掉，玩家看到的是「卡在结算界面」——
  比少拿一个青铜管难查十倍。所以它跳过、把跳过的 id 原样返回，由调用方打日志。

**⇒ 一条通则**：入口的严格程度跟着**调用点**走，不跟着「这个函数应该多严」走。

---

## D13 · `admin_accounts`：**键不在**才建默认管理员；空字典不碰；坏了不自动修

**选**：`ensure_item_fields()` 里分三种情况 ——
① 键不存在 → 建 `admin` / `Admin123`（全新装 / 老存档升上来）；
② 键在但是 `{}` → **什么都不做**；③ 键在但不是对象 → **报警，绝不覆盖**。

**否掉的方案**：① 「一个管理员都没有就补一个」—— 那 `{}` 就永远回不去了；
② 坏了就重建成默认值 —— 那一格里可能还留着用户自己加的管理员。

**理由**：`{}` 和「键不在」是**两个不同的事实**，不是同一件事的两种写法
（铁律 10 的同一个道理：判据要来自能区分两种情况的那个事实）。
`{}` 唯一可能的来源是用户自己删空的 ⇒ 那是「我不要管理页」的意思，
再塞一个弱口令账号回去是帮倒忙。

坏了不自动修同 D10：**判据是哪种失败模式最好查**。「谁都登不进 /admin，
启动日志里有一行说它坏在哪」一眼看得出来，玩家一点感觉都没有；
自动覆盖则会**无声地**吃掉用户加的管理员。

**⇒ 配套**：`admin_names()` / `admin_verify()` 对坏表**容错**（当成一个都没有，
不抛异常，别让运维功能把游戏服拖住，铁律 11）；
但 `admin_add / set_password / remove` 一律拒绝（`admin_table_broken`）。

## D14 · 管理页的配置编辑器是**一个 JSON 文本框**，不是一堆表单

> ⚠ **已被 D16 取代**（2026-09-04，用户嫌烦）。下面这一节留着不删 ——
> 它写明的那条退路正是 D16 走的路，「代价（要认）」那一段也应验了。

**选**：`/admin` 里三个标签页各是一个 `<textarea>`，直接改 `shop.json` /
`recipe.json` / `drops.json` 的原文；**保存前服务端跑 `shopcfg.validate_*`，
不过就不落盘**，错误信息（JSON 语法错的行号列号 / 「第 3 条配方有 5 种材料」）
原样回给页面。另配一个「物品速查」按 itemId 查名字和槽位。

**否掉的方案**：① 给 141 件商品 / 35 条配方 / 24 条掉落各做一套增删改表单；
② 只读展示 + 让用户继续 SSH 上去改文件。

**理由**：**真正的护栏是存盘前那一道校验**，它在服务端，前台长什么样都绕不过去。
表单化要写三套 CRUD + 分页 + 排序，而这三份文件**本来就是设计成给人手改的**
（D7：它们和 `accounts.json` 同目录、同性质），用户已经在记事本里改过了 ——
把同一件事搬到浏览器里、再加上「校验 + 即刻生效 + 不用 SSH」，收益的大头已经拿到。

**代价（要认）**：改一个价格要在几百行 JSON 里找。**如果用户后来嫌烦，
再加表单也不用动服务端** —— 那一层是 `POST /admin/api/config/{name}` +
`validate_*`，表单化只是换一个前台生成同样的 JSON。

**⇒ 配套（都已做）**：以 `_` 开头的键（`_说明`）保存后原样保留，
因为存的是**解析后的对象**而不是校验器的输出；读的时候把
`shopcfg` 的警告一起回给页面 —— 文件坏了服务端会**继续用上一份好的**（D10），
不说的话用户会以为自己刚存的那份已经生效了。

---

## D15 · 管理页登录限速「只记**失败**」—— 和注册限速的极性相反

**选**：`web/admin.LoginRateLimiter` 在**登录失败**时锁住那个 IP（5 秒），
登录**成功**时把处罚清掉。

**否掉的方案**：照抄 `RegisterRateLimiter`（那个是「只有**成功**才记一笔」）。

**理由**：两个限速器防的是两件事。批量注册的脚本要的是**成功**，
锁成功那一侧就够，而且「打错一个字就罚等一分钟」会把正常玩家挡在门外；
爆破口令靠的是**海量失败**，锁失败那一侧才拦得住，
而输对了的人不该被自己上一次的手滑挡住 —— 所以成功要**清零**。

★ 铁律 10 说「禁止固定时间的阈值」，**这里是它明说的那个例外**：
对面是个不会通知我们的攻击者，物理上没有任何事件可等。
代码注释里写清了这一点，别当成漏网之鱼去「修」。

**⇒ 相关**：会话令牌用 `secrets` 不是 `random`（那是认证凭据）；
改口令 / 删账号之后要把那个人**已有的会话全部作废**（`drop_admin`），
否则「我把他删了」和「他还在操作」会同时成立。

---

## D16 · 管理页改成**结构化表单**，JSON 原文彻底去掉（用户 2026-09-04 拍板）

**选**：`/admin` 里三份运营配置各自画成一套控件 —— 商店是卡片网格、配方是
「4 个材料槽 ➜ 产物」的配方卡、掉落是一行一条规则；每个物品都带**图标**；
**页面上再也看不到 JSON 原文**，连折叠的兜底都不留。

**否掉的方案**：① 保留 D14 那三个 `<textarea>`；② 表单为主、底下折叠一个
「高级：直接编辑 JSON」。

**理由**：用户的原话是「直接编辑 json 容易出错，全都用 UI 改」。留一个 JSON
入口就等于留了一条**绕过所有前台约束**的路（比如手写第 5 种材料、写一个
客户端不认识的 id），而这些约束正是表单存在的意义。真正的护栏
（`shopcfg.validate_*`，存盘前不过就不落盘）**一个字都没动** ——
D14 早就写明「表单化只是换一个前台生成同样的 JSON，服务端不用动」，
这次就是兑现它。

**⇒ 三条配套（都是用户当场提的，别顺手改回去）**：

1. **`_说明` 从 json 里搬到页面上**。那几句话本来是写给**手改 json 的人**看的；
   唯一入口变成网页之后，它们的位置就是面板顶上那个说明框

## D20 · 物品定义（`0x0501`）**跟着每一份 id 清单主动发**，不等客户端来问

**背景**：客户端的 `ItemInfo` 表开机是空的，只有 `0x0501` 能填（§28）。
它自己有一套「查不到就发 `0x0601` 问」的机制，理论上服务端只答问就够了。

**选**：既答问，**也在每一发带 id 的下行包（`0x0500` 货架 / `0x0604` 穿着 /
`0x0601` 持有物）前面主动补一发 `0x0501`**。

**理由**是两条**界面在「问」的那一轮里会走坏路径**：

1. `0x0604` 的处理器一旦发现有不认识的 id，就**跳过界面刷新**直接去问
   （`0x44738d` -> `0x447406`）—— 左侧人物模型这一帧不画。要等定义回来、
   而且用途标志正好是 `2`，`0x44602a` 才补画。中间那一段空窗就是用户报的
   「进商店左边没有角色，点个商品加购物车才出来」。
2. 仓库面板是在收到 `0x0601` 的**那一刻**建的（`0x446f8a`）。那时表还空着
   就建成空的，之后补发的定义（标志位是 1，不是 2）**不会让它再刷一次**。

⇒ 「先喂定义再发清单」把这两条路径都变成一次成型。答问那条路**照样留着**
（客户端问过的 id 会被记成「已请求」，不答就永远不再问），当兜底。

**代价**：同一批定义可能重复发。可以接受 —— 一页 8 件的定义 ~500 字节，
而客户端那边 `map::insert` 撞 key 是无操作。**不做「已发过就不发」的缓存**：
那要在连接上维护一份状态，一旦和客户端的实际表对不上（重连、换 stage），
就变成「界面空着而且再也不会好」，比多发几百字节难查得多。

## D25 · 顶栏 + 标签行整块 `position: sticky`

**背景**：用户 2026-09-05：「标签按钮那一行以及以上的内容都作为 header
一直可见，往下滚时只有标签行下面的部分跟着滚」。

**决定**：把 `<nav class="tabs">` 从 `<main>` 里搬出来，和 `<header class="topbar">`
一起装进一个 `.appbar`，整块 `position: sticky; top: 0; z-index: 40`。

**为什么两者必须在同一个 sticky 容器里**：只给 `.tabs` 加 sticky 的话，

⚠ **`sticky` 的前提是祖先里没有 `overflow` 不是 `visible` 的元素** ——
`body` / `main` 现在都没设，以后别顺手加（加了 sticky 会静默失效，
没有任何报错）。

**z-index**：`.appbar` 是 40，物品选择器那个 `.modal` 是 50 —— 弹窗要盖住顶栏。

**标签行的显隐**：它不在 `#mainView` 里了，所以 `showLoggedIn` /
`showLoggedOut` 要**单独**开关它一次，否则未登录时登录框上面会挂一排标签。

## D26 · 管理页的物品浮窗**复用游戏里那段说明**，`desc` 随 catalog 一起发

**背景**：用户 2026-09-05：「选择物品后想看这个物品的详细加成，现在不方便看。

`ShopStock+0x18`，§31③）。两边同一个函数 ⇒ 不可能出现「网页说伤害 4、
游戏里说 5」。

`renderCurrent()` 都整片重建，逐个挂监听器会漏。这样以后新画面只要给格子

**挂在哪**：`slotNode()` 的图标格（商店卡片 / 配方产物 / 材料格 / 掉落规则 /

**z-index 60**：要盖住 sticky 顶栏（40）和物品选择器弹窗（50）——

**回归护栏**：`test_items_carry_the_same_description_the_game_shows`

## D29 · 管理页会话：**滑动 1 小时**，cookie 的寿命和它脱钩

**选**（用户 2026-09-05 拍板）：`SESSION_TTL_SECONDS = 3600`，
`AdminSessions.resolve()` **每认出一次令牌就把到期时刻推到「现在 + 1 小时」**
⇒ 一直在操作就永远不掉线，撂下一小时不动才登出。
cookie 的 `Max-Age` 单独用 `SESSION_COOKIE_MAX_AGE = 7 天`。

**为什么 cookie 不能也写 1 小时**：浏览器不知道服务端在滑动。写 1 小时的话
「登录后连续操作两小时」到第 60 分钟浏览器会自己把 cookie 删掉 ——
明明一直在用却被踢出去，正好和用户要的相反。cookie 只负责
**「关掉页面别消失」**（用户要的「一小时内重新打开跳过登录页」靠的就是它
是**持久** cookie 而不是会话 cookie），真正说了算的是服务端那份到期时刻。
cookie 活得比会话久没有风险：令牌一过期，服务端认不出来就是没登录。

**否掉的方案**：前台定时发心跳续期 —— 那会让「页面开着不动」也永不登出，
和「撂下一小时就登出」直接冲突。**判据就该是请求本身**（有请求 = 有人在操作），
不需要额外造一个事件。

**没做的**：会话仍然**只在内存里**，服务端一重启全部失效（V0.2 D097 的口径）。
用户报的「放久了自动退出」，当天的真实原因八成是我重启了两次服务端，
而不是 8 小时的 TTL 到了。要让会话扛住重启就得把令牌落盘 —— 那是另一个
决定（安全口径变了），等用户明说再做。

## D30 · 配置的「补齐」是**单独一条命令**，不是启动时自动做

**选**：`shopcfg.backfill_defaults()` —— 把默认表里有、现有 `shop.json` /

### D31a · **角色限定改成只读，照原版**（用户 2026-09-06）

**用户报的症状**：在管理页上把某件角色限定装备改宽，进游戏用别的角色穿上去，

## D36 · 管理页保存改成**三方合并**，不是整份覆盖（用户 2026-09-06 拍板）

**选**：`POST /admin/api/config/{which}` 多带一个 `base`（我打开这一页时服务端
给我的那份原文）。服务端拿 `base` / `mine` / **此刻磁盘上那份** 做三方合并
（新模块 `cfgmerge`）：改的不是同一条 ⇒ 直接合并、不提示；改的是同一条 ⇒
**一个字节都不写**，回冲突清单让运营决定要不要「单独提交未冲突的」。

**否掉的方案**：① 整份文件加一个版本号 / mtime，对不上就整份拒收 ——
「另一个人改了别的东西」也会把我挡回去，一个人改配置时另一个人就别想存；
② 前台自己合并 —— 前台手里没有磁盘上的最新那份，它连「别人改过」都不知道。

**三条关键取舍**：

1. **身份不按下标，按自然键**（`items`/`shop` 用 `id`，`recipe` 用配方号，
   `drops` 用 `(模式·关卡·难度·材料)` 四元组 + 同键出现序）。别人在前面插一条，
   按下标配对的话我的每一条都会错位。`drops` 是唯一没有天然主键的一份，
   四元组是用户 2026-09-06 拍板的口径。
2. **商店 ⇄ 合成互斥也算冲突**，而且**只能由服务端判**：我在商店上架 X 的同时
   另一个人在合成上架 X —— 我手上那份 `recipe` 副本是旧的，前台的
   `listingClash()` 根本看不见。所以保存 shop/recipe 时再带一个 `cross_base`。
   ★ 和 D33 分工：前台那道管「**我自己**两边都勾了」（弹框、自动下架另一边），
   服务端这道管「**对方**刚把它在另一边上架了」（算冲突、不写）。
   判据取**窄口径**（我这次让它上架的 ∩ 对方这次让它上架的）—— 「我 base 里
   本来就上着架、这次没动它」不该拦我保存别的东西。
3. **「单独提交未冲突的」那一轮要重新判一遍**（用户明确要求）：从我按下确定
   到这一发落地之间，第三个人可能刚好也改了同一条。所以第二轮带的是
   `only=[身份…]` + **同一个 base**，服务端重新读磁盘重新算。

**顺带**：保存成功后回**落盘后的整份内容**，前台当场换上去 ⇒ 别人改的东西
这一刻就出现在画面上（用户要的「保存后画面直接更新显示 merge 后的最新状态」），
不用再多一次 GET。`base` 不带 = 脚本 / 老页面 ⇒ 退回整份覆盖的老行为。

⚠ 三方合并只解决「谁的改动被吃了」，解决不了「两发同时读到同一份 theirs、
后写的盖掉先写的」。后者靠 `web/admin.py` 的 `_config_locks`（服务器是
`ThreadingMixIn`）—— 两件事，都要有。

## D37b · 列表**重画不动滚动条**；掉落页的排序只在换数据时排一次（用户 2026-09-07）

**用户报的症状**：掉落页选完材料，滚动条「自动滚了一个幅度」。

**真正的原因**不是哪句滚动代码：D44b 给掉落页加的排序是**每次重画都按当前值
重排**，改完材料那一行按新材料 id 挪到别处，视野里的内容整体换了一截 ——
滚动条其实没动，是内容动了。

**定**：
1. 排序名次按**条目对象**记（`DROP_ORDER`，WeakMap），只在 `CFG.drops.entries`
   这个数组被换掉时（读盘 / 刷新 / 保存回执）重算一次；编辑期间不重排，
   新加的条目排最后。⇒ 改完的那一行**保存之后**才归位。
2. 排序搬进 `visibleEntries`，不再在 `pageRows` 里另排 —— `positionOf`
   （翻页、报错定位）看到的顺序才和画面一致。
3. `repaintList` 把 `scrollTop` 存下来再放回去，「不许动」写死。
4. 全页只剩两处会主动动滚动条：保存报错定位到出错那张卡、「添加」定位到
   新卡。两处都改成 `revealIfHidden`：卡已经在视野里就一动不动，不在才挪，
   而且 `block: "nearest"` 挪最少、不做动画。**没有全删**：报错那张卡在视野外
   时不挪等于「点了保存什么都没发生」，新卡在末页底下时同理。

**否掉的方案**：排序时保留一条「刚编辑的条目钉在原位」的例外 —— 那要在每次
编辑时记住是哪一条，比「换数据才排」多一套状态，而且用户一保存又要跳。

捞回来」。崩溃现场是**传输**，35 MB 的 mdmp 不压就是 35 MB 的上行 —— 目的完全不同。
⇒ `server/` 里第一次出现 `zipfile`，取 `ZIP_DEFLATED` + level 6（§58 的实测数据）。

服务端**收到后不解压**（用户明确要求），原样保存 + 一份 `receipt.json`。

## D62 · 先落盘再上传；收包这一段留在请求线程，落位甩给后台线程

**先落盘**：崩溃现场先写进 `logs/.crash_pending/`，**上传成功才删**。
覆盖用户点名的两种丢失场景（崩的时候断网、崩完立刻 `stop.bat`），
中继下次启动时补传。反过来「先传成功再考虑落盘」的话，这两种情况现场就没了。

**服务端侧的线程切分**（用户补充要求「不能阻塞其他操作」）：

* 请求线程只做**必须同步**的那段 —— 字节必须当场读走，不然 HTTP/1.1 keep-alive
  连接会错位；sha256 边读边算几乎零成本，所以校验失败仍能当场回 400；
* `os.replace` 落位、写 `receipt.json`、清理全甩给专用线程。
  理由和日志异步写一模一样（V0.3bot D109 / §150）：auth / game / web 在**同一个进程**里。

实测：一边灌 11.6 MB 的真包、一边打注册页，注册响应中位 27 ms vs 基线 30 ms。

**队列满了就丢并计数**，绝不反压到请求线程（`asynclog.MAX_PENDING` 同款取舍）——
让上传把同进程的游戏拖住，比丢一份崩溃包严重得多。

## D63 · 重试用固定的 3 秒 × 3 次 —— 这是铁律 10 **唯一允许的例外**

次数和间隔由用户指定。之所以不违反「禁止固定次数 / 时间阈值」：
**连不上远端时物理上没有事件可等** —— 网络恢复不会给我们发通知，对端也没法告诉我们
「我起来了」。这正是铁律里写明的那种情形，按要求在 `RETRY_DELAY_SECONDS` 上面
写清「这里为什么等不到事件」。

★ 其余每一处判据都是事件：认 PID 靠 TCP 连接表、等退出靠进程句柄、
崩没崩靠崩溃报告的 mtime、去重靠**状态翻转**（记住上次处理的是哪一份）。

## D64 · 拒收时要先把「已经在路上」的 body 读掉一部分，再关连接

第一版是「一个字节都不读，直接 `close_connection = True`」，理由是不给「先灌满
64 MB 再被拒」留便宜。**实测发现它把错误信息也一起废掉了**：对方正卡在 `send` 上，
被 RST 打断，**连我们刚回的那句「包太大」都读不到**，只看到一个连接错误。

⇒ 回完之后再读掉一部分，上限取 `crash_max_bytes` —— 也就是「我们本来就愿意收的
那个大小」。这样**不多花一分本来不肯花的成本**，而正常的超限客户端能读到 413。
超出这么多的仍然直接断（我们自己的上传器在发之前会先量一次大小，走不到这里）。

## D67 · 两份 `server.config` 模板：把「每个键归哪一边」写进代码，让测试去核对（2026-09-09）

**背景**：§61 —— 服务端包的 `server.config` 是独立手写的第二份模板，

那一行删掉后第二条测试立刻红，只留注释里那行 `#   crash_keep_days ——  …`

**顺带清点了整个 `tools/server-package/`（§62）**：十个文件里只有
`server.config` 这一条现在有守卫，两份 README、六个 `.bat` 共用的
`chcp 65001` 前导块、`serverctl.ps1` ↔ `serverctl.sh`、四份手写的

我拿 `0x532FC4` 那个初始化「连返回值都没测」去代表整条登录路，
但**登录路上另有一发在判**。平时能登录不是因为信使能用（服务器停机 15 年了），
**而是因为那一发返回了 1**：模块在、调用被派发出去就算成功，后面连不上是异步的事。

**教训**（下次做这类「拔掉一个子系统」的改动照着办）：
「所有可见分支都能接住失败」**推不出**「整条路都能接住失败」——
子系统能不能拔，判据只有一个：**把它拔掉，把那条路真的走一遍**。
这一条本来就登记成 Z-70 要实机验，代价是用户替我踩了一脚。

**要再试的话**只剩一条路：换 BigShot 自己那一格 IAT `0x63751C`
（`NMCO_CallNMFunc`）为「直接返回 1、根本不进 nmcogame」的桩 ——
这样 `nmconew.dll` 不会被加载（它是在 `NMCO_CallNMFunc` 里才 `LoadLibrary` 的），
客户端拿到的又还是 1。**没验过，别当结论**；要做也得先在本机登一次再说。

## D82 · §82 的两处守护**再加两处**：判据是「这个线程该不该继续跑」，不是「这一句别崩」（2026-09-11，§84，bug调查/19）

**背景**：V0.3.1 上线当晚又崩一次（`iorikexue` 02:01:56），
崩点从 §82-A 补的 `Enter()` 里**挪到了它的调用方** `nmconew+0x75CDA`。

**为什么会挪**：§82-A 让 `Enter()` 在共享状态已死时干净返回，
调用方于是拿着「锁到手了」接着解引用**同一批已经被拆掉的字段**。
§68 当年那句「跳过崩的那一句只是把崩溃挪到下一句」，在**这个粒度上是对的** ——
错的是 §82 以为逐句堵就够了。

**改的判据**：原版自己在工作线程序言里写了 —— **七个字段任何一个是 0，
这个线程就该 `jmp 0x75EE2` 结束**。我们只是在**拿到锁之后**把那一判重做一遍。

| 选项 | 为什么不选 |
|---|---|
| 在三条回边（`0x75C86` / `0x75D83` / `0x75D76`）上判 | **对象是在那 10 秒等待期间死的**，回边判过也没用 |
| 走原版「没数据」那条路（`[ebp-0x10]=1; jmp 0x75D57`）| 它会 `Sleep(0)` 之后**回到主体重跑**，对象已死 ⇒ 100% CPU 空转 + 迟早再崩 |
| **拿到锁之后判，为空就 `jmp 0x75EE2`** | ✅ **选它**：整个函数只有这一个 `ret`，序言里已有 7 处跳它 |

**同时补 `Mutex::Leave`（`+0x98EE7`）不是可选项**：`ScopedLock` 的析构函数
**无条件**调 `Leave()`，而 `Leave` 读改的 `[state+0x10]` 和 `Enter` 崩的是同一块
⇒ **§82-A 每命中一次，作用域退出时就一定跟着一发往死内存写的 `Leave`**。
这次只是 `+0x75CDA` 先崩把它挡住了。`ScopedLock` 在这个 DLL 里用了 54 处。

★ 从 `+0x75CCE` 跳 `+0x75EE2` **会跳过 `~ScopedLock`**，这是**故意的**：
它要 Leave 的那把锁本来就已经被 `CloseHandle` 掉了，不去碰它才是对的；
`+0x75EE2` 自己摘 SEH 帧、自己按 `ebp` 平栈，三条回边处 `[ebp-4]` 都是 -1
（没有活着的局部对象要析构）。

★ 判「那一页读不读得到」而不是「指针是不是 NULL」：
`+0x75F0F` 先 `UnmapViewOfFile(p)`、`+0x75F18` 才置 0，中间那一小段指针非空视图已没。

## D84 · 反倒卖：**公告编译进 DLL + 换非商业许可证**，但**不做离线失效**（2026-09-11，§86；用户拍板）

**背景**：有人把这个免费项目打包拿去卖钱，买家不知道它本来免费。

### 一、为什么是「登录框顶部那个死掉的公告框」

它是全客户端最显眼、又完全不占游戏内容的一块地方，而且**原本就是用来显示公告的**
（§86）。改一个 4 字节立即数就能接管，不碰任何游戏逻辑。

### 二、为什么走「改立即数 + 本地 HTML」，不走 `document.write`

| | 代价 |
|---|---|
| ✅ **改 `0x42408A` 立即数 → `file:///%TEMP%/psnotice_*.htm`** | 不引入 COM、不新增 lib、复用 `try_patch_handshake_version` 的现成骨架 |
| ❌ `WM_HTML_GETOBJECT` + `IHTMLDocument2::write` | 要 oleacc + 手写 mshtml 调用；而且当前文档是 `res://ieframe.dll/navcancl.htm`，**跨 zone 往错误页里写会不会被拦是未知数**。走 ① 的话 IE 根本进不了错误页 |
| ❌ 隐藏控件 + 自绘 Static | 要 gdi32、要自己管重绘和 DPI，纯粹是把简单问题做复杂 |

### 三、★★ 时序：触发点是**事件**，不是时刻（走了一次弯路，记下来）

**最终做法**：内联钩 `user32!CreateWindowExW`，`lpClassName ==
L"MPlay.Control.MiniBrowser"` 的那一发就是事件本身 —— **控件还没建出来就不可能
被导航**（创建 `0x424067` 和导航 `0x424089` 在同一个函数里，相隔 0x22 字节），
所以这一发在任何机器、任何速度下都必然早于导航。`patch_thread` 里那一轮特征串
轮询降为次要：打上了省事，打不上照样由事件补。

**★ 弯路（值得记）**：最初挂在 BigShot 自己的 IAT 槽 `0x6E6260` 上，
理由是「只拦 BigShot 自己的调用，比内联钩干净」。**实机推翻**（§87）——
那个槽是 ASProtect **惰性解析**的，`+7.9s` 才变成真地址，而公告框控件
`+8.2s` 就起来了 ⇒ 钩子根本装不早，「结构性保证」名存实亡；而且为等它在
`patch_thread` 里死等 4.4 秒，把后面所有 patch 一起拖慢。

当时的第一反应是**退回去比时间**（「轮询特征串打上了，离导航还有 3.9 秒余量，
够了」）—— **用户当场否掉：换台电脑跑就不对了。**
⇒ 这是铁律 10 的另一种犯法：**代码里没有一个 `Sleep(N)`，但你在用实测余量
为设计辩护，那就已经犯了。** 正解不是降级成时间问题，是**换个能装得早的
挂载点**：导出函数的地址和解壳进度无关，`+0.4s` 就装上了。

### 四、混淆只做到「记事本 / strings 找不到」这一档

用户明确要求，**不做自校验、不做反调试**。判据是
`tools/gen_notice_h.py --verify-dll`：11 个特征词 × 3 种编码在 DLL 里 **0 命中**，
`hook/build.bat` 编译后自动跑，红了直接 fail。

★ **网址不算特征词**：GitHub 地址本来就以别的身份明文躺在 DLL 里
（`bshook.c:1066`，更新器拉不起来时那个提示框），改掉那一处也动不了公告一个字。
判据是「能不能定位并改掉这段公告」，不是「DLL 里出现过没有」。

### 五、★ 为什么**不**做离线强制失效（用户拍板「不加」）

联机那半边本来就有现成的版本门禁（改 `config/server-ClientFilter.config`，
热重载，旧客户端一连就被拒 + 更新器自动升级）。**单机（「本机服务器」）那半边
堵不干净**：客户端连 `127.0.0.1`，跑的是包里自带的服务端，门禁配置就在买家电脑上。

任何本地检查（有效期 / 联网激活 / 自校验）都在**对方机器上**、都能被 patch，
而一旦误判就是「免费玩家打不开游戏」—— 倒卖者反而会拿这个当卖点
（「我这份是破解的」）。所以这里**只喂话、不阻断**：公告编译在 DLL 里，
离线单机照样显示，让买家自己去退款举报。

### 六、许可证 GPLv3 → PolyForm Noncommercial 1.0.0

GPLv3 **明确允许收费分发**，「禁止倒卖」在它下面站不住。
PolyForm Noncommercial 是专为软件起草的非商业许可证，措辞干净。
单一版权人（提交历史只有 `liubz102`，无外部 PR）⇒ 重新授权干净。

★ **只对本次及之后的版本生效**，已按 GPLv3 发出去的副本收不回来 —— 这句话
必须写在 `LICENSE` / 两份 README 里，别让人以为能追溯。
★ 顺带一个现在就能用的事实：**倒卖者本来就已经在违反 GPLv3**
（没附源码、没保留许可证声明），这条不用等新许可证生效就能拿去投诉。

## D85 · 上报的版本号里折进 hook 的 SHA-256；**清单里没有的版本一律拒，比清单还老的交给门禁**（2026-09-11，§89；用户拍板）

**要解决的**：D84 的公告只挡得住「拿十六进制编辑器改成品包」。真正好用的那条
路子是 —— **改包根 `BUILD.ver` 那个明文版本号就绕过版本门禁，连重编都不用**，
于是可以一直卖不带公告的旧客户端。

### 一、用户的原始设计 vs 协议的硬约束

用户要的是「① 上报一个加密的版本号 ② 客户端上报自己 hook 的 sha256」。
**② 做不到**：握手只能上报 4 个字节（`SimpleCipher` 是有状态流密码，
插一个字节后面全错位，见 §89）。

⇒ **把 sha256 当密钥用，而不是当数据传**：校验位 = `sha256(hash‖版本码)` 的
低 7 位，和版本码一起塞进那 4 字节。**一次满足两个诉求，零协议改动。**

### 二、★ 版本码必须**明着放**，不能连它一起加密

最初的方案是整个 32 位都加密。**自己推翻的** —— 那样服务端的清单一旦比客户端旧，
新客户端一条都匹配不上 ⇒ 判「改过」⇒ 强制更新到它**已经是**的版本 ⇒ **死循环**。

⇒ 版本码明放，服务端才分得清**「这个版本我不认识」**和
**「我认识、但校验位不对」**（拒）。`test_hookintegrity.py` 专门有一条用例钉它。
★ 二轮收紧（下一节）之后「不认识」不再一概放行，但明放仍是必要的：
要靠它分出「比清单还老」那一档，日志里也才看得出对方是哪版。

### 三、失败处理（2026-09-11 用户第二轮收紧）

用户理由：「**服务端是我配置的，我能保证服务端一定先更新**。清单里没有，
说明就是手动改的。」⇒ 「清单里没这个版本」从放行改成拒。

| | |
|---|---|
| 校验位对不上 / 该带没带 / **清单里没这个版本** | **拒 + 强制更新** |
| 版本**比清单里最老的还老** | 放行，交给版本门禁 —— 那一版发布时还没有这项功能，「清单里没有」证明不了它被改过。★ 所以门禁至少要抬到清单里最老的版本（V0.3.2），否则改个更老的版本号就绕过去了 |
| 对方**压根没上报版本号**（原版 / 很老的客户端） | 放行，交给版本门禁 —— 不然 `server-ClientFilter.config` 填 `0`（不限制）就失去意义了 |
| 清单缺失 / JSON 坏了 / 客户端算不出 hash | **放行 + 告警** —— fail-open，和 `server.config`、版本门禁一脉相承 |

### 三·B、★★ 收紧之后必须配的安全阀（`hook_check_disabled_reason`）

**被拒的客户端会去下载「服务端自己那个版本」**（拒绝文案里写的就是它，
`version_reject_message`）。所以一旦**服务端自己的版本都不在清单里**，
客户端下完还是不在清单里 —— **死循环，而且解不开，全服没人进得来**。

⇒ 服务端每次握手前先看一眼「我自己在不在清单里」，不在就**整项校验自动关掉**
并打一行醒目日志。出现这种状态只有一个原因：打包时清单没跟上
（比如只打了服务端包）。那不是玩家的错。

★ 实机验过：把 `BUILD.ver` 改成 V9.9.9（清单里只有 V0.3.1）后，日志打出
「这一版不校验完整性：清单里没有服务端自己的版本 V9.9.9」，登录照常。

### 三·C、开发机不能被自己锁死

`hook/build.bat` 编完**自动跑一遍 `gen_hook_manifest.py`**（版本号取
`tools/build-ver.config`）。不然本地重编 hook 之后，下一次启动就会被自己的
服务端按「校验位对不上」拒掉。
⚠ 反过来说：**同一个版本号下重编 hook = 作废已经发出去的那一批**
（它们的 sha256 对不上了）。重编就顺手抬版本号。

★ **闸门（用户 2026-09-11 定）：`update-manifest.json` 里最新的版本允许刷新，
比它老的一律冻结。** review 时先做成「在 update-manifest.json 里 = 已发布 =
冻结」，用户否掉：那张表是打包时就写的，不等于上传了，开发机上对最新版本
「改 → 打包 → 测」是反复来的，会被自己卡死。改成只冻结**被更新版本盖过去的
老版本** —— 那批玩家早发出去了，hash 一变全被判「改过」；正在做的最新版本本来
就要反复打。`gen_hook_manifest.py` 冻结版本 hash 变了 → 退出码 2；两个打包
脚本见非 0 一律 `throw`（原来只警告，理由「清单里没有一律放行」已不成立），
`hook/build.bat` 打大字警告；要硬改只能 `--force`。
最新版本发出去之后再重编，规矩靠流程：**整包重新上传 GitHub 并覆盖服务端**，
新更新器（V0.3.2 起）被拒后无视版本比较重下同版本（§90 一），zip 换了就自愈；
只覆盖服务端不换 zip 才是死循环。

### 三·D、`BUILD.ver` 开始进 git（2026-09-11）

以前 `.gitignore` 掉了它，开发机上缺它就按原版 311 上报 —— 收紧之后那会被
直接拒掉，调试当场卡住。现在打包收尾把包里那份**拷回仓库根**并提交，
和 `server/manifest-hook.json` 成对：版本号 + 那一版 hook 的 SHA-256，
一起说清「仓库里这份 hook 属于哪个版本」。

### 四、清单放 `server/`，不放 `config/`

客户端包和服务端包共用同一份 `server/`（铁律 8），放这儿两个包各得一份，
**这一处没有「另一边」要维护**（对照铁律 13）。★ 但打包**只拷 `*.py`**，
JSON 不会自动跟着走 —— 实测踩过，所以 `build-common.ps1` 加了
`Copy-HookManifest`（缺了就 throw，不打半个包）。
条目由 `tools/gen_hook_manifest.py` 在打包时自动 upsert（累积母本，同
`update_manifest.py` 的幂等做法）。

★★ **清单里只能有「带校验码」的那些版本（V0.3.2 起）**。V0.3.1 及更早发出去的
hook 没有这段代码，握手裸发版本号；给它们加条目 = 宣布那批玩家「本该带校验位
却没带」→ 全被拒 → 而他们手里那版更新器又不会重装同版本（§90 一）→ **全体卡死，
无法自愈**。2026-09-11 review 抓到过一条这样的条目：清单里写着 V0.3.1，hash 却是
开发机新编（带校验码）的那份 —— 一部署就是上面的后果。已改：版本号抬到 0.3.2，
清单只留 V0.3.2。

### 四·B、发版顺序：**本机打包 → 客户端上 GitHub → 服务端包整体覆盖云端**（用户既有流程，没问题）

门禁 `server-ClientFilter.config` 是打包时从仓库拷进服务端包的，服务端一覆盖
门禁就一起抬 ⇒ 老客户端立刻被拒去更新，**那时 GitHub 上必须已经有新包**，
所以客户端必须先上。「服务端先」反而更糟：覆盖到上传之间老玩家全被拒，
更新器却找不到新版本。
代价只有一个小窗口：上传到覆盖之间那几分钟里**手动**下了新包的人，会被还没换的
旧服务端弹一次（旧服务端认不出新版本号 / 清单里没有 → 强制降级），服务端一覆盖
又升回来。自动更新的老客户端不受影响，它们只在被拒时才动。
★ 打包前记得在仓库里把门禁抬到新版本（历次「Vx.y.z 打包」提交都这么做的）：
门禁低于清单最老版本时，改个更老的 `BUILD.ver` 就能绕过校验。

### 五、诚实交代的两个限制

1. **客户端自校验永远能被绕过** —— patch 掉算 hash 那段，或者干脆改报一个
   清单里没有的版本号（走「不认识 → 放行」那条）。期望值本身就明写在随包
   发出去的 `manifest-hook.json` 里。**门槛从「改个 JSON」抬到「会用调试器」，
   仅此而已。**
2. **对纯离线单机完全无效** —— 和 D84 结论一致，没变。

## D86 · 存档转移助手：**只有用户名 / 昵称 / 密码明文可改，其余全部加密**（2026-09-11；用户拍板）

**推翻 V0.2 D151 那句「玩家会用记事本改存档，别为了格式洁癖把人挡在外面」。**
不是改主意，是**前提变了**：GM 管理页 `/admin` 现在能改等级 / 金币 / 材料 / 仓库
（`admin_update_account`，在线时不用重登），玩家不再需要自己动存档。
只要还留着一条能吃手写 JSON 的路，加密就等于白做。

### 一、用户当场定的三条

| | 决定 | 用户给的理由 |
|---|---|---|
| 密钥作用域 | **只用内置常量**，不做 per-server 私钥、不加配置项 | 跨服转移要照旧能用 |
| 防重放 | **不做**，不给 `accounts.json` 加字段 | 「金币花完了说明他买装备了，回档了装备也没了，不破坏平衡」 |
| 旧的明文存档 | **一律拒** | —— |

★ 防重放还有一条比这更硬的理由，记下来免得下个会话重新纠结：
**导入是「覆盖」不是「叠加」**，同一份存档在同一台服务器上导一百次，
结果永远是同一个状态，**刷不出任何东西**。

### 二、★★ 诚实交代：这不是安全边界，只是抬门槛

**客户端包里带着一整套服务端**（`Copy-ServerCode` 把 `server/*.py` 全拷进去，
单机模式跑的就是包里那套）。所以玩家可以：起本机服务器 → 改自己那台的
`accounts.json`（或者直接用本机那个 `admin`/`Admin123` 的 GM 页）→ 从
`127.0.0.1:27810` 导出 → 拿到一份用同一把常量密钥加密的**完全合法**的存档 →
传到云服。**这条路堵不住，也不打算堵。**

⇒ 挡住的只有「把下载的 JSON 用记事本改一改」那一档。和 D84 / D85 一个调子
（「门槛从『改个 JSON』抬到『会用调试器』，仅此而已」），
**不要**往上加自校验 / 反调试。

加密挡的是「**凭空造**」，挡不住「**复制自己**」：把明文 `username` 改个没人用
的名字就能在同一台服务器上克隆一个满装备的号（新建路径本来就免鉴权，
也绕过注册 IP 冷却和昵称查重）。唯一的解法是把账号名绑进密文 ——
那样跨服转移就没了，用户不要。**让用户知道自己放弃了什么。**

### 三、构造为什么长这样

标准库里**没有 AES**（零第三方依赖，两个内置运行时的 `site-packages` 都是空的），
能当伪随机函数用的只有 `hmac` + `hashlib`。所以走的是唯一一条不用自己发明东西的
经典路线：HKDF 派子密钥 + HMAC-SHA256 计数器模式加密 + **encrypt-then-MAC**。

- **nonce 当 HKDF 的 salt**（而不是固定 salt）：每份存档一把一次性子密钥 ⇒
  **keystream 永不重用**。这一条不能省 —— 主密钥固定、nonce 也固定的话，
  两份存档 XOR 一下就露出结构，一个**不会读 Python** 的人也能靠「从 A 存档剪
  一段字节贴到 B 存档」做坏事。
- **先验 MAC 再解密**：被改过的密文在 `zlib` / `json` 碰到它之前就被挡掉。
- **先压缩后加密**：仓库 JSON 重复度极高，压完小一个数量级（400 件的账号
  密文才 1.5 KB，比原来的明文存档还小）。CRIME/BREACH 那类攻击要的是「能反复
  注入并观察长度」的在线预言机，一次性离线文件不成立。
- **`sort_keys=True` + 紧凑分隔符** ⇒ 明文字节确定，可以用**固定向量**把算法钉死
  （`test_savecrypt.FixedVectorTests`）。★ 算法和密钥**一旦随包发出去就改不动了**
  —— 改了全世界已导出的存档全部作废。要换只能加一个新 `FORMAT_VERSION`、
  把旧的留着能解。`_KEYS` 因此写成**元组**（第 0 个是当前在用的），
  现在只有一把，但这张表的形状必须现在就留下来。

### 四、为什么多一个 4 字节的 `key_id`

MAC 失败**天然分不出**「被改过」和「别的密钥封的」—— 那就是 MAC 的定义。
但这两件事玩家该做的下一步完全不同（一个是「别改了」，一个是「去原来那台服务器
导入」）。所以头部多带一个**非秘密**的 `key_id`（主密钥的 sha256 前缀），
用它分流。它只是**诊断提示**：拿着任意密钥的人可以把 `key_id` 写成我们的，
那样他得到的是「被改过」。正牌文件的 `key_id` 在 MAC 覆盖范围内，改不动。

### 五、★★ 解压必须封顶 —— MAC 在这里保护不了服务端

「先验 MAC 再解压就安全了」在这儿**不成立**：密钥是公开的（随包发到每个玩家
机器上），攻击者能给任意内容算出**合法的 MAC**。一份 1 MB 的请求体
（`MAX_BODY_BYTES` 的上限）里塞得下一颗把云服内存吃光的 zlib 炸弹
（实测：62 KB 解出 64 MB）。

判据用 `zlib.decompressobj().eof` —— 压缩流**自己的结束标记**，是事件不是阈值
（铁律 10），顺带还能抓住被截断的流。上限 4 MB 是天花板不是工作值。
实测：解到刚好等于上限而流真的结束时 `eof` 仍是 `True`，所以不需要 ±1。

### 六、为什么把「退化形状」那段容忍删掉

老 `parse_save` 有一段「取不到 `account` 就把整个 payload 当账号」的容忍。
删它**不是格式洁癖**：加密之后，一份没有 `data` 段的文件里**根本没有任何游戏
数据**，退化分支会让它一路走到「从默认值起手 + 覆盖」—— 结果是用户名密码都对、
号还在、**东西全没了**，提示还写着「上传成功」。**那是一次伪装成导入的清档。**

★ 同一个机制正是 §91 那条线上风险的来路（旧服务端拿到新存档会静默清档）。

### 七、昵称这一格必须过 `check_nickname()`

`import_account` 以前只做 `strip() or username`，**从来没校验过昵称**。
以前无所谓（没人特意去改），但现在昵称是我们**主动请玩家去改**的三项之一 ——
控制字符会把包和 JSON 弄坏，补充平面字符会让 `w_wstr` 的长度字段少算。
不校验 = 自己开一个崩溃源。★ 昵称**查重仍然不做**（V0.2 有意为之：导入不走查重）。

### 八、这一版之后「谁都改不到」的五个字段

`tutorial_completed` / `tutorial_progress` / `quest_difficulty` /
`quest_unlock_all` / `character` —— GM 页没有它们（`admin_update_account` 只动
等级 / 金币 / 材料 / 仓库 / 穿着），玩家以后也手改不了，只剩「直接改云上的
`accounts.json`」这一条路。实际影响不大（这些本来就是打游戏打出来的），
但真要跳教程 / 解难度就没辙了。**本轮不做**（用户没点这个题），
在意的话下一轮给 GM 页补上。
`display_name` / `password` 不在此列：注册页的「修改昵称」「修改密码」还在，
存档明文区也能改。

### 九、密钥本身不写进任何文档

它只存在于 `server/savecrypt.py` 那两段常量里。抄进 DECISIONS / FINDINGS /
sessions / 提交信息 = 白做那层混淆。它进 git 历史就再也删不掉了 ——
这没关系（它本来就不是秘密），但别让以后有人以为「把它从代码里删掉就安全了」。

## D87 · 打包**先重编 hook 再打**，编不动就一步都不走（2026-09-11；用户拍板）

**用户原话**：「hook 的编译和最后的打包以前一直是分开的两件事，但是最近的防倒卖
篡改的修改之后，打包必须记录 hook 的 sha，所以每次打包前最好重新编译一下 hook，
不然有不同步的可能。如果 hook 当时被占用无法编译，则打包界面要有提示 hook 被占用，
并且不能跑打包逻辑。」

### 一、为什么非并进打包不可

D85 之后，包里那份 `server/manifest-hook.json` 记着 `bshook.dll` 的 SHA-256，
服务端拿它判客户端的 DLL 有没有被改过。两件事分开时的坏法是这样的：
改完 `hook/*.c` **忘了重编**就打包 ⇒ 包里是「上一次编的 DLL + 上一次的 SHA」。
**包自洽、服务端满意、玩家照常玩** —— 一句报错都没有，直到下一次有人按源码
重编才发现线上那一版和仓库里的源码对不上。
「症状不是报错」的坑靠「记得先编一下」防不住，只能靠脚本。

判据和已有的 `Assert-UpdaterStub`（更新器还是原版 NGM 就现场重编）同一个调子：
**打包机就是编译机，「忘了编」不配当打包失败的理由。**

### 二、编不动就中止，不是警告后照打

用户点名的场景是「hook 被占用」—— 最常见就是**游戏正开着**：`bshook.dll` 已经
注进 `BigShot.exe`，以**映像**方式映射，映像段拒绝 `FILE_SHARE_WRITE`，链接器
写不进去。这时候「黄字提醒一下照打」得到的正是要根治的那种包：**旧 DLL + 新 SHA**。
所以是 `throw`，不是 `Write-Host -ForegroundColor Yellow`。

### 三、判据是「开得开写句柄吗」，不是「有没有 BigShot.exe 在跑」

`Assert-HookWritable` 真的去 `[System.IO.File]::Open(..., ReadWrite, Share::Read)`
开一次 —— 开不开得了，和链接器待会儿遇到的是**同一件事**，不是它的近似。
进程名只在报错时当**提示**列出来（`Get-Process BigShot, bsloader`），
列不到也照样报「被占用」：占着它的可能是调试器、杀毒软件、资源管理器预览。
`IOException`（共享冲突）= 被占用，其它异常（只读属性 / ACL）= 写不进去，
两种给两句不同的下一步。

**问两次**：编之前问一次（拿到干净的报错，而不是埋在几十行编译输出里的 LNK1104），
编失败之后**再问一次**（pre-check 和链接之间那段时间里游戏被启动了也算数）——
以「现在写不写得进去」这个事实为准，不去猜编译输出里的错误码。

### 四、为什么编在 `Assert-EmptyTarget` 之前

那一句带 `-Force` 会把 `dist\` 里上一次的成果物整个删掉，`build-menu.ps1` 的
`Clear-Stale` 也一样。hook 编不动时这一次本来就打不成，**旧成果物不该陪葬**。
所以顺序是「先编 → 再删 → 再打」，菜单那一层也在 `Clear-Stale` 之前先编一次
（`Invoke-HookBuildOrExit`，两条分支各一次）。
`test_hookintegrity.PackagingRebuildsTheHookTests` 用下标比较把这个顺序钉住了。

**但也没有提到更前面去**：菜单那次故意排在**读完选择之后**，不是刚打完版本号
就编。不然「双击进来看一眼版本号、又按了个无效键退出」也会重编一次 hook ——
同源码重编照样换 SHA（§92），等于凭空弄脏三个文件。判据是「人已经决定要打了」。

### 五、同一个进程只真编一次

`build-menu.ps1` 打「两个包」时会连着调两个打包脚本，编两遍纯属浪费。
用全局标志 `$global:PopShotHookBuilt` 记「**这一次构建编过了**」这个事实本身 ——
不是「跳过第几次」那种阈值（铁律 10）。单独跑某个打包脚本是全新进程，标志不在，照编。

### 六、配套：`hook/build.bat` 加 `/Brepro`，让编译可复现（用户当场拍板）

本来的代价是：同一份源码重编，产物只差 PE 时间戳，但 sha256 必然不同（**§92**）。
⇒ 每打一次包就无缘无故弄脏三个文件，而且**同版本先前发出去的客户端**会对不上
新打的服务端包里的清单。用户当场决定把它消掉。

做法是两条 `cl` 各加两个 `/Brepro`（**编译一个、`/link` 后面一个**）：
时间戳变成**内容哈希**（实测 `0xD83770A5`，不是 `0xFFFFFFFF`），
连编两次**逐字节完全相同**。`ReproducibleBuildTests` 钉着这两个开关。

★ 加它会让产物**重新排布**一次（调试目录多一条 `REPRO` 记录 ⇒ `.rdata` 整体挪

## D90 · 卖出的四条玩法口径（用户 2026-09-12 拍板）

**一、合成得来的装备，卖出时把配方材料**退实物**，不折价。**
用户原话是「返还全部材料，只有配方里的金币花费额再乘以百分比」。
两种读法（退实物 / 按材料单价折成金币）差别很大，**问过用户，选的是退实物**。
⇒ 左边购物车因此分两块：金额两行 + 一块「将返还的材料」；确认框里两张清单都列。
代价要认：卖出不再是纯粹的「换钱」，仓库里会多出材料。

**二、查不到价的东西走「其他物品」兜底价，不是「不可出售」。**
808 件可拥有物品里有 148 件既没上架商店也没有配方（§93）。用户在
「不可出售 / 兜底价 / 价格 0」三条里选的兜底价。
⇒ 「这件东西没有价」是个死胡同 —— 玩家手上可能有任何一件。

**三、什么都能卖，穿着的**自动脱下**；但**对局中一律不许卖**。**
用户原话：「玩家在房间内或者大厅内等可以自由穿脱的状态下才可以卖出」。
判据用现成的 `gameserver.conn_is_playing()`（§94 一：房间状态翻转，
不是计时器），口径天生就是「待机房里等人算待机」。
★ **提交那一发要再查一次** —— 页面打开到他点确定之间隔着任意长的时间，
`state` 里那个 `in_match` 只是画面。
★ 打到一半脱装备为什么不行：战斗里那份加成是开局时 `0x030b` **一次性**喂进
`[GameSession + 0x250 + 座位*4]` 的，中途改只会让各家客户端算出不同的伤害。

**四、只记服务端日志，不做「卖出记录」页面。**
用户在「做记录页 / 只记日志 / 都不要」三条里选的中间那条。
⇒ 没有 `sellhistory.py`，`eventlog.online` 里一行 `[sell] …` 写全
「卖了什么、得多少、余额从多少到多少、退了什么」。

**五、`sell_items()` 自己写一个，不拿 `admin_update_account()` 拼。**
后者能同时改 `money` / `inventory` / `materials`，看着刚好够用 —— 但它的
`money` 是**绝对值**，调用方得在锁外先读余额再加。读和写之间玩家领个礼物、
打完一局、或者另一个管理员改了一笔，那份收入就被这一发悄悄覆盖掉了。
和 `compose_item()` 那段注释说的是同一件事：**余额只能在锁里算**。

**六、金币钳到 int32（`account_store.MONEY_MAX`）。**
`0x0600` 的金币那一格是 int32，超了 `struct.pack("<i")` 当场抛，
**把那条在线连接一起带走**。回执里把「钳掉了多少」说出来，别让玩家以为服务端吞了钱。

**七、管理员没有同名游戏账号时，卖不了但**照样能改价**（用户第二轮点的）。**
第一版把遮罩盖在整个 `.panel-body` 上，连工具条一起盖住了。

遮罩改成只盖 `.sell-split`（左右分区），工具条永远露着。
服务端本来就是分开的（`_admin_sell_prices_post` 不走 `_sell_target()`）。

## D93 · 卖出页的版式判据：**右栏那排大分类标签必须一行放得下**（用户 2026-09-12 第三轮）

用户点了五处版式问题，根子是同一个：左右分区按 `5fr / 7fr` 分，右栏只拿到

必折行；而为了让一行塞下「余量 + 单价 + 按钮」，格子又被迫做成一行一件。

2. 卡片上**不写单价** —— 同一句话浮窗里本来就有（`paintTip`）。
   拿掉那一列 96 px 之后，格子就能收回「修改仓库」那种小格子（`minmax(230px)`），
   一行摆三格，名字反而更长了。
3. 「将返还的材料」挪到**金额栏下面、清单上面**，画成 `.chips`，
   而且**和金额两行共一个边框**（`.sell-total`，用户第五轮补的）。
   它是「这一单能拿到什么」的另一半（金币那半 + 实物那半）：摆在清单
   最下面的话，清单一长就被顶出视野；单独成块摆在上面又会被当成**待卖出
   清单的第一格**，而它俩的意思正好相反（一个要没、一个要来）。
   里面用一条虚线分开 —— 退的材料不算在上面那个金额里。
4. 价格弹窗：顶上三行说明**删掉**（每个框底下那行小字已经说了同一件事），
   「放弃修改 / 保存」挪到最上面并**钉住不滚**（`panel-body` 不滚，
   滚的是里面一层 `.sell-price-scroll`），价格框**两列排** ⇒
   七个框一屏放得下，正常窗口下一点滚动条都没有。
5. 「其他」**和「装备」平级**，不再挂在装备下面 —— 它是
   `sellprice.quote()` 四条分支里独立的一条（既没上架也没有配方的兜底价），
   不是装备的一种。
6. ★ 两个滚动区都加 `scrollbar-gutter: stable`。**这不是美化，是判据**：
   滚动条一出现就吃掉 15 px，而 `auto-fill` 的列数照剩下的宽度算 ⇒
   「东西少的时候两列，一多出滚动条就变成一列的大格子」。实测左栏内宽 356，
   出了滚动条只剩 337，两列正好要 338 —— **差 1 px 就翻**。
   把槽永远留着，列数就和「这一刻滚不滚」无关；`minmax` 的最小值同时降到
   150（余量 30 px），老浏览器不认这个属性也翻不了。
