用户一次给了四条，全是「玩法数值 / 结算判定」层，和网络无关：

1. 组队 + 夺分，结算界面只有得分最高的**那一个人**「胜利」，队友全「败北」；
2. 房间「选择地图」面板里那颗「随机」点了自动取消、弹回原地图；
3. 任务闯关结算后，分数 / 经验 / 金币是**同一个数**；
4. 经验 → 等级是线性的，升级太快。

**改动全在服务端（`server/`）+ 注册页文案，客户端二进制和 `relay.py` 一个字节没动
⇒ 只需重启服务端，不用重打客户端包。**

## 做法

先用 `tools/re_bs.py`（capstone）把三个问题逆到指令级，再动代码。

### 用户中途追问的两件事（都逆完了才答）

- **「结算触发是不是也该改成全队合成分？」→ 不用改。** `0x55bf20` 第 ② 条比的是
  **个人分**对个人上限，组队只是上限更低（`人数//2` → 4/6/8）。
  `pvp_score_limit()` 早就照抄了这一份（D139），**只有「判谁赢」漏了队伍**。
- **「右上角比分榜能不能显示队伍分？」→ 原版就是个人榜，任何包都改不动。**
  排行表重建 `0x55c2c8` 确实有队伍排法，但 `GameContextNewPvp` 的构造函数
  在建完胜负条件的**下一条指令**就把开关 `[victory+0x181]` 置成 1
  （`0x497c44`）。和 §220「MAX N 开局定死」同一类：纯客户端内存字节。
  要改只能 patch `bshook`，那是**改原版行为**不是修 bug，另案（见「剩下什么」）。

## 四条各自的根因和修法

| # | 根因 | 修法 |
|---|---|---|
| 1 | `RoomQuest.ranking()` **连 `teams` 参数都没有** —— 生存/格斗那一路 §204 早就按队伍判了，夺分/计时这一路漏了 | 照抄 `DeathMatchVictoryCondition` 虚表槽 14（`0x55bfda`）：组队比两队合成分（总分优先、平了比总死亡），个人战用 `(分数+1)*1000-死亡数`、全员并列不判（D147）|
| 2 | `0x0302` 第 4 个字段 = **随机地图开关**，服务端解出来存进 `flags` 之后再没用过；回的 `0x0303` 恒发 0 → 客户端 `[LobbyStage+0x14]` 被清、按钮弹回 | `Room.random_map` + `0x0303` / 房间列表原样回传；**seed 每局重取**（以前恒 0，随机图会永远随到同一张）；开局后房主那一发汇报型 `0x0302` 只记账不回包（D149）|
| 3 | `settle_quest` 里一个 `score` 当五份用 | 新增纯函数 `quest_reward()` / `pvp_reward()`：关卡固定奖励 × 难度系数 + 少量分数加成；对战 = 底薪 + 每杀 + 胜方加成（D148）|
| 4 | `exp // 100 + 1`，线性无上限 | 二次曲线：升一级 `100 × 当前等级`，累计 `50·L·(L-1)`；**上限 60**（`LevelMark.smf` 就 60 帧）（D150）|

### 第 4 条连带的两件事（用户点名要求）

- **老存档迁移**：云服上真有一批号被旧曲线刷到了好几百级。用户拍板
  **「按经验重算，该降就降」**（旧 300 级 → 24 级，经验一分不动）。
  新增 `AccountStore.realign_levels()`，`app.py` 启动时跑一次、把
  「谁从几级变成了几级 / 谁是被 60 级钳住的」打进日志 **和 `eventlog`**
  （`server.out` 每次启动被覆盖，云服又是 `--no-control`）。
  ★ **幂等**，跑完一次清单为空、不写盘，所以不需要 bump `schema_version`。
  ⚠ 踩到的坑：`_merged_account()` 在读的那一刻就把 `level` 重算掉了，
  「旧等级」必须从**原始 JSON 的生字典**里取，否则清单永远是空的。
- **存档转移助手手改等级**：规则从「只能往上抬」改成 **「等级说了算」**（D151），
  网页提示同步改写。★ 但「两个字段一致时原样保留经验」这一条不能省 ——
  否则一次「导出 → 原样导回」就会把本级内攒的经验抹掉（1200 → 1000）。
  ★ 还有一条：`level` **没写在存档里**时要以经验为准 —— `import_account`
  是从默认值起手的，默认等级 1，少了这条判断，一份只写 `experience`
  的手写存档会被当成「他想要 1 级」，经验当场清零。

## 后半场：地上捡到的金币进结算，金币不再吃分数加成（§230 / §231 / D152）

用户随后提出：闯关里怪和 boss 会掉金币、对战里偶尔也掉，**结算时那些金币要
并进「金币 +N」**；既然如此金币就不该再吃一份分数加成 ——
**金币 = 固定值 + 本局捡到的金币**。

### 动手之前必须先回答的问题：客户端是不是已经自己加过一遍了？

**没有。** 逐指令查完（§230）：

- 两种金币共用的 `vf_d4` = `0x51f447`，走的是 `vf_11c(角色)`「当场生效」那条；
- `CoinItem1::vf_11c`（`0x52156f`）/ `CoinItem5::vf_11c`（`0x521b2c`）
  从头到尾**一句金额算术都没有** —— 播一个 `Item-EatCoin` 音效、放个特效，完；
- 两个构造函数逐字节对照只差 vftable 和模型串（都 `push 0xf`），
  **没有任何区分面额的常量**；
- 金币全局 `[0x72e330]` 的 **14 处**引用里，`0x41a541` 是 HUD 读取、
  `0x444`~`0x45d` 一带是大厅 UI、`0x5518bd` / `0x5523e8` / `0x553872`
  分别是 `0x0411` / `0x0309` / `0x0600` 三个包的处理器 ——
  **战斗代码段（`0x47xxxx`~`0x52xxxx`）一处都没有**。

⇒ **金币的面额和记账本来就是服务端的活**，加进去不会重复计数。
顺带勘误了 `packet_api.md` 里「当场生效：金币加钱」那一句 ——
那是当年从「当场生效」四个字推出来的，没核过。

### 修法

服务端手上的数据本来就够：`0x0406` 带物件 id（`remember_item` 早就记了，
§194 当初就是为了这个），拾取**仲裁**又在服务端。所以：

- `RoomQuest.coins[座位]` + `add_coins()` / `coins_of()`；
- 在 **`claim_item()` 成功那一步**按 `item_id_of(handle)` 查面额入账。
  ★ **不能记在 `grant_picked_item()` 里** —— 那个函数第一句就是
  「不是可入槽的道具就 return」，金币根本不进道具槽，会被当场挡掉。
  仲裁那一步还天然只算一次（第二个人来要时 `claim_item` 返回 False）。
- `quest_reward()` 去掉 `+ 分数//10`；`pvp_reward()` 去掉 `+ 10×杀敌`
  —— **杀敌数就是对战的分数**，留着就等于两套口径。现在两种玩法一致：
  **技术好走经验，捡得勤走金币。**「胜方加成」保留（那是固定值，不是分数加成）。
- `settle_quest` 里 `gained_money += quest.coins_of(seat)`，日志写成
  `金币+X（固定 A + 捡到 B）`。

## 第三场：掉落枚数（§231）—— 资源里没有表，全在客户端代码里

用户提示 `Data/Quest/LevelQuest/`。**那里没有，全树也没有。**

| 找过的地方 | 结果 |
|---|---|
| `Data/Quest/LevelQuest/*.txt` / `*.uni` | **过场对白**（TSV + 列名表），指令是 `wideon` / `fadeout` / `$BackToLobby` |
| `Data/Quest/Quest01..07/boss*.ini` | **boss 战斗参数**（`PartCraneHp` / `MissileDamage` / `JumpChaseSpeed`…），无掉落字段 |
| `Data/Mob.ini`（24 个怪）| `Type/Hp/WeaponId/Carrier/Suicide…`，无掉落字段 |
| `HunterMob.ini` / `MobAbility.ini` / `GameProps.ini` | grep `coin\|money\|drop\|item` **零命中** |
| `Data/Item.ini` | 只有 10300+ 带 `CharAttr` 的道具，**金币不在里面** |
| 1059 个 `.evn` | 模型动画事件（`<ArrayOfEvent>`），`Models/Items/Coin.evn` 是金币自己的音效 |
| 174 个 `.map` | 二进制物件布局 |
| `ShopItem*.ini` | **只有图片和 Tag，没有价格** —— 物价也是服务端的活 |
| `*.lua` / `*.lc` / `*.script` | **一个都没有** |

⇒ 转去二进制。`0x4939c0`（造掉落物 + 发 `0x0406`）**全镜像只有 6 个调用点**，
其中**掉金币的只有两处**：

| 路 | 掉什么 | 掉几枚 |
|---|---|---|
| **通关金币雨**（七个关卡上下文各一份，代码完全相同：`0x4a6557` / `0x4a748c` / `0x4a7f5d` / `0x4a8c84` / `0x4a986f` / `0x4aa53d` / `0x4ab22d`）| 金币×1（10101）| `20 × 通关时存活人数`，撒 `(人数+5)` 秒，**只有房主的客户端发**（`0x4a5410` 比座位）|
| **可破坏场景物**打碎（`BreakableObj` 虚表槽 55 = `0x4fa981`）| 金币×5（10102）| `rand()%100 < 6` → 1 枚。对战和闯关都有 ⇒ **「对战里偶尔掉金币」的来源** |

- 「存活人数」= `0x493cb2`：扫 6 个座位问胜负条件槽 4（`0x55e0a3`
  = `最大命数 − 已死次数`），`> 0` 才计数；
- 角色死亡那条掉落（`0x508ce4`）掉的是 **10603 减速地雷**，不是金币；
- 其余掉落走 `GameContext::vf_e8(itemId)`，唯一外部调用点 `0x52e3fe` 是
  **lua_tinker 绑定**（留给关卡脚本的）—— 而资源树里一个脚本文件都没有
  ⇒ **怪物和 boss 本身不掉金币**；
- **第七关多一道门**（`0x4ab21c`）：`[LobbyStage+0x400] == 3` 才撒，否则 0 枚。

### 于是面额可以反推了

金币雨枚数跟人数线性 ⇒ **人均恒定 20 枚**（原版按「每人一份」设计）。
取 `{10101: 10, 10102: 50}` ⇒ **一局通关人均 200 金币**：
低级关卡（固定 100）能翻一倍，高级关卡（固定 1000）占两成。
「捡得勤有回报」成立，又不会盖过「打的是哪一关」这个主导项。

⚠ **实际到手会少一些**：撒币要 `(人数+5)` 秒，而客户端在通关**6 秒后**
就发 `0x040f` 弹结算（§167）—— 两人以上时尾巴那段来不及捡
（能捡的约 `20n × 6/(n+5)` 枚：n=1 全部、n=3 约 45/60、n=6 约 65/120），
而且还得真的走过去踩到。**待验证表第 49 条仍然留着**，但从「凭空标定」
变成了「验证一个有依据的数」。

## 剩下什么

- ⏳ **全部都要实机验收**（见 PROGRESS 待验证表第 43~49 条）。
  ★ 第 **49** 条是**金币面额的复核** —— 枚数已经从客户端逆出来了（§231），
  面额也按它反推过了；实机要确认的是「理论人均 200 里实际能拿到多少」
  （日志里 `捡到 B` 那一格）。
  ★ 迁移那一条**上云之前先拿线上 `accounts.json` 的副本在本地跑一遍**，
  看清单对不对再上线。
- ⚠ **seed 每局重取是本轮唯一「所有对局都会变」的改动**（以前恒 0，
  出生点之类的随机项每局都一样）。验收时专门看一眼普通对战和闯关照常加载。
  回退杠杆：`StartGameHandshake(seed_source=...)` 注入常量。
- 没做、建议另案的三条：右上角比分榜改队伍分（要 patch `bshook` 的
  `0x497c44`）、晋级任务系统（`Promotion.ini` 那 132 条一次性奖励）、
  天梯分（`0x0309` 第 11 格恒 0）。
- 上一轮的遗留还开着：§225 第六节第 4 条（`relay.py` 收到 `PONG` 就丢、没量 RTT）、
  待验证表第 42 条（UDP 的 A/B 对照）。
