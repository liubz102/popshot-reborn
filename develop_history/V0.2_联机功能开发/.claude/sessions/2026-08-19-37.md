# 会话 37（2026-08-19）—— 局号改成**服务端权威的换代号**：删掉 2 秒窗，`0x0303` 直接对齐

## 用户报的

会话 36 定案的修法（D134：局号只在「两边都稳定 2 秒」之后才改写）用户不认：

> 「加一个 2 秒的窗口，窗口内的包不改写」只是治标不治本，没有从根本上改变
> 转发错位的问题，而且 2 秒是大是小也无法确定。请分析这个 N 究竟有什么意义、
> 原版想解决什么问题；针对原版想解决的问题，我们的服务端（包括中继）应该去
> **模仿原版服务端的动作，主动维护换代的各个状态**，而不是单纯转发 + 时间窗绕过。
> 另外：原版服务端到底有没有改写局号的逻辑？如果没有，它怎么处理局号不一致？
> 是不是有某个机制强制让所有玩家局号同步？

用户还给了参考方案：服务端建一张「房间 - 各客户端 - 各自局号」的映射表，
按事件判定，「过渡期」= 从服务端发出换代广播到观测到最后一个成员换完为止。
并要求考虑加载途中掉线、房间中掉线、游戏中掉线。

## 查明了什么（§218 / §219）

**§213 的前提是错的** —— 那句「那个计数器是纯客户端本地的，服务端设不了」
把 D131 和 D134 一起带偏了。翻遍镜像之后真相是反过来的：

**客户端自己从来不会主动改这个号，它的每一次变化都是服务端某一发包造成的：**

| 服务端 → 客户端 | 处理器 | 对局号 |
|---|---|---|
| `0x0100 gspRepLogin`(0) | `0x54f2cc` → 建 `GameSession` → `0x4050f8` | **= -1** |
| `0x0203 gspRepLeaveSession`(0) | `0x54fffe` → `0x550092` → `0x552943` → `0x4054fa` | **= -1** |
| `0x030a`（被踢 / 房间没了）| `0x552880` → `0x552943` → `0x4054fa` | **= -1** |
| ★★ `0x0303 gspSession` | `0x406258` → `0x406756` → `0x556ed1` | **= 包尾那个 u16** |
| `0x0400 gspPrepareGame` | `0x551605` → `0x5517a3` | **+1** |
| `0x0403`（结算看完回房间）| `0x5518fb` → `0x551900` | **+1** |

1. **复位那条**是 `GameSession::Reset`（`0x4054fa`）第一句
   `or dword [esi+0x3c], -1` —— §213 漏的就是它。⇒ 局号的零点是**回大厅**，
   原版**没有**「打完一局全体归零」。
2. ★★ **`0x0303` 那条是原版留给服务端的「说几就是几」入口**：
   反序列化 `0x556ed1` 最后两句 `movsx eax, ax` / `mov [this+0x3c], eax`。
   我们的 `build_update_session` 一直把它当「语义未知」按 D019 填 **0**
   —— 正因为一直填 0，中途进房的人才总是从 0 开始数，`bug调查/8_2` 那种
   「老玩家 3、新来的 1」的稳定分叉才会存在。
3. **「结算 → 房间」那次换代是逐人节奏的**（各人自己点结算界面才发 `0x0403`，
   差十几秒很正常）⇒ 2 秒的时间窗在那次换代上**结构性不够**；
   而且「跨代包原样转发让客户端自己丢」在编号撞上时是**误收**（§219）。

**逐包验证**：按上表建模跑现场三条 dump（`bug调查/9/最后复现`），
**9467 发对上、6 发对不上**，6 发全部落在换代那一刹那（在途包），
其中 dk 那一发 `15:03:30.033` 正是 §217 的毒心跳。
⇒ 模型精确，「对不上」的集合恰好等于「必须按跨代丢掉」的集合。

## 改了什么

**D137 —— 服务端自己维护换代状态，按代判定转发（删掉时间窗）**

- `relayserver.PeerEpoch`：每条连接一份 `{局号值, 代号, 局号→代号历史(16),
  换代是否已确认}`。**代**永远来自我们发出去的字节（硬事实），
  **值**以模型为准、以客户端自报为校准。
- 状态迁移**全部**挂在 `Conn.send()` 认帧头 opcode（`note_epoch_from_frame`）
  —— 字节离开的地方，没有哪个发送点能漏登记。
- 代号由房间现算：`lobby.Room.advance_generation(kind)`，同 kind 幂等
  （`0x0400` 广播给六个人 / `0x0403` 各人各自触发，都必须落在同一代）。
  带锁 —— `0x0403` 是各人各自的线程在调。
- `deliver()` 只剩两条出口：**同代 → 按收件人编号盖章；跨代 → 丢**。
  「过渡期」= 从发出换代包到自报值变过来，一毫秒不多不少。
- 自报值对不上时：换代还没确认 → 当陈旧包丢；已确认 → 值重锚、代不动。
  **任何情况下都不回退到 D131 / D134 的行为**（用户明确要求）。
- 删除 `EPOCH_SETTLE_S` / `peer_game_id_since` / `_epoch_settled` /
  `_note_epoch_race`。

**D138 —— 中途进房的人靠 `0x0303` 直接对齐**

- `build_update_session` 的包尾 u16 变成参数，所有 `0x0303` 发送点都填
  **房间当前的局号**（`Room.epoch_value`：新房间 0，每换一代 +1）。
- 进房本来就要发这一发 ⇒ **一个额外的包都不用发，当场对齐**。
- 中途实现过「开局前补发 (M−v) 发 `0x0403` 顶平」那一版，查到 `0x0303`
  的字段之后**整段删掉了** —— 原版本来就有正门，没必要走偏门。
- 改写局号那条路（D131）留着当兜底，正常情况下一发都不该触发；
  真触发了日志里会点名说「对齐没生效」。

**新增取证工具** `tools/epoch_from_dump.py`：拿逐连接 dump 重跑这套模型，
逐发核对预测值和客户端自报值。下次再怀疑换代就先跑它。

## 验证

- 全量 **833 项测试通过**（`runtime\python` 3.14 和 `runtime-win7` 3.8 各一遍），
  净增 13 条。新用例覆盖：同代改写 / 跨代丢弃 / 撞号仍然丢 / 过渡期一结束
  立刻恢复 / 换代未确认时丢、已确认时重锚 / `0x0303` 带局号 / 中途进房当场对齐 /
  结算交错换代 / 加载中掉线 / 退房复位 / 重连再对齐。
- **现场字节流回放**（D136 那套客户端队列模型）改成两条对照：
  「服务端不知道换代」（= D131 老做法）→ `base` 钉在 31、开局 31 发全没；
  「服务端知道换代」（现在）→ 那一发**根本没投出去**，112 发一发不少，
  而且客户端**一发都不用自己丢**。
- 现场 dump 逐包核对（上面那 9467 / 6）。
