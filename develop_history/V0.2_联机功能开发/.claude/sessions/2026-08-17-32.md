# 会话 32（2026-08-17）—— bug调查/8_2：越界的队伍号 + 分叉的同步局号

## 交待

用户拿会话 31 重打的客户端连云服（**云服还是旧版服务端，同局其他人也是旧客户端**）
打了两局「个人对战 + 生存模式」，两局都出事，日志放在 `bug调查/8_2`：

1. 第一局：另外两人死了都不复活，用户自杀后也不复活；跑 `probe-death.bat`，
   几秒后自动结算。
2. 第二局：进去后**其他人都不会动**（但对局在正常进行，听得见死亡音效、
   看得见有人掉血）；随后**满血状态突然进了观战**；再之后死亡，同样不复活。

## 结论（两条，都是服务端的问题，都已修）

### 一、「活着进观战」和「死了不复活」= 我们发的**队伍号越界**，客户端写坏了别人的战绩

会话 31 把这两条归到「幽灵死亡上报」和「客户端 `0x0413` 断链」，
并加了重生看门狗兜底 —— **方向不对，兜底没错**。真正的链条（§212）：

- 客户端 `QuestVictoryCondition` 里两张表首尾相压：
  每座位战绩 `this + 座位*0x2c`（分数 +0x5c / 死亡 +0x60 / 最大生命 +0x64 /
  队伍号 +0x70），每队伍记录 `this + 40*(队伍号-1)`。
- 构造 `0x55e018` 和读取 `0x498ef0` 都写死**只有两队**（`cmp eax,2 / jge`），
  但每次死亡都要跑的重算 `0x48c942 -> 0x55c5f2 -> vf34(0x55c696)`
  **一个上界检查都没有**。
- 于是队伍号 >= 3 时，队伍记账写到了别人的战绩记录上。
  队伍号 4（座位 3）那一档正好把 **座位 1 的死亡次数** `+=` 掉。
- 生存模式剩余生命 `= max(0, vf_c - 死亡次数)`，而 `vf_c = 0x55db69`
  是 `push 3 / pop eax / ret 4` —— **恒等于 3**。死亡次数被踩到 >= 3 就归零：
  活着被切进观战、死了 `Die()` 在 `0x501976` 把 `[char+0x2d8]` 写成 -1，
  `0x4fe70e` 见负数直接返回，**永远不发 `0x0413`**。

现场数字对得死死的：服务端给座位 1 广播过 **1** 次死亡，
受害者客户端内存里记的是 **9** 次，而他整局只收到过**一发** `0x0406 座位 1`
（从他自己的逐包 dump 里逐帧解出来的）；座位 0 的死亡次数被 `min(旧, 0)`
压成 0。`respawn_at = -1` 也在快照里。

源头是 `lobby.default_team(座位, FREE) = 座位号 + 1`（D092）。
两人局是 1/2 不越界，所以**只在 3 人以上的个人战犯** ——
正是 §211 统计到的「15 例全在 3 人以上」和现场玩家打的「3个人就BUG」。

★ **D092 的理由是误读**：`0x4fedfc` 比队伍号那一处**不决定伤害**。
两条分支在 `0x4fee6b` 汇合，扣血 `[ebp-0x18] - [ebp+0xc]` 在汇合点**之后
无条件执行**；队伍号相同只是跳过 `0x4087c2`（往 `LobbyStage+0x404` 记
「谁打了多少伤害」的战后统计）。已在 D092 原条目上加了更正块。

**修法（D130）**：个人战一律发 `TEAM_NONE`，并在 `build_session_slot`
（所有 `0x0300`/`0x0301` 的必经之路）加一道 0..2 硬闸。
连带 `RoomQuest.pvp_finished()` 加 `team_mode` 参数 —— 非组队模式只看在座人数，
这本来就是客户端 `0x55c594` 的口径（开头 `0x409df1 == 1` 不成立就跳过队伍那段）。

**为什么不改客户端**：越界确实是客户端的洞，但**一起玩的人多半还在用旧客户端**，
客户端补丁救不了他们；而这个洞只有我们自己的服务端会喂到。

### 二、「其他人都不会动」= `UdpPacket` 头 `+4` 的**局号**分叉

中继完全无辜 —— 三个人的同步数据全程 ~8 Hz 送到，解出来的坐标是连续轨迹。
问题在收包入口的硬校验（§213）：

```asm
004078c0  movzx eax, word [esi+4]      ; UdpPacket 的局号
004078c4  cmp   eax, [edi+0x3c]        ; [GameSession+0x3c]
004078c7  jne   0x40793a               ; ★ 不等 -> 整包丢掉
```

`[GameSession+0x3c]` 是**纯客户端本地**的计数器：全镜像里只有
`0x5517a3` / `0x551900` 两处 `inc`，跟着两次阶段切换走（进战斗 +1、回房间 +1），
**没有任何服务端包能设定或清零它**。在同一个房间里多打一局就必然分叉：

| | 进房 | 第一局 | 回房 | 第二局 |
|---|---:|---:|---:|---:|
| 受害者（第一局就在房里）| 0 | 1 | 2 | **3** |
| 第一局之后才进来的三个人 | — | — | 0 | **1** |

双向所有同步包互相全丢。死亡音效和血量还照常，因为那走游戏服的 `0x0406`。

**修法（D131）**：`RelayServer.deliver()` 记下每条连接自己最近自报的局号
（战斗中 ~8 Hz），转发给谁就按谁的号重新盖章。校验和（`0x5bbdc1`）
从 `+0x0c` 起算、**不覆盖头里的局号**，所以改这两个字节不用重算。
挂在 `deliver()` 是因为它是 `0x040e` 回退和原版中继**唯一的汇合点**。

## 做了什么

- `server/lobby.py`：`default_team(…, FREE)` -> `TEAM_NONE`；`TEAM_LAYOUT_*`
  的注释重写成「为什么只能 0/1/2」。
- `server/gameserver.py`：`build_session_slot` 队伍号夹到 0..2；
  `RoomQuest.pvp_finished(…, team_mode=…)`；`Conn.peer_game_id` 字段。
- `server/relayserver.py`：`peer_game_id()` / `restamp_peer_game_id()`，
  `deliver()` 里按收件人盖章，`_note_game_id_gap()` 每对只记一行，
  `status()` 带累计改写数。
- `tools/probe_death.py`：**「最大生命」偏移改对**（会话 31 写的
  `[rule + seat*4 + 0x198]` 是夺分模式的分数上限标量，在生存局里全是垃圾，
  第一轮判断就是被它带偏的）；队伍号 > 2 直接标红；剩余生命归零时
  把「就是这条」写进结论。
- `tools/fakeclient.py`：`peer` / `rpeer` 加**局号**参数；抽出
  `build_udp_packet()`。
- **取证套件退出发布包**（用户要求，同一会话内追加）：根因在服务端修掉了，
  玩家不用再取现场。`probe-death.bat` 从根目录挪进 `tools\` 存档 ——
  里面那行调用从 `%~dp0tools\probe-death.ps1` 改成 `%~dp0probe-death.ps1`，
  文件仍是 **CRLF + UTF-8 无 BOM + 纯 ASCII**（§135 那条铁律），
  在新位置 `cmd /c "…probe-death.bat" <nul` 实跑过一遍、路径解析正常。
  `tools/build-portable.ps1` 不再往客户端包放那四个文件
  （bat / ps1 / probe_death.py / `re\vftables.json`），`BUILD.txt` 的两行提示删掉；
  `README.md` 里「死了一直不复活」和新增的「别人一动不动」两条常见问题
  改写成「已修复，只需更新服务端」。

## 方法上值得记一笔的

- **客户端逐包 dump 是可以完整还原的**，会话 31 说的「8000 次上限烧完了」
  只对**一段**成立：`bshook` 每次 `connect` 都调 `snow_log_reset()`，
  计数器归零、日志重新开闸。所以按「计数器回退」把记录**切段**，
  每段开头对 `SimpleCipher` 的 (i1, i2) 暴力试一遍 1176 种初态
  （拿帧头签名 `ff 00 ?? ?? 00 00 00 00` 定位），整局的服务端下行就都出来了。
  解析脚本在临时目录，思路记在这里就够。
- 两个把人带偏的坑：`Decrypt` 记录里的「入」是**密文**（得自己解）；
  日志里紧跟着可能是 `★loadkey#N` 的 key dump，按「读到下一条 `★` 为止」
  收十六进制会**凭空多出 16 字节**，流从此错位。按 `min(len, 256)` 截就对了。
- **`probe-death.bat` 这次是决定性的**：`respawn_at = -1` 和「死亡次数 9」
  这两个数字只有进程内存里有，靠日志永远推不出来。取证脚本值得继续养。

## 遗留 / 下一步

   队伍号 0 会读到 `this - 40`。现在组队战一律 1/2 碰不到，

   战况必然越走越远，分歧被放大。D127「只认本人上报」仍然该留着。
