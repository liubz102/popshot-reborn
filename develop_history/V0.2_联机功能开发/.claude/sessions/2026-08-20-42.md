# 会话 42 —— `bug调查/udp验证` 验收：UDP 旁路到底有没有起效

用户问：「最近改了 udp 之后……udp 有没有真正起效果？对于网络的改善有没有作用？」
日志在 `bug调查/udp验证/`（客户端日本时区、服务端美国时区，**差正好 1 小时**，
本文一律用**服务端**时间）。**只读日志，没有改任何代码。**

结论全文在 `FINDINGS.md` §225，这里只记做了什么、怎么做的、剩下什么。

## 做了什么

1. 先确认那轮改动的设计依据在哪 —— **不在 FINDINGS / DECISIONS / PROGRESS /
   sessions 里**（提交 `693fcd6` 一份文档都没留），只在
   `server/udpsync.py` 的文件头注释（四条铁律 + 线格式）。
2. `online.log` 的 `同步转发 … UDP 抢先 a/b 过期丢弃 c 等事件 d` 逐行**相减**
   （那几个计数器是累计值，`report_peer_timing` 只 reset 三个耗时表），
   得到每 30 秒的上行占比、以及 `a+c+d` vs `3×b` 的丢包核对。
3. 数 `server.out` 里 `→ 发出 … 明文` 且 `+8..9==0x040f`、内层 `0x4001` 的条数
   → **下行**还有多少走 TCP。
4. ★ 关键一步：从 `bshook` 的 `★Simple::Encrypt#` + 明文 dump 里挖出
   **客户端发出心跳的时刻**，和服务端到达分布并排 —— 这才分得开
   「源头抖」和「路上抖」。
5. 用「下行退回 TCP 的那 1214 发」按整包字节做指纹配对（掩掉 `+4..5` 局号），
   量「TCP 到达时刻 − 实际转发时刻」= UDP 的领先毫秒。

四段脚本的思路记在 §225 第七节，含两个踩过的坑（bshook 那份 hexdump 第 8 字节
后面是**两个空格**；`SNOW 入 (NN bytes)` 夹在标题行和 dump 之间）。

## 结果（一句话）

**在跑，很干净，但这一局没什么可救的。**

- 上行 97% / 95% / 8% 抢先，下行 **97.6%** 走 UDP，跨境 UDP 丢包 0.01~0.03%，
  全窗口 **0 发讨重传**（铁律 3 的闸门有效）。
- 111 个 30 秒窗口里，`转发间隔 p95` 比 `到达间隔 p95` 平均只好 0.0~0.2 ms；
  **只有 1 次**真救援（13:52:33，三人同时，省了 222/182/126 ms）。
- 原因：testuser1 的**发送侧 p95 = 到达侧 p95 = 130 ms**，链路一毫秒没加
  （`bug调查/9` 当时是 432 ms）。testuser3 是**虚拟机**，发送侧就 p95 233 ms
  —— 卡在它自己的游戏循环。
- 「UDP 抢先 8%」不是坏事：正常时 UDP 只早 **0~2 ms**，是照相冲刺；
  输了也没有损失（TCP 那份照样即时转发）。

## 后半场：把 §225 第六节的前三个小毛病修掉（用户当场要求）

**改动全在服务端 + 客户端包里的 `relay.py`，客户端二进制一个字节没动。**

1. **误报的「⚠ 20 秒没等到服务器回应」**（`relay.py`）
   新增 `first_hello_at`（每条游戏连接清零）和纯判据
   `UdpSyncRelay._quiet_warning_due(now)` —— 抽成一个方法是为了能单测，
   `_pump_timer` 是死循环。三条**都**成立才提示：没提示过 / 从**第一发
   HELLO** 起算够 20 秒 / **这条游戏连接一个回应都没收到**。
   ★ 第三条用的是新加的 `replies`（每条连接清零），不是 `received`
   （整个进程累计）—— 否则「先连好服务器、再换一台没放行 UDP 的」
   就永远不提示了。顺手删掉了因此变成死字段的 `started_at`。
2. **每次登录必刷的「认不出票据」**（两版，第一版被否）
   - **第一版（已废）**：`NACK_LOG_AFTER = 2`，跳过头一发。
     用户当场否掉，并立成一条通用规矩：**所有判据都要事件驱动，
     不许用固定次数 / 固定时间** —— 那个 `2` 是拿这台机器上
     「登录包 0.2 秒就处理完」当常量，慢机器 / 慢线路 / 虚拟机上就不成立，
     **它掩盖竞态而不是消除竞态**。已写进用户的全局 `CLAUDE.md`
     和 `DECISIONS.md` D146。
   - **第二版（定案，D146）**：找「真正区分这两种情况的事实」——
     它在**服务端**手里。服务端有票据表，分得清「票据是我们签发的、
     只是还没有哪条游戏连接认领它」和「根本不认识这张票」。
     于是加结果码 `udpsync.ACK_NOT_LOGGED_IN = 3`（`_on_hello` 查不到连接时
     先问注入进来的 `ticket_known`），中继按它分流：前者安静等，
     后者**第一发就报**、且只在状态翻转时报一次（`refused_logged`）。
   - 票据有效性用新加的 `TicketStore.is_live()` 问，**不是** `resolve()` ——
     后者每次调用都续期，而这只是旁观者在问「这张票是不是真的」；
     旁观者能续期的话，一个只会重发 HELLO 的客户端就能把一张从没登录过的票
     养到永不过期。
   - 线格式没变、版本号不动：老中继把新码当「不是 OK」，新中继连老服务端
     收到的仍是 `ACK_BAD_TICKET` —— 两个方向都只是退回今天的行为。
3. **`status()` 少了 `delivered_udp`**（`relayserver.py` + `gameserver.py`）
   那行改成「投递 UDP x / 中继 y / 回退 z」。
   ★ 查的时候发现 `RelayServer.status()` **一个调用者都没有** ——
   控制通道的命令表里根本没它。只改字符串等于白改，所以补了一条控制命令
   `relay`（和 `rooms` / `delroom` 一样不需要连接）。
   ⚠ 云服默认 `--no-control`，线上要看下行占比还是得数日志。

**验证**：新增回归 19 项（`RelayNoticeTests` 11 + `ServerTests` 4
+ `TicketStoreTests` 2 + `StatusLineTests` 2），全量 **942 项**双运行时全绿。
另外用真 socket 端到端跑了三个场景：
① 压着 `UDP_QUIET_WARN_S=1` 空转 3 秒（游戏没连上）一行不打、HELLO 之后
1.2 秒才警告；② 登录竞态（票据真、还没登进来）5 秒里一行不打，
登录完成后只有一行 ✓；③ 票据真过期，重试 3 发只打一行。
★ 跑 3.8 时撞到一次 `test_account_store` 的
`os.replace` `WinError 5`（临时目录被占），连跑 8 轮只出现 1 次，
和本次改动无关（那条测试碰都没碰到），**是这台机器上的老 flake**。

## 剩下什么

- **待验证表第 42 条**：同一场会话里做 A/B（`--no-udp-sync`），
  而且**要用 `start.bat`**，别再用 `start-debug` —— 逐包落盘本身在加抖动。
  现在这份数据分不开「那天网络好」和「下行搬走之后 TCP 也跟着好了」。
- §225 第六节第 4 条（`relay.py` 收到 `PONG` 就丢、**没量 RTT**）还开着。
  补上它才能在客户端侧直接看到「这条 UDP 比 TCP 快多少」，
  而不是像本次这样从服务端日志反推。
- ★ 1 / 2 两条改的是 `relay.py`，它在**客户端包**里 —— 玩家要看到效果
  必须**重打客户端包**（`toolsuild.bat`）；3 只要重启服务端。
- `logs-client2` 那次退出是 `exit code 0xC0000005`（15:05:31，
  正在重新登录、刚打完「开闸」那行），**在测量窗口之外**，本次没查。
