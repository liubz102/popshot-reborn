## 用户原话

在注册页「存档转移助手」上面一行并排加「修改密码」「修改昵称」两个按钮；
点击后打开对应 popup。修改要先验证旧密码，新密码输入两遍；两个修改操作不加提交
频率限制；popup 只能点右上角关闭，点击变暗背景不能关闭。

## 做了什么

### ① 账号存储层（§197 / D116）

`server/account_store.py` 新增：

- `_require_password_unlocked()`：在调用方已经持锁时校验账号和旧密码；
- `change_password()`：验证旧密码后复用注册密码规则，原子写回新密码；
- `change_nickname()`：验证旧密码后复用现有昵称规则和大小写不敏感查重，允许保留
  自己当前的昵称，留空则改回用户名。

三者的关键边界是：`AccountStore` 每次会重写整份 JSON，所以「验旧密码 → 修改 → 写盘」
必须落在同一个 `RLock` 临界区，不能拆成一次 `verify()` + 一次独立写盘。

### ② HTTP 接口

`server/web/server.py` 新增：

```text
POST /api/change-password
     {username, old_password, new_password, new_password2}

POST /api/change-nickname
     {username, old_password, display_name}
```

- 两遍新密码前台先检查，后台再次检查；
- 两条接口完全不查询、不标记 `RegisterRateLimiter`；
- 成功操作写 `[online]` 运营事件，但日志不包含旧密码或新密码；
- 昵称修改成功提示明确写「重新登录后生效」。游戏连接的 `self.account` 是登录时的
  副本，本次没有侵入在线房间广播去做热改名。

### ③ 页面和 popup

`server/web/index.html`：

- 「修改密码」「修改昵称」放在同一个 `.account-actions` flex 行，下一行才是
  全宽「存档转移助手」；
- 两份独立 popup 均有右上角关闭按钮；密码表单为用户名 / 旧密码 / 新密码 / 再次输入；
  昵称表单为用户名 / 旧密码 / 新昵称；
- 把原存档助手也接进同一个 `bindPopup()`；只有 `closeId` 的 click 会移除 `open`，
  mask 本身和 Escape 都没有关闭监听；
- 打开 popup 时聚焦第一个用户名框。
