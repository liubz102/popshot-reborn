# 会话 36（2026-08-19）—— 「第二局打不死人」现场定案：**D131 是根因、D134 是修它**

## 用户报的

会话 35 把探针改成调试模式常驻之后，用户挂着玩，**一把就复现了**。
日志放在 `bug调查/9/最后复现`：

- `logs-server/` —— 云服三条游戏连接的逐包 dump（`game_032/033/034`，双向）+ `online.log`
- `logs-复现电脑/` —— 探针日志 `probe_sync_20260819_160013.log` + bshook（verbose）
- `logs-同局其他电脑/` —— 另一台的 bshook（normal，没探针）

现场：日本时间 16:02 那一局，**进去第一把就出现**。

## 结论（一句话）

**会话 32 D131 的局号改写就是根因，会话 33 写好的 D134 就是修它 —— 只是还没部署。**
§216 末尾那句「数量对不上、所以 D131 不是现场那一局的根因」**是错的**，
详见 §217 第三节：毒性**不在丢了几发，在丢的是哪一发**。

## 怎么查的

1. **对表**（服务端时钟 = 客户端 − 1:00:02.2，用「换局那一刹那」校的）：
   房间 #19，`test2` = 座位 0（房主）、`test1` = 座位 1、`dk` = 座位 2（复现者）。
   只打了一局（局号 1，15:03:29.96 ~ 15:07:53）。
2. **写了一套 dump 解析器**（scratchpad）把逐连接 dump 还原成结构：
   `0x040e`/`0x040f` 的 12 字节 `UdpPacket` 头、内层 opcode、序号、局号、
   心跳里的 N，以及 `rpExplode` 的目标句柄和 f32 伤害。
3. **切纪元顺序**：座位 0 `.964` → 座位 1 `30.008` → **dk `30.390`（最后，晚 426 ms）**。
   `15:03:30.036`/`.046`：服务端把 dk 那发**局号 0、`0x4001`、N=31** 的心跳
   **改写成局号 1** 投给另外两台 —— D131 的回归，**逐字节比对确认**。
   ⇒ 两台的「座位 2 队列」被钉成 `base=31`、已激活=1。
4. **转发这一侧一个字节都没错**：dk 本局 112 发事件（seq 0..111 一个不缺）
   服务端**逐字节原样**全投给了两台，局号都是 1；探针也显示 **dk 自己的收包侧
   全好**（座位 0 的 `base=上界=102`，102 发一发不落）。**单向失效坐实。**
5. **症状那一侧**：dk 对座位 0 命中 32 发 **713 点**、0 次击杀；`test2` 整局
   **一次都没报过自己死**；反向 `test2` 打 dk 每发 27 点、**5 发 135 点正好打死**
   （两次都是），三方对表一致 ⇒ 收方按 `rpExplode` 里的伤害数字直接结算，
   机制没问题，就是 dk 的包在那台不生效。
6. **补完 §216 缺的那一环**（关键）：把消费者
   `GameSession::ProcessReliableQueue`（`0x407c84`）那张 switch 表里每个分支
   push 的宽字符串逐个读出来 —— 内层 opcode 终于有名字了：
   `rpChangeWeapon` / `rpFire` / `rpExplode` / `rpSplashDamaged` / `rpJump` /
   `rpDash` / `rpCrouch` / `rpRespawn` / `rpReqState` / `rpRepState` /
   `rpReqDie` / `rpAiMsg` / `rpGuard` / `rpCreateTotem`。
   - dk 被吃掉的 seq 0 就是本局的 **`rpChangeWeapon`**，后面还有 **9 发 `rpFire`**；
   - `rpFire` body 里**没有弹体句柄**，`rpExplode` body 头 4 字节**是**弹体句柄
     ⇒ 收方必须自己按同样的顺序分配；
   - 现场 30 发 `rpFire` 的句柄**步长恒定 +4**（0x493e2 … 0x49456，
     29 个步长一个例外都没有），`test2` 换武器之后弹体数从 3 变 1、步长也跟着变；
   - ⇒ 少喂一发，收方那台的句柄分配器**永久错位** ⇒ 之后每一发 `rpExplode`
     都指向不存在的弹体 ⇒ **整局零伤害**。「队列会在 `seq == base` 那一发
     自己恢复」只恢复了传输，**恢复不了游戏状态**。
   - 旁证：三份 dump 里**一发 `0x4002` 讨重传都没有** —— 比 `base` 老的号是被
     `Insert` 静默丢掉的，消费者根本看不见空洞。
7. **「打不死」这个观感的最后一环**：dk 的客户端算出对方 HP 归零 → 发 `0x0408`
   → 被服务端的幽灵死亡过滤挡掉（本人那台没死）→ **没有 `0x0406` 广播**
   → 客户端不会调 `Character::Die()` → 屏幕上人还站着、血剩一丝。
8. **顺带纠正 §216 三处**：`ResetQueues`（`0x407678`）有**五个**调用点不是两个；
   `PktQueue +0x10` 是「待收（空槽数）」；`Grow` 的 resize 和 `FlushTo` 的 erase
   都是标准 vector 操作（所以「中毒后槽位里留野指针」这条不成立，查的时候怀疑过）。

## 改了什么

**转发逻辑一个字没动**（D134 早就写好了，这次只是验证它挡得住现场那一发）。

1. **`server/test_relayserver.py`（D136）**：加了一份**客户端收包队列的模型**
   （`PktQueue` / `PeerClient`，逐字段逐分支对着 `re/BigShot_22524.img` 抄，
   地址写在每个方法上），把现场那串真实字节灌进**真的 `RelayServer.deliver()`**：
   - `EpochRaceFieldReplayTests`：两条用例只差 `_epoch_settled` 让不让改写。
     D134 之前 → `base` 钉在 31、开局 31 发（含 `rpChangeWeapon` + 9 发 `rpFire`）
     全没；D134 之后 → 那一发不改写、客户端自己按局号丢掉，**112 发一发不少**。
   - `PktQueueModelTests`：7 条，把会话 34 在**真客户端**上逐条测过的那张表
     照抄成断言（只入队不派发 / 第一发心跳定基线 / 停在空洞 / 小毒性自愈 /
     复位后重新定基线 / 自己那条不要求已激活 / 同号去重）。
2. **`server/gameserver.py`**：`describe_peer_header()` 解出**内层 opcode 的名字**
   （新增 `PEER_INNER_NAMES`）和心跳里的 `N=`；`--verbose` 下**每发** `0x040e`
   都打一行解出来的头（原来走的是那个对同步包必然抛的 "string + int32*" 试解）。
3. **`server/relayserver.py`**：`局号分叉` 那行日志带上**两边各自换局号距今多少秒**
   （新增 `_epoch_ages()`）。`EPOCH_SETTLE_S` 唯一挡不住的情况就是
   「某台机器切纪元慢了超过 2 秒」，真撞上了那个秒数会紧贴阈值。
4. `server/test_room.py`：3 条钉住上面那个头解析。
