# 会话 31（2026-08-17）—— bug调查/8：幽灵死亡上报 + 重生看门狗

## 交待

用户把打包发出去之后收到两条反馈，日志放在 `bug调查/8`：

1. 3 人以上对战（尤其个人战）有时**人死了不复活**。这个问题之前用 GLM 修过一次，
   没修好。
2. 有时**人还活着，画面却突然进了观战模式**，人物还能动，左键开枪变成切视角。

另有一份 GLM 的最新修改差分放在 `bug调查/8_glm修正差分`，要求评估对错。

## 做了什么

### 一、把当天的日志全量对过一遍

`server-logs/server.out` 3.0 亿字节（`--verbose`）。做法是先 grep 出死亡 /
重生 / 开局 / 结算 / 座位证据五类行（12091 行），再用脚本按「一局」切开，
逐条把每一发死亡广播配上「哪几台机器报过 / 5 秒后有没有 `0x0413`」。
conn->座位 用**本局内**的证据交叉确认（重生请求 id、结算行、聊天座位、
用道具座位、拾取座位、加入/离开座位），跨房间的证据一律不用。

结论（详见 §211）：

| | 数量 |
|---|---|
| 玩家死亡广播 | 613 |
| 其中受害者**本人没报过**（幽灵） | 46（≈10%）|
| 幽灵里照常重生的 | 42 |
| 该重生却没重生（下发次数 < 3） | **15，全在 3 人以上的局** |
| 15 例里是幽灵的 | 5 |
| 15 例里是自爆的 | 3（而当天 30 例自爆有 26 例正常重生）|
| 同一句柄 5 秒内被广播两次 | 4 对（2 对是怪）|

关键反例：房 #48 21:17:30 座位 0 的**第 3 次**死亡照样重生了 —— 「命用完了」
这条解释当场被否掉。

客户端侧：空空那份 10.5 MB 的逐包 dump 里，卡住之后 `0x040e` 照常 8 Hz、
内容帧帧不变（= 角色确实冻在死亡状态），聊天和结算都正常收发，就是没有
`0x0413`。房 #51 的 L47 一边卡着一边打字「我又观战了」「不能复活了」，
座位 2 打字「3个人就BUG」。

试过但走不通：想静态反汇编 `0x4fe78f` 那条发送链把守卫看清楚 ——
磁盘上的 `BigShot.exe` 是压缩壳（`.text` VirtualSize 0x236000 / Raw 0xcf800），
capstone 拿到的全是壳数据。要闭环只能在**卡住的进程**上跑
`tools/probe_death.py`。

### 二、对 GLM 差分的评估

| GLM 的改动 | 结论 |
|---|---|
| D127 玩家死亡只认本人上报 | **方向对，采纳**（但它对第 1 条症状没用）|
| D128 服务端权威计数 + 3 秒时间窗 | **一半对**：权威计数采纳；时间窗只该给怪，给玩家加窗只会多一种「真死亡被吃掉」|
| D129 凶手==自己座位改写成 0xff | **不采纳** —— 证据不支持，GLM 自己的注入实验也已证伪 |
| 「死了不复活」的兜底 | **完全缺失** —— GLM 自己在 §211 里写了「确切机制没有闭环」，然后只放了一条被证伪的缓解 |

也就是说 GLM 的差分修好了症状 2、没修症状 1（用户报的主症状），
另外还带了一条无依据的行为变更。

### 三、改了什么

`server/gameserver.py`：

`tools/fakeclient.py`：`die [次数] [座位]`，第二个参数给别人的座位就是一发

### 五、现场取证脚本（用户要求，同一会话内追加）

根因还在客户端侧、只能等玩家再撞上时读现场 —— 而撞上的人是**拿发布包的玩家**，
不是开发机。所以做了一套双击就能跑的取证：

- `probe-death.bat`（**纯 ASCII / CRLF / 无 BOM**，§135 那条铁律）—— 只负责转发，
  中文一个字都不放。
- `tools/probe-death.ps1`（UTF-8 with BOM / CRLF，和 `launch.ps1` 同规格）——
  自己 `Get-Process BigShot` 找 pid（**不用手输**；开了两个客户端就每个各采一份），
  先给 6 秒倒计时让人切回游戏（★ 游戏不在前台时主循环几乎不跑，读数会冻住），
  然后跑 `probe_death.py` 盯 90 秒，写 `logs/probe_death_<时间>_pid<pid>.log`，
  最后把判据行摘几条打在屏幕上并提示「把这个 log 发回来」。
- `tools/probe_death.py` 的 `verdict()` 补了一行：`[char+0x614]` 非 0 时亮出来
  （标成「待现场坐实」，不下断言 —— 那条守卫是 bug调查/8 记的，还没实测过）。
- **打包脚本一并改了**（`tools/build-portable.ps1`）：`probe-death.bat` /
  `tools/probe-death.ps1` / `tools/probe_death.py` / `re/vftables.json` 进客户端包，
  `BUILD.txt` 和 `README.md` 各加一段说明。`probe_*.py` 本来是「开发工具不进包」，
  这一个是例外，理由写在打包脚本的注释里。

踩到的两个坑（都已修，记下来免得下次再踩）：

1. `Start-Process $env:ComSpec -ArgumentList '/c', $cmd` 里同时有「带空格的路径」
   和 `>>` 重定向时，cmd 报「文件名、目录名或卷标语法不正确」——
   要把整条命令**再包一层引号**：`/c ""a" "b" ... >> "c" 2>&1"`。
2. `Start-Process -PassThru` 回来的对象不留句柄，进程结束后 `.ExitCode` 恒为
   `$null`，于是 `$null -ne 0` 恒真、每次都误报失败。启动后立刻摸一下
   `$run.Handle` 就好。

- **取证窗口开关**：`--respawn-watchdog 秒`（`app.py` 和 `gameserver.py` 都加了，
  `0` = 关掉兜底）。★ 没有它这套取证就跑不起来 —— 兜底一开，卡住的人 8 秒就被
  捞起来了，根本来不及切出去双击 bat。要闭环根因时，云服临时用
  `--respawn-watchdog 0`（或调大到 60）再复现。它同时也是这条新自动行为的急停开关。

验证：`.\probe-death.bat <nul` 非交互跑通三条路径 —— 游戏没在跑（退出码 2 +
中文指引）、正常采样（拿 `cmd.exe` 改名成 `BigShot.exe` 当靶子，日志头 +
探针输出 + UTF-8 编码都对）、以及打包 helper 的干跑（四个文件都按各自编码进包）。
