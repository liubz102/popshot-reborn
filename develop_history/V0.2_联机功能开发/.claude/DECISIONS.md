## D061 战斗内同步方案 = **先探查再定**，不预先押注

- **决策**：里程碑 J 拆成 J.1 探查 → **J.2 停下来问用户** → J.3 实现。
  在 J.1 拿到实测结论之前，不写任何 UDP / 中继代码，也不预先承诺哪种架构。
- **理由**：
  1. 现有线索（FINDINGS §122）只够支撑「大概率是 P2P UDP + TCP 中继兜底」这个**推论**，
     没有一个字节的实测。押错方向的代价是整段白写。
  2. 两条路的工作量差一个数量级：P2P 只要服务端转发对端地址；
     TCP 中继要从零逆 `RelayConnection` / `rcpRegister` 那套帧格式。
  3. 这直接决定「云端联机到底能不能打」，是产品级取舍，应该由用户拍板而不是 agent 替他定。
- **被否**：直接实现服务端中继（可能白做）、直接做 P2P（云端可能不可用）。
- **反悔条件**：J.1 发现同步其实就在 gcp/gsp 里（比如 `0x040a`/`0x040b`/`0x040d`
  之一就是位置包），那这条决策自动作废，直接实现即可。
- **来源**：用户在 V0.2 会话 01 明确选择「先探查再定」。

## D062 服务端包 Windows / Linux **两边都自带独立 Python 运行时**

- **决策**：`tools/build-server-package.ps1` 产出的服务端包里同时带
  `runtime-win/python/`（复用现有 CPython 3.14.3 embeddable）和
  `runtime-linux/python/`（`python-build-standalone` 的 `x86_64-unknown-linux-gnu`）。
  `start.bat` / `start.sh` 各自挑对应的那份，**目标机什么都不用装**。
- **理由**：用户明确选择。开服的人不一定懂 Python 环境；云主机镜像自带的 python3
  版本参差（有的还是 3.6），而 `server/` 用了 `str | None` 这类新语法。
  自带运行时把「版本对不对、pip 装没装」整类问题一次消掉。
- **被否**：依赖系统 `python3`（包只有几百 KB，但要写版本检查和一堆报错提示）；
  只自带 Windows 那份。
- **反悔条件**：Linux 运行时体积或授权成为问题时，退回「优先用自带、找不到就用系统 python3」
  的双轨兜底 —— 但不能反过来（默认系统 python3）。
- **注意**：下载 `python-build-standalone` 时**必须记录 SHA-256** 并写进 FINDINGS，
  沿用 V0.1 D055 对内置 CPython 的做法；上游许可证随包保留。

## D063 单机模式的本地服务端也监听 `::`

- **决策**：客户端包里那个「单机游玩」用的服务端，和云端服务端**用完全相同的监听方式**
  —— `socket.create_server(('::', port), family=AF_INET6, dualstack_ipv6=True)`。
  不为单机单独做一套只绑 `127.0.0.1` 的分支。
- **理由**：
  1. 用户明确选择。
  2. 铁律 8 要求单机和云端共用同一套代码，**差异只能体现在配置上**。
     为单机加一个「只绑本机」的分支，就等于开了两套行为的口子。
  3. 顺带白送一个能力：想在局域网开黑的人不必去部署服务端包，
     直接让朋友填自己的内网 IP 就能连。
- **代价（要如实告诉用户，写进 README）**：玩单机时本机的 47611 / 27799 / 注册页
  三个端口对局域网开放。存的是明文密码，所以这不是零风险的。
- **被否**：只绑 `127.0.0.1`（最安全但和云端行为分叉）；
  加一个 `server.config` 开关（用户明确说监听地址「不用设置」）。
- **反悔条件**：用户改主意，或出现被局域网扫描骚扰的实际问题。

## D064 认证服和游戏服合并成**一个进程**（`server/app.py`）

- **决策**：`server/app.py` 是唯一入口，一个进程里起认证（47611）、游戏（27799）、
  注册网页、调试控制通道四个监听器。`authserver.py` / `gameserver.py` 降级为模块，
  它们的 `main()` 保留（单独调试时还能用），但监听逻辑抽成可被 `app.py` 调用的函数。
- **理由**：
  1. **票据必须跨这两个服务共享**。V0.1 靠往 `accounts.json` 里写 `active_account`
     绕过了这个问题，那只在「全世界只有一个玩家」时成立。多账号下要么合并进程，
     要么再造一套 IPC —— 后者纯属自找麻烦。
  2. 服务端包的启动脚本从「起两个进程还要各自看住」变成一行。
  3. 大厅 / 房间的共享状态（谁在线、有哪些房间）本来就该在一个进程里，
     跨进程还得同步。
- **被否**：保持两个进程 + 用文件或本地 socket 传票据（多一层故障面，且 Windows 上
  文件锁很难做对）；把认证服的功能塞进游戏服（端口和协议完全不同，混在一个类里更乱）。
- **反悔条件**：将来真的要把认证独立部署（比如多台游戏服共用一个账号中心）。
  那时 `AccountStore` 换成 HTTP 客户端即可，`app.py` 的结构不用动。

## D065 联机模式靠**本机 TCP 中继**接远端，不改客户端的 `connect` 目标

- **决策**：客户端包里带一个 `server/relay.py`，联机时
  `bshook` 把 `connect` 重定向到 `127.0.0.1:47621` / `127.0.0.1:27809`，
  由中继用 `getaddrinfo` 解析 `server.config` 里的地址再转发到远端的 47611 / 27799。
  中继**纯字节转发**，不碰协议。
- **理由**：
  1. 客户端是 2007 年的 32 位程序，`connect` 的参数是 `sockaddr_in`（**纯 IPv4**）。
     需求要支持 IPv6 和域名，在 hook 里没法表达 —— 除非在本机加一跳。
  2. 域名解析放在 Python 侧比在 C 的 hook 里做省事得多，且 `getaddrinfo`
     天然吃 IPv4 / IPv6 / 域名三种写法，需求一次满足。
  3. SnowCipher / SimpleCipher 都是**有状态的流密码**，中继只能整字节透传，
     绝不能拆包重组 —— 纯转发反而是最安全的形态。
- **被否**：在 `bshook` 里做 DNS 解析后填 IPv4（IPv6 无解）；
  改客户端命令行 `/serverip:`（V0.1 §14 提到有这个开关，但地址还是 IPv4 字符串，
  且改不了「按单选钮切换」的需求）。
- **反悔条件**：实测发现客户端还有别的出站连接没被 hook 覆盖（比如公告页用 wininet），
  那些不影响游戏，忽略即可。

## D066 单机 / 联机的区分靠**重定向到不同的本地端口**，不靠中继猜

- **决策**：`bshook` 的 `det_connect` 读登录框单选钮（`1011` 单机 / `1012` 联机）的状态：
  单机 → `127.0.0.1:47611` / `127.0.0.1:27799`（本地服务端）；
  联机 → `127.0.0.1:47621` / `127.0.0.1:27809`（中继）。
- **理由**：`connect` 发生在用户点「开始」之后，那一刻单选钮状态是**确定的**，
  判定没有竞态。若改成「中继和本地服务端都听同一个端口，由谁去猜模式」，
  就得引入模式文件或握手，凭空造一个时序 bug 出来。
  端口区分是零状态的，两个后端各管各的。
- **被否**：让 `launch.ps1` 提前问用户模式（用户要求在**登录界面**里选）；
  用文件传模式（有读写竞态）。
- **反悔条件**：客户端在别的时机建连（比如登录框出现前就连），
  那时改成「默认单机，切到联机后重连」。

## D068 登录框的注册链接**由我们接管**，不去猜原版怎么处理点击

- **决策**：给 `id=1010` 那条 Static 加 `SS_NOTIFY`、`SetWindowPos(HWND_TOP)`
  提到分组框上面、再子类化它的窗口过程，自己在 `WM_LBUTTONUP` 里
  `ShellExecuteW` 打开我们的注册页。同时保留 `ShellExecuteW/A` 的 hook
  （用于改写万一还有别的地方跳注册 URL，也用于日志）。
- **理由**：实测那条链接**在原版里就点不动**（FINDINGS §125）——
  没有 `SS_NOTIFY` 所以鼠标消息到不了它，而且 z 序上被分组框压着；
  真点上去**没有任何 `ShellExecute` 调用**。也就是说没有「原版行为」可以顺着改，
  只能自己造一个。子类化是最短的路径，且完全不碰游戏代码字节。
- **被否**：只 hook `ShellExecute`（客户端根本不调，白搭）；
  在内存里改那个已死的 tiancity URL 字符串（改了也没人去读它）。
- **反悔条件**：将来发现客户端在别的入口也会跳注册页，那时 hook 就派上用场了
  —— 两条路并存，互不干扰。

## D067 密码明文保存，但**日志里只打票据不打密码**

- **决策**：`accounts.json` 按用户要求明文存密码；但服务端日志（`logs/*.out`、
  每连接的 `game_*.txt`）**不打印密码**，登录相关只打用户名 + 票据前 8 位。
  注册页 / 登录页都要有明确的中文风险提示。
- **理由**：明文存盘是用户明确的产品决定（几十人规模、不用 DB），认了；
  但日志会被随手贴进 issue、发给别人排查，多一个泄漏面没有任何收益。
  V0.1 的 `authserver.py` 现在会把密码原样打进日志（`密码={p!r}`），**必须改掉**。
- **被否**：哈希存储（用户明确要求明文，且存档要能导出成人可读的 JSON）。
- **反悔条件**：无。这条只是把「明文」的范围限制在必要的地方。

## D069 登录失败的提示**用客户端自带的中文**，不自己造文案

- **决策**：认证服回 `20025`（不存在的帐号）/ `20026`（密码错误）这两个
  **客户端认识的 NMCO 错误码**，让它自己弹自己的中文框（FINDINGS §128）。
  不去 hook `MessageBoxW` 改写文案，也不在 hook 里另造一个提示窗。
- **理由**：
  1. 文案、字体、按钮全是原版的，和游戏里其它提示长得一模一样，
     玩家看不出这是我们加的东西 —— 复刻项目里这一点很值钱。
  2. hook 换文案要判「这个框是不是登录失败的那个」，还要知道**失败原因**；
     而原因只有服务端知道，联机时服务端还在另一台机器上，
     等于要为一句提示专门造一条旁路通道。回一个整数就没这些事。
  3. 翻译已经躺在 `Data/Chinese.ini` 里了，一个字都不用我们写。
- **被否**：bshook 换 `MessageBoxW` 文案（原计划 F.6，现作废）；
  在应答的字符串字段里塞中文（实测客户端**不显示**那两个字符串，
  `s2` 还被它当票据转发给了游戏服，§123）。
- **反悔条件**：将来要报的失败原因超出客户端那张表能表达的范围
  （比如「服务器维护中」「你被封号到 X 月 X 日」），那时再考虑自造窗口。

## D070 导入存档时**等级只能往上抬**

- **决策**：上传的存档里 `level` 比经验推出来的等级高 -> 把经验补到那一级的起点，
  让手改的等级真的生效；否则以**经验**为准（FINDINGS §131）。
  也就是说想降级必须把 `experience` 一起改小。
- **理由**：`level` 是派生字段（D024），两个字段打架时没法猜出玩家改的是哪一个，
  只能挑一个方向认。挑「往上抬」是因为：
  1. 玩家改存档十有八九是想变强，「把 level 改成 5」是最直觉的做法；
  2. 反过来认（level 永远说了算）会把「只改经验、不动 level」这种同样常见的
     改法**反向抹掉**，代价更大；
  3. 抬等级只动经验一个数，存档仍然自洽，读回来不会再变。
- **被否**：让 `level` 独立存储、不再由经验推（要动 D024 和结算/经验条整条链）；
  两个字段都照收（读一次就自相矛盾一次）。
- **反悔条件**：将来经验曲线变成分段/非线性，`(lv-1)*每级经验` 不再是那一级的起点。

## D071 被顶号回 `result=2`，其它票据失败仍回 `result=3`

- **决策**：`TicketStore` 记一张被作废票据的表；游戏服 `resolve()` 落空后再问
  `revoked_reason()`，**只有「被同账号的新登录顶掉」**这一种回
  `gspRepLogin(result=2)`（客户端弹「现有连接已断开。请重新尝试连接。」），
  其余（乱码票据、真的过期、从没签发过）仍然回 `result=3`（§132）。
- **理由**：
  1. 这两句话是**客户端自带的**，一个字都不用我们写，也不用改 bshook
     —— 和 D069「登录失败靠结果码说话」是同一条路子；
  2. 全都回 2 的话，一个乱码票据也会被告知「你的账号在别处登录了」，
     那是**在撒谎**，排查时会把人往错误方向带；
  3. 被顶号是**每次顶号必然发生**的一条路（客户端 9 毫秒后自动重连重放旧票据），
     不是边角情况，值得单独给一句对的话。
- **代价**：`TicketStore` 要多留一张表。已按同一个 TTL 过期，长期开服不会无限攒。
- **被否**：给旧连接发一个「你被踢了」的包再关（协议里没找到这么个包，
  而且客户端照样会重连重放票据，问题原样存在）；直接回 `result=1`
  （文案是「请重新确认帐号和密码」，账号密码根本没问题，更误导）。
- **反悔条件**：将来做「账号被封」「服务器维护」时需要更多种失败原因，
  客户端那三句话不够分，那时才谈自造窗口。

## D072 连接事件日志单独一个模块、单独一个文件，且和 `--verbose` 无关

- **决策**：新增 `server/eventlog.py`，统一前缀 `[online]` 打到 stdout，
  同时**追加**写 `logs/online.log`。认证 / 游戏服 / 注册页三处都往它记：
  谁认证通过、谁连上游戏服、谁登录成了、谁被顶号、谁断开（带 IP 和在线时长）。
- **理由**：
  1. 用户的需求是「谁连接了、谁断开了、IP 是什么」，这是**运营信息**，
     和逆协议用的逐包 dump 是两码事，不该被同一个开关关掉（§133）；
  2. 云服务端包要出**两套启动脚本**（精简 / debug），精简那套下这份流水
     就是唯一的排查依据，所以它必须在两套下都在；
  3. 另存一份文件是因为 `server.out` 每次启动被重定向覆盖。
- **被否**：把连接事件混进现有 `log()`（精简模式下也在，但会被逐包日志淹掉，
  且没法单独留档）；用 Python 的 `logging` 模块（要配 handler / formatter，
  比现在这三十行多，收益是零 —— 服务端全程只有一个进程、一个格式）。
- **反悔条件**：将来要按天切分 / 限制大小 / 输出 JSON 给别的工具吃，
  那时再换成 `logging` + `RotatingFileHandler`。

## D073 GameGuard 断点：等**目标指令解壳**，而不是等「主线程离开 APC」

- **决策**：采纳并合并 GPT-codex 给出的修法（`hook_merge\hook_DR0修改版\`）——
  武装 DR0 的判据从「主线程 EIP 不在那四个 DLL 里」换成
  「`0x54b0fc` 的 5 个字节已经是已知明文」，并加一条 10 毫秒的 DR0 守护回合。
  在它基础上我又改了三处：**保留 §124 的 2 秒余量**（GPT 版用满了整个超时，
  会和 bsloader 抢着报超时，DLL 的失败原因就写不出来）；
  `IsBadReadPtr` 换成 `VirtualQuery`；**加兜底武装**（详见 §134）。
- **理由**：旧判据在别人的电脑上 5 毫秒就成立，而那时主线程正落在
  **主模块自己的 ASProtect 壳**里（主模块不在排除表内），DR0 随即被壳的
  CONTEXT 恢复清掉 —— 日志写着「已武装」，断点永不命中。
  我这台机器不炸纯属采样时机的运气（§134）。
  新判据是「壳跑完了没有」的**直接证据**，不是对 EIP 的推测。
- **和 §124 的关系**：不推翻，两个坑叠在一起。§124 修的是「循环上限按次数算」，
  §134 修的是「判据本身错了」。合并后的代码两条都在。
- **被否**：只加守护、判据不动（能救回来，但每次都要先被清一次再补，
  且中间那段时间断点是失效的，一旦壳恰好在这窗口里执行到 `0x54b0fc` 就漏掉）；
  固定延时后再武装（V0.1 一开始就否掉的路子，机器快慢差几倍）。
- **反悔条件**：将来遇到按页惰性解壳的变体（`0x54b0fc` 直到被执行前一刻才明文），
  那时新判据永远等不到，会走兜底路径 —— 日志里会写「兜底已武装」，看到就来查这条。

## D074 启停 `.bat` 只写 ASCII，中文提示全部由 `.ps1` 负责

- **决策**：`start.bat` / `start-debug.bat` / `stop.bat`（以及里程碑 K 的服务端包脚本）
  **一个汉字都不放**，注释也用英文。它们只做三件事：`chcp 65001`、调 `.ps1`、
  转发退出码。所有面向玩家的中文 —— 包括「[启动失败]」和「这个窗口可以关掉」——
  搬进 `tools\launch.ps1`（失败路径用脚本级 `trap`）和 `tools\shutdown.ps1`。
- **理由**：`chcp 65001` 下 cmd 按字符算偏移、按字节 seek，文件里任何多字节字符都在
  累积漂移，漂到某处就把一条命令行从中间劈开（§135）。这个坑有三个恶劣性质：
  1. **和 CRLF 无关**，修了行尾也不管用；
  2. **`rem` 注释里的中文一样致命**，「只是注释」这个直觉是错的；
  3. **是否发作取决于前面累计的字节数**，所以「今天能跑」不代表明天加一行还能跑
     —— 每次改 bat 都是重新掷骰子。
  `.ps1` 走 UTF-8 with BOM、整文件读进来再解析，压根没有这个偏移概念。
  把中文集中到那一侧，等于把整类问题一次性消掉，而不是每次改完再赌一把。
- **附带好处**：提示只剩一处，不会再出现「bat 和 ps1 各打一遍」的重复文案
  （用户 2026-08-11 报的那个）。而且 ps1 里能带上 `server.config` 的实际地址和端口，
  bat 里只能写死。
- **被否**：给 bat 加填充字符凑偏移（脆得离谱，改一个字就重来）；
  bat 存成 GBK（和铁律 3 的「UTF-8 无 BOM」打架，且服务端包里还有 `.sh` 要统一）；
  改用 `goto` 绕开括号块（**试过，不行** —— 顶层 `rem` 照样被截断，§135）。
- **反悔条件**：无。真要在 bat 里显示中文，只能改成 `powershell -Command "Write-Host ..."`
  这类由别的进程去输出的形式。

## D075 离开/踢人广播用 `0x0301` **action 1**，并把「不许发 1/2」的护栏换成「只挡跳表不认的码」

- **决策**：`SEAT_ACTION_LEAVE` = **1**（不是 3）。`build_session_member_update`
  原来那条「action 1/2 会销毁角色对象，服务端绝不能发」的 `ValueError` 删掉，
  改成只挡 0~4 之外的码（跳表 `0x4064f7` 不认，发了等于没发）。
- **理由**：客户端里**只有 1/2 会走 `0x405f8f` 销毁座位的 3D 模型**；3 走的是
  `0x406628`（按座位数据重建），对空座位干脆什么都不做（§147）。
  发 3 的效果是「玩家列表空了、模型还在」—— 正是用户报的现象。
- **那条护栏当初为什么写**：V0.1 是单人假服务端，屏幕上只有「我」一个座位，
  销毁模型 = 把自己弄没了，所以当时「绝不能发」是对的。**多人之后前提变了**：
  要销毁的是**别人**的模型，而且非销毁不可。护栏留着反而挡住了唯一正确的码。
  ★ 这类「V0.1 单人时代的假设」在 V0.2 里可能还有，遇到别的怪现象时先想想这条。
- **被否**：① 每次有人离开都补发一份 `0x0300` 全量快照（能修好 —— 房主转移那条路
  正是这么歪打正着的，见 §147 —— 但 6 个座位全量重发只为擦掉一个模型，
  而且 `0x0300` 会重写「我」的座位 IP，副作用比增量包大得多）；
  ② 发 action 2（和 1 在客户端里逐指令等价，挑 1 只因为它是小的那个）。
- **反悔条件**：若将来发现 1 和 2 在**别的 stage**（比如 RoomStage 自己的处理器，
  目前只找到大厅跳表这一处）里有区别，再回来分。

  还能把服务端广播的每一帧**逐字节打出来**（真客户端那边永远看不见字节）。
  这次修 §147 就是靠它同时验到了两个方向：真客户端看到的**画面**、
  假客户端收到的**字节**。
- **被否**：继续用 `gs_ctl.py raw` 手搓（只能发单个包，验不了「服务端自己会不会

  开第二个真客户端进程（GameGuard 绕过 + 显卡 + 窗口焦点全要抢，而且照样看不到字节）。

## D077 战斗内同步走 `0x040e`/`0x040f` **服务端转发**，不实现原版中继、不依赖 UDP

- **决策**：里程碑 J 的传输层就用客户端自带的「通道 A」：服务端发
  `0x0410`（int32 1）打开开关，然后把每个客户端发来的 `0x040e` 载荷**原样**
  转成 `0x040f` 发给同房间的其他人。**不回 `0x0210 gspJoinRelay`**，
  也不去管客户端自己那条 UDP 直连。
- **理由**（全部有实测支撑，§149~§151 + §155）：
  1. 这条路**是原版自带的**，不是我们发明的绕道 —— 客户端里
     `0x408619` 的 else 分支就是它，一行代码都不用改客户端；
  2. **一个 NAT 问题都没有**：全程复用玩家已经连着的那条游戏服 TCP，
     云服务器在 NAT 后照样能用；
  3. **服务端不用理解载荷**：纯字节搬运，一个 12 字节头都不用解
     （解只为打日志）。里程碑 J 的传输层因此从「要逆一整套 rcp 协议」
     缩成「转发 + 一个开关」；
  4. **重复投递无害**：客户端按序列号在 `PktQueue::Insert` 里去重（§151），
     局域网里 UDP 那一路也送到了也不会双重结算。
- **被否**：
  - **实现原版的 TCP 中继服务器**（`0x0210` + rcp 那套，§152）：传的是
    **同一个 `UdpPacket`**，效果完全一样，却要多一个监听端口、多一套认证
    （`RelayAuthData` 三个 int32）、多一条连接的生命周期，还多一个断线时
    弹公告框的失败模式。**收益为零**。
  - **只保证局域网 P2P**（让 UDP 直连自己去打）：客户端上报的是**内网 IP**
    （V0.1 §44），公网必然打不通，等于放弃云端联机 —— 而这正是 V0.2 的目标。
  - **给 UDP 做打洞 / 中继**：要改客户端的地址上报逻辑，风险和工作量都远超收益。
- **边界 / 反悔条件**：
  - 这条通道的带宽全压在游戏服上：一个人 ~8 Hz × 43 字节，六人房转发出去是
    6×5 = 30 份/tick。真打起来包会更大更密，**如果实测发现服务端扛不住或者
    延迟不可接受**，退路仍然是 §152 那套原版中继（协议已经逆完，照着实现即可）。
  - UDP 那一路我们**关不掉**（`[GameSession+0x3f8]` 是客户端构造时写死的 1），
    只能让它在公网上打水漂。局域网里它会真的送到，靠去重兜住。

## D078 ★ 用户拍板（J.2）：**原版的连接方式和回退方式全部原样还原**

- **决策**：**推翻 D077 的「不实现原版中继」那一半**。传输层要**两条都做**：
  1. **原版 TCP 中继**：`0x0310 gcpStartTcpRelay` → 回 `0x0210 gspJoinRelay`
     （NetAddress + RelayAuthData），服务端另起一个中继监听器说 rcp 协议
     （opcode 0 register / 1 ping / 3 数据，§152），并支持 `0x0211` 拆连接；
  2. **`0x040e`/`0x040f` 服务端转发**（已实现）：**这本来就是原版的回退路径**
     —— 客户端 `0x408619` 在「没有中继连接」时走的就是它。保留不动。
  客户端自己那条 UDP 直连（通道 B）我们**本来就没干预**，天然是原样的。
- **理由**：**用户明确选择**（2026-08-11 会话 06 的 J.2 决策点）。原话是
  「再实现一遍原版 tcp 中继，原版的所有连接方式以及回退方式都原样还原」。
  这是**保真优先**的取舍 —— 本项目是把一个停运 15 年的游戏抢救回来，
  「和原版一样地跑」本身就是产品目标，不只是「能玩就行」。
  D077 那套「收益为零」的论证只在**纯功能**视角下成立，在保真视角下不成立。
- **D077 里仍然有效的部分**（不要一起推翻）：
  - `0x040e`/`0x040f` 那条路**保留**，它是原版回退路径的还原，不是权宜之计；
  - 「重复投递无害」（§151 的序列号去重）仍然是两条通道并存的依据；
  - UDP 那一路关不掉（`[GameSession+0x3f8]` 客户端写死 1），仍然如此。
- **实现要点**（RE 已全部做完，照着写即可）：
  - 帧格式和加密**和 27799 完全相同**（§156）：同一把 `SimpleCipher`、
    `RawPacket` 10 字节头；**但没有明文版本号开场白**；
  - `RelayAuthData` 那三个 int32 **由我们签发**（客户端只是把 `0x0210` 里
    收到的原样回抛），所以可以拿它当「房间号 / 座位 / 一次性随机数」用来认人；
  - `0x0210` 里的 `NetAddress` 要填**客户端连得到的地址**。服务端不知道自己的
    公网地址（和注册页同一个老问题），所以沿用 D065/D066 的既有架构：
    **固定填 `127.0.0.1:<中继端口>`，由客户端包里的 `relay.py` + `bshook`
    的 `det_connect` 按单机/联机把这个端口转出去** —— 和 47611/27799 一个套路。
- **反悔条件**：若实测发现中继那条路有原版特有的坑（比如 ping 超时策略、
  断线弹框），而它又挡住了正常游玩，则**默认关掉中继**（不回 `0x0210`），
  让客户端自然走 `0x040e` 回退路径 —— 两条都在，切换只是「回不回 `0x0210`」一句话。

## D079 中继地址固定发 `127.0.0.1:27798`，单机 / 联机的区分仍然交给 `bshook` 的端口映射

- **决策**：`0x0210 gspJoinRelay` 里的 `NetAddress` **永远**填 `127.0.0.1:27798`
  （`config.PEER_RELAY_PORT`）。客户端包里：
  - **单机** —— `popshot_map_port` 不映射，`connect` 直接落到本机服务端的中继口；
  - **联机** —— 映射成 `127.0.0.1:27808`（`RELAY_PEER_PORT`），
    由 `server/relay.py` 的第三条隧道转发到 `server_address:27798`。

  和 47611→47621 / 27799→27809 **完全同构**，`popshot_map_port` 只多一行。
- **理由**：
  1. **客户端连不到那个地址的代价极大**：`RelayConnection` 连接失败会走
     `OnDisconnected`，而它会让客户端**自己发 `0x0203` 退出房间**并清掉
     通道 A 的开关（§158）。所以这个地址**不能靠猜**，必须是确定的。
  2. 服务端不知道自己的公网地址（和注册页同一个老问题），而客户端的
     `connect` 参数是纯 IPv4 的 `sockaddr_in`（D065 的老约束一字不变）——
     所以「发一个本机地址 + 本机加一跳」是唯一能同时吃下 IPv4 / IPv6 / 域名的形态。
  3. 模式判定留在 `bshook`（D066）就还是**零状态**的：`connect` 那一刻
     单选钮的状态是确定的，没有竞态。
- **被否**：
  - **让服务端按「游戏连接是不是从 loopback 来的」猜模式**，据此发 27798 或 27808
    （能不改 `bshook`、不用重编 32 位 DLL）。否掉是因为它把一个**必须确定**
    的地址变成了推断；猜错的后果不是「中继没连上」而是「玩家被踢出房间」。
  - 在 `0x0210` 里填服务端的真实地址：`make_localhost` 会把任何 IPv4 目标
    一律改写成 `127.0.0.1`（`bshook` 现有行为），填了也没用；
    何况服务端本来就不知道自己的公网地址。
- **代价**：`bshook.dll` / `bsloader.exe` 要重编一次（已做，`hook\test-watchdog.bat`
  回归通过），旧客户端包连不上中继。**旧包不会因此变糟** —— 老服务端不认识
  新端口这件事不成立（端口在服务端这边定），而老客户端拿到 `0x0210` 会去连
  `127.0.0.1:27798`，联机时那里没人听 → 退房。所以**客户端包和服务端包要一起发**。
- **反悔条件**：若将来要支持「服务端知道自己的公网地址」（比如加一个
  `public_address` 配置项），可以让 `0x0210` 直接发真地址、去掉本机那一跳。
  但那要求客户端只用 IPv4 —— D065 当初就是为了绕开这条才加的中继。

## D080 中继连接绑**游戏连接**，不绑房间；换房间不重发 `0x0210`

- **决策**：`RelayServer` 的表以 `gameserver.Conn`（一条 27799 上的 TCP）为 key，
  一条游戏连接一辈子只签一张票、只回一发 `0x0210`。房间是**每次投递时现查**
  （`LOBBY.room_of(sender)`），换房间、退房再进房都不需要动中继连接。
- **理由**：
  1. §159 说得很死：`0x0210` 回第二次，旧的 `RelayConnection` 就变成孤儿，
     它将来那一次 `FD_CLOSE` 会把**新**连接一起带走并把玩家踢出房间。
     「一条游戏连接一发」是唯一不用去追踪客户端内部状态就能保证的口径。
  2. 换房间要重发的话，就得先 `0x0211` 再 `0x0210`，中间那个窗口里
     两边的状态谁先到达是不确定的 —— 凭空造一个时序 bug。
  3. `RelayAuthData` 里的房间号 / 座位号因此**只是签发时的快照，只用于日志**；
     真正认人的是第三个 nonce。这一点必须写死在注释里，
     免得以后有人拿它当权威的房间号用。
- **被否**：按「房间 + 座位」认人（换座位、换房间都要重签）；
  每次进房都重发 `0x0210`（正是 §159 的定时炸弹）。
- **反悔条件**：若将来一个进程要开多个互相隔离的中继实例（分区/分服），
  那时 key 要带上实例 id —— 但仍然不该带房间。

## D081 中继投递「有中继走中继，没中继退回 `0x040f`」

- **决策**：`RelayServer.deliver()` 对同房间的每个其他人分别判断：
  有已注册的中继连接就走 rcp opcode 0，否则走它自己的游戏服连接发 `0x040f`。
  `0x040e` 收到的数据也走同一个 `deliver()`（不再直接广播 `0x040f`）。
- **理由**：中继连接是**异步**建的 —— 客户端要先发 `0x0310`（每座位 10 秒一发）、
  收到 `0x0210`、再 TCP 连过来、再 `rcpRegister`。进房之后必然有一段
  「有人已经在中继上、有人还没」的窗口，实测里这个窗口有好几秒。
  那几秒里同步不能断，而 `0x040f` 本来就是原版的回退路径（D078），
  两条路在客户端进的是同一个入口 `0x407869`，收哪条都一样。
- **被否**：只走中继（那几秒里没接上中继的人就是瞎的）；
  两条都发（客户端按序列号去重不会算重，但白白翻倍带宽，
  而且 `0x4001` 那类「不排队不去重」的内层 opcode 会被处理两次，§155）。
- **反悔条件**：无。这条只是让两条原版路径共存时不留缝。

## D082 结算：`0x0309` **每座位一份**，`0x0411` **每人只发自己那份**

- **决策**：一局结束时，房里每个人都收到「每个在座座位一份 `0x0309`」，
  然后只收到「自己那个座位的 `0x0411`」。
- **理由**（RE 依据在 §161）：
  - `0x0309` 的处理器 `0x55210d` **全程按包里的座位号索引**
    （`[ctx+座位*4+0x2c/0x44/0x5c]` 三行数值、`[ctx+0x184]` 名次表），
    重复投递零副作用 —— 不每座位发一份的话，结算界面上队友那几行全是 0。
  - `0x0411` 的处理器 `0x551804` 在 `0x5518b4` 处
    `cmp 包里的座位, 我的座位`，只有相等才更新右上角数据栏的四个全局。
    多发几份**不会串账**，但每一份都会走到 `0x4087f0` 让客户端**再回一发
    `0x0505` 遥测**，而「重复调 `0x4087f0` 安不安全」没有任何 RE 依据。
    保真项目里，没读到底的分支不主动去踩。
- **代价（明说）**：队友那一行的「分数 / 生命」来自
  `[GameContextQuest + 座位*0x34 + 0x3ec]`，**只有 `0x0411` 会写**，
  所以会显示 `0 / 3`。经验 / 金币 / 竞技场分数三行来自 `0x0309`，是对的。
- **反悔条件**：两台真机实测确认队友那一行确实难看，且改成每座位一份
  `0x0411` 之后没有出现异常的 `0x0505` 洪水或崩溃 —— 那就改成全发。
  改动量是 `send_end_game()` 里一个循环。

## D083 对战胜负按**本局分数**判，全场 0 分则谁都不判

- **决策**：房间描述符 type != 2（非闯关）时，`0x0309` 尾部数组按分数排名：
  最高分（含并列）填 `1`、其余填 `-1`；**所有人都是 0 分时全填 0**。
  闯关（type 2）是合作：通关了所有在座座位一起填 `1`，没通关全填 `0`。
- **理由**：
  - 尾部数组有**三个档**（§161）：`1` = 完成/CLEAR + 胜利曲、
    `0` = 未完成/FAILED + **胜利曲**（`0x55223f` 的 `setge` 是 `>= 0`）、
    `-1` = 未完成/FAILED + 失败曲。所以「输」必须是负数。
  - **原版按什么判胜负不可知**（服务端早就没了，客户端里也没有这段逻辑）。
    分数是我们手上唯一一个全房间可比的、客户端自己算出来上报的数
    （`0x0410`，累计值），拿它排名最省事也最不容易冤枉人。
  - 全场 0 分 = 多半没打就散了。判谁输都是瞎判，而两边一起放失败曲更难看，
    所以退回「不判」那个档。
- **被否**：按死亡次数判（`RoomQuest.deaths` 手上就有）—— 闯关模式下死亡
  次数和胜负没关系，两套规则会让代码里多一个分支；按房主指定 —— 没有这个包。
- **反悔条件**：将来查明原版对战的胜负字段（多半和 `QuestVictoryCondition`
  的子类 `DeathMatchVictoryCondition` / `NewDeathmatchVictoryCondition` 有关，
  两个类名在 `re/vftables.json` 里），照原版改。

## D084 战斗处理器**只许有一条代码路径**，「不在房间里」用一份 solo 状态顶上

## D085 死亡次数下发「客户端报的值 + 1」，服务端**不另起一份权威计数**

- **决策**：`0x0406` 里那一格照旧是 `0x0408` 报上来的值 +1。
  `RoomQuest.deaths` 那张每座位表只用来记账和打日志，不参与下发。
- **理由**：看着该由服务端当权威，其实两者永远相等 ——
  `[char+0x600]` 全镜像里**只有 `0x0406` 的处理器会写**（§161），
  所以每台机器上的值就是我们上一次发下去的那个。
  而「报的值 +1」是 V0.1 实机验过的（§109，含跨换图那一段），
  自己另起一份计数只会多一个可能对不上的真源。
- **顺带**：正因为这一格在所有机器上同值，它才能当死亡去重的键的一半
  （键 = `(句柄, 报上来的死亡次数)`，见 §161）。
- **反悔条件**：若实测发现多人时心形数会跳（说明有客户端漏收了广播），
  再改成服务端权威 —— 但那时要先解决「漏收」本身。

## D086 打包的文件清单改成「反向排除」，并把两个包的入口合并成 `tools\build.bat`

## D087 每次打包都用**包内 Python 跑包内服务端**做冒烟自检

- **决策**：`build-portable.ps1` / `build-server-package.ps1` 的最后一步，

## D088 Linux 运行时以**未解压的 `.tar.gz`** 随服务端包发，首次启动时在 Linux 上自解

- **决策**：`-LinuxRuntime download` 拉 python-build-standalone 的
  `x86_64-unknown-linux-gnu-install_only_stripped`（约 35 MiB），
  **原样**放进 `runtime-linux/`，由 `tools/serverctl.sh` 在第一次
  `./start.sh` 时 `tar -xzf` 解开。校验和不写死在脚本里，
  改为从同一个 release 的 `SHA256SUMS` 里现取现比。
- **理由**：打包是在 Windows 上做的。那个发行版的 `bin/python3` 是指向
  `python3.14` 的**符号链接**，另外整棵树都带可执行位 —— 在 Windows 上解开
  两样都保不住，解出来的东西到 Linux 上跑不了。留着压缩包是唯一
  不需要在 Windows 上模拟 POSIX 文件属性的做法。
  （⚠ 「Windows 上解开会坏」这一条**没有实测**，是按 install_only 的布局推的；
  但即使它其实能用，留压缩包也没有额外代价。）
  校验和写死则必然过期：上游每月出新版。
- **存哪**：项目根的 **`runtime-linux\`**（和 `runtime\` 同构，跟着 git 走），
  **不是** `tools\_dl\` 那种可丢弃的下载缓存 —— 见 D090。
- **默认值**：`-LinuxRuntime auto` = 「用 `runtime-linux\` 里那份」，**从不联网**；
  `download` = 「项目里没有（或校验不过）才下，下完存进项目」。
  菜单默认项 [5] 走 `download`，所以第一次会下一次，以后一直是本地 copy。
- **只要稳定版**：按 `<系列>.<纯数字>` 匹配资产名，`3.15.0rc1` 这种
  **预发布版天然被挡掉**（§164）；默认系列 `3.14`，和包里的 Windows 运行时
  （CPython 3.14.3）同一个大版本，减少「Windows 上好好的、Linux 上不一样」。
- **缓存必须带旁证**：校验通过才在旁边写 `<文件>.sha256`；`auto` 模式
  只认「有旁证且哈希对得上」的缓存文件，其余一律当没有。
  否则一次失败的下载会把没验过的 35 MiB 悄悄带进发布包（§164 实际发生过）。
- **反悔条件**：若将来改在 Linux 上打包，直接解开即可。

## D089 两个包共用**一个批次号**和**一份共用服务端代码哈希**，都写进 `BUILD.txt`

- **决策**：一次构建里客户端包和服务端包拿同一个 `BuildId`；
  `BUILD.txt` 另记一行「共用服务端代码」= 包内 `server\` 全部 `.py`/`.html`
  的总哈希（**`relay.py` 除外**，它是客户端包独有的本机一跳，算进去两个包
  永远对不上）。
- **理由**：D079 要求客户端包和服务端包**成对发**，但「成对」在收到包的人

  批次不一致 = 拿错包；批次一致但代码哈希不一致 = 有人手改过其中一个包
  （铁律 8 被破坏）。测试的人报问题时第一句就能问「BUILD.txt 贴一下」。

## D090 Linux 运行时存进项目的 `runtime-linux\`，跟着 git 走，不当成下载缓存

- **决策**（用户要求）：那份 34 MB 的 `cpython-*-linux-gnu-install_only_stripped.tar.gz`
  放在项目根的 `runtime-linux\`（连同 `.sha256` 旁证和 `README.md`），
  **提交进 git**。打包时直接 copy；只有目录里没有的时候才联网下载一次。
  原先放在 `tools\_dl\`（被 `.gitignore` 排掉的下载缓存目录）。
- **理由**：它和 `runtime\`（Windows 那份 22 MB 的 CPython）**是同一个角色** ——
  发布产物的一部分，不是可随时重下的构建中间物。放进仓库之后：
  1. 任何一台 clone 下来的机器都能**离线**打出带 Linux 运行时的服务端包；
  2. 版本被钉死，不会因为上游发新版而在不同机器上打出不同的包；
  3. 上游哪天删了那个 release 也不影响我们。
- **被否**：每次打包联网下载（用户明确否掉：「不要每次打包都联网重新下载」）；
  留在 `tools\_dl\` 但把它从 `.gitignore` 里挖个洞 —— 那会让「`_dl` 是可丢弃的」
  这条约定变得半真半假，以后清缓存的人会把它删掉。
- **代价**：仓库多 34 MB；换 Python 版本时旧的那份会永远留在 git 历史里
  （`runtime-linux\README.md` 里写了「换版本记得删旧文件」）。
- **反悔条件**：若将来要同时支持多个架构（aarch64 云主机），几份 tarball 加起来
  就太大了，那时改成「按需下载 + 校验和写进 README」。

## D092 队伍号按**房间模式**分配，闯关全在一队

> ⚠ **会话 32 已被 D130 取代**：下面「个人战 = 座位号 + 1」那一档是错的，
> 而且是 bug调查/8「活着进观战 / 死了不复活」的**根因**（客户端的队伍数组
> 只有两格，>= 3 会写进别人的战绩，§212）。本条的**理由**也被证伪 ——
> `0x4fedfc` 比队伍号那一处不决定伤害，只决定伤害统计记账。
> 组队战和闯关那两档仍然有效。

- **决策**：`lobby.Room.default_team_for(座位)` 按模式给三种口径（§165）：

  | 模式 | 判据 | 队伍号 |
  |---|---|---|
  | 组队战 | `type==1 且 arguments[0]==1` | 座位号 % 2 + 1（1/2 交替）|
  | 个人战 | `type==1` 其余 | 座位号 + 1（**每人一队**）|
  | 闯关等 | 其余 type | 全部 1（**同一队**）|

  房主在房间里切「组队战 / 个人战」（`0x0302`）时，**口径变了才**重排
  （`reassign_teams()`）并给变了的座位补一发 `0x0301 action 3`；
  有人进房时**只定新人那一格**，绝不重排 —— 那会把别人手动选的队伍冲掉。
- **理由**：队伍号不是装饰。客户端 `0x4fedfc` / `0x4ffec3` 比双方队伍号，
  **相同就直接不结算伤害，而且这一处不分游戏模式**（§165）。于是：
  1. 以前全填 0 = 全场互相免疫，**对战根本打不动人**；
  2. 若无脑按奇偶分，**闯关里队友之间会互相伤害** —— 那是实打实的退步；
  3. 个人战里若都同队，同样谁都打不动谁，所以必须人人不同号。
- **代价（要如实告诉用户）**：组队战下客户端要求两队人数相等才让开局
  （`0x468495` → 错误码 3 →「两组人数不相同。请调整人数。」），
  **3 人 / 5 人的组队战本来就开不起来**。这是原版行为，不是本次改动引入的
  —— 但在「所有人都是 0 队」的旧行为下这条检查恒等成立，所以用户会觉得是变化。
  想 3 个人打就选「个人战」，或者用「变更队伍」凑成 2v2。
- **被否**：全部填同一个队（闯关对、对战废）；全部按奇偶（对战对、闯关废）；
  按「人数最少的队」平衡（客户端自己填 Dummy 座位用的就是奇偶，没有理由自创）。
- **反悔条件**：若查明原版在闯关里也发奇偶队伍号（也就是闯关本来就有友军伤害），
  把 `TEAM_LAYOUT_COOP` 那一支删掉即可。

## D093 对战由**服务端**判胜负并推结算，判据照抄客户端的 `DeathMatchVictoryCondition`

- **决策**：房间描述符 `type != 2`（非闯关）时，服务端自己盯三条
  （`RoomQuest.pvp_finished`）：时间到 240 秒 / 有人杀敌数达上限 / 只剩一边，
  任一成立就走**和闯关完全同一条**结算路径（`send_end_game()` →
  每座位一份 `0x0309` + 每人一份 `0x0411`）。对战的「分数」用**杀敌数**
  （从 `0x0408` 的凶手字段数出来），不用 `0x0410` 报上来的 `quest_score`。
- **理由**：
  1. **客户端在对战里根本不会结束这一局**（§167 有逐指令依据 + 一整局的实机
     日志佐证）：它的 `CheckMatchOver` 第一行要求 `GameContextQuest.state == 2`，
     而唯一的赋值点要求「地图带剧本」，对战地图没有。整局零发 `0x040f`。
     所以这不是「服务端要不要抢活干」，而是**除了服务端没有别人能做**。
  2. 判据不能自创：玩家看到的是客户端 HUD 上的分数和倒计时。数字对不上会变成
     「明明还没到时间就结算了」。所以时间上限、分数上限的表全部照抄
     `0x55e133` / `0x55be71`。
  3. 分数改用杀敌数是**被逼的**：对战里客户端一发 `0x0410` 都不发，
     `quest_score` 恒 0，D083 的排名会永远落到「全场 0 分不判」那一档。
- **实现上的取舍**：时间上限**不另起定时器线程**，挂在 `0x040e`（约 8 Hz）
  和死亡广播之后判。没人发包 = 没人在等结算，晚判几百毫秒无所谓；
  多一个线程就多一份和房间状态的竞态。
- **代价 / 已知未验**：⚠ **「真客户端收到服务端推来的 `0x0309`+`0x0411` 之后
  会不会乖乖进结算界面并回房间」还没在真的对战局里验过**。闯关那一路是同样的
  两个包、同一个函数，V0.1 起实机跑通过，所以风险不高但不是零。
  见 PROGRESS ⏳ 区第 12 条。
- **被否**：等客户端发 `0x040f`（永远等不到）；靠 hook 在客户端里把
  `[GameContextQuest+0x3b0]` 改成 2（要动游戏代码字节，且那条路后面还依赖
  剧本对象，风险远大于收益）。
- **反悔条件**：若查明对战地图其实也该有剧本（只是我们没下发某个包），
  那就把那个包补上，让客户端自己走原版流程 —— 那才是最保真的。

## D094 注册页的「跳过新手教程」默认**勾着**，但接口默认**不跳**

- **决策**（用户要求）：注册页加一个「跳过新手教程」勾选框，**进页面时默认勾选**；
  勾着注册出来的账号 `tutorial_completed=True`（首登直接进大厅），
  取消勾选则维持原版（首登被拉进教学关）。
  但 `POST /api/register` **不带 `skip_tutorial` 字段时按 False 处理**，
  `AccountStore.register()` 的形参默认值同样是 False。
- **理由**：
  1. 默认勾着是用户明确要求 —— 这是复活老游戏给熟人玩，每个人重新注册都要
     再看一遍 2007 年的教学关，收益为负。
  2. 接口默认 False 是另一回事：**「不说」应当等于「不改变原版行为」**。
     页面每次都会把这个布尔显式发上来（而且注册页是 `Cache-Control: no-store`，
     不存在「浏览器缓存了旧页面所以少发字段」），所以这个默认值只影响
     手搓请求的人 —— 对他们来说沉默地跳过教程才是意外。
  3. 只写 `tutorial_completed`，**`tutorial_progress` 保持 0**：后者是
     「客户端自己上报过什么」的保真记录（§168 的表），我们没跑过教程，

- **被否**：注册时顺手把 `tutorial_progress` 也填成 4/5（伪造客户端上报值，

## D095 玩家列表**不列自己**；「推荐对手」= 全部在线的人按等级接近度排序

- **决策**：`0x0212` 回的名单里**永远不含请求方自己**。过滤开关两档：
  - `1`（客户端默认，「待机玩家」）→ 只有**没在打游戏**的人；
  - `0`（「推荐对手」）→ **全部在线的人**，按 `|对方等级 - 我的等级|` 升序、
    同距按昵称排。
- **理由**：
  1. 「分不清哪个是自己」在协议层**无解**：客户端的渲染循环 `0x441df5` 和命中测试
     从头到尾不比昵称，条目里也没有「是不是我」这一位（§169）。既然没法标记，
     就只能不列 —— 而且列表点一行是「看**对方**的玩家情报」，
     「推荐**对手**」更不可能是自己，不列自己也符合这个面板的用途。
  2. 「待机玩家」这一档必须真的过滤，否则和标签直接矛盾（用户就是这么报的：
     人已经进游戏了还挂在「待机玩家」里）。判据用**房间状态**
     （`SESSION_STATUS_PLAYING`），和房间列表显示「游戏中 / 待机中」同一个真源，
     两边口径不会打架。坐在「待机中」的房间里等人**算待机**。
  3. 「推荐对手」原版按什么推荐**已经无从得知**（服务端 2009 年就没了，
     客户端里也没有这段逻辑）。选「全部 + 按等级接近排序」而不是「按等级开窗过滤」：
     几十个人的熟人服里，开窗过滤十有八九是**空列表**，而空列表和「服务端挂了」
     在玩家眼里长得一模一样（这条教训 §143 起就一直在踩）。
     排序至少让「和我水平接近的人」浮到前面，又不会让任何人消失。
- **顺带**：`UserSnap` 那三个 int32 按 §169 各归各位（在打游戏 / 等级 / 竞技场等级）。
  竞技场等级存档里没有这项数据，统一发 `LADDER_GRADE_UNRANKED = 20`（最低档）——
  和发 0 画出来是同一张图，但线上的值落在客户端认的 1..20 区间里。
- **被否**：给自己那一行填个特殊等级/天梯值当标记（那是**伪造数据**，
  而且玩家看不出这是「我」的意思）；两档都排除在打游戏的人
  （那就没有任何一档能看见「谁在玩」，而 `P` 徽章本来就是给这件事准备的）。
- **反悔条件**：将来存档里真有了竞技场分数，「推荐对手」就该按天梯分接近度排
  （那才是原版这个词的意思）；那时把排序键换掉即可，过滤规则不用动。

## D096 票据改成**滑动过期 + 登录后长效**，让客户端自己的重连链路能走通

> ⚠ **本条的「落盘」那一半已被 D097 推翻**（用户当天拍板）。
> 下面第 3 点只作为历史记录保留 —— 现在票据**只在内存里**，
> 服务端重启 = 所有人重新登录。前两点（滑动过期 / bind 后长效）仍然有效。

- **决策**（推翻 `tickets.py` 原来那句「服务端一重启全部作废 —— 这没问题」）：
  1. `resolve()` 每次命中就续期；
  2. 游戏服登录成功时 `bind()`，把 TTL 从 600 秒换成 `BOUND_TTL_SECONDS = 12 小时`；
  3. 票据表落盘 `server/data/tickets.json`（`--tickets` 改路径、
     `--no-ticket-file` 关掉），存**绝对到期时刻**，停机时间照算。
- **理由**：
  1. **客户端断线后只会反复重放手里那张旧票据，永远不会回认证服重新登录**
     （§171 逐指令查过：`0x54da2e` → `0x5bc41a`）。也就是说「服务端重启后
     玩家重新登录一次就好了」这个假设**在客户端上不成立** —— 它压根没有
     「回到登录框」这条路，只会一直撞在 `result=3` 的公告框上。
     用户报的正是这个：「服务器恢复上线后显示『在无法连接的地方尝试了连接』」。
  2. 三条改动**各治一个独立的失败原因**，少一条就修不好：不落盘 → 重启即废；
     不续期 → 玩一局超过 10 分钟就废；不给 bind 长 TTL → 「服务端挂了、
     人过来把它拉起来」这几分钟到几小时里没人能续期，一样废。
  3. 重连之后的事**全是客户端自己做的**（`[0x6dc678]` → `0x020b` 回频道，§171），
     服务端一个新包都不用加 —— 代价小得不成比例。
- **安全上的取舍（明说）**：票据是明文存盘的 bearer 凭证，
  和 `accounts.json` 的明文密码同一个信任域（D067），且 `.gitignore` 已排掉它。
  日志仍然只打前 8 位。**已 bind 的票据 12 小时内可以被任何拿到它的人重放** ——
  这个窗口是为了保住重连，不是疏忽。
- **被否**：
  - 让服务端「凭 IP + 上次的账号」认回来（`0x0100` 里除了票据只有内网 IP，
    NAT 后面一堆人同 IP，等于谁都能顶别人的号）；
  - 把 TTL 一律拉长到 12 小时（**未用过**的票据是登录流程里的一次性凭证，
    没有任何理由活那么久 —— 分两档才是对的）；
  - 票据表落盘但不续期（能扛重启，扛不住「玩了半小时才断线」）。
- **反悔条件**：将来要多台游戏服共用账号中心（D064 的反悔条件）时，
  票据表要换成共享存储；那时这三条语义不变，只换存储。

## D097 ★ 用户拍板：票据**只放内存不落盘**；认不出票据一律回 `result=2`

- **决策**（推翻 D096 的第 3 点）：
  1. `TicketStore` **不落盘**，`server/data/tickets.json` 不再存在，
     `app.py` 的 `--tickets` / `--no-ticket-file` 一并删掉；
  2. **服务端重启 = 所有人重新登录**（客户端也要重启）。断线自动重连
     只服务「**网络故障恢复**」这一种情况 —— 那时服务端进程还活着，
     票据还在内存里，滑动过期 + bind 后 12 小时（D096 前两点）足够撑住；
  3. 顺带把「票据认不出来」的回码从 `3` 改成 **`2`**，只有「压根没带票据」
     才回 3。
- **理由**：
  1. **用户原话**：「考虑到 tickets.json 会让服务端的文件越来越大，
     没有定期删除机制，所以我想改成不要保存硬盘，tickets 只放到内存即可，
     服务端重启后，客户端都应该重启。客户端的断线重连只用在网络故障恢复上」。
     这是产品级取舍，而且他说得对：那个文件是**只增不减的凭证表**，
     真要长期开服就得再写一套清理逻辑（按时间切、按大小切、启动时清），
     而它换来的收益只有「重启服务端时玩家少点一次登录」。
  2. 内存版**天然没有那个问题**：进程一退全没，`_purge_unlocked()` 每次
     访问顺手过期清理。而 D096 真正要治的那个坑（客户端**只会重放旧票据、
     永远不回认证服**，§171）在「网络故障恢复」这条路上照样被治好了 ——
     那才是断线重连的主要用途。
  3. 回码改成 2 是**为了让「服务端重启」这件事说人话**：内存版之下，
     重启后每个还开着的客户端都必然撞上「票据认不出来」。回 3 那句
     「在无法连接的地方尝试了连接。」会让玩家以为被封 IP / 连错服务器；
     回 2 那句「现有连接已断开。请重新尝试连接。」恰好就是他该做的事。
     三种走到这里的情况（被顶号 / 过期 / 服务端重启过）玩家的动作完全一样，
     所以不再分。
- **和 D071 的关系**：D071 当初要求「只有被顶号才回 2，其余回 3」，
  理由是「乱码票据也被告知『你的账号在别处登录了』属于撒谎」。
  ★ 那条理由**站不住**：`result=2` 的客户端文案是
  「现有连接已断开。请重新尝试连接。」，**一个字都没提「别处登录」**
  （那是我们自己在日志里写的话）。它对三种情况都是准确的。
  D071 里「文案用客户端自带的、靠结果码说话」这个大方向不变。
- **代价（明说）**：服务端重启后，正在玩的人会看到「现有连接已断开。
  请重新尝试连接。」然后被断开，**必须重开客户端重新登录** —— 这是设计。
  ⏳ 区第 17 条的期望值已按这条改写。
- **被否**：保留落盘但加清理（定时/按大小/启动时清）—— 那是为了一个
  次要收益引入一整套要维护的策略，用户已经明确不要；
  只把「已 bind 的」落盘（文件还是只增不减，同一个问题）。
- **反悔条件**：将来真的需要「服务端可以随时重启而玩家无感」
  （比如要做热更新/滚动重启），那时再谈落盘 —— 但那时应该连房间状态一起持久化，
  只存票据是半吊子。

    宽度能有 213）：和 `1011` 不左对齐，看着像缩进错误。
- **反悔条件**：将来还要往第二行加字时，**先在真控件上试排版**
  （`SetWindowPos` + `SetWindowTextW` 改运行中的登录框 + `PrintWindow` 抓图），
  确认 145 宽仍然装得下；装不下就折成三行（加高是安全的，加宽不是）。

## D099 远程代理只加在客户端 `relay.py`，地址为空即直连；启用后**失败不回退直连**

- **决策**：
  1. `server.config` 增加 `proxy_type / proxy_address / proxy_port / proxy_username /
     proxy_password`，以 **`proxy_address` 非空**作为唯一启用条件；旧配置没有键、
     或新配置把地址留空，都保持直连。
  2. 代理实现只放在客户端包独有的 `server/relay.py` 出站端，覆盖远程认证 47611、
     游戏 27799、原版战斗中继 27798 三条 TCP；本机服务器的直连路径不改。
  3. 标准库原生实现 SOCKS5 和 HTTP CONNECT（含可选认证），不引入第三方依赖。
  4. 只要代理已启用，任何代理连接 / 认证 / CONNECT 失败都直接失败，**禁止直连兜底**。
  5. 实际使用路径逐连接写进客户端 `logs/relay.out`，只写协议和代理端点，
     不写代理用户名 / 密码。面向玩家的配置说明只放 `server.config` 注释，
     不往登录框、启动提示或 README 再塞一套代理说明。
- **理由**：
  1. D066 已经用不同端口把本机 / 远程分成两条确定路径；代理挂在只服务远程路径的
     本机中继上，天然满足「只影响远程服务器」，也不需要冒险修改 32 位 hook。
  2. 三条远程连接本来就汇聚到同一个纯字节中继；在它建远端 socket 的唯一位置换成
     CONNECT 隧道，握手后的收发代码完全复用，SnowCipher / SimpleCipher 字节不变。
  3. SOCKS5 和 HTTP CONNECT 覆盖常见本地代理，Python 标准库足以实现；继续保持
     客户端包零安装、零 pip（D062 / D087 的同一约束）。
  4. 用户显式配置代理通常不只是「能连上」问题，也包含出口选择；故障时静默直连会
     让日志看似成功、实际绕过用户选择，是最危险的失败方式。
  5. `proxy_address` 单独当开关最兼容：不用额外 `proxy_enabled` 制造「开关和地址互相矛盾」
     的第四种状态，也保证旧配置文件自然关闭代理。
- **被否**：
  - 在 `bshook.c` 里实现 SOCKS / HTTP（重复造网络栈、凭据编码更麻烦，且会影响高风险 DLL）；
  - 读取系统代理 / `HTTP_PROXY`（行为不由 `server.config` 决定，且 SOCKS 口径不统一）；
  - 代理失败后回退直连（违背明确出口选择）；
  - 给本机 `app.py` 也套代理（本机连接绕出去再回来，直接违反需求）；
  - 只支持一种代理协议（会无谓排除另一类常见本地代理）。
- **反悔条件**：若将来明确要求「注册链接也必须由本配置强制代理」，需要另做本地 HTTP
  入口或接管浏览器配置；当前注册链接由外部浏览器打开，遵循浏览器 / 系统自己的代理。
  若要求代理客户端间 UDP，也必须单独设计 UDP ASSOCIATE；两者都不属于本次
  「连接远程游戏服务器的三条 TCP」范围。

## D100 打包冒烟检查用**主动 TCP 连接**，不依赖系统监听表

- **决策**：`Invoke-ServerSmokeTest` 等包内 Python 启动时，对认证 / 游戏 / 原版中继 /

- **理由**：
  - D082 的代价在两台真机上如期兑现了：用户合作打完一局，
    **两个人看到的分数对不上** —— 各自那一行对，队友那一行是 0。
    那一格（`[GameContextQuest + 座位*0x34 + 0x3ec]`）**只有 `0x0411` 会写**。
  - D082 留的反悔条件是「重复调 `0x4087f0` 安不安全没有 RE 依据」。
    §178 把依据补上了：`0x4087f0` 是 `0x0505` 的**排空式**上报，
    靠 `0x55bc5f` 把累计伤害和一个空对象 **swap** 再发再析构 ——
    第二发起送的是空表，不重复计数也不改别的状态。
    另外两处重复投递也都读到底：`0x4a4096` 纯按座位号写、
    `0x4913fc` 有 `cmp byte [esi+4]` 重入保护。
  - **自己那份排第一**：`0x4913fc` 每一发都会被调到，真正建界面的是第一发。
    自己排第一 ⇒「先更新右上角四个全局、再弹界面」的时序和 V0.1 实机验过的
    单人版逐字一致；队友那几行是界面弹出来之后补的，
    而结算界面画每一行时是**当场**去读那 13 个 dword（`0x4a4b45`），补得进去。
- **被否**：把队友那份排前面（会让「界面弹出来时自己的经验/金币还是旧值」
  变成没验过的新时序）；只补发队友那份、自己那份不发（少一发包，
  却把唯一实机验证过的那条路径改掉了，不划算）。
- **代价**：一局结束时客户端会多回 N-1 发空的 `0x0505`（六人房 5 发）。
  服务端本来就不处理这个包。
- **单机一个字没变**：`settlement_seats()` 只有一个座位时，
  发出去的仍然是「一份 `0x0309` + 一份 `0x0411`」，V0.1 的老用例逐字节钉着它。
- **反悔条件**：真机上出现结算界面异常（弹两次 / 数据错位 / 崩）。
  改回去就是 `end_game_order()` 只返回自己那一个座位。

## D102 GameGuard 的 DR0 由 **bsloader 从进程外抢先武装**，失败了就**自动重来**

- **决策**：
  1. `bshook.dll` 在 DllMain 里装完 VEH 就置位 `INJECTED` 事件；
     `bsloader.exe` 收到之后开始每 2ms 读一次 `0x54b0fc`，
     一认出已知签名就 `SuspendThread + SetThreadContext` 把 DR0 摆上去并守护，
     直到 DLL 那条武装线程置位 `READY`（接管）或 VEH 置位 `HIT`。
  2. 绕过失败（DLL 认出 GameGuard 错误框，或进程在 `HIT` 之前就退出）
     ⇒ 杀掉重来，最多 3 次；前几次把错误框吃掉，最后一次照常弹给玩家看。
- **理由**：
  - §179：DLL 里那条武装线程是 `CreateThread(DllMain)` 出来的，
    线程入口要等加载器锁 —— 用户那台机器上**三条 DLL 线程一起卡了 3.3 秒**，
    而 GameGuard 校验在那之后只有 2.2 秒就执行了。
    余量由别人机器的锁竞争决定 ⇒ 「有概率启动报错，重启就好」。
  - bsloader 是**另一个进程**，目标进程的加载器锁完全管不着它。
    这不是加一层保险，是把武装时机从「等锁」改成「不等锁」。
  - 判据、DR0/DR7 的值、守护动作两边**完全一样**（字节定义提到
    `gg_bypass.h` 里共用），同时写也只是把同一个值写两遍。
  - 自动重来是兜底：race 再窄也不等于零，而「重启一次就好」本来就是
    用户手工在做的事，让 bsloader 替他做。
- **被否**：
  - 在 DllMain 里就武装（那时壳还在跑，既会被壳的 `NtContinue` 清掉，
    也可能撞上 ASProtect 的调试寄存器检查）；
  - 改回「patch 5 个字节」（V0.1 实测 4 次里 3 次被壳的 CRC 抓到）；
  - 只把超时调长（等的根本不是解壳，是线程调度，调长没用）。
- **必须守住的三条**：`INJECTED` 一定在 `AddVectoredExceptionHandler` 成功
  **之后**才置位；`HIT` 在 VEH 里就地置位（别指望被锁压着的 `watch_thread`）；
  DLL 的武装线程要认得「断点在我跑起来之前就已命中」（返回 3）这一支。
- **反悔条件**：外部 `SuspendThread` 被某些反作弊/安全软件当成调试器
  （目前没有证据；GameGuard 本体在我们这条链上根本没跑起来）。
  真出问题就把 `external_arm_loop` 整个跳过，退回纯 DLL 武装。

## D103 有人中途离开正在打的一局 ⇒ 服务端补一发 `0x0414 gspChangeControllerSlot`，并在服务端**镜像一份**控制者表

- **决策**：
  1. 房间处于「游戏中」且 `room.quest` 在时，任何人离开（退房 / 断线 / 被踢 /
     被顶号）都给**还留着的每个人**发一发
     `0x0414 gspChangeControllerSlot(old=走的人的座位, new=接管者的座位)`；
  2. 服务端在 `RoomQuest` 里**镜像**客户端那张表的类别 20~25 那 6 格
     （开局时按客户端同一个公式 `占用座位[i % n]` 算，§180），
     用它决定「走的人到底有没有欠着控制权」和「谁接管最划算」；
  3. 接管者 = 还在座的人里**当前持有格数最少**的那个，并列取座位号最小的；
  4. 走的人一格都不占（表里没有它）⇒ **一个包都不发**（日志记一行）；
  5. 房间不在「游戏中」⇒ 不发。等待房那张表客户端自己也建，但那儿没有怪，
     发了没有意义，只会给日志添噪音。
- **理由**：
  1. **除了服务端没有别人能做这件事**（和 D093 同一个结构）：控制者表是
     客户端在 `GameContext::StartGame` 里按「当时在座的座位」算死的，
     客户端自己**没有任何一条路**会因为「某个座位空了」而重算它（§180）。
     闯关里的怪和刷怪点全在类别 20，控制者恒等于座位号最小的在座玩家
     = 通常的房主 —— 房主一走，**没有任何一台客户端刷怪或跑怪 AI**，
     关卡的闸门再也不会开，玩家表现就是「走到屏幕最右边被屏幕挡住」。
  2. **这个包是原版为这件事准备的**：载荷就是 `(old, new)` 两个座位号，
     处理器把类别 20~25 里等于 `old` 的全换成 `new`，再逐个通知世界里的
     怪 / Boss / 刷怪点重算一次「这只归不归我」。保真优先（D078 的同一条口径）
     —— 我们不发明新机制，把原版留的那条路接上就行。
  3. **镜像表是必要的，但只用来做决策，不是权威**：客户端才是权威
     （它自己算初值、自己应用替换）。镜像哪怕和客户端错开，
     我们挑出来的 `new` 仍然是一个「还在座的座位」，客户端照样能接管 ——
     也就是说镜像出错的代价是**负载分配不均**，不是功能坏掉。
     这一点必须写在注释里，免得以后有人拿它当权威去做别的判断。
  4. **挑「持有最少」而不是「新房主」**：六人房里房主走了之后，
     新房主本来就已经持有自己那一份，再把走的人那几格全压给他，
     他一台机器要跑两倍的怪。挑最闲的那个是一行 `min()` 的事。
- **被否**：
  - **每次离开都重发一整套「重新轮转」**（把 6 格全部按剩下的人重排）：
    协议做不到 —— `0x0414` 只能表达「一次 old→new 替换」，
    要重排就得发多发、且中间状态各机器不一致（收包顺序不保证）。
  - **恒定发给新房主**（`new = room.host_seat`）：简单，但六人房里负载翻倍，
    而且房主转移和控制权交接是两件不相干的事，绑在一起以后会互相牵制。
  - **在等待房里也发**：多一条没有任何效果的代码路径（那儿没有怪），
    却要多一套「等待房的镜像表什么时候建」的状态。
  - **猜「鬼影挡路」并去销毁掉线者的角色**：§180 已经读到底 ——
    我们发的 `0x0301 action 1` 走的 `0x405f8f` 本来就 `World::Remove` + 析构，
    和 stage 无关，战斗中一样生效。往那个方向修等于修一个不存在的 bug。
- **代价 / 已知未验**：⚠ **「真客户端收到 `0x0414` 之后会不会真的接管刷怪」
  没有实机验证**（假客户端只能证明字节发对了）。RE 上三条链都读到底了
  （表的读侧 `0x491225`、包的处理器 `0x493780`、七个 `vf_E8` 实现），
  但只有两台真机在同一局里才能证。见 PROGRESS ⏳ 区第 20 条。
- **反悔条件**：若实机发现接管之后怪的行为异常（比如同一只怪被两台机器同时跑），
  那说明 `vf_E8` 那一路还有没读到的状态，退路是「只在房主离开时发一发、
  new 固定填新房主」，把变量减到最少再查。

## D104 —— 我们自己的每一条 TCP 都关 Nagle（`tune_stream`）

**2026-08-13 会话 17。**

- **背景**：用户报「局域网联机也不跟手，看着躲过子弹了还是被打中」。
  §181 查明战斗同步是**事件驱动**的、没有 tick 兜底 ⇒ 链路上多一毫秒手感就差
  一毫秒；§182 查明 `TCP_NODELAY` 在整个项目里**一处都没有**，
  而联机时一份同步数据要过**三段我们自己的 Python TCP**。
- **决定**：`server/netlisten.py` 新增 `tune_stream(sock)`，在**六处**调用 ——
  三个 accept（`relayserver` / `gameserver` / `authserver`）、
  本机中继 `handle()` 的 `client` 和 `remote` 两条、`connect_remote()` 的出站。
- **为什么这不违反 D078「原版的连接方式原样还原」**：
  **客户端自己就在关 Nagle** —— 收到 `0x0410` 时 `0x408703` 顺手
  `setsockopt(TCP_NODELAY)`（§150），`RelayConnection` 连上也设（§152）。
  我们是在**补齐**原版行为，不是改它。原版的中继服务器不可能开着 Nagle 还能玩。
- **被否**：
  - **只在监听 socket 上设一次**：Linux 上 accepted socket 不继承（Windows 上会）。
    服务端包两边都要跑，靠继承等于赌平台。
  - **顺手把包合并 / 加发送队列**：那是在 Nagle 之上再造一个 Nagle，
    而且会踩 V0.1 §120 那个「必须一次 sendall」的时序约束。
  - **提高客户端同步频率**：会偏离原版行为，且 §181 已经说明同步是事件驱动的
    —— 没有「频率」可提。
- **代价 / 已知未验**：⚠ **两台真机上的实际手感没验**（agent 只能在 loopback 上
  量到 0.2~0.4 ms）。见 PROGRESS ⏳ 第 21 条。
- **反悔条件**：若实机 RTT 仍是几十毫秒以上，说明瓶颈不在 Nagle，
  拿 `[online]` 里那几行 `中继 RTT` / `同步转发` 的数字重新定位
  （转发耗时 < 1 ms 就能排除服务端自己）。

## D107 —— 注册限流：**前台倒计时只是装饰，闸门在服务端按 IP**；只锁「成功」

**2026-08-13 会话 18，用户提的需求。**

- **决策**：
  1. `server.config` 新增 `register_cooldown_seconds`（默认 **60**，`0` = 关闭）。
     **前台按钮倒计时和后台 IP 限流共用这一个值**（用户明确要求一致）。
  2. 后台：一次注册**成功**之后，同一个客户端 IP 在冷却期内的注册请求一律拒绝。
     限流查询排在 `_api_register` 的**最前面**，比重名 / 密码校验还早。
  3. **只有成功才计时**，任何失败（重名、两次密码不一致、用户名不合法）都不计。
  4. IP 表**只在内存里**，`{IP: 解禁时刻}` + 每次访问顺手清过期项，服务端一重启就没。
  5. 前台把**绝对解禁时刻**写进 `localStorage`，刷新页面接着倒数；
     应答里带 `retry_after`，成功和「被后台拦下」都用它来架倒计时。
- **理由**：
  1. **限流放最前面**是为了不把它变成账号枚举接口：如果「已存在」和「频率超限」
     回的话不一样，一个个试就能问出谁注册过。这条不是洁癖 ——
     这台服务器上的密码是明文的（D067），账号名泄露的代价比一般站点更大。
  2. **只锁成功**：脚本要的是**建成号**，锁成功那一侧就足够挡住批量注册；
     而锁失败会把「密码敲错一个字」的正常玩家罚等一分钟，损失全在好人这边。
  3. **不落盘**沿用 D097 对票据的同一条口径 —— 用户已经明确不要「只增不减、
     没人清理」的文件。而这份数据天然只有几十秒寿命，重启丢掉零损失。
  4. **前台那半明说是装饰**：localStorage 一清、换个浏览器、直接 `curl` 就绕开了。
     它解决的是「手滑连点」和「刷新一下重来」，真正的闸门只能在服务端。
     两边共用一个秒数是为了**别让玩家看到自相矛盾的两个数字**。
  5. **`0` 要能关掉**：局域网熟人服、或者一群人同时开号时，60 秒会让共用一条
     宽带出口（同一个公网 IP）的人互相排队。
- **实现上的两个取舍**：
  - **端口和秒数分开清洗**（`_PORT_KEYS` / `_SECOND_KEYS`）：秒数允许 `0`，
    端口不允许。共用一个 `_clean_port` 会把「关掉限流」当成填错值。
  - **`make_server(cooldown=)` 的默认值是 60 而不是 0**：漏传参数时应当
    **多限一点**而不是不限。测试里要连着注册的那一组显式传 `cooldown=0`。
- **被否**：
  - **按账号 / 按 User-Agent 限**（账号是一次性的，UA 随便伪造）；
  - **信任 `X-Forwarded-For`**（谁都能自己填一个头，等于把限流关掉）；
  - **只做前台倒计时**（用户要的就是「后台也同样限制」，而且前台可以绕开）；
  - **失败也计时**（见理由 2）；
  - **给限流单独一个配置项**（用户明确要求两边时间一致，两个键必然会被改歪）。
- **代价（明说）**：几个人共用一个公网 IP 时会互相排队 —— 已写进服务端包
  README 和 `server.config` 注释，并给了「调小或填 0」的出路。
- **反悔条件**：真出现「一群人同时开号被挡住」的实际抱怨，就把它改成
  「同一 IP 每 N 分钟允许 M 个」的令牌桶 —— 但那时仍然不落盘。

## D108 —— 客户端 IP 用**固定优先级 + 内网对端判据**取，**不加配置项**

**2026-08-13 会话 18，用户拍板。**

- **背景**：D107 那条按 IP 的限流用的是 `self.client_address`。
  藏在 frp / nginx 后面时它永远是代理自己 ⇒ 全服玩家挤进同一个桶 ⇒
  限制退化成「整台服务器 60 秒一个号」（§189 有实测复现）。
  agent 先做了一版 `register_trusted_proxies` 可信名单，**用户明确否掉**：
  「我不想把 register_trusted_proxies 放在配置文件里，请通过其他方式实现，
  比如取客户端时，按照 X-Forwarded-For，X-Real-IP，connection.remoteAddress，
  socket.remoteAddress 的优先级取得客户端 ip」。
- **决策**：按用户要的固定优先级取，**一个配置项都不加**：

  ```text
  1. X-Forwarded-For   ┐ 只有 TCP 对端是环回/私网/链路本地地址时才看
  2. X-Real-IP         ┘
  3. TCP 对端（client_address）
  ```

  `X-Forwarded-For` 内部**从右往左**找第一个公网地址。
- **理由**：
  1. **那个内网判据不是可选的装饰，是让这条限制不变成摆设的唯一东西。**
     `X-Forwarded-For` 是客户端自己就能写的普通头；无条件采信 =
     `curl -H "X-Forwarded-For: 随便一个IP"` 每次换一个桶 = 限制彻底失效，
     而「脚本批量注册」正是它唯一要防的。
  2. **判据能零配置成立，是因为它用的是一个物理事实**：公网上的客户端
     不可能以 `127.0.0.1` / `192.168.x` 这种地址连到我们。对端是内网地址
     ⇒ 那一跳只可能是我们自己前面那层 frp / nginx / docker。
     所以「公网直连 ⇒ 只认对端」「内网对端 ⇒ 认转发头」两种部署各自都对，
     不需要人去填任何东西 —— 这正是用户要的「不放配置文件里」。
  3. **从右往左**：每一跳代理都把「它看到的对端」追加到链尾
     （nginx 的 `$proxy_add_x_forwarded_for`），右边是我们自己人写的。
     从左往右取（最常见的写法）等于直接采信客户端塞进来的那一截。
- **被否**：
  - **`register_trusted_proxies` 可信名单**（agent 的第一版）：安全上最严格，
    CDN 也能覆盖 —— **用户明确不要配置项**。
  - **无条件采信 `X-Forwarded-For`**（字面照搬 Node 那套写法）：
    见理由 1，等于把 D107 整条限制删掉。
  - **再加一个「按 TCP 对端的宽松兜底桶」**：能在伪造时兜住，但要引入一个
    没有配置项的魔数（每窗口允许几次），一群朋友同时开号时会莫名其妙被挡，
    而收益只覆盖「内网伪造」这一种已经接受了的情况。
- **代价（明说，已写进 README）**：
  1. **同机 / 同局域网的人可以靠伪造这个头绕过冷却**（他们的对端也是内网地址）。
     实测确认过。接受 —— 那是熟人绕过 60 秒，不是公网批量注册。
  2. **公网 CDN 在前面时不生效**（对端是 CDN 的公网 IP ⇒ 走直连分支）。
  3. 游戏那三个裸 TCP 端口没有这种头，frp 转发时 `[online]` 里的游戏连接
     `ip=` 仍是 frp 的地址 —— 只影响日志可读性，本版不处理。
- **反悔条件**：真要支持公网 CDN，就得回到可信名单那条路；那时可以做成
  **命令行参数**（`--trusted-proxies`）而不是配置文件项，仍然满足用户的要求。

## D109 —— 道具模式的道具由**服务端**刷，用 `0x0404 gspCreatedItem`，位置随便给

**背景**：用户实机报「道具模式下地图里找不到道具」。
§191 查到底：地图文件里一件道具都没放（174 张 `.map` 全扫过），
客户端也没有任何一处会自己请求生成 —— **只有服务端能把道具放到地图上**。
我们的服务端从来没发过，所以一件都不会有。

### 选 `0x0404 gspCreatedItem`，不选 `0x0413 gspCreateObject`

两个包都能建物件（都走 `ObjectFactory 0x513278`），差别在客户端替我们做多少事：

| | `0x0413 gspCreateObject` | **`0x0404 gspCreatedItem`** |
|---|---|---|
| 坐标取模进地图 | ❌ | ✅ `fmod(X, 宽) / fmod(Y, 高)` |
| 埋在地形里就找空位 | ❌ | ✅ 五像素步长、四方向、最远 300 像素 |
| 找不到空位 | 照建 | **整包丢掉**（不会出现半截埋在墙里的东西）|
| 有没有被真客户端验过 | ❌ 没有 | ✅ V0.1 §113 起就是掉落物那条路 |

⇒ **用 `0x0404`**。服务端因此**不需要任何地图几何数据**，这一点很重要：
服务端包里没有 `Pack_decrypt/`，也不该为了刷道具去解析 `.map`。

### 位置：随机给正数，交给客户端夹

X 取 `[0, 11400)`、Y 取 `[0, 2048)`（比最宽 11400 / 最高 2048 的图都不小），
客户端取模之后自然铺满整张图。**这是本条决定里唯一的猜**：

- 落在空中的会浮着（这个游戏有跳跃和翅膀，浮空道具不算离谱）；
- 落在地形里的会被顶到地面上；
- 埋得太深（300 像素内找不到空位）的那一发**会被客户端整包丢掉**，等于白刷一次。

**反悔条件**：用户实机说「道具老是在够不着的地方」或者「半天看不到一件」，
下一步有两条现成的路（都不需要地图数据）：
① 把 Y 的范围压到偏下的一段；
② **拿玩家死亡上报（`0x0408` 带 X/Y）的位置当刷新点** ——
那是实测可达的坐标，而且正好落在打得最凶的地方。

### 刷新节奏：开局 5 秒后第一件、之后每 10 秒一件、地图上最多同时 8 件

原版数值已无从考证（服务端 15 年前就没了）。常量在 `gameserver.py` 顶部
（`ITEM_SPAWN_FIRST_DELAY` / `ITEM_SPAWN_INTERVAL` / `ITEM_SPAWN_MAX_ALIVE`），
**不做成 `server.config` 的配置项** —— 它不是玩家该关心的东西，
真要调也是我们按实机反馈调一次就定了（同 D108 「零配置」的口径）。

### 道具池：15 + 2 件，**10305 绝对不能进**

`Item.ini` 里有 `FastShot(10305)`，但工厂的跳表 `0x513b56` 那一格指的是
default 分支 —— 发下去客户端建不出对象。`PVP_ITEM_IDS` 里没有它，
`test_battle.ItemPoolTests` 钉着这一条。
`TeamHpCharge(10313)` / `TeamReflect(10314)` 只在**组队战**里刷
（个人战里「全队」就是自己一个人，摆出来只会让人以为捡错了）。

### 节拍挂在 `RelayServer.deliver()` 上，不挂在 `Conn.on_peer_data()` 上

★ **原版中继一旦建起来，整局连一发 `0x040e` 都不会再有**（§160 实测：
235 份同步数据全从中继走）。`deliver()` 是两条通道唯一的汇合点，
所以「每帧问一次」的房间级判断都必须挂在那儿。
**顺带修掉一个没人报的隐患**：对战的 240 秒时间上限本来也只挂在
`on_peer_data` 上，中继模式下一局不死人就永远不结算。
回调外面套了 `try/except`：中继连接一断客户端会自己退房（§158），
转发这条主路不许被任何附加逻辑带崩。

## D110 道具进槽 / 用道具 / 效果生效 —— 三个包全由服务端发，且**各发各的人**

- **决策**（承接 D109，把「捡到之后」那一半补完）：

  | 时机 | 发什么 | 发给谁 |
  |---|---|---|
  | 拾取放行之后，捡到的是 PvP 道具 | `0x040b`（int32 物件 id）| ★ **只发给捡到的那个人** |
  | 收到客户端的 `0x040c`（按 Ctrl）| `0x040c`（int32 槽位号，原样回显）| ★ **只发给用道具的那个人** |
  | 同上 | `0x040a`（座位 + 道具 id + `0` + `-1`）| ★ **广播全房间** |

  服务端在 `RoomQuest` 上镜像每个座位手上的道具（`item_slots`，上限 4 件，FIFO），
  以及每个掉落物句柄对应的物件 id（`item_handles`）。

- **理由**（RE 依据全在 §194，三条链都读到底了）：
  1. **除了服务端没有别人能做**。`Character::AddItem` 在 PvP 一局里唯一的
     触发者就是 `0x040b` 的处理器；`RemoveItem` 和 `UseItemEffect` 更狠，
     **各自只有那一个调用点**。客户端按 Ctrl 只发一发包 + 放一声音效，
     然后就等着 —— 和 V0.1 §108/§111/§113/§115、V0.2 §191 是同一个形状。
  2. **`0x040b` / `0x040c` 必须点对点**：两个处理器都用 `0x409f39`
     取「**收包这台机器上的本地玩家**」，包里根本没有座位号。广播出去
     = 一个箱子人手一件、一次 Ctrl 全场各掉一件。
  3. **`0x040a` 必须广播**：它按包里的座位号找角色（`0x404ff6`），
     六台机器上算出来是同一个人。不广播的话别人屏幕上你既不加速也不亮护盾，
     而伤害结算是各机器各算的 —— 那就直接对不上了。
  4. **服务端必须自己记住每个人手上是什么**：`0x040c` 只带槽位序号不带 id，
     不记的话 `0x040a` 里那个 id 无从谈起。而记这份镜像是**免费**的 ——
     槽里的东西本来就是我们发 `0x040b` 放进去的、发 `0x040c` 拿出来的，
     两边天然同步。
- **两条跟着客户端走、不许自作主张的口径**：
  - **满 4 格就不发 `0x040b`**。客户端 `AddItem` 扫不到空槽是**静默返回**，
    我们照发的话它不收、镜像却多一件，之后按 Ctrl 会用出一件它没有的道具。
  - **槽位序号照包里的来**，不要因为「客户端恒发 0」就写死 0。
    万一将来发现别的分支会发别的值，跟着走才是对的。
- **`0x040a` 那两个附加参数填 `0` 和 `-1`**：抄 `PvpItem::vf_11c`
  （`0x5225fb`）自己调 `UseItemEffect(id, 0, -1, "")` 的那一组。
  实际上 `0x508441` 把这两格全当局部变量重写了，填什么都一样 ——
  但保真项目里没有理由不照抄（同 D046 的理由）。
- **被否**：
  - **拾取放行时顺手把效果也广播了**（不经过道具槽）：那是「捡起来即生效」，
    是金币 / 红心的行为。PvP 道具的整个设计就是「先揣着、按 Ctrl 再用」，
    这么做等于把游戏玩法改了。
  - **让客户端自己管槽、服务端只广播效果**：客户端**做不到** ——
    `AddItem` / `RemoveItem` 在 PvP 里没有任何本地调用点。
  - **服务端不记镜像，`0x040a` 里回一个固定 id**：那就是随机发效果。
- **反悔条件**：若实机发现真客户端收到 `0x040b` 之后道具栏仍然不显示，
  说明「道具栏画的不是这 4 格」，那时要回去查 HUD 的读侧
  （目前只找到 `[Character+0x798]` 那一路，`0x516904` 起，带 3 秒计时器）。
  ⚠ 但「用得出去」这一半和 HUD 无关，那条链是闭合的。

## D113 日志自动清理：**启动时一次 + 每天凌晨 4 点一次**，按 mtime 删，白名单匹配

- **决策**（用户 2026-08-14 提的需求，实现选择在此）：新增 `server/logcleanup.py`。
  - **触发点一**：`app.py` 启动时清一次。★ 「服务端已经在跑、启动脚本跳过启动」
    的情形**天然跟着跳过** —— 因为清理挂在 `app.py` 的启动路径上，
    那种情况下 `app.py` 根本没被执行（`launch.ps1` 第 2 步）。**不用为它写一行代码**。
  - **触发点二**：每天本地时间 **4:00**（`seconds_until_daily` 用 `mktime` 算，
    不是「睡 86400 秒」—— 后者会被夏令时 / 改时区慢慢带偏）。
  - **在后台守护线程里做**，循环体整个套 `try` —— 清垃圾绝不能把服务端弄挂。
  - 保留天数 = `server.config` 的 `log_retention_days`，默认 **3**，`0` = 关掉
    （关掉时**连线程都不起**）。
- **判据用「文件最后修改时间」，不用文件名里的日期**：
  1. 正在写的日志（`server.out`、今天的 `online.log`、活着那条连接的
     `game_NNN.txt`）mtime 就是刚才，**天然选不中** —— 「不能影响正在进行的游戏」
     这条需求因此不需要任何额外的「谁在用」判断；
  2. 只有 `bshook_*.log` 的文件名带日期，别的都不带。
- **删哪些用白名单**（`LOG_PATTERNS`），不是「删掉目录里所有文件」：
  `logs/` 里还躺着 `.server_mode` / `.relay_target` 两个**状态文件**
  （启动脚本靠它们判断要不要重启中继/服务端，删了会白重启一遍），
  以及逆向时留下的截图和探针输出。**以点开头的一律不碰。**
- **`online.log` 按天切分**：它是**追加**打开、跨重启不截断的，所以它永远
  「刚写过」，3 天的窗口对它**永远不成立**。跨过零点（或重启时发现文件是前几天的）
  就把它改名成 `online-YYYYMMDD.log`，让它自己老去、到期被清掉。
  当天那份**始终叫 `online.log`**，所以文档和 ⏳ 里那些「把 `logs\online.log`
  发回来」一个字都不用改。
- **被否**：
  - 让启动脚本（`launch.ps1` / `serverctl.sh`）去清 —— 那要写两遍（Windows 一遍
    Linux 一遍），而且**云主机那条「每天 4 点」根本没地方挂**（总不能要求人家配 cron）；
  - 用 `logging` 的 `TimedRotatingFileHandler` —— 它只管自己那一个文件，
    管不到 `bshook_*.log` / `server.out` / `game_*`（那些是别的进程和重定向写的）；
  - 按目录总大小限额删最老的 —— 「3 天」是用户明确要的口径，而且大小限额在
    「一局 debug 就 7 MB」的场景下会把当天的日志也吃掉。
- **反悔条件**：若将来 `logs/` 下出现需要长期留档的东西，把它挪进别的目录
  （或以点开头），不要去松动这条白名单。

## D114 显示昵称：**只限 BMP 字符**，重名检查和用户名**分两条路各报各的**

- **决策**（用户 2026-08-14 需求）：注册页加「显示昵称」输入框，留空 = 用户名。

- **「不许 emoji」不是洁癖，是协议硬约束**：`gameserver.w_wstr()` 写的长度字段是
  **Python 的字符数**，正文却按 UTF-16LE 编码。BMP 内的字符（含全部汉字）一个字符
  恰好两字节，两者对得上；emoji 这类补充平面字符在 UTF-16 里占**两个码元**
  —— 长度字段会少算，客户端从那个包起**整条流都解错位**。
  与其在十几个组包点去数码元，不如在注册这唯一的入口挡掉。
- **「昵称留空 = 用户名」会顺带挡住用户名**：`alice` 把昵称起成 `bob` 之后，
  真的叫 `bob` 的人就注册不了（他的默认昵称撞车）。这是**对的** ——
  否则游戏里会出现两个 `bob`。提示语里专门说清了这一点。
- **存档导入（`/api/import`）不做昵称查重**：那条路是「把自己的号从另一台服务器
  搬过来」，为了别人先占了昵称就把人挡在门外，代价远大于收益。
  ⚠ 已知后果：靠导入可以造出重名昵称。真出现了再说。
- **被否**：昵称也走用户名那套 ASCII 正则（那就没法用中文昵称，需求直接落空）；
  把两种重名合并成一句「用户名或昵称已存在」（用户明确要求「分别单独 check」）；
  在前台补默认值（前后台各补一次，将来改规则必然只改一边）。
- **反悔条件**：若实测发现客户端对某个长度以上的昵称会画崩 / 截断得太难看，
  把 `NICKNAME_MAX_LENGTH` 调小 —— **在真控件上量，别算**（§175 的教训）。

## D118 `0x040d` 转发时**座位号以连接为准**，且**不回给上报的人**

**背景**：客户端在自己的效果结束时发 `0x040d(座位, 属性号)`（§200）。
包里带着座位号，服务端有两种选择：原样转发，还是用连接自己的座位重填。

**决定**：**重填**（`self.my_seat`），两者不一致时打一行警告继续。
另外**不发回给上报的那个人**。

**为什么**：

1. 客户端的发送点（`0x509843`）本来就只会填自己的座位 —— 重填一次
   等于把「谁能替谁撤效果」钉死在服务端，一条改过的客户端也没法
   替别人撤掉护盾；
2. 和同一条链上的 `0x040c`（`on_use_item`）口径一致 —— 那个包里
   根本没有座位号，只能用 `my_seat`。两个包用两个不同的真源才是危险的；
3. 不回给上报者：客户端 `0x551dfb` 第一句就是
   `if (座位 == 我的座位) return`，回过去也是白费字节。

**代价**：如果 `my_seat` 真的错了（目前没有已知路径），会撤错人的效果。
但那种情况下 `0x040a`（效果生效）本来就已经发错人了，先坏的是那一个。

## D121 生存模式按原版“三命 + 最后一队”规则由服务端主动结算

**背景**：D093 已证明所有 PvP 客户端的 `GameContextQuest.state` 都不会进入 2，原版
`CheckMatchOver` 因而不会运行；胜负只能由服务端代判。会话 10 当时只还原了模式 3 的
`DeathMatchVictoryCondition`，却把它用于所有非闯关房。用户随后实机遇到模式 0 中一队
全员各死三次仍不结束。§204 又从工厂 `0x55e0de` 和
`SurvivalVictoryCondition::vf8`（`0x55db6f`）证明两种模式的规则确实不同。

**决定**：

1. `Conn.check_pvp_finished()` 必须先读房间描述符 `arguments[1]`：模式 0 / 2 走
   `survival_finished()`，模式 3 保留原 `pvp_finished()` 夺分规则；
2. 生存模式每名在座玩家固定 **3 条命**。组队战只有当某队**所有成员**剩余生命都为 0，
   使存活队数 ≤1 时结束；个人战在存活玩家数 ≤1 时结束；之后才看 240 秒（模式 0）/
   300 秒（模式 2）时限；
3. 生存结算的 1 / -1 也从剩余生命得出：个人 / 本队剩余生命 >0 为 +1，耗尽为 -1；
   不能继续借杀敌数排名。时间到且两队都还有生命时，按原版双方都是 +1；
4. 服务端死亡镜像以已经广播给客户端的 `reported + 1` 为准并单调取最大值，而不是另起一份
   只会 `+1` 的计数。这样判胜和 HUD 的生命真源始终是同一个值。

**为什么**：

- 这是原版逐指令可证的玩法规则，不是按用户描述猜一个近似实现；
- “某个玩家第三次死就结束”在两人以上的队伍里是错的：同队其他人还有命时原版明确继续；
- 只补结束判据、不补结算排名，会让全场杀敌数为 0 的典型生存局进入结算后双方都落在 0
  （不判），或者把已淘汰但人头高的一队判赢；两处必须同源修改；
- 不 patch 客户端：D093 的阻断发生在整个无剧本 PvP 状态机，单独勉强唤醒某个胜负类会扩大
  客户端二进制和时序风险；现有服务端主动结算链已经被夺分模式复用和回归覆盖。

**没有选择**：

- 把夺分杀敌上限调成 3：那仍是按人头，不知道被杀者属于哪队、队友是否还有生命，自杀和
  环境死亡也永远结束不了；
- 整队共用 3 条命：`0x55e018` 是逐座位写 3，再累加到队伍总数，硬证据相反；
- 本轮顺手实现模式 1 计时赛：这版中文 UI 不提供该项，用户现象也与它无关，完整规则和结算
  口径应当独立逆向、独立测试。

**兼容边界**：正常 type 1 房固定带三个参数。只有参数缺失 / 损坏的控制通道路径退回旧夺分
规则，避免改变 V0.1 手搓包行为。模式 2 虽在当前中文 UI 中隐藏，但原工厂与模式 0 共用同一
生存类，故一并接对；模式 1 暂时保留旧兜底并在 §204 明记为未还原。

**反悔条件**：若第 32 条真客户端验证显示结算界面的 1 / -1 与 `0x55de15` 的直接读法不符，
只复核 `survival_ranking()`；三命淘汰判据已有 `0x55db6f` 硬证据，不随表现层反馈推翻。

## D124 IME 崩溃残留（0x4301BD）按「整段跳过」修，不做零填充

bug调查/5 的 20 份证据全部指向 UiImeCandidates 布局里 SumRect 之后的

## D125 0x0410 的状态缓存只做「去重优化」，权威在开局链的强制重发

§150 早就写明「每次进房/每次开局都要重发」，旧代码只做了进房一半、

## D126 发送截止时间之后的处置：游戏服拆连接、中继绕开回退，不搞 0x0419 补发

流密码半发送 = 流永久错位，没有「再试一次」可言。游戏服连接拆掉让客户端

## D127 玩家的死亡**只认本人上报**；怪不受限

`0x0408` 报的是「**这台机器模拟出来的**某个角色 HP 归零了」。每台客户端都
模拟全场伤害，所以射手那台和受害者那台对同一次溅射得出不同结论是必然的，
不是网络问题、也调不掉。既然只有本人那台的 HP 模拟能代表「他到底死没死」，
服务端就只该采信那一发（§211 一）。

代价是明确的：当天 10% 的玩家死亡广播（46/613）源自「本人没报」，改完这些
死亡不再发生 —— 但它们**本来就是错的**，受害者自己的模拟里他活着。
「我明明打中他了他却没死」比「我明明活着却被判死、还白烧一条命」轻得多，
而且后者会连带把生存模式的三条命提前烧完。

不给怪套这道门：怪由控制者那台模拟，谁都可能替它报，去重仍归
`RoomQuest.record_death`（那里才是怪的正确位置）。

顺带修正了一处一直没人注意的偏差：`record_kill` 用的「凶手」那一格
（`[char+0x158]`）现在来自**受害者本机**，而不是自称打中了的那台 ——
计分反而更准。

★ 房间外的调试 / 协议试探路径（`battle_seat_index()` 返回 `None`）保持老行为，
不然 `gs_ctl raw` 那一路全被挡掉。判「是不是本人」用**大厅那份座位表**，
不用 `conn.my_seat`（后者在房间外默认 0，会把手搓包误判成座位 0）。

## D128 「死了不复活」按**服务端补重生**兜底，不去猜客户端卡在哪道守卫

客户端那条 `Die() -> 5 秒 -> 0x0413` 的链上有三道守卫
（`[LobbyStage+0x1c]` / 剩余生命 / `[char+0x614]`），到底是哪一道卡住
**没查实**，而且磁盘上的 exe 是压缩壳、静态反汇编拿不到码（§211 二）。
会话 30 已经在这上面猜错过一次（「凶手=自己座位」被自己的注入实验证伪，
本轮的全量数据也不支持它）。**再猜下去只会继续赌。**

改成打**出口**：客户端等的就是一发 `0x0419`，而 `0x0419` 完全由服务端说了算，
且它本身会清掉 `[char+0x614]` —— 所以不管卡在哪一道，服务端到点补一发都能
把人拉起来。`RoomQuest` 广播死亡时上闩，收到本人的 `0x0413` 撤闩，
`RESPAWN_WATCHDOG_S = 8` 秒还没撤就自己补一发并广播。

- **8 秒**：客户端写死 5 秒，看门狗必须明显晚于它才不会抢在正常重生前面；
  再大玩家就干瞪眼太久。正常路径下这个函数永远什么都不做。
- **心跳挂在 `_relay_battle_tick`**：同步数据战斗中恒定 ~8 Hz，而且它是
  中继和 `0x040e` 回退两条通道**唯一的汇合点**（§160），和
  `check_pvp_finished` / `maybe_spawn_item` 同一个理由。
- **坐标**：优先本人上次自报的重生点、其次这张图上**任何人**用过的
  （重生点表整张图共用）、最后退回死亡地点。服务端手上没有任何地图数据，
  这三档都是客户端自己算出来过的合法位置，不会重演 §88 那种「传送到地图
  边缘 + `0x0106 gcpReportHack`」。
- **生存模式要还有命才补**：三条命用完就该躺着，那是原版规则（§204）。
  中途退房的、已经结算的，一律不补。

这和 D126 末尾那条「不搞 `0x0419` 补发」不矛盾：D126 说的是**流已经错位、
连接都要拆掉**的场合（那时补发只会把活人传回出生点）；这里的前提是连接完好、
服务端刚刚才广播过这个人的死亡、而且他**没有**发过 `0x0413`。

## D130 个人战的队伍号改成 **0（没分队）**；**D092 的理由被证伪**

- **决策**：`lobby.default_team(座位, TEAM_LAYOUT_FREE)` 返回 `TEAM_NONE`。
  三种口径的取值收敛成：

  | 模式 | 队伍号 |
  |---|---|
  | 组队战 | 座位号 % 2 + 1（1 / 2）|
  | **个人战** | **0（没分队）** |
  | 闯关等 | 全部 1 |

  另外在**线格式那一处**（`build_session_slot`）加了一道硬闸：
  队伍号不在 0..2 就按 0 发。所有 `0x0300` / `0x0301` 都从那里过，漏不掉。
- **理由**：客户端的队伍记录数组**只有两格**，而每次死亡都要跑的重算
  `vf34`（`0x55c696`）按 `this + 40*(队伍号-1)` 写、**没有上界检查**。
  队伍号 >= 3 时写出去的地址正好压在**别人的每座位战绩记录**上，
  把别人的死亡次数越写越大；生存模式剩余生命 `= max(0, 3 - 死亡次数)`
  一旦归零，受害者**活着会被切进观战**、**死了永不重生**。
  逐指令依据和现场数字在 §212。
- **D092 的理由是误读，在此更正**：`0x4fedfc` 比队伍号那一处**不决定伤害**
  —— 两条分支在 `0x4fee6b` 汇合，扣血在汇合点之后无条件执行；
  队伍号相同只是跳过 `0x4087c2` 那发**伤害统计**记账
  （`LobbyStage+0x404`，属于战后统计，不影响谁能打死谁）。
  所以「个人战人人填 0 = 全场互相免疫」这个担心不成立。
- **连带改动**：`RoomQuest.pvp_finished()` 多一个 `team_mode` 参数，
  **非组队模式不看队伍号**，只看在座人数 —— 这本来就是客户端
  `0x55c594` 的口径（开头 `0x409df1(描述符) == 1` 不成立就直接跳到
  非组队分支，一格队伍号都不读）。以前个人战靠「每人一队」让
  `sides` 天然 >= 2 才没露馅，改成 0 之后不分模式就会一开局判「只剩一边」。
- **被否**：
  - **个人战也按奇偶 1 / 2** —— 不越界，但同奇偶的两个人在
    `0x4fedfc` 里被判成队友，伤害统计不记账；而且服务端的
    「只剩一边」判据要额外绕开，收益为负。
  - **改客户端（给 `vf34` 补上界）** —— 越界确实是客户端的洞，但
    **一起玩的人多半还在用旧客户端**，客户端补丁救不了他们；
    而这个洞只有我们自己的服务端会喂到，堵在服务端一次全治。
- **反悔条件**：若哪天实测到个人战里「伤害统计 / 战后伤害排行」是玩家在意的
  数字，可以改成「个人战按奇偶 1 / 2」——**绝不能回到 >= 3**。

## D131 玩家间同步转发时**改写 `UdpPacket` 头里的局号**

- **决策**：`RelayServer.deliver()` 记下每条连接**自己最近一次自报的局号**
  （`UdpPacket` 头 `+4`，战斗中 ~8 Hz 一发），转发给谁就按**谁的号**
  重新盖章，其余字节一个不动。两边号相同时是空操作；
  收件人还没发过任何同步包时原样转（尽力而为，窗口只有一帧）。
  分叉每对只记一行日志（`局号分叉：…`），`status` 里带累计改写数。
- **理由**：那个字段是收包入口 `0x4078c4` 的硬校验（不等就整包丢掉），
  而它是**纯客户端本地**的计数器（只有 `0x5517a3` / `0x551900` 两处 `inc`，
  服务端设不了也清不了）。同一个房间里多打一局就必然分叉，
  症状是用户报的「其他人都不会动，但对局在正常进行」。逐指令依据在 §213。
- **为什么可以改**：校验和（头 `+6`，`0x5bbdc1`）从 `+0x0c` 起算，
  **不覆盖头里的局号**。实测（隔离端口 + 两个假客户端，一个发 3 一个发 1）
  收件人拿到的就是自己那个号，body / 序列号 / 校验和逐字节未变。
- **为什么挂在 `deliver()`**：它是**两条传输通道唯一的汇合点**
  （`0x040e` 回退和原版中继都过这里），和 `_relay_battle_tick` 同一个理由。
- **被否**：
  - **让服务端下发一发包把大家的计数器对齐** —— 全镜像里没有任何写它的
    包处理器，做不到。
  - **不管它，让玩家每局重进房间** —— 那是把 bug 写进说明书。
  - **只在检测到分叉时才改写** —— 就是现在这样（相同则不动），
    但**判据必须是「和收件人比」而不是「和第一次见到的比」**：
    每台客户端的号会各自往上走，只有逐包对收件人比才不会漂。
- **风险**：局号的原意是「丢掉跨局的陈旧包」。按收件人**当前**号盖章之后，
  一个刚好卡在阶段切换那一帧的包可能被放行。同步数据 8 Hz 全量重发、
  且客户端还有按序列号的 `PktQueue` 去重（§151），代价可以忽略。

## D134 ~~局号只在**分叉稳定 2 秒之后**才改写~~ **已被 D137 取代**

> ⚠ **这条从没部署过，也不要再用**。它的前提（§213「服务端没有任何包能
> 设定局号」）本身是错的 —— 见 §218。时间窗在「结算 → 房间」那次换代上

- **背景**：D131（转发时把 `UdpPacket` 头 `+4` 改写成收件人的局号）修好了
  「其他人都不会动」，但引入了 bug调查/9「第二局我打不死人」。
  根因见 §216：局号**同时**是客户端每座位收包队列的纪元号 ——

  钉在旧纪元的序号上（`base` 只进不退），新一局的事件包全被 `seq < base` 丢掉。

- **决策**：`RelayServer.deliver()` 只在**发送方和收件人的局号都已经
  超过 `EPOCH_SETTLE_S = 2.0` 秒没变过**时才改写；否则**原样转发**，
  让收件人按客户端原本的规矩自己丢。每条连接多记一个
  `peer_game_id_since`（局号**变化**时才刷新，同号重发不刷）。
  两条分支各有一行去重日志（`局号分叉：…` / `跨局包不改写：…`），
  `status` 里两个计数都带上。

- **为什么是「稳定期」而不是别的判据**：
  - 真正需要改写的那种分叉（有人中途进房，bug调查/8_2）**一整局都对不上**，
    晚 2 秒动手毫无影响；
  - 阶段切换的竞态**实测最长 350 ms**（本次现场 315 ms），2 秒盖得住；
  - 判据只用服务端已有的信息（每发同步数据都自报局号，~8 Hz），
    不需要知道房间在哪个阶段，也就不会和开局/结算链的时序再耦合一次。

- **为什么是「原样转发」而不是「丢掉」**：原样转发 = **D131 之前的行为**，
  收件人本来就会按局号丢掉它，服务端不必替它做决定；而且万一哪天判据错了，
  最坏也只是回到老行为，不会凭空少一份数据（铁律 1 的精神）。

- **被否**：
  - **撤销 D131** —— 「别人一动不动」会回来，而那条现场（房 #69）是真实的。
  - **只对 `0x4001` 心跳不改写** —— 位置就在心跳 body 里（§187），
    不改写等于中途进房的人看别人原地罚站，等于撤销 D131。
  - **按房间阶段判（`IN_GAME` 前后 N 秒不改写）** —— 服务端确实知道阶段，
    但客户端换纪元的时刻是它**自己**的帧决定的，和服务端发包的时刻差多少
    没有上界；用「客户端自报的局号什么时候变的」才是直接观测量。

- **反悔条件**：若实测到中途进房的人在**开局后 2 秒内**明显看不见别人
  （目前判断不会：那 2 秒里两边局号相同的包照转不误，只有真分叉才受影响），
  把 `EPOCH_SETTLE_S` 调小到 1.0 即可 —— 只要仍然大于各机切纪元的最大时差。

## D135 取证探针改成**调试模式常驻**，不再指望玩家「卡住那一刻去双击」

> ⚠ **会话 37 已撤掉「调试模式自动挂」这个入口**（用户 2026-08-19 拍板）：
> bug调查/9 已经从根上修掉了（§218 / D137 / D138），常驻探针没有存在的理由，
> 而它是 8 Hz 的跨进程 `ReadProcessMemory` + 一份带房间/座位/序号的日志。
> **脚本本身留在 `tools/` 存档**（`probe-sync.bat` / `probe-sync.ps1` /
> `probe_sync.py`）—— 「每座位收包队列」那一侧只有它看得见，以后真要再看，
> 手动双击 `tools\probe-sync.bat` 给已经在跑的游戏挂上。
> 下面这条决策的推理过程保留。


- **背景**：bug调查/9「第二局打不死人」**不是每次都复现**（会话 35 用户连试
  几把都没撞上）。而 §216 要看的现场就在**换局那一刹那** ——
  队列基线是「复位后收到的第一发心跳」一次定死的，等玩家发现打不死人再去
  双击 `probe-sync.bat`，那一帧早过去了，采到的只是既成事实的稳态。
  会话 33/34 那套「打到那一局时采一份」的取证流程，对不稳定复现的 bug 无效。

- **决策**：`start-debug.bat`（即 `launch.ps1 -DebugLog`）在拉起客户端之后
  自动挂 `probe-sync.ps1 -Background -WaitForGame`，**从游戏起来一直采到
  进程退出**。玩家正常玩，撞上了把 `logs\probe_sync_<时间>.log` 发回来即可。
  `-NoProbe` 可以关掉；`tools\probe-sync.bat` 保留，用于给已经在跑的游戏
  中途挂探针。

- **为什么只挂在调试模式**：`start.bat`（正常游玩）那条路一个字不改。
  探针是 8 Hz 的跨进程 `ReadProcessMemory`，开销不大但不是零；
  更重要的是**日志里有房间/座位/序号这些东西**，没必要让所有人默认产出。
  调试模式本来就是「我知道我在采证」的模式，日志早就 4 MB 起。

- **为什么挂在「清残留 + 拉 bsloader 之后」**：探针认的是 `auto`
  （自己找 `BigShot.exe`），而 `launch.ps1` 前面刚好会**杀掉残留实例**
  （互斥体 `BigShot_Assa`，V0.1 §9）。提前挂就会附到那个马上要死的进程上，
  然后探针跟着它一起「收工」，日志里只剩一行「游戏进程已退出」。

- **配套的三条，都是为了「长期挂」这个前提**：
  - **日志滚动**（默认 64 MB × 3 份）—— 挂一整天也撑不爆磁盘；
  - **判据变成有状态的**（每种毛病一局只报一次、换局清账）——
    原来那个无状态 `verdict()` 在 15 分钟的日志里就刷了几百行
    `base >= 上界`，真正的现场会被自己的告警淹掉；
  - **判「卡死」要求对方心跳还在推进** —— 游戏窗口切到后台时主循环几乎不跑，
    队列本来就不动，不加这条会满屏误报（§216 文件头那句「读到的值会冻住」
    以前只是写在注释里提醒人，现在探针自己也认这条）。

- **被否**：
  - **在客户端 hook 里埋点**（bshook 直接打队列状态）—— 要动客户端二进制，
    而这一轮的前提正是「别人和服务器都用老版本代码」，改客户端等于换掉
    复现环境；跨进程读内存是**只读**的，不改变被观测的东西。
  - **服务端侧推断**（从转发的序号流反推收件人队列）—— 服务端看得见每个人
    发了什么，但**看不见收件人那条队列吃没吃**，而 §216 的三种死法差别正好
    全在收方。日志再全也只能猜。
  - **让探针跨进程重启后自动重连**（游戏崩了自动附新进程）—— 客户端崩溃会
    重跑 `start-debug.bat`，那时会挂一个新探针，没必要在探针里再做一套。

## D136 探针到不了的那一侧，改用「客户端收包队列模型 + 现场字节流回放」做回归

- **背景**：bug调查/9 的失效是**单向**的 —— 中毒的队列在**受害者**那台机器上，

  `_epoch_settled` 让不让改写：

  用例全是实机量过的数。

  - `describe_peer_header()` 现在把**内层 opcode 的名字**解出来

    会紧贴阈值 —— 这是判断要不要调阈值的唯一依据。

## D137 局号改成**服务端自己维护换代状态、按代判定转发**，删掉 2 秒时间窗

- **背景**：D131（转发时按数字改写局号）修好了「别人一动不动」，但把跨代的
  心跳也放行了 → bug调查/9「第二局打不死人」（§217）。D133 那一轮的 D134
  用「两边局号都稳定 `EPOCH_SETTLE_S = 2.0` 秒才改写」绕开它 —— 用户
  2026-08-19 指出这只是治标：没改变「服务端在猜」的本质，2 秒这个数也没有依据。
  查下去发现 §213 的前提就是错的（§218）：**局号的每一次变化都是服务端某一发
  包造成的**，服务端手里本来就有精确答案，根本不需要猜。

- **决策**：服务端为每条连接维护一份换代状态（`relayserver.PeerEpoch`）：

  | 字段 | 来源 | 说明 |
  |---|---|---|
  | `gen` 代号 | **我们发出去的字节** | 硬事实，不猜、不接受推翻 |
  | `value` 局号 | 模型为准、客户端自报为校准 | 只有它可能对不上 |
  | `gen_of` | 最近 16 条「局号 → 代号」 | 换代那一刹那的在途包靠它归代 |
  | `pending` | 换代是否已被自报确认 | 最危险的窗口，见下 |

  状态迁移**全部**挂在 `Conn.send()` 里认帧头 opcode（`note_epoch_from_frame`），
  也就是**字节离开的地方** —— 这样没有哪个发送点能漏登记（结算回房间、
  控制通道的 `back-to-room`、将来新增的路径都自动被覆盖）。
  代号由房间现算（`lobby.Room.advance_generation`，同 kind 幂等），
  **没有「先发布再消费」那一步**。

  转发（`RelayServer.deliver`）只有两条出口：

  ```text
  同一代 -> 按收件人的编号盖章（相同则一个字节不动）
  不同代 -> ★ 丢掉，不投递
  ```

  「过渡期」由此**恰好**等于「从服务端发出换代包，到这条连接自报的局号
  变成新值为止」，一毫秒不多不少。`EPOCH_SETTLE_S` / `peer_game_id_since` /
  `_epoch_settled` / `_note_epoch_race` 全部删除。

- **为什么跨代必须丢、不能「原样转发让客户端自己丢」**：中途进房的人编号
  起点不同，发送方的旧号可能正好等于收件人的当前号 —— 那就是误收，
  而且必然是最毒的那一发（§219）。

- **模型和自报值对不上时怎么办**（★ 用户明确否掉了「退回老行为」）：
  - **代不动摇**（那是我们发出去的字节决定的）；
  - 换代还没被确认（`pending`）→ 当陈旧包**丢**，继续等确认。这段窗口正是
    毒包所在的地方，宁可丢也不放行；
  - 已经确认过了 → 把**值**重锚到自报值（代不动），记一行 `模型失准（已重锚）`，
    之后照常按代判定。**自愈、不降级**，任何情况下都不回到 D131 / D134 的行为
    —— 那两种行为本身就是有 bug 的，留一条回去的路只会让人在出问题时切回去。

- **被否**：
  - **保留时间窗当兜底** —— 两套判据并存，出问题时分不清是哪套在起作用；
    而且时间窗在「结算 → 房间」那次换代上必然失手（§219）。
  - **跨代包照转不误** —— 见上面那条误收。
  - **把换代状态放在 `lobby.Room` 里由业务逐处更新** —— 漏一处就是一个
    永远查不出来的偶发 bug；挂在 `send()` 上是唯一「不可能漏」的位置。

- **代价**：`send()` 多一次首字节判定 + 一次 u16 解包 + 一次字典查
  （量级 0.3 µs，相对客户端自己 100 ms 的心跳可忽略，§187）。

## D138 中途进房的人靠 `0x0303 gspSession` **直接对齐**，不靠补发换代包

- **背景**：D137 把「什么时候能转」解决了，但「两台机器编号不同」本身还在。
  原来的办法是转发时改写头里那两个字节（D131）。

- **★ 查明**：`0x0303 gspSession` 的**包尾那个 u16 就是局号**
  （`0x556ed1`：`movsx eax, ax` / `mov [GameSession+0x3c], eax`，§218）。
  客户端自己只会 `inc` 和「复位成 -1」，**这是原版留给服务端的唯一一个
  「说几就是几」的入口**。我们以前把它当「语义未知」按 D019 填 0 ——
  巧的是正因为一直填 0，进房的人才总是从 0 开始数，`bug调查/8_2` 那种
  「老玩家 3、新来的 1」的分叉才会稳定复现。

- **决策**：`build_update_session` 把那个 u16 变成参数，
  所有 `0x0303` 的发送点都填**房间当前的局号**（`lobby.Room.epoch_value`，
  新房间 0、每换一代 +1）。进房本来就要发这一发，所以中途进来的人
  **当场就和全房间对上**，一个额外的包都不用发。

- **被否（本次实现过又推翻的方案）**：**开局前给落后的人补发 (M−v) 发
  `0x0403` 把局号顶平**。技术上可行（`0x0403` 对坐在房里的客户端就是一发
  纯粹的 +1），但：① 要小心它和 `0x0400` 的先后顺序，补发早了会把房间推进
  错误的代；② 客户端那一帧可能真重建一次房间 UI，还要跟着补 `0x0600`/`0x030b`；
  ③ 一局 +2，打了十局的房间要给新人灌 20 发包。
  `0x0303` 那个字段既是原版本来的设计，又只要改一个立即数，**没有理由不用它**。

- **改写局号那条路留着当兜底**（用户 2026-08-19 拍板）：对齐正常工作时
  `deliver()` 里一发都不会改写；真改写了会打一行
  `同代改写局号：… ★ 开局前的强制对齐正常时不该出现这一行`，
  那就是「对齐没生效」的唯一信号。

- **反悔条件**：如果哪天发现某个客户端版本的 `0x0303` 处理器不写 `+0x3c`
  （本镜像 `BigShot_22524` 是写的，逐指令核对过），中途进房的人会退化成
  「靠 D131 改写」—— 功能上仍然对，只是服务端要一直替那个房间改写。

## D139 夺分胜利线按**开局那一刻的人数**冻结，不跟着掉线的人往下走

- **背景**：用户 2026-08-19 报「三人个人战掉线一个之后，右上角还写着目标 6，
  实际杀到 4 就结算了」。

- **★ 前提（§220 逐指令核对）**：客户端右上角那个「MAX N」是
  `[victory+0x198]`，**全镜像里只有 `DeathMatchVictoryCondition` 的构造函数
  `0x55be71` 写过它**，而那个对象只在 `GameContextQuest` 构造函数里造一次。
  ⇒ **一局开打之后，服务端发任何包都改不动客户端上那个数字。**
  「让它刷新成 4」这条路在原版协议里根本不存在。

- **决策**：让服务端跟客户端一样冻结。`RoomQuest` 新增 `start_seats`
  （开局那一刻在座的座位号快照，和已有的 `assign_controllers(seats)` 同一个
  时刻、同一份入参），夺分的胜利线改走 `RoomQuest.score_limit()` 按它算。
  日志里一并打出「胜利线 N 分（按开局 M 人算）」。

- **为什么不是反过来「让服务端保持 4、想办法把 4 显示出来」**：
  那要么改客户端内存（`bshook.dll` 写 `[victory+0x198]`），要么自造一个
  原版没有的包 —— 两条都违反「客户端是权威、服务端照抄它的口径」这条基线，

## D145 夺分记分照抄 `Character::Die`：自杀 / 杀队友**扣一分**，而不是「不记分」

§224 查明客户端在收到 `0x0406` 时对凶手做的是三选一：`OnKill(+1)` /
`OnSuicide(-1)` / 什么都不做，而服务端只实现了「+1 或什么都不做」。
差出来的那一分让「HUD 写着 5」和「服务端数到 6」变成同一局的两套账。

**选「扣分」而不是「让客户端别扣」**：那个数字是客户端每帧自己从
`[char+0x604]` 画出来的（§224 二），一发包都改不动它 —— 和 §220 那个
「MAX N」是同一类东西。**能改的只有服务端这一侧**，所以口径必须以客户端为准。

具体照抄到什么程度（每一条都有对应的反汇编依据，见 §224 一）：

| 客户端 | 服务端 `RoomQuest.record_kill` |
|---|---|
| 凶手座位越界 / 0xff（`0x4045f9` 返回 0） | 返回 `0`，一分不动 |
| 凶手座位**没人**（退房了） | 返回 `0` —— 靠 `teams` 里有没有这个座位判断 |
| 凶手 == 受害者 | `-1`，**下限 0** |
| 组队战 + 同队 | `-1`，**下限 0** |
| 其余 | `+1` |

- **返回值从 `bool` 改成 `int`（+1/-1/0）**，调用方据此把日志写成
  `杀敌数 +1 -> 3` / `杀敌数 -1（自杀 / 杀队友要扣分，§224）-> 2`。
  真出问题时，日志里能直接看出「服务端到底给谁记了什么」。
- **组队判定必须先问 `team_mode`。** 个人战里 `lobby.default_team` 给所有人
  发 0（那是为了不越界写客户端的两格队伍数组），不分模式地比队伍号
  会把**每一发击杀**都当成杀队友 —— 一整局谁都涨不了分。
  `test_a_free_for_all_kill_is_never_treated_as_a_team_kill` 钉死这条。
- **`teams=None` 保持老行为。** 协议试探 / 控制通道手搓包那条路没有房间，
  拿空字典当「谁都不在座」会把它整条废掉；那时只判自杀（不需要房间信息）。
- **不去改结算面板的分数来源。** 结算的 `分数` 本来就取 `quest.kills`，
  扣分之后它和 HUD 一起变小 —— 这正是我们要的：一局打完，
  屏幕上那个数、判胜负那个数、结算那个数，三处终于是同一个数。

## D146 时序噪音一律**按事件分流**，禁止「跳过头 N 发」这类次数阈值

**背景**：`bug调查/udp验证` 里，位置 UDP 旁路每次登录都会先打一行
「服务器没接受这条通道（认不出票据）」，紧接着 0.2 秒才转 ✓；
而票据真过期时（client3 停在登录界面）同一行连刷了 45 行（§225 第六节第 2 条）。

**第一版修法（已废弃）**：`NACK_LOG_AFTER = 2` —— 连着被拒到第 2 发才打。
用户当场否掉，并把它上升成一条通用规矩：

> 以后所有的修改，都不要用固定的次数或时间来驱动，
> 「固定跳过 xx 次」「固定跳过 xx ms」这种修法都不要有 ——
> 这种代码换一台机器就跑不通了。要等待到真正标志性的事件再触发相应处理。

**为什么这条规矩是对的**（不只是口味问题）：`2` 这个数字是拿这台机器上
「登录包 0.1~0.2 秒就被处理完」这个观测值当常量。慢机器、慢线路、
虚拟机上完全可能连着被拒 3 发以上 —— 那时该说的话又被吞了；
反过来，票据真的坏了时它还要白等 2 秒。**它掩盖竞态，不消除竞态。**

**定案**：找出「真正区分这两种情况的那个事实」，让**掌握事实的那一方明说**。

- 事实在**服务端**手里：它有票据表（`tickets.py`），分得清
  「这张票是我们签发的、只是还没有哪条游戏连接认领它」和
  「根本不认识这张票（重启过 / 过期 / 被顶号）」。
- 于是新增结果码 **`udpsync.ACK_NOT_LOGGED_IN = 3`**：
  查不到连接时，先问 `ticket_known(ticket)`，是真票就回它，否则才回
  `ACK_BAD_TICKET`。中继收到前者 = 「还没轮到，安静等」，收到后者 =
  「**第一发就报**」（不用等第二发，慢机器上那要多等 2 秒）。
- 判据用 `TicketStore.is_live()` 而**不是** `resolve()`：后者每次调用都续期，
  而这只是旁观者在问「这张票是不是真的」—— 旁观者能续期的话，
  一个只会重发 HELLO 的客户端就能把一张从没登录过的票养到永不过期。
- **日志去重也改成按状态翻转**（`refused_logged`，收到 `ACK_OK` 或换了一条
  游戏连接才重新允许说），不再按次数 —— 和「下行 已就绪 / 未就绪」同一个套路。

**兼容性**：线格式没变，版本号（`MAGIC` 末字节）不动。老中继把新码当成
「不是 OK」，退回今天的行为；新中继连老服务端时收到的仍是 `ACK_BAD_TICKET`，
最多回到「登录时多打一行」。两个方向都不会坏。

**代价**：`ACK_NOT_LOGGED_IN` 比 `ACK_BAD_TICKET` 多泄露一个 bit
（「这张票是真的」）。票据是 128 bit 随机数，猜中的概率不值得考虑；
而且同一个区分在游戏服 TCP 登录那边本来就是公开的（认不出票据回 `result=2`）。
这一条写进了注释，免得下一个会话把它当成疏忽「修」回去。

## D147 组队夺分的胜负**照抄原版**：比两队合成分，而不是「最高分玩家所在队获胜」

用户报的现象是「只有得分最高的人显示胜利，队友全败北」，他自己给的期望是
「得分最高的人的一整队都胜利」。逆完 `DeathMatchVictoryCondition` 虚表槽 14
（`0x55bfda`，§226）之后发现原版的口径是**比两队的合成分**，两者在
「低分队人多、总分反超」时会给出相反的结果。

**选原版。** 理由：

- 这个项目的一贯口径是「照抄客户端，口径才对得上」（§167 起的一整条线）。
  服务端判胜负是因为客户端那套跑不到，不是因为我们要另立规则；
- 「谁个人分最高」在组队里说不通：3 打 3 时一个人刷 9 分、队友 0 分，
  对面三个人各 4 分（共 12），按个人口径前者赢 —— 玩家会觉得莫名其妙；
- 用户拍板确认了这一条。

同时把**个人战**那一路也一并对齐原版（合成分 `(分数+1)*1000 - 死亡数`、
全员并列不判）。以前是「最高分 = 1，其余 -1；全场 0 分不判」——
在「全场同分且非 0」时和原版分叉（我们判全胜，原版不判）。

⚠ 一并明确：**结算的触发不改**。`0x55bf20` 比的是个人分对个人上限，
组队只是上限更低（`人数//2`），服务端 `pvp_score_limit()` 早就是这样了（D139）。

⚠ 右上角比分榜**不改**：夺分（`GameContextNewPvp`）的构造函数在建完胜负条件
之后就把队伍排行榜的开关 `[victory+0x181]` 置成了 1，纯客户端内存，
没有任何包能改（§226 第三节）。要它显示队伍分只能 patch `bshook`，
那是**改原版行为**，另案。

## D148 每局奖励：关卡固定奖励 + 少量分数加成，经验和金币各有各的系数

`settle_quest` 以前拿一个 `score` 当五份用（§227）。三个候选：

| 方案 | 取舍 |
|---|---|
| 纯按分数换算、三个系数不同 | 改动最小，但难度差异体现不出来 —— 简单关刷分和困难关通关收益一样 |
| 纯关卡固定奖励，与分数无关 | 最像「原版任务奖励」的味道，但打得好没有任何正反馈 |
| **关卡固定奖励 + 分数加成**（选中）| 主导项是「打的是哪一关、什么难度」，分数只做浮动；三个数天然互不相同 |

数值量纲对齐 `Promotion-chn.ini`（经验 20~120、金币 100~1000，§227），
**只借量纲不搬语义** —— 那张表是一次性晋级任务的奖励，不是每局结算。

- 闯关：基础经验 `20 + 10*(关卡id-1)`、基础金币 `100 + 50*(关卡id-1)`，
  难度系数 `{1:1.0, 2:1.6, 3:2.5}`，加成 `经验 += 分数/20`、`金币 += 分数/10`；
- **没通关也给** `QUEST_FAILED_RATIO = 0.3` 的基础部分。打了半天一无所获
  只会让人中途退，而且客户端在「未完成」时照样弹结算界面；
- 对战一起改（用户拍板）：`底薪 + 每杀 + 胜方加成`，输的一方**底薪照给**。
  只改闯关的话，玩家会发现对战几乎不涨经验，等于逼着大家去刷闯关。

「胜」直接读改动一算好的尾部数组（`tail[seat] == 1`），
这样 `0x0309` / `0x0411` / 入账三处的口径天然一致，不会自相矛盾。

## D149 「随机地图」开关服务端只做**转发**，不自己挑图；seed 每局重取

逆清楚之后（§228）发现挑图完全是客户端的活：全房间用 `0x0400` 里同一个 seed
调 `0x40b6e5`，结果必然一致；房主再回发一发 `0x0302` 把结果汇报上来。

所以**服务端不实现地图目录**（那要把 `map.ini` 的 OpenLocale / MinLevel /
MaxUser / AvailableMode 全部搬过来，还要和客户端那五处过滤口径逐一对齐，
V0.1/V0.2 已经在这上面栽过两次 —— §119 / §221）。服务端只做两件事：

1. 把 `0x0302` 的第 4 个字段存进 `Room.random_map`，在 `0x0303`
   和房间列表项里原样发回去；
2. **seed 每局重取一次**，取值 `[1, 2^31-2]`。

第 2 条是新增的行为变更，影响**所有对局**（以前恒 0，出生点之类的随机项
每局都一样）。选「一律重取」而不是「只在随机地图打开时重取」：

- seed 的语义本来就是「这一局的共享随机」，恒 0 是 V0.1 单机时代
  「只有一个客户端、可复现优先」的产物，不是原版行为；
- 加一个「随机图开着才随机」的条件分支，等于让两种房间走两条代码路径，
  以后再有别的东西吃这个 seed 就会踩到；
- 回退杠杆留着：`StartGameHandshake(seed_source=...)` 可注入常量。

取值下界是 1 不是 0：`-1` 在 `0x40b737` 是「改用线程本地随机源」的哨兵，
发出去房里每人各随各的图；0 只是「永远同一张」。

**开局之后房主那一发 `0x0302` 只记账、不回包**（§228 第四节）：它是汇报不是请求，
而此刻广播 `0x0303` 会把 Session 状态和局号重灌进正在加载关卡的客户端。
判据用新加的 `room_started()`（`PREPARING` 或 `IN_GAME`），
**不去放宽 `room_in_battle()`** —— 刷道具 / 判胜负那几处依赖它现在的严格语义。

## D150 经验曲线换成二次曲线（每级 `100 × 当前等级`），上限 60；老存档**按经验重算**

曲线形状三选一（都给了「按每局 ~120 经验估算要打多少局」的对照表），
用户选了二次曲线：升一级需要 `100 × 当前等级`，累计 `50·L·(L-1)`。
到 21 级（原版内容上限）21000 点 ≈ 175 局，到 60 级 177000 点 ≈ 1475 局。

上限 **60** 不是拍脑袋：`LevelMark.smf` 的帧数就是 60，客户端 `0x441fc0`
自己也钳到 1..60，超过会取到图外的像素（§229）。

**老存档迁移：按经验重算，该降就降**（用户拍板）。三个候选：

| 方案 | 结果 |
|---|---|
| **按经验重算**（选中）| 经验一分不动，旧 300 级 → 24 级、旧 60 级 → 11 级 |
| 保等级、补经验、钳到 60 | 谁都不掉级，但所有人的经验被凭空拉高，60 级的号直接封顶 |
| 只处理超 60 的 | 断层：旧 65 级 → 60，旧 55 级 → 11，两个差不多的号差 5 倍 |

配套的**探测与报告**（用户要求）：新增 `AccountStore.realign_levels()`，
在 `app.py` 启动时跑一次，把「谁从几级变成了几级」和「谁是被 60 级上限钳住的」
打进日志 **和 `eventlog`** —— `server.out` 每次启动被覆盖，而云服跑
`--no-control`，报告只能靠不被覆盖的那一份流水留存。

★ **幂等，所以不 bump `schema_version`**：跑完一次之后清单为空、不写盘，
每次启动都可以跑，以后有人手工丢一份旧 JSON 进来也会被自动纠正。
按状态翻转说话：没东西可改就一行都不打。

## D151 存档转移助手：**等级说了算**，但两个字段一致时经验一分不动

旧规则是「只能往上抬，想降级得连经验一起改小」。用户要求改成
「等级说了算，经验由等级重新计算，网页上写清楚改经验没用」。

规则：

```text
level 没出现在存档文件里            -> 以经验为准
level 读不出数 / <= 0               -> 以经验为准
level 和经验推出来的等级一致        -> ★ 原样保留经验
两者矛盾                            -> 经验 = experience_for_level(min(level, 60))
```

★ **第三条不是优化，是必须**：导出的存档里两个字段本来就自洽，无条件按等级
重算的话，一次「导出 → 原样导回」就会把玩家**本级内攒的那部分经验**抹掉
（5 级、总经验 1200 会被打回本级起点 1000）。存档转移是这个功能的主用途，
不能因为要照顾手改而把它弄坏。

★ **第一条也不是可选的**：`import_account` 是「从默认值起手再把存档里有的字段
盖上去」，而默认等级是 1 —— 少了这一条，一份只写了 `experience` 的手写存档
会被当成「他想要 1 级」，经验当场清零。所以 `experience_for_import()`
要拿到 `parse_save()` 解出来的**真正写了哪些字段**，不能只看合并后的 account。

⚠ **故意保留的口子**：玩家可以把 `level` 手改成 60 再导回，从而绕过 D150 的降级。
存档转移助手允许手改等级是 V0.2 就明写的设计
（「玩家会用记事本改存档，别为了格式洁癖把人挡在外面」）。要堵它是另一个决定，
本轮不堵 —— 几十人规模的复活服，玩家自己改自己的号不构成问题。

## D152 金币 = **固定值 + 本局捡到的金币**，不吃分数加成（修正 D148 的一半）

> ⚠ **D153 部分修正本决定**：`固定值 + 本局捡到`、去掉分数加成以及
> `RoomQuest.claim_item()` 入账点继续有效；下文「客户端完全不做金额算术」和
> 面额 10 / 50 已被完整反汇编推翻。保留旧文字作为当时方案的决策记录。

D148 定的是「关卡固定奖励 + 少量分数加成」，经验和金币各有各的系数。
用户随后指出：闯关里怪和 boss 会掉金币、对战里偶尔也掉，**那些金币要进结算**；
既然如此，金币就不该再吃一份分数加成 —— **金币 = 固定值 + 地上捡到的**。

改动：

| | 以前（D148）| 现在（D152）|
|---|---|---|
| 闯关经验 | 关卡基础 × 难度 + 分数/20 | **不变** |
| 闯关金币 | 关卡基础 × 难度 + 分数/10 | 关卡基础 × 难度 **+ 本局捡到的金币** |
| 对战经验 | 底薪 + 3×杀敌 + 胜方加成 | **不变** |
| 对战金币 | 底薪 + 10×杀敌 + 胜方加成 | 底薪 + 胜方加成 **+ 本局捡到的金币** |

**为什么对战的「每杀 10 金币」也一起砍掉**：杀敌数**就是**对战的分数
（服务端从 `0x0408` 的凶手字段数出来，`scores` 那一格），留着它就等于
「对战的金币仍然吃分数加成」，和闯关两套口径。砍掉之后两种玩法一致：
**技术好的回报走经验，捡得勤的回报走地上那些金币。**

「胜方加成」保留：它是**固定值**（赢了就是这个数），不随分数缩放，
和「分数加成」是两回事。输的一方底薪照给，理由同 D148。

**会话 43 当时采用、现已由 D153 撤回的面额**
`COIN_ITEM_VALUES = {10101: 10, 10102: 50}`：

- **比例 1:5** 来自类名（`CoinItem1` / `CoinItem5`），是硬证据（§230）；
- **绝对值按原版的「掉几枚」反推**（§231）：通关金币雨是
  `20 × 通关时存活人数` 枚**金币×1**，枚数跟人数线性 ⇒ **人均恒定 20 枚**。
  取面额 10 ⇒ **一局通关人均 200 金币**，对照关卡固定奖励
  （Quest1 简单 100 … Quest7 困难 1000）：低级关卡能翻一倍、高级关卡占两成。
  「捡得勤有回报」成立，又不会盖过「打的是哪一关」这个主导项。

⚠ 一开始定的是 1/5，那是**只有类名比例、没有枚数**时的保守取法；
把两条掉落路径逆出来（§231）之后枚数是确定的，才敢按「想让金币雨值多少钱」反推。

⚠ **实际到手会比 200 少**：撒币要 `(人数+5)` 秒，而客户端在通关**6 秒后**
就发 `0x040f` 弹结算（§167）——两人以上时尾巴那段来不及捡
（能捡的约 `20n × 6/(n+5)` 枚），而且还得真的走过去踩到。
**最终仍要拿实机日志里 `捡到 N` 那一格标定**（待验证表第 49 条）。

★ 顺带钉死的两条（§231）：**怪物和 boss 本身不掉金币**（那条路是留给关卡脚本的
lua 绑定，而资源树里一个脚本文件都没有）；**对战里那些金币来自可破坏场景物**
（`BreakableObj` 打碎时 6% 掉一枚金币×5）。

★ **入账点选在 `RoomQuest.claim_item()`**，不是 `grant_picked_item()`：
后者第一句就是「不是可入槽的道具就 return」，金币根本不进道具槽，会被挡掉。
仲裁那一步才是「这一件确定归这个座位」的唯一判定点，而且天然只算一次
（同一件东西第二个人来要时 `claim_item` 返回 False）。

⚠ 会话 43 当时写成「客户端捡金币时一分钱都不加」。§232 已纠正为：客户端会
维护本局累计面额，但不改持久账户金币；因此服务端仍须入账，却必须镜像 1 / 5。

## D153 金币面额以客户端完整算术为准：**1 / 5**；不把普通金币雨改成 5、10、15

用户实机看到通关金币雨依次弹 `1, 2, 3`，并记得老游戏可能是 `5, 10, 15`。
完整重读 `CoinItem1/5::vf_11c` 后，§230 / D152 的面额依据被推翻（§232）：

- `CoinItem1` 把常数 **1**、`CoinItem5` 把常数 **5** 传给 `0x493d96`；
- `0x493d96` 累加每座位的本局金币值，`0x493d76` 读回当前累计值给头顶浮字；
- 通关金币雨在 `0x4a5552` 硬编码请求 10101，故显示 1、2、3；
- 5、10、15 是连续拾取 10102 的结果，当前客户端里它来自可破坏物的 6% 掉落。

**决定**：

1. `COIN_ITEM_VALUES` 定为 `{10101: 1, 10102: 5}`，服务端持久化结果必须与
   客户端战局累计值完全一致；
2. 不 patch 客户端的 1 / 5 常数，也不把 boss 金币雨的 10101 偷换成 10102。
   用户的记忆是有对应代码来源的，但不能压过当前 3.11 二进制的硬证据；
3. D152 的奖励结构保持：金币仍是**玩法固定值 + 本局拾取面额**、不吃分数加成；
   只撤回 10 / 50 以及「绝对面额可按理想经济量反推」这两个决定；
4. 待验证表第 49 条不再承担面额标定，只验证真客户端的浮字、服务端日志
   `捡到 B`、结算金币和账户实际增量四者一致。

原因：掉落枚数只能说明一局有多少枚，不能覆盖物件生效函数里已经写死的绝对面额。
10 / 50 虽然在经济量级上看似合理，却会造成屏幕累计值和真实到账相差十倍；
复活工作的优先级应是忠实还原客户端既有规则，经济重平衡必须另立明确改版决定。

## D154 版本管理：握手立即数补丁 + JSON BUILD.ver + 门禁热重载（§233）

用户需求：每个包有自己的版本号；log 里能看出对方版本；服务器能拒绝太旧的
客户端；发版流程尽量轻。关键决定与被否掉的备选：

1. **版本号走握手 int32（补丁 `0x54d98f` 立即数），不动协议流。**
   备选「握手后追加一个版本包」被否：SimpleCipher 是有状态流密码，bshook
   要自己维护镜像状态才能加密注入帧，复杂且脆；补丁立即数零协议改动、
   中继透明、auth 通道（NMCO 加密，注入成本极高）完全不用碰。
   版本上报发生在游戏服握手（账号认证后 1 秒内），门禁放在那里就够。
2. **版本号不编译进 bshook.dll**（启动读包根 `BUILD.ver` 现算现补）。
   这样日常发版永不重编 hook，`hook\bin` 二进制与版本解耦；
   BUILD.ver 变了，下一次启动游戏就上报新值。
3. **`BUILD.ver` 用 JSON 且 `version` 永远是第一个键**，bshook 只扫第一个
   `"version"` 取值（C 里不做完整 JSON 解析）。原 BUILD.txt 的构建元数据
   （buildId / 共用代码哈希 / 成对使用警告）收进 JSON 的其余字段 ——
   **D079 的成对核对能力必须保留**，只是换了个文件名。
4. **门禁 fail-open + 热重载**：`server-ClientFilter.config` 认不出/缺文件
   = 不限制（+醒目警告），绝不让服务端起不来或把所有人挡死（server.config
   哲学）；按 mtime 缓存每条连接重读，改配置不用重启服务器。0 = 完全不限制
   （含不发送版本号的旧客户端）。
5. **拒绝分两道**：握手层回 `[非零结果码 + 提示 wstr]` 走客户端自带的
   升级弹框分支（逆向确认但未真机验证），登录层 `result=2` 兜底 ——
   提示文案最坏不显示，但旧客户端一定进不了大厅。
6. **初始值用户拍板 `0.2.7 / 0.2.7`**：下一个带版本上报的包按 0.2.7 重发，
   门禁同时生效 —— 现有已发出的（无版本上报的）旧包连新服务端都会被要求
   升级，包括现存 V0.2.7 存档包。
7. **编码约束进打包校验**：`311` 保留、编码下限 1000、段超限一律在打包
   第 0 步 throw —— 几十分钟的打包不能死在最后一步才发现版本号写错。

## D155 自动更新：替换 BsPatcherChn.exe 为自研更新器，GitHub 全量托管（§234）

## D159 停服务端的判定名单只认「本包 runtime 路径 + 树收养再核验」（§236）
2026-08-23 · 会话 50 · 真机踩坑修复

背景：用户真机触发自动更新，下载完成后误报「本机服务端进程结束不了」。
根因有两层（§236）：等待名单混进了全系统 python.exe；树收养又把
conhost.exe（保护进程，杀必失败）捡了进去。

1. **失败判定只看 `mine[]` 名单**：根 = 按 exe 完整路径匹配本包两份
   runtime 的 python；树收养的成员**必须再过一遍同样的路径核验**才进
   名单。杀（`procs_tree_kill`）可以全树开火，但「停不掉」的结论只允许
   从这份名单得出 —— 宁可放过（后面有 apply 的改名让位兜底），不可
   误报（用户看到的直接就是失败）。
2. 等不到就**补杀一轮再等一轮**（20×250ms × 2），仍活着才报失败 ——
   首轮 TerminateProcess 可能因权限/时序单发失败。
3. **不给 conhost 特判**（否掉「按名字排除 conhost.exe」）：PID 复用
   会让 ppid 指到任意系统进程，名单里按名字做减法永远列不全；按
   「路径 ∈ 本包 runtime」做加法一次就把 conhost / 错收养的全挡了。
4. e2e 固化回归：沙箱假服务端（本包路径）+ 诱饵 python（无关路径）并存，
   断言「该死的死、不该死的活、不误报」。

## D160 取消节拍 = 独立看门狗线程纯计时器；否掉「缩短接收超时」（§238）

   句柄，把阻塞中的 QueryDataAvailable/ReadData 撬开。收尾先 join
   看门狗再按 req_closed 分工关句柄，防双重 Close。
