## §1 ★ 这台机器的 Git Bash heredoc 把中文按 CP936 落盘，不是 UTF-8

**结论：写任何含中文的文件，一律用 Write / Edit 工具，不要用 Bash 的 `cat > x <<EOF`。**

实测：heredoc 写两行中文，落盘 104 字节，`decode('utf-8')` 全是替换字符；
按 CP936 解才对。项目里 `.md` / `.py` / `.json` 全是 **UTF-8 无 BOM**，
混进一个 CP936 文件后，服务端读它会 `UnicodeDecodeError`，而 git diff 里看不出异常。

`.md` 的行尾约定是 **LF 无 BOM**（拿 V0.2 的 `CLAUDE.md` 核对过：CRLF 0 处、LF 184 处、
无 BOM）。Write 工具默认就是 LF 无 BOM，正好一致。

## §4 ★ `UdpPacket` 校验和算法已经逆出来，且本版重新实测 25091/25091 全中

算法在 [tools/fakeclient.py:138](tools/fakeclient.py) 的 `udp_checksum()`，
出处是客户端 `0x5bbdc1`：

```python
acc = 0x17                       # 0x5bbdc8  push 0x17 / pop eax
for b in body:                   # 0x5bbdcb  lea esi,[buf+0xc]  ← 只覆盖 body
    signed = b - 256 if b >= 128 else b     # 0x5bbdd2  movsx dx, byte[esi]  ★ 带符号
    acc = (acc * 0x103 + signed) & 0xFFFF   # 0x5bbdd6  imul eax,eax,0x103 / add eax,edx
```

比对在 `0x4078f0`（`cmp word [esi+6], ax`），**只比低 16 位**。

本版验证：拿 `game_003_27799.dec.bin` 的全部 25091 发 `0x040e` 逐包重算，
**25091 命中、0 例外**。⇒ 服务端合成 bot 的 `UdpPacket` 时照抄这个函数即可，
**这一块没有未知风险**。

★ 不算它的后果：真客户端在收包入口 `0x4078ab`/`0x4078f0` 就把包丢掉，连队列都进不去
（V0.2 会话 34 实机踩过 —— 以前假客户端恒填 `0x1234`，互相不校验所以没暴露）。

## §5 ★ 坑 1：闯关模式里 bot 占座会让一部分怪从开局就不动

客户端 `GameContext::StartGame` **自己**算控制者表（谁模拟哪一批怪 / 刷怪点）：

```
for (i = 0; i < 6; i++)
    [ctx+0x294+i*4] = 在座座位[i % 在座人数]
```

服务端的镜像是 `RoomQuest.assign_controllers()`（`gameserver.py`），抄的就是它。
bot 座位分到的控制格**没有任何机器在模拟**，那一批怪从开局就是死的。

**对策**：开局进 stage 7 之后立刻调现成的 `Conn.handover_controller_slots()`
（走 `0x0414 gspChangeControllerSlot`），把 bot 的控制格交给真人。
这条路 V0.2 就为「加载途中有人掉线」写好了（V0.2 §180 / D103），直接复用。

## §6 ★ 坑 2：不改代码的话 bot 永远不会死

死亡链是：HP<=0 → `Character::OnHpZero` → `GameContext::vf_1c()` **恒返回 0**
（客户端**不自己判死**）→ 发 `0x0408` 上报 → **等服务端回 `0x0406` 才真的倒下**。

而 `Conn.on_report_hp_zero()` 从 V0.2 的 bug调查/8 起对玩家座位**只认本人上报**：

```python
if 0 <= seat < ROOM_SEAT_COUNT and reporter is not None and reporter != seat:
    return          # 「幽灵死亡上报」，丢弃
```

理由是「谁死没死只有本人的 HP 模拟说了算」—— 射手那台算「我炸死他了」、
受害者那台算「我躲过去了」的分歧是必然的，旧逻辑会让受害者的客户端对活着的自己
执行 `Die()`（用户报的「人还活着却进了观战模式」）。

**bot 没有本机 ⇒ 一发合法的 `0x0408` 都不会有 ⇒ 打不死。**

**对策**：bot 座位放宽这条限制，接受任何真人代报的第一发；去重仍由
`RoomQuest.record_death()` 的 `(句柄, 死亡次数)` + 时间窗负责。
为什么这样安全见 D3。

## §7 ★ 坑 3：只剩一个真人时服务端会把玩家间同步关掉

`Conn.sync_peer_relay()` / `after_someone_left()` 里有一条优化：
「掉回一个人就把玩家间同步关掉，省得客户端对着空房间每秒发 8 发」。

1 真人 + N bot 的房间会命中它 ⇒ 通道 A（`0x040e`/`0x040f`）被关 ⇒
**真人收不到 bot 的任何动作**。

**对策**：判据从「房里几条连接」改成「房里几个**会动的座位**（真人 + bot）」。

## §8 组队战：客户端要求两队人数相等才让开局

客户端 `0x468495` 数 1 队和 2 队的人数，不等就回错误码 3 →
「两组人数不相同。请调整人数。」

⇒ 组队房加 / 删 bot 时必须维持两队平衡。
`Room.default_team_for(seat)` 在 `TEAM_LAYOUT_TEAMS` 下就是「座位号奇偶交替 1/2」
（抄客户端 `0x468952` 的 `idiv 2 ; inc dl`），按它落座天然平衡；
`/team` 手动改完之后如果不平衡，要发系统提示警告房主。

★ **个人战的队伍号必须全是 0**：客户端的队伍记录数组只有两格，
队伍号 >= 3 会越界写进**别人的战绩**（`lobby.py` 开头 `TEAM_LAYOUT_*` 的注释里有
完整的越界地址推演，V0.2 bug调查/8_2 §212）。所以 `/team` 在个人战无效是**必须**的，
不是偷懒。

## §14 `bot.py` 和 `gameserver.py` 的导入方向：只能单向，且方向是反的

`bot.py` **模块级** `import gameserver`（`class BotConn(gameserver.Conn)` 建类
那一刻就要 `Conn`）；`gameserver.py` 反过来只在 `on_chat()` 里**函数内**
`import bot`。

两边都写成模块级 = 循环导入：`gameserver` 执行到顶部的 `import bot` 时
`Conn` 还没定义（它在 4325 行），`class BotConn(gameserver.Conn)` 当场
`AttributeError`。

代价：`bot.py` 缺失 / 语法坏掉时服务端**照样启动**，直到有人在房间里说第一句话
才炸，而且炸的是那个玩家的连接。所以 `server/app.py` 里补了一发显式
`import bot`（`# noqa: F401`），把它变回「启动就炸」。
打包脚本 `tools/build-common.ps1` 的必选文件清单也加了 `bot.py`。

## §15 `broadcast_system_chat()` **不含自己**，命令回执要另走一条

`Conn.broadcast_system_chat()` 走的是 `broadcast()`（默认排除自己，和大厅那套
广播口径一致）。房主敲完 `/bot` 之后，他自己**看不到**这行系统提示。

本版加了两个方法（`gameserver.py`）：

| 方法 | 发给谁 | 用在哪 |
|---|---|---|
| `send_system_chat(text)` | **只发自己** | 命令回执：报错、用法、`/help` 那张表 |
| `room_system_chat(text)` | 自己 + 房里其他人 | 通告：「bot 1 加入了房间。」 |
| `broadcast_seat_leave(seat)` | 自己 + 其他人，`0x0301` **action 1** | 删 bot（`broadcast_seat_slot` 只能发还在的座位） |

同一个道理适用于 `0x0301`：`announce_join()` 用的也是 `broadcast()`，
所以 bot 加入必须走 `broadcast_seat_slot()`（那个**含自己**）——
房主的客户端和别人一样，只认 action 0 那一发才建 3D 模型（`0x405e1c`）。

## §16 bot 换角色 / 换队 / 准备一律发 `0x0301` **action 3**，不发 action 4

## §18 ★★★ 地形的**形状不在 `.map` 里** —— 在地形 PNG 的 alpha 通道里

> ★★ **2026-08-25 会话 06 勘误：本节说的是 `TerrainObj` 那一层，仍然成立；
> 但「M4 要靠合成 PNG alpha」这个结论已经作废。** `.map` 的**尾部**烘着一份
> 现成的逐像素碰撞位图 `TerrainData`，客户端自己的碰撞查询读的就是它。
> **M4 直接搬那一份**，一张 PNG 都不用开。见 **§27**。

这条推翻了 M4 原来的设想（「从 `.map` 里提取碰撞段」）。**`.map` 里根本没有碰撞几何。**

一个 `TerrainObj` 的 blob 解完就这些（版本 >= 12，实测 `Camel00` 解完只剩 4 字节）：

```
版本 >= 17: i32, i32, i32(bool)
版本 >= 12: f32 x, f32 y          ★ 位置，经 0x511d25 设进去
            f32 scaleX, f32 scaleY   ★ 缩放，**负数 = 镜像翻转**（实测 -1.00）
            f32, f32, f32 rot        ★ 最后一个是弧度旋转（实测 -0.26）
            wstring（空）
            wstring                  ★★ **地形贴图路径**，如
                                     `Maps/Camel/Terrain/st06_a_14.png`
```

⇒ **一张图的实心区域 = 所有 `TerrainObj` 精灵按 (x, y, 缩放, 旋转) 贴出来之后，
alpha 不透明的那些像素的并集。**

**(x, y) 是精灵的中心，不是左上角。** 判据：按中心贴出来的 `Camel00` 是一座
结构完全正确的宫殿（柱子正好顶着平台、地面在最下方）；按左上角贴则整体错位。

**贴图都在** `Pack_decrypt/` 下，路径就是 blob 里那个字符串原样拼接
（`Pack_decrypt/Maps/Camel/Terrain/st06_a_14.png`）。全树共 566 张 `*/terrain/*.png`，
`Camel00` 的 19 块**一张不缺**。全是 **8 位 RGBA（颜色类型 6）非交错** PNG。

尺寸差别很大（12×140 的细柱 ~ 1146×210 的大地面 ~ 800×652 的建筑），
一张图只用十几到几十块拼成 —— 所以**逐像素合成完全跑得动**，不需要什么空间索引。

### ⇒ M4 的做法要改

原计划「逆 `.map` 的碰撞段」**不存在**。改成：

1. 解 `.map` -> `TerrainObj` 列表（贴图路径 + x/y + 缩放 + 旋转）；
2. 读每张 PNG 的 alpha -> 实心掩码，按变换贴进一张地图大小的位图；
3. 从位图里抽**站立面**（每一列实心区的上沿）和**弹道遮挡体**。

★ 开发机上 **Pillow 12.1.1 已装**，`tools/mapdata.py` 可以直接用它。
但**产物**（`server/bot_mapdata/`）必须是纯数据，
服务端运行时绝不能依赖 Pillow —— 便携运行时里没有它。

⚠ **还没查**：`HidingObj`(201) 是不是真的挡子弹（名字也可能只是「挡视线的前景」）；
`BreakableObj`(203) 打碎之后地形变不变；版本 < 12 的图（v7/8/9，21 张）
那 7 个 float 在**外层记录**里，字段顺序要单独核对一遍。

## §19 ★★ 客户端自己吃掉 `/team `，服务端**永远**收不到 —— 换队命令改叫 `/tm`

**结论**：带参数的 `/team 1` 一个字都到不了服务端。客户端在发 `0x0305` 之前，
先拿输入串和六个前缀挨个 `wcsnicmp`（**不分大小写**，且**必须连末尾那个空格
一起命中**），中了就把前缀切掉、只把余下的正文发出来，同时改掉聊天类型：

| 前缀（★ 含末尾空格）| 命中后 `0x0305` 的聊天类型 |
|---|---|
| `/team ` · `/팀 ` | **1**（队伍） |
| `/to ` · `/tell ` · `/say ` · `/귓 ` | **2**（悄悄话） |

**证据**：`0x54e727` 起五段 `push 长度; push 前缀; push 输入; call 0x5f6dad`，
命中分支各自 `mov dword ptr [ebp-0x14], 1/2` —— 那个数就是发出去的聊天类型
（韩文那两个前缀是运行时 `0x401979` 拼的，在 `0x69263c` / `0x69260c`）。
**实测**：玩家敲 `/team 1`，服务端收到的 `0x0305` 载荷是 `01 01 00 31 00`
= 类型 1 + 正文 `"1"`（`logs/server.out` 01:17:16 / 01:19:59 / 01:23:44 三次一致）。

★ **光杆 `/team`（不带空格）不命中**，会原样送到服务端 —— 所以它还能拿来回一行
「请改用 `/tm`」的提示（D12）。

⇒ 以后**起任何聊天命令名都要先躲开这六个前缀**。护栏放在两处：
`bot.CLIENT_RESERVED_PREFIXES` 这张表，加 `test_bot.py` 里
`test_no_command_name_collides_with_a_client_reserved_prefix` 一条单测。

## §20 房间聊天框一次只看得见 **4 行**，多发的会被顶出去

用户实测：`/h` 逐行发 8 行，屏幕上只留得住后 4 行。**到边自己折出来的行同样占额度**，
所以「行数」和「每行宽度」要一起卡。

⇒ `/h` 压到 **3 行**，每行 **≤ 50 个半角宽**（中文和全角标点算 2，ASCII 算 1）。
50 这个数是从实测反推的：旧版最长那行（`/char` 那条）54 宽，玩家数出来仍是 4 行，
说明框宽 ≥ 54，往回收一点当余量。
一条命令一行的排法不能要，改成**多条命令挤一行**、命令之间 `;` + 两个空格。
（聊天历史本身能存 80 条，`0x40605d` 里 `cmp eax, 0x50` 满了才丢最老的 ——
**存得下不等于看得见**，看得见的只有 4 行。）

## §22 控制格的接管者**只能是真人**（§5 的补充）

`Conn.handover_controller_slots()` 原来从「所有在座座位」里挑接管者。
房里有 bot 之后这条就错了：**控制格的意思是「这批怪由谁那台机器模拟」，

交接」一模一样（怪杵着不动），从日志上完全看不出区别。

⇒ 接管者池改成 `room.human_seats()`。**没有 bot 的房间行为零变化**
（那时它就是全部在座座位），所以 V0.2 那批交接用例一条都没红。

bot，镜像跟着它错才是对的。bot 那几格是**开局后立刻交接掉**的，不是一开始
就不分给它。两件事别搞混。

## §24 ★★★ 心跳 `0x4001` body 的完整布局（★ **§3 的位置字段是错的**）

| `+0x02` | **`+9..10`** | i16 | ★★ **位置 Y** ← `f32 [char+0x38]` |
| `+0x04` | `+11..12` | i16 | `[char+0x4c4] + [char+0x120]` |

## §25 ★★ 角色状态结构的**收侧**行为（把 §24 的三处口径改对了）

反序列化器 `0x5041e1` 逐字段读完了。**§24 的布局是对的，但三格的语义是错的**：

| body 偏移 | §24 说的 | 实际 |
|---|---|---|
| `+17..18` | 「速度」 | ★ **角度（度）** —— 发侧 `× 57.29578`（=180/π，`0x69379c`）、收侧 `× 0.0174533`（=π/180，`0x693778`）⇒ `[char+0x584]` 是**弧度**。语义 🤔 像炮口角度，0 是众数 |
| `+25..28` | 「`0x4295cb` 的两个返回值」 | 准星 —— ⚠ **本节说的「屏幕坐标 / 纯展示 / 填常数就行」是错的**，它是**世界坐标**（`0x4295cb` 取完光标还调了一发 `0x5cc42f` 做视口变换），而且**决定角色的身体朝向**。见 **§36** |

### ★ 收侧对**位置**做的事：默认是**插值**，不是硬置

```
if ([char+0x164] != 0)              -> 整个位置更新跳过
else if ([char+0x128] == 0 且 新包 bit2 == 1)  -> 硬置 [char+0x34/0x38]
else                                -> [char+0x34] = 旧×0.6 + 新×0.4
                                       [char+0x38] = 旧×0.6 + 新×0.4 + 0.5
```

常数 `0x6937c4`=0.6 / `0x6937c0`=0.4 / `0x69371c`=0.5。
真客户端的 bit2 绝大多数时候是 1 ⇒ **插值才是常态**，bot 照着来即可
（代价：换位置时滑过去而不是瞬移，0.6^5≈8%，约 5 发心跳收敛）。

### 位域 `+19..22` 的六个位（收发两侧完全对上）

`bit0..1` = `[char+0x2d0]`（2 位**有符号**，实测 -1/0/1）、`bit2` = `[char+0x128]`、
`bit3` = `[char+0x4bc]`、`bit4` = `[char+0x2dc]`、`bit5` = `[char+0x59c]`。

🤔 `bit0..1` 像**朝向**：拿紧跟着那一发 `rpFire` 的发射角对穿，
= 1 时发射角落右半边 2689 : 1294（68%）、= -1 时落左半边 2000 : 1054（65%）
—— **有倾向但没到证明**。反了的症状是「bot 背对着开枪」，纯外观。

### ★ `0x5f895c` 是**朝零截断**，不是四舍五入

它是 MSVC 的 `_ftol2`：`fistp`（就近偶数）之后用 `fsubp` 比差值符号、
`adc`/`sbb` 掰回靠近零的一侧 = C 的 `(int)`。Python 用 `int()` 才对，
`round()` 会差 1（`round(2.7)`=3，客户端给 2）。

### 头字段的两条实测（`packet_api.md` 已同步）

## §26 ★★ `BotConn.send()` **必须**跑 `note_epoch_from_frame()`

## §27 ★★★ `.map` 尾部烘着一份**逐像素碰撞位图** `TerrainData` —— M4 直接搬它

**结论**：19 类循环之后那一大段（1.5 KB ~ 42 KB）是 **`TerrainData`**
（RTTI 实锤：vtable `0x66c8c8` -> `.?AVTerrainData@@`）。它是**和地图同尺寸、
每像素 2 bit** 的碰撞网格，RLE 压缩。**客户端自己的碰撞查询读的就是它。**

⇒ §18 说的「M4 要合成地形 PNG 的 alpha」**作废**：不用处理镜像 / 弧度旋转 /
「alpha 多大才算实心」，也不用 Pillow —— 提取全程只要标准库。

### 线格式（`TerrainData::Load` = `0x47c4a4`）

```
i32   恒 1（174 张全是 1），像是子格式版本
i32   宽      ★ 和地图头的宽**严格相等**（174/174）
i32   高      ★ 同上
i32   clen
clen 字节     RLE：(count u8, value u8) 一对一对 memset（0x5f47e0）
              解出来正好 ((w*h+15)/16)*4 字节 = 每像素 2 bit
```

**位序**（采样器 `TerrainData::Get` = `0x472fe0`）：
`i = y*w + x`，`值 = (buf[i*2/8] >> (i*2 % 8)) & 3`。行优先、低位在前。

★★ **出界返回 2（实心），不是 0。** 照抄别改 —— 改成「出界算空」
bot 会觉得图外能走，一路走出地图。

### 格值：**有序**的「硬度」，不是枚举

`0x51a9e0` 对 3×3 邻域取 **max**，所以 0 < 1 < 2 < 3 是有大小关系的。

| 值 | 是什么 | 证据 |
|---|---|---|
| 0 | 空 | — |
| **1** | ★ **单向平台**（游戏里那种细白线，见 **§29**） | 1207 个出生点里 **77 个**正下方第一个非零格就是它；渲染出来是几像素粗的细线，上下都是空；用户实机确认「站得上去、按 ↓ 能穿下去」 |
| 2 | 实心 | 绝大多数；出界也返回它 |
| 3 | 原版 174 张里**一个都没有** | 只在运行时出现（`0x4fa844` 拿它当哨兵） |

✅ **值 1 的语义已经查清了，见 §29** —— 它是**单向平台**，而且**完全不挡子弹**。

### 尾部还有一张「贴图路径 -> 该精灵的掩码」表

`i32 n` + n 组 (wstring 路径, `TerrainData`)，路径基本都是 `*/Breakable/*.png`
—— 破坏物碎掉时拿来从主网格里抠格子用的。bot 用不上，**但必须读完**：
读不完就说明前面字段错位了，`tools/mapdata.py` 拿它当最后一道校验。

### 实测（174 张）

解压后字节数**精确**等于 `((w*h+15)/16)*4`、尺寸**精确**等于地图尺寸、
文件读到底只剩 0 字节（只有 `testipkn.map` 尾部多 1 字节填充）。
全部位图 zlib 之后合计 **1.0 MB**（原始 132 MB）。

## §29 ★★★ 碰撞位图的值 **1 是单向平台**，而且**完全不挡子弹**

**结论两条，M5 直接用**：

| | 值 0 | **值 1** | 值 2 / 3 | 出界 |
|---|---|---|---|---|
| 挡**人**（走路 / 下落） | 否 | **是**（站得上去） | 是 | 是 |
| 挡**子弹** | 否 | ★ **否** | 是 | 是 |

⇒ 服务端必须分成**两个**判据：`is_solid()`（挡人，`cell != 0`）和
`blocks_bullet()`（挡子弹，`cell >= 2`）。弹道判定用错会让 bot
「隔着一根白线打不到人」，而它明明打得到。

### 证据 1：用户实机确认（2026-08-26）

> 「原游戏里白线是可以站人的线，站在上面按下键可以穿过白线处掉到下面去。」

对照 M4 导出的可视化：值 1 渲染出来正是那些**悬在空中、上下都是空**的细带
（`Camel00` 里平台之间那几根、`Beginner` 里的斜细线）。⇒ 值 1 = 游戏里的白线。

### 证据 2：弹体的扫掠碰撞里，值 1 那条分支**永远走不到**

判定点 `0x47f976`（在 `0x47f738` 这个函数里）：

```
挡住 = (cell == 2) || (cell == 3) || (cell == 1 && al)
al   = this->vf_0x100()        // 0x47f94b，返回 0 就整条不成立
       && <逐步位图那一位>      // 0x47f966
       && dy >= 0              // 0x47f96a，dy < 0（向上飞）直接 al = 0
```

两条独立的锁：

1. **`0x47f738` 只属于弹体。** 全镜像反查这个函数指针：它出现在
   **19 个类**的虚表里（`BulletObj` / `BounceBullet` / `BoundBall` /
   `BowlingBullet` / `AppleGrenade` / `FlameBomb` / `FlamingBottle` /
   `MineBomb` / `PlasmaCannon` / `RasTurret` / `SeedBomb` / `SliceBullet` /
   `SoldierGrenade` / `SpiralKnife` / `ThrowerFlame` / `ThrowerWater` /
   `TimeBomb` / `TotemLauncher` / `TrainingGrenade`），**全部在同一个槽
   `+0x168`，没有任何角色类有它**。⇒ 这段就是子弹的地形碰撞。
2. **那 19 个类的 `vf_0x100` 全是默认实现 `0x46e188` = `xor al, al ; ret`**
   （`return false`，251 个类共用的那个默认桩）。⇒ `al` 恒 0
   ⇒ `cell == 1` 那条分支**一次都不会成立**。

⇒ **子弹穿过单向平台，任何方向都穿。**

### 顺带：`dy >= 0` 这一项说明单向平台的方向性是**在同一套判定里**做的

角色那条路径（`vf_0x100` 会返回真的那一侧）用的是同一个模式：
**向上运动（dy < 0）时值 1 不挡** —— 所以从下往上跳能穿过去。
「按 ↓ 掉下去」应该就是把 `vf_0x100` 或那个位图位关掉一帧，
**没有继续逆**（用户实机已经确认了行为，M5 用不到具体机制）。

★ 附带推翻一个顺手的猜测：值 1 **不是**「薄的可站立面」这种描述性的东西，
它是有明确游戏语义的**单向平台**。M4 会话里 §27 那张表按前者写的，已改。

## §31 ~~心跳位域的 bit2 = 「我此刻是静止的」~~ ★ **已被 §35 推翻，别按这条写**

|---|---|

重新回归了一遍：`dx / vx` 中位数 **4.111**（13253 组）、`dy / vy` 中位数 3.467。

## §32 ★★ bot 的帧率限流（0.125 秒）和驱动它的心跳**同频** ⇒ 拍频丢帧

**结论**：会话 05 那版 `_tick_bot` 有一句「距上一帧不足 `BOT_FRAME_INTERVAL_S`
(0.125 s) 就跳过」，而驱动它的真人心跳恰好也是 ~8 Hz（0.125 s）。两个同频的
东西撞在一起就是**拍频**：链路一抖，一半的帧落进阈值里被丢掉，bot 的实际帧率
掉到 4~6 Hz 而且忽快忽慢 —— 用户报的「平移的时候一卡一卡、跳起来在空中尤其
一顿一顿」。

**改法**（两条，都在 `bot.py`）：

1. **判据换成事件**：`Conn.sync_trail_seq`（每记一个位置点 +1）。bot 记住
   「上一帧消费到 `(座位, 第几个点)`」，号没变就不动 ⇒ 和它跟的那个真人
   **逐发对齐**，一发不多一发不少。阈值常量整个删掉（铁律 10）。
   ★ 顺带解决了另一件事：转发路上跑的不只有心跳（`rpFire` / `rpExplode` /
   `rpAiMsg` 加起来比心跳还多），老版本靠那个阈值把它们挡掉，现在靠「有没有
   新位置」这个事实挡。
2. **落脚点在两个采样点之间插值**，不吸附到采样点上（`trail_point`）。
   吸附时「往回 120」落在哪个采样点是**跳变**的：真人速度不匀时 bot 每帧走
   0 / 一步 / 两步。插值之后跟随距离是常数 ⇒ **bot 每帧走的距离恒等于真人
   这一帧走的距离**。用例 `test_the_bot_step_equals_the_humans_step_that_frame`
   拿旧实现跑会失败（实测轨迹 `[0,0,0,0,30,90,120,180,210,300,360,420]`，
   步长 0/30/60/90 乱跳）。
   ★ 起跳标记跟着改成取插值区间**靠老**的那一端 —— 那正是 bot 这一帧越过的
   采样点；靠新的那一端会让它提前一帧跳。

## §35 ★★★ 心跳位域的 **bit2 = 「我踩在地面上」**（★ 推翻 §31 的「静止位」）

**结论**：`bit2`（= `[char+0x128]`）是 **on-ground**，速度两格
（body `+11..14` = `[char+0x120]`/`[0x124]`）是**离地时的运动速度**。
**角色踩在地上走的时候，速度两格是 0。**

| 位置变了 | bit2 | 速度全 0 | 发数 | 是什么 |
|---|---|---|---|---|
| 否 | 1 | 是 | 28267 | 站着不动 |
| **是** | **1** | **是** | **20341** | ★ **在地上走** |
| 是 | 0 | 否 | 18070 | 腾空（跳 / 被击飞 / 下落） |
| 是 | 0 | 是 | 399 | 腾空的顶点附近 |
| 是 | **1** | 否 | **9** | 几乎不存在 |

（全 41 个语料文件、67186 发心跳，按「同一座位相邻两发」逐发比。）

### ★ §31 错在哪：拿相关当因果

§31 统计的是「速度全 0 ↔ bit2=1」，相关性 99%+，**没引入「位置变没变」
这第三个变量**。那条相关来自**共同原因**「在地上」——
而那 20341 发「位置在变、bit2=1、速度 0」的样本，在那个口径下和
「站着不动」混在同一格里，正好把反例藏掉了。

### 逐指令实锤（`0x507610`，角色每帧的运动更新）

```asm
0050761e  cmp  byte [edi+0x128], 0    ; 「不在地面」吗
00507625  jne  0x507660               ; ★ 在地面 -> 整段速度积分**跳过**
00507627  fld  [ebp-0x14]             ; dt
0050762d  fmul [edi+0x124]            ;   × vy
00507643  fmul [edi+0x120]            ;   × vx
0050764c  call 0x50e4e9(this, dx, dy, &landed)   ; 移动 + 地形碰撞
00507651  cmp  byte [ebp-0xd], 0
00507657  mov  byte [edi+0x128], 1    ; ★ 落地 -> 置「在地面」
...
00507685  fld  [edi+0x4c4] ; fadd [edi+0x120] ; fstp [edi+0x120]   ; 重力积分
```

⇒ **收方真的拿那两格速度每帧积分推进角色位置**，只在离地时推。

### 这就是用户 2026-08-26 第二轮实机报的「一跳一跳、像在抽搐」

会话 07 那版按位移反推速度、并把 bit2 清零 ⇒ bot 每一发都在说
「我在空中，速度 (9, 0)」⇒ 收方一边拿 9 往前推、心跳一边把它插值拉回来
（§25 的 0.6/0.4），一推一拉就是「走一下停一下、像不停点按左右键」。
走路动画同时也没有 —— 姿势是按「腾空」画的。

★ 顺带解释了会话 05 那版（bit2 **恒填 1** + 速度按位移填）为什么是
「平移、没有动画」：恒 1 时收方永远走插值分支，位置被平滑推着走，
而速度那两格因为 `[0x128]==1` **根本不被读**，等于一个「贴着地面滑行」的人。

### 改法（会话 08）

把 `(on_ground, vx, vy)` 和坐标一起记进真人的轨迹点
（`gameserver.SyncTrailPoint`），bot 回放到哪一段就**原样抄哪一段的**，
取插值区间**靠老**那一端（和起跳标记同口径）。
`botsync.character_state()` 在 `on_ground=True` 时**强制**把速度归零。

⇒ `VELOCITY_PER_STEP = 4.111` 那个回归常数**整个不需要了**，已删。

## §38 ★★ 客户端**每 1000 ms 才广播一发**加载进度 —— 1v1 时进度条几乎是空的

**结论**：`0x4005` 的发侧有一道 1 秒节流：

```asm
0046fe4b  lea  eax, [esi+0x820]      ; 上次发送时刻
0046fe53  add  ecx, 0x3e8            ; ★ + 1000 ms
0046fe59  cmp  ecx, ebx ; jge 不发
0046fe5f  call 0x4708ec              ; 当前进度 (0..1)
0046fe64  fmul [0x693740]            ; ×100
0046fe76  call 0x408202              ; 发 0x4005
0046fe8b  fstp [eax + 我的座位*4 + 0x238]   ; 自己那一格
```

（加载完之后还有一条 5 秒的重发路 `0x46feb7 add eax, 0x1388`，
条件是进度已经 == 1.0，然后才发 `0x0403`。）

**收侧**（`0x4079be` -> `0x407657`）有一道门禁：
`0x4045f9(this, 发送方座位)` = 「那个座位上有人吗」（`[this+座位*0x3c+0x40]`），
过了才写进 `[GameSession + 座位*4 + 0x238]`。bot 是有座位的，这道门不挡它。

⇒ **用户 2026-08-26 报的「1v1 很容易没有进度条、多人就有」是这么来的**：
bot 的进度完全照抄真人（§30），而 1v1 时房里只有一个真人在读图，
一两秒读完 ⇒ 统共报一两发 ⇒ bot 那一格几乎没画过东西。多人时要等最慢的
那个，报的发数多，条自然看得见。**和局号 / 跨代 / 转发路都无关。**

**改法**（会话 08，用户拍板，**D26**）：**别跟真人的进度了，一进加载界面
就报 100**。bot 没有客户端、没有一个字节的资源要读，它一开始就是加载完的
状态 —— 这和 D4（「广播出去那一刻就算它加载完」）本来就是同一句话。

挂点两处，都是**事件**：刚广播完 `0x0400`（开局）、刚广播完 `0x0417`（换图），
各调一次 `bot.report_bots_loaded()`。★ 100 那一发必须**排在**把大家推进
stage 7 的 `0x0402` 前面，否则客户端已经切场景了，那一格白画。

⇒ 「客户端 1 Hz 节流」这条硬事实**仍然成立且仍然要记着**（M5 以后若要按
真人进度做别的事会再撞上它），只是 bot 的进度条不再受它影响了。

## §39 ★★★ 心跳的六位掩码 = **方向键状态**，走路动画和收方的本地行走全靠它

## §40 ★★ 位域 **bit3 = 冲刺**（右键快跑）；★ **扬尘特效只有自己看得见**

**结论**：`bit3`（= `[char+0x4bc]`）就是「按住鼠标右键、耗能量、跑得快」
那个状态。收方拿它把**这个角色整帧的 `dt` 乘上 `FastRunRate`**：

00507594  fmul [ebp-0x14]                         ; ★★ dt × FastRunRate
005075a1  fstp [ebp-0x14]                         ;   ★ 整帧的 dt 就此变快
005075a9  fld [edi+0x2a4] ; fsub … ; fstp …       ; 扣能量

## §41 ★★ 蹲下是**单独一个事件包** `rpCrouch`(0x000b)，心跳里一个位都没有

**结论**：`[char+0x2b5]` = 蹲。它**不在心跳的任何一格里** —— 只有按下 / 松开
那两下各发一发 `0x000b rpCrouch`，**body 2 字节**：

```
+0  u8  座位号        ← 语料 394 发和 UdpPacket 头 +1 的发送方 100% 一致
+1  u8  1 = 蹲下 / 0 = 起立   ← 213 : 181，成对出现
```

组包点 `0x492f13`（两发 `0x5d5901` = 各写 1 字节），
收方 `0x492f5f` 取到角色后 `call 0x5026e1` 设 `[char+0x2b5]` 并播 `"Crouch-Start"`。

⇒ **它是「状态」不是「一次性动作」**，和 `rpJump` 正相反：收发两侧都得自己
记着，漏发一次那个角色的姿势就一直错到下一次翻转。

### `[char+0x2b5]` 在收方管的三件事（都在所有角色都跑的那个更新函数里）

| 地址 | 干什么 |
|---|---|
| `0x507250` | `fadd st(0), st(0)` —— **体力恢复 × 2**（`SpCharging` 默认 0.25/帧）|
| `0x507607` | `fmul [0x69387c]` = **`dt × 1/3`** —— 蹲着走只有 1/3 速度 |
| `0x507fdd` / `0x508061` / `0x508111` | 姿势换成 `Crouch-B` / `Crouch-F` / `Crouch` |

⇒ 用户 2026-08-26 说的「下蹲并加快体力恢复速度」逐条对上了。

★★ 顺带说明**为什么 bot 必须跟着蹲**，而不只是好看：那个 `× 1/3` 是收方
**自己**替这个角色算位移用的（§39 那条链）。真人蹲着走时坐标是 1/3 步长的，
bot 抄了坐标却说自己站着 ⇒ 收方按 3 倍速度替它走，心跳再一发发拽回来。
和 §40 的冲刺是同一个坑，方向相反。

### 改法（会话 11）

* `Conn.sync_crouch`（状态，`rpCrouch` 到达时翻转，换图 / 新一局清零）
  → 每个 `SyncTrailPoint` 带一格 `crouch`；
* bot 回放到某一段时，**只在和自己当前状态不一样**时补一发 `rpCrouch`
  （`BotConn.crouched`，按状态翻转去重，铁律 10）。
* `reset_battle_frame()` 里把 `crouched` 清掉 —— 客户端换图时角色重建、
  `[0x2b5]` 归零（`0x4ffc4a`），两边的记账必须一起清。
* ★ **死亡同理**：死亡处理器 `0x4ffbb7`（虚槽，`Character` / `MyCharacter`
  同一格；开头 `mov byte [ebx+0x2b4], 1` 就是「我死了」那个标志）里也有一句
  `mov byte [ebx+0x2b5], 0`。所以 bot「躺着等重生」那条早退路上也要清 ——
  不清的话真人一直蹲着时 bot 看不到翻转，**重生之后不会再蹲**。

## §42 ★★★ `rpFire` / `rpExplode` 的收侧全逆完了 —— D18 的两个问题都有答案

**一句话结论**：**命中判定和伤害数值都在「射手那一台」算**，别人的子弹在你屏幕上
只是飞。bot 没有「那一台」⇒ **只发 `rpFire` 的话，没有任何一台客户端会替它算爆炸，
子弹永远飞下去、一滴血都扣不掉**。⇒ **服务端必须自己当射手**（见 D28）。

### 1. 内层 opcode 的收侧在哪（★ 一次找齐）

分发器 = `GameContext` 虚函数 **`vft+0xc4`**（基类实现 `0x491821`）：

```asm
00491834  mov eax,[edi+0xc] ; movzx eax, word [eax+0x0a]  ; ★ 内层 opcode = 头 +0x0a
0049183b  dec eax ; cmp eax,0x1a ; ja 0x491d7f            ; 越界 -> 静默丢弃
00491847  jmp [eax*4 + 0x491d90]                          ; 跳转表 27 项，索引 = opcode−1
```

★ 表里 **`0x0a` / `0x0d` / `0x0e` / `0x0f` / `0x10` / `0x14` 六项直接指向出口**
—— 客户端**不认**这几个内层 opcode，发过去等于没发。

| 内层包 | 收侧 | 说明 |
|---|---|---|
| `0x0002 rpFire` | `vft+0xc8` = **`0x491f12`** | `ret 0x20`，8 个参数 |
| `0x0003 rpExplode` | `vft+0xd0` = **`0x492715`** | `ret 0x18`，6 个参数 |
| `0x000b rpCrouch` | `0x492f5f`（非虚） | §41 |

**`OnFire(who, slot, weaponId, Vec2* pos, float angle, float power, int count, int senderSeat)`**
—— ★ 最后那个 `senderSeat` **不是从 body 读的，是从 `UdpPacket` 头 `+1` 取的**
（`0x4918bf: mov ecx,[edi+0xc]; movsx ecx, byte [ecx+1]`），收方把它写进弹体 `+0x2f8`。

**`OnExplode(projHandle, targetHandle, damage, Vec2* pos, hitType, flags)`**
—— ★ body `+24` 那个 f32 在**分发器里**就被 `0x5f895c` **朝零截断成 int**
（`0x491930`）才传进来。**它就是伤害值**（§23 原来标的「像伤害或半径」🔍 → 现在 ✅）。

### 2. ★★★ 句柄编码 —— 「打不死人」的根就在这

`0x473e65` = `HandleToOwner(h)`：

```asm
00473e65  add eax, -0x186a0        ; h − 100000
00473e6a  jns 0x473e70 ; push 0x14 ; pop eax ; ret   ; ★ h < 100000 -> owner = 20
00473e70  cdq ; mov ecx,0x186a0 ; idiv ecx ; add eax,0xa   ; (h−100000)/100000 + 10
```

| 东西 | 值 | 出处 |
|---|---|---|
| **角色句柄** | `座位号 × 100000 + 100001` | `0x405f02: imul ecx,ecx,0x186a0; add ecx,0x186a1` |
| **owner 编码** | `10 + 座位号`；怪 / 中立 = `20` | 同上公式；和 `rpFire` body `+0` 是**同一套编码**（§23）|
| **弹体句柄** | 从 `mgr[0x14 + owner*4]` **取当前值再 `++`** | `0x484920` / `0x49172e`，两处一模一样 |
| **计数器初值** | **`座位号 × 100000 + 100002`** | `ProjectileMgr::Reset` `0x47346f`：`0x473509 lea eax,[ebx+0x3c]`（= `mgr+0x14+10*4`，owner 10 那一格）、`0x473520 mov [ebp-8],0x186a2`（100002）、每格 `+= 0x186a0`，共 30 格（owner 10..39）|
| **重置时机** | **`ForceReloadTerrain`**（宽字符串 `0x66bfb0`，`0x4749fd`）| 开局 / 换图各一次 —— 和服务端 `reset_sync_trails()` **完全同一个口径** |

⇒ ★★ **服务端能精确预测 bot 每一发子弹在所有客户端上被分配到的句柄**：
`座位号 × 100000 + 100002 + 本图已发弹数`。每发 `rpFire` 消耗 **`count` 个**句柄
（OnFire 里外层 `count / [weapon+0x84]` 轮 × 内层 `[weapon+0x84]` 个）。

★ `GameContext + 0x244` 是 **`owner(10..39) → 座位号`** 的映射表；
`[0x72e29c] + 0x1cc` 是 **「我的座位号」**（`UdpPacket` 构造的第 3 个参数就是它，
写进头 `+1`，`0x5bbe4d`）。

### 3. ★★★ 「谁开的枪，谁那台算命中」

弹体的爆炸处理 `0x47eb1f` 一开头就是这道守卫：

```asm
0047eb3c  call 0x50d294   ; IsMine(弹体)   : HandleToOwner(句柄)==20，或
                          ;   ctx->seatOf[owner] == 我的座位号 [0x72e29c]+0x1cc
0047eb47  call 0x50d2c6   ; IsNeutral(弹体): HandleToOwner(句柄)==20
0047eb4e  je  0x47ecfb    ; ★★ 两个都不成立 -> 整段跳过，SendExplode 根本不会被调用
0047ecc2  call 0x492557   ; SendExplode（全镜像**唯一**调用点）
```

⇒ **本机只替「自己的」和「中立/怪的」弹体做命中判定并广播 `rpExplode`。**
bot 的弹体 owner 映射到 bot 的座位号，**任何真人的 `mySeat` 都不等于它**
⇒ `IsMine` 对每一台都是假 ⇒ **没有一台机器会替 bot 的子弹算爆炸**。

伤害数值也一样是射手算好写进包的：`OnExplode` 把 `damage` 原样交给**目标角色**的
`vft+0xd0`（`Character::OnHit` = `0x4ff27d`，★ `Character` 和 `MyCharacter`
**共用同一个实现**）。收方不重算，照抄。

### 4. ★ `OnExplode` 查不到句柄 = 静默丢弃

```asm
00492724  push [ebp+8] ; mov ecx,[0x72e2d4] ; call 0x474225   ; 按句柄查弹体
00492750  je 0x492b53                                          ; ★ 查不到 -> 整个 return
00492841  push [ebp+0xc] ; call 0x474225                       ; 按句柄查目标
00492856  je 0x4929be                                          ; 查不到 -> 跳过直伤
```

⇒ 句柄错位**不报错、不重试**，就是「打不死人」（V0.2 §216/§217 的机制在这里）。

### 5. 顺带查实的几条（都会影响 bot 怎么开火）

| 事实 | 出处 |
|---|---|
| **`count ≥ 30` 的 `rpFire` 被整包丢弃** | `0x491f41: cmp [ebp+0x20],0x1e; jge 退出`（防作弊）|
| `[weapon+0x84] == 0` 时**不散布** | `0x491ffb..0x492010`；`0x637a7c` 实测 = **0.0** |
| 散布用的是**每 owner 一份的确定性 RNG** | `mgr+0x12c + (10+seat)*0xe8`（`0x492026`），种子在 Reset 里按索引播（`0x5d8b64(i)`）。⇒ **bot 用不散布的武器就完全不碰 RNG 同步** |
| 散布角步长 `0x693bbc` = **0.049087** ≈ π/64 | `0x491fd4` / `0x491fe6` |
| 弹体基类是 **`SplashDamage`**（vft `0x66eeac`），`vft+0x14c` 是**空实现** `ret 0x18` | 真正扣血走的是**目标**的 `vft+0xd0` |

🔍 **全部是逐指令 + 唯一 xref 得出的，没有实机跑过。** 实机第一次开火时要先验的就是
「句柄预测对不对」—— 对不上的表现是**子弹飞过去但不炸、不掉血**（第 4 条那个静默丢弃）。

## §44 ★ 「射程」这个东西**原版根本没有** —— 别再拿 `LockonRange` 当它

### 1. `LockonRange` 是**自动瞄准**的作用距离，而且只有 1 号轻武器有

| 槽位 | `LockonRange` | 说明 |
|---|---|---|

## §46 ★★★ `rpFire +22` 的 `count` = **`SpreadFrags`**，填 1 的话散射武器一颗都造不出来

00491fa5  idiv dword [ebp-0x24]   ; ★ 外层轮数 = count / SpreadFrags（整数除法）

## §47 ★★★ 弹道模型全解开了：`tick = 32 ms`、`Velocity` 是「单位 / tick」

§44 那个「`Velocity` 的尺度不明」的 ❓ **销掉了**。收侧一共只有三段代码：

| 在哪 | 干什么 |
|---|---|
| `0x4920a1` 三岔口 | 按 `PowerControl` 算**初速矢量** |
| `0x4921c9` | `[弹体+0x314] = 系数 × GravityFactor` |
| `0x47f603`（弹体 **`vft+0x158`**，所有弹体类共用）| 每 tick：`v.y += GetFrameDt() × [+0x314]`；`pos += v × [+0x274]` |

### 1. 初速（`0x4920a7` / `0x4920bf` / `0x492137`）

| `PowerControl` | 初速 | 备注 |
|---|---|---|
| 0 | `dir × power × Velocity` | `power` 语料恒 1.0；★ **不读 `MaxVelocity`** |
| 1 | `dir × power`，超 `MaxVelocity` 按比例压回 | ★ 压回时 `[ebp-0x30] = 比例²`，最后**乘进重力**（`0x4921ce`）|
| 2 | `dir × Velocity × ((power + 15) × 0.04)` | 常数 `0x69381c`=15.0、`0x693bb8`=0.04；`power=10` 时正好是 `Velocity` |

`vx = cos(angle) × s`、`vy = sin(angle) × s`，**+y 向下**（和心跳坐标一致）。

### 2. 每 tick 的递推

`GetFrameDt()`（`0x40a04f`）= `[ctx+0x344] × 1.2`，而 `[ctx+0x344]` 是恒 1.0 的
逻辑步长 ⇒ **`v.y += 1.2 × GravityFactor`**；`[弹体+0x274]` = 1.0 ⇒ **`pos += v`**。

### 3. tick 有多长 —— 语料回归出来的

把 41 个语料里的 `rpFire → rpExplode` 按**几何**配对（爆炸点必须落在开火射线上），
4529 对，算 `距离 / 时间 / Velocity`。★ 测出来的值只会**偏小**（dt 里含网络和
帧延迟），所以看**上包络**不看中位：

| ammo | `Velocity` | n | 中位 | p95 | 最大 |
|---|---|---|---|---|---|
| `1002030` | 25 | 964 | 30.95 | 32.03 | — |
| `1001030` | 20 | 35 | 30.73 | 31.33 | **31.34** |

⇒ **31.25 = 1000 / 32** ⇒ **tick = 32 ms**。`Velocity` = 5 / 6 / 20 / 25 / 100 /
130 / 150 / 180 八个值都对得上（怪的 `2003020` Vel=5 量到 154~158，`5×31.25=156.25`）。

⇒ ★ `Velocity = 100` 的枪是 **3125 单位/秒**，不是 100 —— §44 那个「弹速比人
走路还慢」的悖论就是这么来的。

### 4. 重力系数 —— 也是语料对上的

拿 `PowerControl=2` 的手雷（`v0` 公式已知）反解每 tick 加速度，除以 `GravityFactor`：

```text
1000500 → 1.1972   1001020 → 1.1546   1000020 → 1.1967   1101020 → 1.2000
```

⇒ **`1.2`**，和 `0x40a04f` 里那个 `fmul [0x693784]`（= 1.2）一字不差。

### 5. ⇒ 抛物线武器可以用了

服务端解发射角就是课本上那条抛射方程（离散递推比连续模型多掉 `a·n/2`，
迭代两三轮就收敛），实现在 `server/ballistics.py`，
单测 `test_ballistics.py` 拿**逐 tick 递推**和闭式解对拍。
判别式 < 0 = **超出最大射程**，`solve()` 老老实实返回 `None`。

## §49 ★ `Acceleration`：7 把武器**边飞边加速**，不建模的话飞行时间差 10 倍

`BulletObj` 的 **`vft+0x24`**（`0x47de6a`）每 tick 跑一次：

```asm
0047de87  call 0x56976d          ; dir = normalize(v)
0047de92  fld [eax+0x2c]         ; ★ Acceleration（eax = [弹体+0x308] = 武器记录）
0047dea4  v.x += dir.x × Accel ; 0047dead  v.y += dir.y × Accel
0047ded6  fcomp [eax+0x28]       ; |v| 和 MaxVelocity 比
0047df07  fdivr [eax+0x28]       ; 超了就 v *= MaxVelocity / |v|
```

⇒ **`v += 单位方向 × Acceleration`，封顶 `MaxVelocity`。**

有这一格的 7 把武器（`1100030` / `1103030` / `1102020` / `1104020` / `1105020` /
`1106030` / `1110030`）**全是 `GravityFactor = 0` 的直射弹**，所以加速只改
「飞多久」，不改方向。

★ 不建模的后果很难看：`ch100-03` 初速才 **3/tick**，直接按匀速算飞 600 单位要
**6.4 秒**（实际 0.7 秒）；`ch104-02` 初速 1、上限 20，按匀速算要 **19.2 秒**。
延后爆炸等这么久 = 实机上就是「bot 打了半天不掉血」。

★ **`HomingRange` 那 4 把（追踪弹）服务端不建模** —— 弹道会拐弯，
算出来的飞行时间是个近似。伤害不受影响（爆炸点和目标句柄都是我们写死的）。

★ 顺带：弹体每 tick 还有一次 `v *= (1 − vft+0xa0())`，但基类那一格
（`0x4caaf3`）**恒返回 0.0** ⇒ 没有空气阻力，模型是精确的。

## §50 ~~事件包要等**下一发心跳**才被执行~~ ★★ **已被 §52 推翻，别按这条写**

> 🔴 **这一节整条是错的**（会话 16 用逐指令 + 语料 + 实机日志三面推翻）。
> 事件包**每帧都 flush**，包一入队就把队列上界抬起来了，心跳只是丢包时的
> 兜底上界；「看不见子弹」的真因是 **bot 贴到目标身上（20 个单位）**，
> 子弹没有可见的行程。**看 §52**。本节只留作「当初是怎么想错的」的记录，
> 末尾那段「⚠ 原版也一样」尤其要当反面教材看 —— 它和用户「真人玩没这个
> 问题」的实机结论直接打架，那时候就该推翻结论而不是圆场。

**一句话结论**：内层 opcode `< 0x4000` 的事件包进收方的 `PktQueue` 之后
**不会立刻执行**，要等一发带更大 N 的心跳来 `FlushTo(N)`。
所以 `rpFire` 和 `rpExplode` 只要挤在**同一个 N** 里，收方就会在**同一瞬间**
造出弹体又把它炸掉 —— 别人屏幕上是「有开枪动画、看不见子弹、凭空掉血」。

用户 2026-08-26 报的就是它：「所有武器现在看不见弹体，bot 有开枪动画，
但是看不见子弹，过一会儿我就凭空被打中了。」

### 为什么会挤在同一个 N 里

bot 一帧的发包顺序是「**先冲在飞的子弹 → 心跳 → 开火**」，而一帧 ≈ 125 ms
（跟着真人的心跳走，§32）。于是：

```text
帧 k     : 心跳(N=e) ; rpFire(序号 e)
帧 k+1   : rpExplode(序号 e+1) ; 心跳(N=e+2)      ← 飞行时间 < 125 ms 时
收方     : 收到 N=e+2 -> FlushTo(e+2) -> 一口气执行 rpFire + rpExplode
```

★★ **近距离必然中招**：bot 跟在真人身后 120 个单位（`BOT_FOLLOW_DISTANCE`，
D16），基础枪 `Velocity=100` = 3125 单位/秒 ⇒ 飞过去只要 **38 ms**，
远小于一发心跳。所以「打得中但看不见子弹」是**每一发**都会发生。

### 改法：等「那一发 `rpFire` 被心跳报出去过」这个事件

`BotSyncStream.announced` = 最近一发心跳报出去的 N。
`bot._explosion_ready()` 的判据从「飞到了」变成**两条**：

```python
shot.due <= now  and  sync.announced > shot.fire_seq
```

第二条一成立，爆炸就一定排在**下一个** N 里 ⇒ 收方那边弹体至少活一整个
心跳周期（~125 ms），肉眼看得见。★ 这是**事件**判据，不是「等 XX 毫秒」
（铁律 10）。

### ★ 顺带一条通用结论

**任何两发需要在画面上分开的事件包，中间必须夹一发心跳。**
以后再做「起跳 → 落地」「换弹 → 开火」这类成对动作时照这条来，
别指望发包的时间差能传过去 —— 传过去的只有 N。

⚠ 原版也一样：真人近距离射击时，`rpFire → rpExplode` 的间隔也小于一发心跳，
远端同样看不见子弹。语料里真人的间隔中位数是 **127 ms**（≈ 恰好一发心跳），
因为他们的交战距离通常在 380~600 单位。所以 bot 现在这条「至少隔一发心跳」
的规矩，效果上就是**贴脸时也按原版的常见交战距离那样显示**。

## §52 ★★★ 收方的事件包**每帧都 flush**，根本不等心跳 —— **§50 是错的**

**一句话结论**：内层 opcode `< 0x4000` 的事件包进 `PktQueue` 之后，
**下一帧就会被执行**。心跳里的 N **不是**执行的开关，它只是**丢包时的兜底
上界**。⇒ 会话 15 的 §50 / D37（「爆炸要多等一发心跳才看得见弹体」）
**整条作废**，代码已撤。

### 三段硬证据（逐指令）

**1. 队列上界在「入队」那一刻就被抬起来了**

```asm
00407c01  ; 事件包入口：queue = ctx + 0x2e4 + 发送方座位*0x24，seq = 头 +8
00407c17  call 0x54bb8c                     ; PktQueue::Insert(queue, seq)
0054bb9d    cmp edi,[esi+8] ; jl 丢弃        ; seq < base -> 过时，丢
0054bba4    mov eax,edi ; call 0x54bb66      ; ★★ 拿**这一发自己的 seq** 抬上界
0054bb66  ; Reserve(seq): if (seq >= [esi+0xc]) { 扩容; [esi+0xc] = seq+1; }
```

心跳走的是另一条路（`0x407b94`），它做的是**同一件事**：
`0x407ba7 dec eax`（N−1）→ 同一个 `0x54bb66` → 上界 = N。
⇒ 两条路都只是「把上界抬到我知道的最大序号」，**谁先到谁抬**。

**2. flush 在每帧的网络 tick 里，无条件**

```asm
004057cf  ; GameSession::Tick —— 调用方是 stage 的 Update（0x4673d7 / 0x47889c）
00405810    call 0x407c1d                   ; ★ 先 flush 六条收包队列
00405834    cmp [edi+0x3bc],0 ; call 0x409ff3
00405848    cmp eax,0x64 ; jl 跳过          ; ★ 再看「离上一发心跳够 100 ms 没」

```

flush 循环（`0x407c1d`）对每个座位：`cur = base; while (cur < 上界) 取包执行`，
**取不到就停下来发 `0x4002` 讨重传**（`0x407ddb`~`0x407e29`）。

⇒ **原版客户端自己的心跳是固定 100 ms 一发**，而 flush 是每帧（~16 ms）。
心跳只在「事件包丢了」时才起作用：它把上界抬过空洞，让收方发现缺号。

**3. 语料佐证**：真人 `rpFire` → `rpExplode` 之间夹 0 发心跳的占 1.7%

—— 而用户明说「和真人玩的时候没有看不到子弹的问题」。

## §57 ★★★ 收侧弹体的**整条路**读完了：**一处按 owner / 座位分流的分支都没有**

会话 17 把 `rpFire` 到「画在屏幕上」之间的每一步逐指令读了一遍。**结论是否定的**：
从收包到渲染，没有任何一处会因为「这颗子弹是谁发的」而少做事。
⇒ 「找一个 bot 专属的 if」这条路**到头了**，别再重走。

### 1. 整条链的地址表（下次直接用，不要重逆）

| 步 | 地址 | 干什么 | 有没有 owner 分支 |
|---|---|---|---|
| 分发 | `0x49186c` | 读 8 个字段 → `call [vft+0xc8]` | 无 |
| `OnFire` | `0x491f12` | 见下面第 2 条 | **只有一处，且不碰弹体** |
| 工厂 | `call [武器定义+0x108]`（`0x4921a5`）| `Create(句柄, &pos)` | 无 |
| `Init` | `0x47d6a1`（`vft+0x154`）| 建模型 / 特效 / 拖尾 / **弹道线** | 无（守卫只有 `[+0xd0] != -1` 和几个武器定义字段是否为空串）|
| 登记 | `0x473e7c`（`ProjectileMgr::Add`）| 插 `mgr+0xb4` 的 map（key = 句柄）+ 按 `vft+0x48` 插 `mgr+0xc8` | 无 |
| **每帧 tick** | `0x490609`~`0x490665` | 遍历 `mgr+0xb4`：`[+0x54]==2` → 置 3；`vft+4` 真 → `vft+0x24` | 无 |
| 推进 | `0x47de6a`（`vft+0x24`）→ `0x480378` → `0x47e0f7`（`vft+0x11c`）| 加速度 / 位置 / 碰撞 | 无 |
| 渲染插值 | `0x4908f0` | 遍历 map，`[+0x2c]/[+0x30] = lerp(上一帧, 这一帧)` | 无 |
| 清死弹体 | `0x4741c5` | `[+0x54]==4` 且 `0x5cd641()` → 摘掉 | 无 |

★ 顺带答了 §56 留的那个问题：**弹体是被 `0x490609` 那个循环每帧推进的**
（`vft+0x24`，不是 `vft+0x158`）。`0x47f603` 确实没有调用点，那是条死路。

★ `vft+4`（`0x50d3de`）= `!IsDead(this)` **且** `[this+0x16c]` 那个计时器不在跑。
`IsDead` = `[this+0x54] ∈ {3,4}`（`0x417c72`）。两个判据都和 owner 无关。

### 2. `OnFire` 里**唯一**一处按座位分流的地方，和弹体无关

```asm
00491f62  call 0x47d48a          ; 10 <= who < 20 ?
00491f6b  mov esi,[edi+eax*4+0x244]   ; ctx->seatOf[owner]
00491f7b  call 0x404ff6               ; -> [[0x72e29c]+0x1d0+seat*4] = 角色对象
...                                    ; ★ 弹体创建 / Init / Add 全在这之后，不看 esi
0049237e  test esi,esi ; je 0x4923ab
00492382  mov ebx,[ebx+4] ; test/cmp 3 ; jne 0x4923ab   ; 武器 Type ∈ {0,3}
004923a5  call [角色vft+0x13c]        ; = 0x501ba8：播 "Attack%02d" + EffFire
```

⇒ **`Character::vft+0x13c` 就是「开枪动作 + 枪口火焰」**（字符串 `0x6858e0`
= `Attack%02d`，遍历 `[武器定义+0x124]` = `EffFire`）。它排在**所有弹体
创建之后**。用户说「看得见 bot 的开枪动作和枪口火焰」⇒ **OnFire 一路跑到底、
esi 非空、弹体全都造出来了**。这条交叉验证比原来更硬。

### 3. 「弹体确实存在」这条也加固了

`OnExplode`（`0x492715`）在动手之前要过两关，**任何一关不过就整个 return**：

```asm
00492730  call 0x474225           ; 按弹体句柄查 mgr+0xb4 的 map
00492744  call 0x5f5192           ; __RTDynamicCast(弹体, ..., 0x6dff90)
00492750  je 0x492b53             ; ★ 0x492b53 = mov ecx,[ebp-0xc] … ret 0x18（函数尾，已核实）
```

⇒ **掉血 + 爆炸动画 = 弹体在 map 里、而且动态类型也对**。§53 那条「🟡 半排除」
可以升成 ✅。

### 4. ⇒ 剩下的只可能是「弹体对象上某一格的值不对」

代码路径完全一样，那差别只能在**数据**上。而数据在运行时才有 ——
**静态逆向到此为止**，改用客户端 hook 把那一格直接抓出来（见 §58 / D39）。

## §58 ★ 客户端弹体诊断 hook（`hook/bshook.c`，M3b 收口后删）

装三个 inline hook，`BSHOOK_PROJ_DIAG=0` 可关，默认开：

| tag | 挂在 | 打什么 |
|---|---|---|
| `FIRE>` | `0x491f12` `OnFire` | 收方**解析出来**的 8 个参数 + `who` 换算出的座位和角色对象指针 |
| `PROJ+` | `0x473e7c` `Add` | 每颗弹体登记那一刻的**全字段快照**：句柄 / owner / 位置 / 速度 / 状态 / 重力 / **模型(+0xe8) · 特效(+0xe4) · 弹道线(+0x30c) · 拖尾(+0x310)** |
| `PROJ.` | `0x47de6a` 每帧 tick | 按**整数位置翻转**去重的轨迹点（不动的弹体只出现一行）|

**为什么这三个够**：同一局里「自己开的枪 / 真人开的枪 / bot 开的枪」走的是
同一批函数，三份 `PROJ+` 快照并排一比，差在哪一格一目了然；
`PROJ.` 回答「动没动、往哪飞」；`FIRE>` 回答「参数被读成了什么」。

★ 弹体字段偏移的出处（都在 `Init` / `OnFire` 里写死）：
`+0x2c/+0x30` 渲染位（`0x5107ce`）、`+0x34/+0x38` 逻辑位、`+0x54` 状态、
`+0xd0` 句柄、`+0xe4/+0xe8` 特效/模型（`0x47d9cc` / `0x47d8f4`）、
`+0x120/+0x124` 速度（`0x47d7eb`）、`+0x15c` 槽（`0x47d7d3`）、
`+0x2f8` 发方座位（`0x4921e6`）、`+0x304` 武器 id、`+0x308` 武器定义、
`+0x30c` 弹道线（`0x47dbc3`）、`+0x310` 拖尾（`0x47da6d`）、
`+0x314` 重力（`0x4921d1`）、`+0x32c` 碰撞型（`0x4921dd`）。

★ 三个 detour 都是 `__declspec(naked)`，栈偏移已经用 `dumpbin /disasm`
核过（`pushad`+`pushfd` 之后第 1 个栈参在 `[esp+0x28]`；`OnFire` 那 8 个
连续 `push [esp+0x44]` 的偏移**故意都一样** —— 每压一次 esp 减 4、
要取的槽位也往上挪 4）。

## §61 ★★★ 真人**自己的**子弹也是从网络回来的 —— 和 bot 走的是同一条路

会话 18 把会话 17 留下的 hook 日志（`logs/bshook_20260827_*.log`）重新读了一遍，
挖出**同一把枪**的真人 / bot 并排样本。结论把「本地路径 vs 网络路径」这一整族
假设整条砍掉了。

### 1. ★★★ 客户端**没有本地预测**：自己开的枪也要等服务端把包发回来

`logs/bshook_20260827_103649_pid28528.log` 等每一份日志里，真人自己开的每一发
都在 `FIRE>` 里出现，而且 **`发方 = 我的座位`**：

```text
FIRE>  who 10(座位 0, 角色 3B891120) 发方 0 槽 1 武器 1002010 …  ← 我的座位 0
```

`发方` 取自 `UdpPacket` 头 `+1`（§42），所以这一发是**从网络收回来的**。
⇒ 客户端把 `rpFire` 发给服务端，服务端广播（含发送者自己），
收方 `OnFire` 才造弹体。

**佐证**：真人连打 13 发火箭，句柄是 `100005 / 100007 / 100009 …`，
**步长恒 2**（= 溅射武器的 `handle_step`）。要是本地还预测造一颗，
步长就该是 4。⇒ **一发一颗，没有本地那一份。**

⇒ ⛔ 「本地造的看得见、网络造的看不见」这条路**堵死了** ——
两边是**同一个函数、同一种包**。
（`0x484920` 那第二处句柄自增不是本地预测，别再往那儿猜。）

### 2. ★★★ 同一把枪的并排快照：弹体对象**逐格一致**

`logs/bshook_20260827_112829_pid29248.log`，同一局、相隔 1.15 秒、

### 3. ⛔ ~~直射武器的弹体本来就只活 1 帧~~ —— **已被 §62 推翻，别按这条走**

**那是取样取偏了**：那一局真人和 bot 贴在一起，真人的子弹**打中了对方**才

⇒ **「只被推进 1 帧」正是异常本身**，见 **§62**。

★ 火箭（`1001030`，初速 20）不一样：真人的飞了 **17~18 帧**（每帧 ~32 ms，

以及客户端本地的追踪 / 碰撞把它打掉 —— **另一笔账**，别和「看不见」混。

### 4. ★ 弹道线是 `EffectMngr` 的**第 5 类特效**，创建处也没有 owner 分流

`Init`（`0x47d6a1`）里：

```asm
0047db6e  push 5 ; lea eax,[ebp+0x14] ; push eax ; push [0x6e9aa0] ; call 0x47ff31
0047ff62  lea eax,[mgr + kind*4 + 0x44] ; call 0x476f8d   ; ★ 插进第 kind 条链
```

`0x47ff31` 从头到尾没有一处按 owner / 座位分流。⇒ **线肯定进了绘制表。**

### 5. ★ 唯一找到的**一格不一样**：线对象 `+0x20`

`logs/bshook_20260827_115337_pid28540.log` 的对象 dump（线对象 vft `0x6602E8`）：

```text
真人 1002010  线@3CD1F560: 006602E8 00000002 00000000 <弹体> <ptr> 00000281 <ptr> 006E0000 00000001 0002849A
bot  1001010  线@3CD1F560: 006602E8 00000002 00000000 <弹体> <ptr> 00000288 <ptr> 006E0000 00000064 0002857E
                                                                                    ↑+0x20  1 vs 100
```

顺便认出来两格：`+0x14` 是**帧计数**（差 7 帧 ↔ 差 226 ms ↔ 32 ms/帧）、
`+0x24` 是**毫秒时间戳**。

⚠ **这不是干净的 A/B** —— 两发是**不同的枪**（`1002010` vs `1001010`）。
★ 会话 18 后来在反汇编里认出来了：`+0x20` 是**拖尾每个点存活多少毫秒**
（`0x416e9e` / `0x416ecc` / `0x416f31` 三处都拿它当时间间隔用），
逐武器的参数，**和这个 bug 无关**，这条线索到此为止。`0x64`（=100）在 `OnFire` 里也出现过一次
（`0x492351 push 0x64`，紧接着 `Add` 之后按 `[武器定义+0xf0]` 建东西），
但那一段两边都走。**要判它，必须拿同一把枪的真人 / bot dump 并排比。**

### 6. ★ 工具口径：`bslog` 一行约 **2 ms** —— 日志时间戳不能当帧率用

`PROJ.` 的时间戳看着像「3 帧挤在 6 ms 里」，其实是**写日志本身**的开销
（同一发的 12 行 ≈ 24 ms）。⇒ 用 hook 日志推「客户端一帧多久」是错的，
只能用**帧数**和**位置**。

| `FIRE>` 后面多一行 **★射手角色位置(+34,38) + 发射点−角色** | 弹体是不是从「和角色对不上的地方」飞出去的（收方的角色位置是它自己插值 / 积分出来的，§5.6；服务端的发射点是另算的）|
| `PROJ+` 的 `绑定(+8c)`，以及三个特效对象 dump 加长到 **20 dword** | 线 / 特效对象**的内容**到底差在哪（尤其上面那个 `+0x20`）|

## §62 ★★★★★ 结案：**bot 的弹体一出生就撞掉了** —— 枪口位置填错

会话 18 实机取证（自己跑的一局，真人和 bot 用同一个角色、同一把枪 `1000010`）。

### 1. 现象：bot 的弹体**被推进 1 帧，位置一步没动**

`PROJ.` 逐帧日志，同一局里并排：

| | 被 `vft+0x24` 推进的帧数 | 走过的距离 |
|---|---|---|
| **真人自己的子弹** | **5~11 帧**（每帧 ~32 ms，均匀）| 每帧 129 个单位，一路飞出屏幕 |
| **bot 的子弹**（几十发，无一例外）| **1 帧** | **0** —— 每一行都停在发射点 `(760.00, 215.00)` |

★ 开 `/noboom`（一发 `rpExplode` 都不发）**照样只有 1 帧** ⇒
**不是爆炸包杀掉的**，是弹体自己在第一次推进时就撞掉了。

### 2. 根因：枪口放在**角色脚下 20 个单位**，落在碰撞盒里

hook 把「`rpFire` 的发射点」和「射手角色**当时**的坐标（`[char+0x34]/[0x38]`）」
并排打出来（会话 18 新加的探针）：

| 射手 | 发射点 − 角色 |
|---|---|
| **真人**（客户端自己算的）| **(+43, −57)** —— 枪管在身前 43、肩高 57 |
| **bot**（服务端算的）| **(−3.7, −21)** —— 身后 3.7、膝盖高 21 |

服务端那两个数来自 `BOT_AIM_HEIGHT = 20`（注释写的是「角色多高的一半」，
**是猜的**），而且**横向偏移压根没有**。⇒ 弹体在**自己的碰撞盒里**出生；
又因为 `trail_point()` 让 bot 贴在真人身上（D16 的固有缺陷），
它同时也在**目标的**碰撞盒里 ⇒ 第一次推进就命中，当场结束。

★ 这解释了此前**每一条**观察，而且**和距离无关**（用户否掉三次的那件事，
他一直是对的）：
弹体对象逐格正常（§61.2）、收侧代码路径没有 owner 分流（§57）、
开枪动作和枪口火焰看得见（`OnFire` 跑完了）、爆炸动画和掉血正常
（爆炸位置来自 `rpExplode` 包、伤害由服务端判，都不经过弹体的飞行）。
**唯一没人查的就是「弹体到底走没走」。**

### 3. 修复 + 实机验证

`server/bot.py` 新增 `BOT_MUZZLE_HEIGHT = 57` / `BOT_MUZZLE_FORWARD = 43`
和 `_muzzle(x, y, toward_x)`（横向偏移跟着朝向翻）；
`BOT_AIM_HEIGHT` 从 20 抬到 57（枪口对枪口，见 D41）。

实机复验（同一套 hook）：**bot 的弹体连飞 11 帧、走了 1287 个单位**，
逐帧数据和真人自己的子弹**一模一样**；截图里那条白色曳光线在两帧之间
明显往前推了一段。⇒ ✅ **看得见了。**

### 4. 还没解决的（别混进这一条）

- **贴脸仍然没有行程**：bot 跟随时永远只落后 `BOT_FOLLOW_DISTANCE`（120），
  枪口再往前 43 ⇒ 枪口到目标最多 77 个单位，初速 100 的枪连**一个客户端
  tick**（32 ms）都飞不满 ⇒ 走 `instant` 当场结算那条路。
  **要让 bot 保持交战距离**，那是 **M5**。
- 爆炸时刻还是**粗到一个 bot 帧**（~125 ms）：诊断那一局里瞄的是 400 个单位，
  弹体却飞了 1287 个才没 —— 爆炸特效和弹体位置对不上。M5 一起收。
- 每个角色的骨骼位置略有不同，`57 / 43` 是角色 0「泰尔」1 号枪实测的那一组，
  当统一值用。

### 5. 教训（★ 这一条比结论值钱）

**五轮实机 + 三轮逆向都在问「弹体长什么样」，没有一轮问「弹体走没走」。**
`PROJ+` 那份全字段快照从会话 17 就有了，可它只拍**出生那一刻**；
真正的判据是**第 2 帧还在不在**。
⇒ 查「看不见」的东西，先问**它存在多久、动没动**，再问它长什么样。
