## §1 ★ 这台机器的 Git Bash heredoc 把中文按 CP936 落盘，不是 UTF-8

**结论：写任何含中文的文件，一律用 Write / Edit 工具，不要用 Bash 的 `cat > x <<EOF`。**

实测：heredoc 写两行中文，落盘 104 字节，`decode('utf-8')` 全是替换字符；
按 CP936 解才对。项目里 `.md` / `.py` / `.json` 全是 **UTF-8 无 BOM**，
混进一个 CP936 文件后，服务端读它会 `UnicodeDecodeError`，而 git diff 里看不出异常。

`.md` 的行尾约定是 **LF 无 BOM**（拿 V0.2 的 `CLAUDE.md` 核对过：CRLF 0 处、LF 184 处、
无 BOM）。Write 工具默认就是 LF 无 BOM，正好一致。

## §3 `0x4001` 心跳 body（31 字节）的布局

## §4 ★ `UdpPacket` 校验和算法已经逆出来，且本版重新实测 25091/25091 全中

算法在 [tools/fakeclient.py:138](tools/fakeclient.py) 的 `udp_checksum()`，
出处是客户端 `0x5bbdc1`：

```python
acc = 0x17                       # 0x5bbdc8  push 0x17 / pop eax
for b in body:                   # 0x5bbdcb  lea esi,[buf+0xc]  ← 只覆盖 body
    signed = b - 256 if b >= 128 else b     # 0x5bbdd2  movsx dx, byte[esi]  ★ 带符号
    acc = (acc * 0x103 + signed) & 0xFFFF   # 0x5bbdd6  imul eax,eax,0x103 / add eax,edx
```

比对在 `0x4078f0`（`cmp word [esi+6], ax`），**只比低 16 位**。

本版验证：拿 `game_003_27799.dec.bin` 的全部 25091 发 `0x040e` 逐包重算，
**25091 命中、0 例外**。⇒ 服务端合成 bot 的 `UdpPacket` 时照抄这个函数即可，
**这一块没有未知风险**。

★ 不算它的后果：真客户端在收包入口 `0x4078ab`/`0x4078f0` 就把包丢掉，连队列都进不去
（V0.2 会话 34 实机踩过 —— 以前假客户端恒填 `0x1234`，互相不校验所以没暴露）。

## §5 ★ 坑 1：闯关模式里 bot 占座会让一部分怪从开局就不动

客户端 `GameContext::StartGame` **自己**算控制者表（谁模拟哪一批怪 / 刷怪点）：

```
for (i = 0; i < 6; i++)
    [ctx+0x294+i*4] = 在座座位[i % 在座人数]
```

服务端的镜像是 `RoomQuest.assign_controllers()`（`gameserver.py`），抄的就是它。
bot 座位分到的控制格**没有任何机器在模拟**，那一批怪从开局就是死的。

**对策**：开局进 stage 7 之后立刻调现成的 `Conn.handover_controller_slots()`
（走 `0x0414 gspChangeControllerSlot`），把 bot 的控制格交给真人。
这条路 V0.2 就为「加载途中有人掉线」写好了（V0.2 §180 / D103），直接复用。

## §6 ★ 坑 2：不改代码的话 bot 永远不会死

死亡链是：HP<=0 → `Character::OnHpZero` → `GameContext::vf_1c()` **恒返回 0**
（客户端**不自己判死**）→ 发 `0x0408` 上报 → **等服务端回 `0x0406` 才真的倒下**。

而 `Conn.on_report_hp_zero()` 从 V0.2 的 bug调查/8 起对玩家座位**只认本人上报**：

```python
if 0 <= seat < ROOM_SEAT_COUNT and reporter is not None and reporter != seat:
    return          # 「幽灵死亡上报」，丢弃
```

理由是「谁死没死只有本人的 HP 模拟说了算」—— 射手那台算「我炸死他了」、
受害者那台算「我躲过去了」的分歧是必然的，旧逻辑会让受害者的客户端对活着的自己
执行 `Die()`（用户报的「人还活着却进了观战模式」）。

**bot 没有本机 ⇒ 一发合法的 `0x0408` 都不会有 ⇒ 打不死。**

**对策**：bot 座位放宽这条限制，接受任何真人代报的第一发；去重仍由
`RoomQuest.record_death()` 的 `(句柄, 死亡次数)` + 时间窗负责。
为什么这样安全见 D3。

## §7 ★ 坑 3：只剩一个真人时服务端会把玩家间同步关掉

`Conn.sync_peer_relay()` / `after_someone_left()` 里有一条优化：
「掉回一个人就把玩家间同步关掉，省得客户端对着空房间每秒发 8 发」。

1 真人 + N bot 的房间会命中它 ⇒ 通道 A（`0x040e`/`0x040f`）被关 ⇒
**真人收不到 bot 的任何动作**。

**对策**：判据从「房里几条连接」改成「房里几个**会动的座位**（真人 + bot）」。

## §8 组队战：客户端要求两队人数相等才让开局

客户端 `0x468495` 数 1 队和 2 队的人数，不等就回错误码 3 →
「两组人数不相同。请调整人数。」

⇒ 组队房加 / 删 bot 时必须维持两队平衡。
`Room.default_team_for(seat)` 在 `TEAM_LAYOUT_TEAMS` 下就是「座位号奇偶交替 1/2」
（抄客户端 `0x468952` 的 `idiv 2 ; inc dl`），按它落座天然平衡；
`/team` 手动改完之后如果不平衡，要发系统提示警告房主。

★ **个人战的队伍号必须全是 0**：客户端的队伍记录数组只有两格，
队伍号 >= 3 会越界写进**别人的战绩**（`lobby.py` 开头 `TEAM_LAYOUT_*` 的注释里有
完整的越界地址推演，V0.2 bug调查/8_2 §212）。所以 `/team` 在个人战无效是**必须**的，
不是偷懒。

## §14 `bot.py` 和 `gameserver.py` 的导入方向：只能单向，且方向是反的

`bot.py` **模块级** `import gameserver`（`class BotConn(gameserver.Conn)` 建类
那一刻就要 `Conn`）；`gameserver.py` 反过来只在 `on_chat()` 里**函数内**
`import bot`。

两边都写成模块级 = 循环导入：`gameserver` 执行到顶部的 `import bot` 时
`Conn` 还没定义（它在 4325 行），`class BotConn(gameserver.Conn)` 当场
`AttributeError`。

代价：`bot.py` 缺失 / 语法坏掉时服务端**照样启动**，直到有人在房间里说第一句话
才炸，而且炸的是那个玩家的连接。所以 `server/app.py` 里补了一发显式
`import bot`（`# noqa: F401`），把它变回「启动就炸」。
打包脚本 `tools/build-common.ps1` 的必选文件清单也加了 `bot.py`。

## §15 `broadcast_system_chat()` **不含自己**，命令回执要另走一条

`Conn.broadcast_system_chat()` 走的是 `broadcast()`（默认排除自己，和大厅那套
广播口径一致）。房主敲完 `/bot` 之后，他自己**看不到**这行系统提示。

本版加了两个方法（`gameserver.py`）：

| 方法 | 发给谁 | 用在哪 |
|---|---|---|
| `send_system_chat(text)` | **只发自己** | 命令回执：报错、用法、`/help` 那张表 |
| `room_system_chat(text)` | 自己 + 房里其他人 | 通告：「bot 1 加入了房间。」 |
| `broadcast_seat_leave(seat)` | 自己 + 其他人，`0x0301` **action 1** | 删 bot（`broadcast_seat_slot` 只能发还在的座位） |

同一个道理适用于 `0x0301`：`announce_join()` 用的也是 `broadcast()`，
所以 bot 加入必须走 `broadcast_seat_slot()`（那个**含自己**）——
房主的客户端和别人一样，只认 action 0 那一发才建 3D 模型（`0x405e1c`）。

## §16 bot 换角色 / 换队 / 准备一律发 `0x0301` **action 3**，不发 action 4

两条现成的路完全一致。

## §18 ★★★ 地形的**形状不在 `.map` 里** —— 在地形 PNG 的 alpha 通道里

这条推翻了 M4 原来的设想（「从 `.map` 里提取碰撞段」）。**`.map` 里根本没有碰撞几何。**

一个 `TerrainObj` 的 blob 解完就这些（版本 >= 12，实测 `Camel00` 解完只剩 4 字节）：

```
版本 >= 17: i32, i32, i32(bool)
版本 >= 12: f32 x, f32 y          ★ 位置，经 0x511d25 设进去
            f32 scaleX, f32 scaleY   ★ 缩放，**负数 = 镜像翻转**（实测 -1.00）
            f32, f32, f32 rot        ★ 最后一个是弧度旋转（实测 -0.26）
            wstring（空）
            wstring                  ★★ **地形贴图路径**，如
                                     `Maps/Camel/Terrain/st06_a_14.png`
```

⇒ **一张图的实心区域 = 所有 `TerrainObj` 精灵按 (x, y, 缩放, 旋转) 贴出来之后，
alpha 不透明的那些像素的并集。**

**(x, y) 是精灵的中心，不是左上角。** 判据：按中心贴出来的 `Camel00` 是一座
结构完全正确的宫殿（柱子正好顶着平台、地面在最下方）；按左上角贴则整体错位。

**贴图都在** `Pack_decrypt/` 下，路径就是 blob 里那个字符串原样拼接
（`Pack_decrypt/Maps/Camel/Terrain/st06_a_14.png`）。全树共 566 张 `*/terrain/*.png`，
`Camel00` 的 19 块**一张不缺**。全是 **8 位 RGBA（颜色类型 6）非交错** PNG。

尺寸差别很大（12×140 的细柱 ~ 1146×210 的大地面 ~ 800×652 的建筑），
一张图只用十几到几十块拼成 —— 所以**逐像素合成完全跑得动**，不需要什么空间索引。

### ⇒ M4 的做法要改

原计划「逆 `.map` 的碰撞段」**不存在**。改成：

1. 解 `.map` -> `TerrainObj` 列表（贴图路径 + x/y + 缩放 + 旋转）；
2. 读每张 PNG 的 alpha -> 实心掩码，按变换贴进一张地图大小的位图；
3. 从位图里抽**站立面**（每一列实心区的上沿）和**弹道遮挡体**。

★ 开发机上 **Pillow 12.1.1 已装**，`tools/mapdata.py` 可以直接用它。
但**产物**（`server/data/mapdata/`）必须是纯数据，
服务端运行时绝不能依赖 Pillow —— 便携运行时里没有它。

⚠ **还没查**：`HidingObj`(201) 是不是真的挡子弹（名字也可能只是「挡视线的前景」）；
`BreakableObj`(203) 打碎之后地形变不变；版本 < 12 的图（v7/8/9，21 张）
那 7 个 float 在**外层记录**里，字段顺序要单独核对一遍。

## §19 ★★ 客户端自己吃掉 `/team `，服务端**永远**收不到 —— 换队命令改叫 `/tm`

**结论**：带参数的 `/team 1` 一个字都到不了服务端。客户端在发 `0x0305` 之前，
先拿输入串和六个前缀挨个 `wcsnicmp`（**不分大小写**，且**必须连末尾那个空格
一起命中**），中了就把前缀切掉、只把余下的正文发出来，同时改掉聊天类型：

| 前缀（★ 含末尾空格）| 命中后 `0x0305` 的聊天类型 |
|---|---|
| `/team ` · `/팀 ` | **1**（队伍） |
| `/to ` · `/tell ` · `/say ` · `/귓 ` | **2**（悄悄话） |

**证据**：`0x54e727` 起五段 `push 长度; push 前缀; push 输入; call 0x5f6dad`，
命中分支各自 `mov dword ptr [ebp-0x14], 1/2` —— 那个数就是发出去的聊天类型
（韩文那两个前缀是运行时 `0x401979` 拼的，在 `0x69263c` / `0x69260c`）。
**实测**：玩家敲 `/team 1`，服务端收到的 `0x0305` 载荷是 `01 01 00 31 00`
= 类型 1 + 正文 `"1"`（`logs/server.out` 01:17:16 / 01:19:59 / 01:23:44 三次一致）。

★ **光杆 `/team`（不带空格）不命中**，会原样送到服务端 —— 所以它还能拿来回一行
「请改用 `/tm`」的提示（D12）。

⇒ 以后**起任何聊天命令名都要先躲开这六个前缀**。护栏放在两处：
`bot.CLIENT_RESERVED_PREFIXES` 这张表，加 `test_bot.py` 里
`test_no_command_name_collides_with_a_client_reserved_prefix` 一条单测。

## §20 房间聊天框一次只看得见 **4 行**，多发的会被顶出去

用户实测：`/h` 逐行发 8 行，屏幕上只留得住后 4 行。**到边自己折出来的行同样占额度**，
所以「行数」和「每行宽度」要一起卡。

⇒ `/h` 压到 **3 行**，每行 **≤ 50 个半角宽**（中文和全角标点算 2，ASCII 算 1）。
50 这个数是从实测反推的：旧版最长那行（`/char` 那条）54 宽，玩家数出来仍是 4 行，
说明框宽 ≥ 54，往回收一点当余量。
一条命令一行的排法不能要，改成**多条命令挤一行**、命令之间 `;` + 两个空格。
（聊天历史本身能存 80 条，`0x40605d` 里 `cmp eax, 0x50` 满了才丢最老的 ——
**存得下不等于看得见**，看得见的只有 4 行。）

## §22 控制格的接管者**只能是真人**（§5 的补充）

`Conn.handover_controller_slots()` 原来从「所有在座座位」里挑接管者。
房里有 bot 之后这条就错了：**控制格的意思是「这批怪由谁那台机器模拟」，
而 bot 没有机器** —— 交给它等于没交，那批怪照样不动，而且症状和「压根没
交接」一模一样（怪杵着不动），从日志上完全看不出区别。

⇒ 接管者池改成 `room.human_seats()`。**没有 bot 的房间行为零变化**
（那时它就是全部在座座位），所以 V0.2 那批交接用例一条都没红。

★ 相对的，`RoomQuest.assign_controllers()` 的**初值仍按全部在座座位算** ——
它是客户端 `GameContext::StartGame` 那个公式的镜像，客户端不知道哪一格是
bot，镜像跟着它错才是对的。bot 那几格是**开局后立刻交接掉**的，不是一开始
就不分给它。两件事别搞混。

## §24 ★★★ 心跳 `0x4001` body 的完整布局（★ **§3 的位置字段是错的**）

| `+0x0c` | `+19..22` | i32 | 位域：`[char+0x128]` / `[char+0x4bc]` / `[char+0x2dc]` 三个 bool + `[char+0x2d0]&3`。**高 3 字节恒 0** |

| `+0x12` | `+25..26` | i16 | `0x4295cb` 返回的第一个 float |
| `+0x14` | `+27..28` | i16 | `0x4295cb` 返回的第二个 float |
| `+0x16` | `+29..30` | — | ★ 同样**从没写过** —— `+29` 实测两种值（0x1a / 0x19），`+30` 恒 0 |

### ★★ 勘误：§3 把 `+25..28` 当成了「当前位置」，**错了**

真正的角色位置是 **`+7..8` / `+9..10`**。两条独立证据：

1. **反序列化器 `0x5041e1`** 读 struct `+0` / `+2` 两个 i16，`fild` 成浮点后
   `fstp [esi+0x34]` / `[esi+0x38]` —— 那两个 float 就是角色坐标（`rpDash` /
   `rpSetOnFire` 里的 `[esi]` / `[esi+4]` 也是它俩）。
2. **实包对穿**：拿 3815 发 `rpFire` 里的精确开火坐标（f32）去比同座位上一发
   心跳的每一个 i16 槽位（容差 40）——
   X：`+7` 命中 **27.8%**，`+25` 约 1%；Y：`+9` 命中 **24.5%**，`+27` 只有 11.9%。
   （命中率不到 100% 是因为枪口位置带偏移、心跳只有 ~8 Hz，比的是**相对高低**。）

⇒ **M3 合成 bot 心跳时，位置写 `+7..8` / `+9..10`，不是 `+25..28`。**
按 §3 那版写的话，bot 在别人屏幕上会一动不动 —— 而且症状和「包根本没发出去」
一模一样。

### §3 里其余几处口径也要修正

| §3 的说法 | 实际（67186 发逐字节统计） |
|---|---|
| 「`+3..6` 恒 0」 | `+3..5` 恒 0，**`+6` 是座位号**（0..5） |
| 「`+16` 恒 0x39」 | 未初始化的填充，实测 **12 种**取值（0x6b / 0x39 / 0xe3 / 0xca …） |
| 「`+20..24` 恒 0」 | `+20..22` 和 `+24` 恒 0，**`+23` 是那个 6 位掩码**（13 种取值） |
| 「`+29..30` 恒 0x001a」 | 未初始化的填充，`+29` 有 **两种**值（0x1a / 0x19） |

也没关系（但为了和真客户端的流看起来一致，抄一份常见值更稳）。
