# 会话 38（2026-08-29）—— 修掉一条偶发性失败的回归用例

用户报的：`server/test_botsync.py` 里的
`BotGameModeDamageTests.test_the_fire_wall_doubles_in_deathmatch`
在 3.14 上**单独重复跑 40 次会挂 1 次**，断言 `模式 N 该掉血` 失败
（`burns` 为空）；Win7 的 3.8 上跑全量回归也偶尔命中。

**只动了测试，`bot.py` / `gameserver.py` 一个字没改** —— 产品代码是对的。

## 一、先复现

```
for i in 1..200: runtime\python\python.exe server\run_tests.py \
    test_botsync.BotGameModeDamageTests.test_the_fire_wall_doubles_in_deathmatch
```

**200 次红 2 次**，两次都是 `模式 3`（夺分，也就是循环的**第二轮**）。
把红的那一次的日志抓出来，四行 `火烧` 是：

```
挨了 10 点（第 1 tick …）   ← 第一轮（生存），座位 0
挨了 10 点（第 1 tick …）   ← 第一轮，座位 2（bot 自己）
挨了 20 点（第 21 tick …）  ← ★ 第二轮的「站位那一步」，烧的是上一轮那道旧墙
挨了 20 点（第 21 tick …）
```

**第 21 tick** 那两行就是凶手：它不该发生，发生了就把这一轮量的那一发吃掉。

## 二、链路

用例按 `(生存, 夺分)` 两轮跑，每轮：

```
清 burnt → 走一步（拿落点）→ 造新墙（born_tick -= 20）→ fires=[新墙]
→ clear() → 再走一步 → 量 rpSplashDamaged
```

* 上一轮那道墙活 **76 个 tick**（`60 + 4×4` ≈ 2.4 秒，`_fire_wall_ticks`），
  第二轮开头**还在 `machine.fires` 里**；
* 再烧的账记在**人**身上（§85），第二轮开头刚被清空 ⇒ 旧墙在「走一步」
  那一帧**可以再烧一次**，把 alice 的免伤时刻戳按到「此刻」；
* 于是 20 个 tick 的冷却把新墙第 1 个 tick 那一发挡掉 ⇒ `burns` 空。

★★ 而旧墙烧不烧，取决于 **`time.monotonic()` 有没有跨过一个 tick 边界**：
`_advance_fires()` 里 `end = _clock_tick(now)` 是这一帧才读的挂钟，
`start = born_tick + ticks + 1` 是上一帧留下的。同一个 tick 内 `range()` 是空的
（99% 的情况），跨一格就多出**恰好一个** tick，够旧墙再烧一次。
一个 tick 32 ms，单测一整轮才几十微秒 ⇒ 几百次翻一次。

这就是**铁律 10 踩在测试里**：判据落在真实时间上。

## 三、修法

`fires` 和 `burnt` **一起**在墙装好之后清，中间不再走帧：

```python
self.bot_conn.fires = [wall]
self.bot_conn.burnt = {}     # ★ 挪到这儿（原来在循环开头）
self.clear()
self.walk(self.alice, [tuple(spot)])
```

判定就只剩「墙推到第 1 个 tick、账本是空的」：`start = born_tick + 1`
恒 ≤ `end`（`born_tick` 已经往回退了 20 个 tick），**和挂钟走了多远无关**。

★ 没有采用「`born_tick` 多退一个 tick 离边界远一点」那条 —— 那只是把翻面的
概率调小，判据还在挂钟上，下一台更慢的机器上照样翻。

顺手把这一段的来龙去脉写进用例的 docstring（下一个人删掉那行 `burnt = {}`
的位置就会知道为什么它必须在那儿）。
