# 会话 49（2026-09-01）—— 卡顿治理：日志异步化 + 日志归档 + 弹道加速

## 用户交代的两件事

1. bot 多、子弹多的时候游戏**突发性掉帧**（不是位置跳），怀疑是 hook 里的
   「逐包 + 弹体逐帧诊断」高频写日志。要求把**客户端和服务端所有 log 改成
   异步写入**，并顺带查还有没有别的原因、一并修掉。
2. 同一天多次重启时 `server.out` / `relay.out` / 连接抓包**不要被覆盖**，
   只清理过期日志。

## 查到了什么

全部写进 **§150**，四条：

- 客户端 `bslog_emit` 每条日志同步 `FlushFileBuffers` —— **2 ms/条**，
  而且握着全局临界区。
- **`BSHOOK_PROJ_DIAG` 默认是开的**，`proj_tick_log` 每帧每弹体最多 3 条
  会 flush 的日志。精简模式日志里 89% 出自它。**这是掉帧的头号原因。**
- 服务端所有日志是 `print(..., flush=True)`，而 `BotConn.log` / `Conn.log`
  就在 `room.sim_lock` 里面 —— 房间线程等磁盘 = 真人的同步转发一起等。
  `server.out` 里真打出过 5 次 `[sim] ⚠ 落后 38 格（1216 ms）`。
- `bot._terrain_contact()` 逐像素扫，空中飞 300 像素 **270 µs**，
  每颗在飞的弹每 32 ms 一次 ⇒ 10 颗就吃掉 2.7 ms / 32 ms。

日志覆盖的三个源头也在 §150 里，其中 `auth_016` 那个孤儿文件是磁盘实证。

## 做了什么

决策 **D109 ~ D113**。改动清单：

### 客户端 `hook/bshook.c`（D109 / D113）

- `bslog_emit` 改成「格式化 + memcpy 进 4 MB 环 + 可能一次 SetEvent」；
  新增 `log_writer_thread` 整批取走、一次 `WriteFile` 写一批。
  flush 判据是「这一批里有没有关键记录」，不是计时器（铁律 10）。
- 环满就丢 + 计数，写线程按状态翻转补一行「丢了 N 条」。
- `OutputDebugStringA` 挪到写线程。
- `bslog_shutdown()`：`DLL_PROCESS_DETACH` 和三条 `return FALSE` 之前就地排空。
- `proj_diag_enabled` / `move_diag_enabled` 默认改成跟 `g_verbose` 走；
  `proj_tick_log` 的三条从 `bslog` 换成 `bsvlog`；`proj_dump_obj` 加 `detail` 参数。
- `bslog` / `bsvlog` / `bslog_hex` 的签名一个字没改，142 个调用点没动。
- 重新编译，`bshook.dll` + `bsloader.exe` 一起换（铁律 6）。

### 服务端（D109）

- 新 `server/asynclog.py`：`emit` / `emit_text` / `emit_bytes` /
  `start` / `stop` / `drain`。**没 `start()` 时同步写**，所以现有测试一行没改。
- 改了十几处「最后落笔」的地方：`app.log` / `Conn.log` / `Conn.ft` /
  `[sim]` 那 5 条裸 print / 注入给 relay 和 udpsync 的 lambda / 控制通道 /
  `BotConn.log` + `bot.py` 11 处裸 print / `authserver.log` / `relay.log` /
  `web/server.py` / `eventlog._write` / verbose 抓包的 `fb_raw`+`fb_dec`。
- `eventlog` 的跨天切名搬到写线程上执行（回调式目标）；`configure()` 先 drain。
- `Conn` 断线收尾时先 `asynclog.drain()` 再关抓包文件（不然队列里的字节会丢）。
- `app.py`：`asynclog.start()` + `atexit` + KeyboardInterrupt 各一发 `stop()`。

### 日志归档（D112）

- `tools/wincompat.ps1` 新增 `Move-LogAside`；`launch.ps1` 三处、
  `serverctl.ps1` 一处在起进程前调它。`serverctl.sh` 加等价的 `rotate_log()`。
- `logcleanup.RUN_STAMP`；`authserver` / `gameserver` 的抓包文件名带上它。
- `test_logs.py` 的「每一种真会长出来的文件」清单补上新命名 + 一条格式用例。

### 弹道加速（D110）

- `mapdata.MapTerrain.bullet_coarse()`（根地图一份 + variant 补破坏物外接矩形）。
- `bot._terrain_contact()` 加粗网格快路；原实现原样留成 `_terrain_contact_exact()`。
- 粗网格在 `_warm_navigation_now`（后台预热线程）里跟着可达图一起烘。
- `botbreak.Ledger.alive()` 加缓存，失效判据是「`broken_at` 变了」或
  「越过下一件该长回来的时刻」（事件驱动，不是定时器）。

### 诊断（D111）

- `RoomLoop.run_tick()` 量分段耗时进 `self.spent`；`_note_late()` 报「落后」
  时跟着一起打。

## 结果

- 回归 **2078 项绿**（CPython 3.14 + Win7 3.8 各一遍）。
  新增 `test_asynclog.py` 17 项、`test_ballistics.CoarseTerrainTests` 6 项、
  `test_logs` 补 2 项。
- 弹道差分：**174 张真图 × 20880 条随机线段，0 不一致**。
  中途逮到 129 条失败，全是同一个原因（残缺的边界块，见 §150）。
- 客户端日志 **47 MB → 21 KB**（三次启动实测 20736 / 21247 / 21309 字节）。
- 弹道 300 像素 **217 → 112 µs**（1.9×），随机全量 2.0×。
- 三轮启停实证归档：`server-20260901-023840.out` / `relay-20260901-023842.out` /
  `bsloader-20260901-023844.out` 都在，旧的没被冲掉；
  抓包文件 `auth_20260901-023945_001_47611.txt` 带上了启动时刻。

## 遗留

- ⏳ **实机验收**（3 条，见 PROGRESS）。核心那条是「开满 bot、子弹密集时
  还卡不卡」—— agent 做不了。
- 弹道加速**只有 2×**，不是当初估的量级级。想再快要上粗网格的距离场，
  代价是每图多几十毫秒预热 + 一批新边界情况，而这条是命中判定路径。
  没做，理由写在 D110 里。
- `AccountStore._write_unlocked` 的 `json.dump` + `os.fsync` **确实在
  `sim_lock` 里**（局末结算那一格）。但它是一次性尖峰，和用户报的形态不符。
  **先量再改** —— D111 的分段耗时就是给它准备的。
- 根粗网格构造最大的图要 90 ms。现在挂在后台预热线程上，没落在战斗那一格里；
  但如果哪天预热被绕过，那 90 ms 会掉进第一格。
- **没有替用户提交任何东西**，改动全停在工作区。
