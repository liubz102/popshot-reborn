## ★★ 一开工就推翻了 M4 的做法（→ §27 / D19）

写解析器时顺手统计了「19 类循环之后还剩多少字节」，发现**每张图都还剩
1.5 KB ~ 42 KB**（§17 只写了一句「还有一段没逆完」）。查过去：

- `0x474773` 起那一段读的是 `[World+0x1c60]`；
- 分配点 `0x47c15c` 写的 vtable 是 `0x66c8c8`；
- `vftables.json` 和 RTTI 都说它叫 **`TerrainData`**。

`TerrainData::Load`（`0x47c4a4`）读的是：`i32 恒1 / i32 宽 / i32 高 / i32 clen /
clen 字节 RLE(count,value)`，解出来正好 `((w*h+15)/16)*4` 字节 =
**每像素 2 bit**，而且**宽高和地图头严格相等**。采样器 `0x472fe0`
就是客户端自己的碰撞查询。

⇒ **`.map` 里烘着一份逐像素的碰撞位图，客户端自己读它。**
会话 02 定的「读 566 张地形 PNG 的 alpha、按位置/缩放/旋转合成」整个不用做了。

**这条不只是省事**：合成出来的东西再像也只是「我猜客户端这么算」，
而搬过来的这一份**和客户端逐像素同源**。还少三个自己拍的判据
（镜像怎么翻、弧度旋转怎么采样、alpha 大于多少算实心）——
那三个数拍错了，症状是「bot 偶尔卡在某处」，最难查。

顺带把 §17 剩的两处「未逆完」也补了（→ §28）：v<13 的 type 是拿**贴图路径的
第 3 段目录名**判的（`TERRAIN/LAYER/COVER/EFFECT/BREAKABLE`，`0x5130a8`），
v≥10 的尾巴是 `i32 n` + n 组 key/value 属性表。补完之后 **174 张逐字段读到
文件尾，一个字节不剩**。

## 几个当场定下来的判据

- **出界 = 实心（2）**，照抄 `0x472fe0`。写反了 bot 会觉得图外能走。
- **值 1 是薄的可站立面**，不是噪声：1207 个出生点里 **77 个**正下方
  第一个非零格就是它。所以 `is_solid` 认它。
- **站立面的判据只有一条**：本格非空、正上方是空。要不要滤掉「站不下人的
  窄檐」是 **M5 的策略**，产物不替它决定（D20）。
- **不做降采样网格**：位图 zlib 后 174 张才 1.0 MB，省 64 倍没意义，
  而降采样要多拍一个「一格里多少像素算实心」的阈值（D20）。

## 踩到的两个坑（都在写完之后自查揪出来的）

1. **逐格 Python 循环跑不动**：抽站立面要 `宽 × 高` 次循环，大图 900 万次，
   174 张跑了 15 分钟还没完。改成**把整行当一个大整数**
   （`cur & ~prev` 一次出一整行的上沿），全量 13 秒。
2. **预览 PNG 差点被打进服务端包**：一开始写到产物目录里，而那个目录整个
   会被 `Copy-ServerCode` 拷进包。挪到 `logs/mapdata-preview/`，
   并且 `Copy-MapData` 只拷 `*.json`（两道保险）。

另外把 `update-mapdata.bat` 的 Python 改成**优先用开发机的 `C:\Python314`**
—— 便携运行时里没有 Pillow（也不该有），用它 `--verify` 就画不出图。
`write_preview` 同时改成「没装 Pillow 返回 False」而不是抛错。

# 续（2026-08-26）—— M4 核对通过，顺带修掉一个真 bug

## 用户回话

> 「像。原游戏里白线是可以站人的线，站在上面按下键可以穿过白线处掉到下面去。」

第一句 ⇒ **M4 验收通过**：坐标系、位序、y 轴方向全读对了。
第二句 ⇒ 直接定死了值 1 的语义：**它是单向平台**，不是我写的
「薄的可站立面」那种描述性说法。

## ★★ 顺着这条把弹体的地形碰撞逆完了（→ §29）

判定点 `0x47f976`：`挡住 = (cell==2) || (cell==3) || (cell==1 && al)`，
其中 `al` 要求 `vf_0x100()` 为真、某个逐步位标志为真、且 `dy >= 0`。

两条独立的锁把结论钉死：

1. **`0x47f738` 只属于弹体** —— 全镜像反查这个函数指针，它出现在 **19 个类**
   的虚表里（`BulletObj` 和全部子弹 / 手雷），**全在同一个槽 `+0x168`，
   没有任何角色类有它**。
2. **那 19 个类的 `vf_0x100` 全是默认桩 `0x46e188` = `xor al,al ; ret`**
   ⇒ `al` 恒 0 ⇒ `cell == 1` 那条分支**一次都走不到**。

⇒ **单向平台挡人、完全不挡子弹。**

## 揪出来的真 bug

`server/mapdata.py` 的 `line_blocked()` 用的是 `is_solid()`（值 != 0），
把单向平台也算成挡子弹。**弹道判定错了**，症状是 bot 觉得隔着一根白线
打不到人 —— 而它明明打得到。M5 接瞄准的时候才会暴露，那时候极难联想到这里。

改法：拆成两个判据，别让调用方自己去想用哪个。

```
is_solid(x, y)       挡人（走路 / 下落）    cell != 0
blocks_bullet(x, y)  挡子弹                 cell >= 2   ★ 单向平台不挡
is_one_way(x, y)     是不是单向平台          cell == 1
```

`line_blocked()` 改用 `blocks_bullet`。补了 3 个用例（含「往上打、往下打
都穿得过单向平台」和「挡人 ≠ 挡子弹」），`test_mapdata` 23 → **25** 个。

## 结果

- `C:\Python314\python.exe server\run_tests.py` → **1195 全绿**；
- `runtime-win7\python\python.exe`（3.8）→ **同样 1195 全绿**。

## 这一轮的教训

用户那句「按下键可以穿过去」是**一句话顶一轮逆向**。如果只收下「像」就收工，
`line_blocked` 那个 bug 会一直躺到 M5 调瞄准的时候 ——
到那时症状是「bot 有时候不开枪」，跟地形数据八竿子打不着。
**实机核对要连「它在游戏里是怎么用的」一起问，不要只问「对不对」。**
