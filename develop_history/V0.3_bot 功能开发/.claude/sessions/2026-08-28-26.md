## 结果

### 2（先说这条，另外两条都跟它有关）：句柄记账错位（§86 / D60）

取证方法是这一轮最值得记的东西：**客户端 hook 的 `PROJ+`（收方实际分配的
句柄）和服务端 `开火:`（预测的句柄）一行一行并排比**。

```text
苹果雷 A   服务端 200020   收方 200020   ✓
苹果雷 B   服务端 200022   收方 200022   ✓   ← 第一次分裂就在这一发之后
苹果雷 C   服务端 200032   收方 200030   ✗ 差 2
苹果雷 D   服务端 200042   收方 200036   ✗ 差 6
苹果雷 E   服务端 200052   收方 200041   ✗ 差 11 …一路涨到本局结束
```

`weapon.handle_step`（`shots × (2 if 溅射 else 1)`，§46）是**总数**，
只在「本发的 `rpExplode` 全发完之前不开下一枪」时才等于开火时的步进。
**分裂弹的四片碎片是同时在飞的**，`_split_shell()` 按总数记 ⇒ 四片排成
`base, base+2, base+4, base+6`，收方给的却是**连号**。

改成按事件记：`fire_step`（开火时每颗弹体 1 个）+ `explode_step`
（爆炸时溅射对象 1 个，`sync.explode()` 负责）。`/noboom` 那条特判跟着删了
—— 不发爆炸收方就不创建溅射对象，两边天然一致。

★ 回归钉子 `ReceiverLedger`：把收方那本账复刻出来，喂 bot 发出去的每一帧，
断言「一发 `rpExplode` 都没被丢弃」。改回旧记账立刻红。

### 1：夺分模式伤害 ×2（§87）

`0x4806bf` 是**射手那台机器上所有伤害的必经之路**，开头三句：

```asm
004806d8  call 0x409e0a          ; 游戏模式 = 房间描述符 arguments[1]
004806dd  cmp eax, 3 ; je        ; 夺分
004806e9  cmp eax, 5 ; jne
004806f1  shl dword ptr [eax], 1 ; ★ ×2
```

进它的有四条路：直接命中（`0x47ec5b`）、溅射（`0x481dfd`）、
地面燃烧 / 近身（`0x480e52`）—— 全在 `IsMine` 门后面。
所以服务端也得在**塞进包之前**乘。

⚠ 同一个函数后面还有装备 / 附魔 / 宠物的百分比加成，bot 白板号一个都没有，
真人那份归他自己那台机器算。★ 模式 3 里另有两条 ×0.75（远距离、
`[char+0x128]` 置位）**没做** —— 触发条件还没量清楚，写进 §87 了。

### 3：苹果弹落点（§88 / D62）

两份原因：
* **大头是第 2 条**：母弹的 `rpExplode` 被丢弃 ⇒ 收方那颗**永远没被收走**，
  一直躺在原地；而碎片是服务端在自己算的那一点用 `rpFire` 生出来的。
  用户看到的「停下的位置和炸裂开的位置不一样」主要是这个。
* **小头是法线**：拿实机 57 次反弹反推法线，把采样半径从 `Size+1` 调成
  `Size × 2`，出射方向中位误差 17.1° → 10.4°，而且不再有「量不出法线」的情况。

⚠ 残差还在：19 条活满引信的轨迹，末点差中位 **40**、p90 **185** 个单位。
反弹那 0.5 的速度衰减是**硬的**（57 次中位 0.4999），竖直面连方向都对得死，
**斜坡上的法线是拟合的**。D62 把「什么时候允许拟合参数」写成了口径。
