# 会话 71（2026-09-08）—— 下载中点「取消」没反应：界面线程被进度回调饿死（D153 / §195）

## 用户要的

> 最近刚改了自动更新器的代理功能，我发现改完之后，在下载过程中点取消按钮没反应，
> 无法取消，请帮我调查原因并修复。

## 查

先把嫌疑排掉：`ui_cancel_requested` / 看门狗 / `net_download_file` 的取消链路，
会话 70 的两笔提交**一行都没动**（`download_progress` 只是把 `mib_wide` 改名成
`mib_to_wide`）。变的只有一件事 —— 下载地址从直连换成了优选出来的快源。

真机日志（用户 2026-09-08 00:09 那次）：**378 MB / 9 秒 ≈ 42 MiB/s**。

复现夹具（40 MiB/s、400 MB 的本地服务器 + 真窗口 + 自动点取消）+ 临时计数器：

| | 会话 70 的版本 | 修完 |
|---|---|---|
| `download_progress` 被调次数 | **51250 次 / 10 秒**（≈ 5100 次/秒） | **27 次** |
| `PostMessage` 成功 | 47110 | 26 |
| 点击 → `on_button` 收到 | **滞后 4 秒，且在 `zip ready` 之后** | **同一秒** |
| 结果 | 400 MB 照下完，取消无效 | 下载 5.4 秒被切断 |

机理见 §195：`sink_write` 每收一块网络数据就调一次 `progress`，而 `progress` 一路
通到 `PostMessage`；Windows 的 `GetMessage` **把 post 队列排在鼠标键盘输入前面**，
队列一直不空，点击就永远排不上队。坏版本的日志把这一点拍得很直白 —— 驱动脚本在
下载途中连点 7 次，7 条 `ui: button btnCancel` **全堆在下载结束那一秒**才一起送达。

## 改

- `updater/src/net_http.c`：`Sink` 加 `watching`；看门狗一起来就由**它**按 200 ms
  节拍报进度（本来就是取消节拍），`sink_write` 只数字节。看门狗没起来（建线程失败）
  才退回逐块报，别把进度和取消一起丢了。文件头写清了为什么。
- `updater/src/net_http.h`：`net_progress_fn` 的契约改成「按看门狗 200 ms 节拍调，
  不是按网络分块」，并写明逐块回调会饿死界面线程。
- `updater/src/ui_window.c`：`on_button` 加一行 `log_line("ui: button %ls stage=%d")`。
  这类「玩家点了但没生效」的毛病，日志里没有「按钮到底收到没有」就只能靠猜。
- `game_patched/BsPatcherChn.exe` 重编。

### 夹具（`updater/scripts/test_cancel_ui.py`）—— 它本来抓不到这个 bug

三处硬伤，都修了：

1. **坐标点错了。** IE 档按 `(543, 499)` 点，实测按钮在窗口坐标
   `x 504~559 / y 477~495` —— 点在**下沿外 4 px**，一次都没点着。
2. **判据假过。** 只看日志里有没有「已取消更新」，可收尾的 `CloseMainWindow()`
   自己就会触发取消 —— 点没点着都能过。现在**先断言 `ui: button btnCancel`**。
3. **点得太早也测不出来。** 一看到「下载开始」就点的话，快源的 post 队列还没堆起来，
   坏版本照样能过（实测就是这样）。现在由**服务器数着自己发出去多少字节**，
   流到一半才放行 `GO_FLAG`，驱动脚本等到它才点 —— 快机慢机都在「下到一半」点。

顺带：多场景共用一个沙箱会串日志（`os.makedirs` 还会直接炸），改成一场景一个沙箱；
驱动脚本全程按事件推进（等日志出现 `download http` / `ui: button btnCancel` /
`FINISH-OK`），不再用固定 `Start-Sleep`。

新增 `fast` 场景（40 MiB/s、400 MB），跑法：

```
runtime\python\python.exe updater\scripts\test_cancel_ui.py [1|3|both|stall|fast|all]
```
