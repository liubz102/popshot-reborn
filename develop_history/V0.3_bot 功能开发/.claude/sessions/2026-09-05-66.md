# 会话 66：bot 卡顿、瞬移的整体复查

用户要求重新调查，明确反馈本机服务器也会出现。本轮完成源码、原版机器码和
已有本机两端日志交叉核对；没有启动新对局，没有改生产 server/hook，也没有宣称修复完成。

## 结论

当前最关键的问题在 **bot 模拟与原版客户端之间的运动同步契约**：服务端已经算过
跳跃/受击，发出相应事件和结果状态；客户端又按自己的事件队列、运动约束和物理
阶段处理同一个角色。双方没有共同保证“这个快照已经包含哪些事件、现在谁能移动它”。
于是包可以及时到达、字段也各自合理，客户端仍会先停住、错误加速，随后被下一次
有效位置校正拉走。

本轮确定了两个此前未覆盖的机制；它们不是对所有画面峰值的逐帧归因。

## 1. Jump/Hit 与位置快照的应用顺序冲突

生产路径：`bot._own_step()` 先模拟 → `_tick_bot()` 发 Jump → 发结果心跳。
腾空时水平键统一清零。旧测试只断言这两包按该顺序发出。

原版的实际处理方式：

```text
收到 Jump ────────────> 放进可靠事件队列
收到 heartbeat ──────> 立即写入角色位置、速度、按键
本帧消费可靠事件 ────> 执行 Jump，再次读按键、重算速度
角色物理更新 ────────> 按被改写后的速度移动
```

`0x407be7` 是立即心跳处理点，`0x405810 → 0x407c1d` 是按帧事件消费。
`0x492d60 → 0x501d57` 的 Jump 同时用于一、二段跳；`0x501e81/0x501e9f`
读取左右键，零键在 `0x501ebe` 写 vx=0，`0x501ef9` 重设 vy。
旧 §93 只证明**普通空中积分**不读键，却被推广成“腾空时所有行为都不读键”。

我用 Unicorn 运行原版镜像中的完整心跳解码器，以及 Jump/Hit 的原始速度写入块：

| 情形 | 锚应用后 | 事件执行后 |
|---|---|---|
| 第一次跳跃 | vx=10，vy=-18 | vx=0，vy≈-20.7846 |
| 第二次跳跃 | vx=10，vy=-22 | vx=0，vy=-24 |
| 伤害 >10，push=(8,-8) | vx=8，vy=-6 | vx=16，vy=-14 |

前两项证明水平运动会被打断；第三项证明已包含击退的快照可能被再叠一次击退。
事件先执行、锚随后应用的对照组可恢复 vx=10，证明结果依赖**消费阶段**。
示例服务器 vx=10.5 时，四个 32 ms 格的水平差可达 42 px；这是无碰撞、无其他
校正的量级计算，不是对任一具体视频帧的测量。

去掉即时锚也不根治：前一发空中心跳已将键清零，下一次二段跳仍会清 vx。
仅改按键也不足：Jump 还会重算 vy，且两段模拟和事件执行阶段必须一致。
对受击而言，事件来自射手流，受害者心跳里的 N 不能表示跨座位的因果依赖。

## 2. 原版运动约束状态在服务端完全缺失

内层 `0x0017`，body 两个对象句柄，处理器 `0x49361e` 调 `0x50e636`，
令第一对象受第二对象约束，关联句柄记在 `[char+0x164]`。
原版心跳解码器只要看见它非零，就跳过**坐标和速度**。
`bot.note_peer_hit()` 忽略这个 opcode，`Body` 没有对应状态，服务端仍独立推进。

原版 setter + 完整解码器重放：约束存在时，连续五发位置锚全部无效；
解除后同一发立即生效。增加心跳频率无法解决这条分歧。

现有日志中的关键时间线（本机，Iceria02）：

| 时间 | 证据 |
|---|---|
| 11:28:19.132 | 客户端 bot1 y=798.71，服务端开火位置反推 y=794.00，差 4.71 px |
| 11:28:19.165 | 真人发 `0x0017`：200001（bot1）受 100001（真人）约束 |
| 11:28:19.224 | 服务端继续报 bot1 y=773、vy=-5 |
| 11:28:19.353 | 服务端报 y=763，并从 y=763.2 的身体位置开火 |
| 11:28:19.356 | 客户端执行同一发开火；角色 y=902.71，差 **139.51 px** |

来源：`logs/server-20260905-114002.out:198107/198162/198167`，
`logs/bshook_20260905_104126_pid29956.log:337459/337579/337580`。
该关联与原版静态机制吻合，但日志没有当帧 `+0x164` 的直接值，不能声称
这次峰值的每一次写入均已取证；它不是单凭网络延迟能解释的差异。

## 3. 整批日志与测试说明了什么

分析 `server-20260905-114002.out` 及配套 `bshook_20260905_104126_pid29956.log`：

- 32,313 发 bot 心跳；23,291 发腾空心跳，全部清水平键。
- 2,454 发 Jump；到下一发锚的间隔中位 0 ms、p99 1 ms，形状与顺序反例吻合。
- 3,671 发原始开火与客户端快照配对：发包记录到处理，中位 3 ms、p99 36 ms、
  max 71 ms。配对使用座位、武器、枪口、角度、力度、颗数，不只靠时间接近。
- 客户端实读位置与服务端身体位置差：保守下界 p99 62.33 px、max 143.15 px；
  y 单轴最大 139.51 px。横向不知道枪口朝向时取两个候选中较小的差，避免夸大。
- 同份日志确有一次 96 ms 房间落后（11:30:00.771）。不能排除性能问题，
  但它不能解释多个开火仅 1–4 ms 就到达、角色却已偏离百像素的时刻。
- 现有相关 **35 项测试在 3.14 和 Win7 3.8 均通过**，机器码反例同时成立。
  `PeerClient` 模型只测事件队列，`MotionTransitionAnchorTests` 只测发包顺序，
  缺的是解码→事件消费→物理更新后的角色状态断言。

这些位置差是分处发送/接收时刻的快照差，含正常的投递和帧量化影响；不是所有
非零误差都代表卡顿，也没有把所有异常峰值归因给 Jump 或 `0x0017`。

## 修复应从哪里开始

首先明确 bot 的权威运动状态与事件应用顺序：结果状态不能被它已经包含的 Jump/Hit
再次改变；补齐约束、解除与相应运动状态。需要把客户端的应用阶段纳入设计，
同流 TCP 顺序、固定等一帧、增加心跳都不是因果保证。

如果采用 bot 专用客户端同步，需要明确版本、模拟 tick、快照包含的事件进度，
在确定的帧阶段应用，处理迟到事件与跨座位受击；不能只拿受害者自己的 N 代替全部依赖。
如果保持原版客户端不变，就必须完整复现原版输入/状态机语义，并证明所有到达组合
下的行为，不能把客户端当成只显示坐标的画布。

之后再审平台、天花板、斜坡：服务端仍用近似点碰撞，原版还会用形状偏移扫掠，
这一部分没有完成完整差分验证。自由飞行重力相同不能证明碰撞响应相同。

验收依据应是接收、事件执行前后、物理更新后的逐帧角色状态，区分：
“事件改坏速度”“约束期间忽略快照”“实际碰撞分歧”“线程或网络确实迟到”。
本轮提供的是调查结论与可重复反例，**没有交付生产修复或实机观感验收**。
