# 会话 14 — 一键启停脚本 + 「启动慢/玩着卡」根因（2026-08-07）

## 用户要求

1. 加一键启动脚本（**不要重复启动后台服务器**）和一键关闭脚本。
2. 游戏启动很慢、玩的时候有时候很卡。怀疑是输出大量调试 log 导致的，
   查清原因；如果确实是，加 flag 控制，并做两个启动脚本
   （带 log 调试用 / 不带 log 正常玩）。

**用户的猜测完全正确**，而且比预想的还严重。

## 做了什么

### 1. 定位根因（§105）

拿会话 13 留下的 `logs/bshook_20260807_114523_pid13448.log`（8.4 MB / 96,333 行）
按时间戳做统计：

```text
相邻两行间隔   中位数 2.0 ms / 均值 2.51 ms
间隔 <20ms 的累计   197.5 秒（94,144 条）
SNOW 相关行     24,229（加上各自的 hexdump 行占全部行数 ~99%）
```

`bslog` 每条都 `FlushFileBuffers`（同步刷盘）+ `OutputDebugStringA`。
SnowCipher 的 detour 每次加解密写 1 行头 + 最多 16 行 hexdump
（`SNOW_MAX_LOG_BYTES=256`）= **17 × 2ms ≈ 34 毫秒**。
战斗中每个网络包都要解密 → 一个包卡两三帧。
进大厅要解 `Pack\*.pkn`，上万次解密 → 那「~100 秒」大部分是在等 flush。

会话 03 的死路清单里其实已经记过同一件事（「每次加解密都 bslog 会把游戏拖死」），
当时的处理是把日志推迟到 connect 之后，治了「进不了登录界面」，
但 connect 之后的整个游戏过程仍然背着这个开销。那时协议没解完，逐包 dump 是刚需。

### 2. 日志分级（客户端）

`hook/bshook.c`：

- 新增 `g_verbose`（`DllMain` 里由 `read_log_level()` 读 `BSHOOK_VERBOSE_LOG`，
  **必须排在 patch 线程之前**，因为那个线程要按级别决定装不装 cipher hook）。
- 把 `bslog` 拆成 `bslog_emit(detail, ...)`：
  - `bslog` = 关键事件，两档都记，**照常 flush**（崩溃时不能丢）
  - `bsvlog` = 详细事件，只在 verbose 记，**不 flush、不 OutputDebugString**
- `bslog_hex` 拆出 `bslog_hex_ex(detail, ...)`，加 `bsvlog_hex`。
- SNOW 段的 21 处日志调用全部改走 `bsvlog` / `bsvlog_hex`。
- **精简模式根本不装 cipher hook**（`patch_thread` 里加分支）。
- banner 里打一行当前日志级别，方便下个会话一眼确认。

### 3. 日志分级（服务端）

`server/gameserver.py`：

- 模块级 `VERBOSE`，由新的 `--verbose` 设置（默认关）。
- `Conn.vlog()` = 只在 verbose 记；`send()` 的 hexdump、`on_game_packet` 的
  「试解」都改走它。
- `NOISY_OPCODES = {0x0406, 0x0408, 0x0410, 0x0104}`：非 verbose 时**只报第一次**
  （完全不记会让「客户端还在不在发」失去依据）。
- `game_*.raw.bin` / `.dec.bin` 改成只在 verbose 时**开文件**（以前每次连接都建，
  非 verbose 下就是两个 0 字节文件）。
- 新增 5 项测试（`NoisyPacketLoggingTests`），其中一项专门断言
  **两种日志级别下下发的字节逐字相同** —— 静音绝不能碰应答逻辑。

### 4. 一键脚本

| 文件 | 说明 |
|---|---|
| `start.bat` | 正常游玩 → `tools/launch.ps1` |
| `start-debug.bat` | 调试 → `tools/launch.ps1 -DebugLog` |
| `stop.bat` | 关闭 → `tools/shutdown.ps1` |

`launch.ps1` 做的事：环境自检（GameGuard 已改名 / bshook 存在 / 串流是否在跑）
→ **按 47611+27799 的监听状态决定要不要起服务端**（已在跑就复用）
→ 清残留 `BigShot.exe` → 设环境变量 → 拉 `bsloader.exe`。

「不重复启动」用端口的 `OwningProcess` 判断（D045）：`gameserver.py` 不开
`SO_REUSEADDR`，第二个实例会静默绑定失败，光看进程列表会被骗。
另外把当前日志模式写进 `logs/.server_mode` —— 用 `start-debug.bat` 时如果沿用
一个精简模式起的服务端，日志里就是没有 hexdump，人会以为代码坏了。
模式不匹配就自动重启服务端。

`shutdown.ps1` 只停「占着 47611/27799/27800 的进程」+ `BigShot`/`bsloader`，
不做 `Get-Process python | Stop-Process`（会误伤用户其他 Python 工作）。

## 实机验证

**两种模式各跑一遍完整链路**（`gui_probe.py` 自动登录 + `click.py` 走到战斗）：

```text
                     改之前    start.bat   start-debug.bat
登录 → 大厅第一个包    ~100 秒    14.6 秒       15.1 秒
bshook 日志（进大厅）   8.4 MB    18.7 KB       4.2 MB
战斗中 30 秒的增量        ——     +44 字节      +44 字节
关卡加载 0x0402→0x0403    ——      8.8 秒         ——
```

### ★ 一个和预期不符的结果，值得记住

动手前我以为「详细模式必然还是慢，那是它的代价」，**实测不是** ——
详细模式只比精简慢 0.5 秒。因为那 100 秒的大头根本不是 dump 本身，
而是 `FlushFileBuffers`：`bsvlog` 不刷盘之后，逐包 dump 照写不误也快了。

所以两个改动的分工其实是：

- `bsvlog` 不 flush → **提速的全部来源**（~100 秒 → 15 秒，两种模式都受益）
- 精简模式不装 cipher hook → 省磁盘（4.2 MB → 18.7 KB）、省格式化 CPU、
  **让关键行不被几万行 hexdump 淹掉**

已把文档里「debug 模式仍要 ~100 秒」的写法全部按实测更正
（PROGRESS / FINDINGS §105 / DECISIONS D044 / `start-debug.bat` / `launch.ps1` /
`bshook.c` 的注释）。**这条本来是要写进文档的错误结论，靠跑一遍 debug 路径才拦下来**
—— 只验证「快的那条路」是不够的。

## 两个顺带发现

- **§107 `game_patched\GameGuard.des` 一直没按铁律 2 改名。** 没出事是因为
  bshook 在 `0x54b0fc` 的 patch 让校验函数直接返回 `0x755`，那个文件从头到尾
  没被加载过。已改名 `.bak`，并实机复验改名后全链路照常。
  `launch.ps1` 现在会在启动前挡这一条。
- **§106 `.ps1` 必须 UTF-8 with BOM**，和 `.bat` 的「无 BOM」正好相反。
  无 BOM 的 `.ps1` 被 PowerShell 5.1 按 CP936 读，中文乱码里混进引号
  直接变成 `The string is missing the terminator` 语法错误 —— 踩了一次。
