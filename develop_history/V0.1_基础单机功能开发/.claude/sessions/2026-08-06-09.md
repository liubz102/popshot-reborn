## 做了什么

### 1. 换了个查法：按韩文原串反查（→ D034）

会话 08 顺着行为反推，查到 `0x465935` 那条「等级 + 地图名一起送进 `0x464995`」的链，
**是错的** —— 那其实是房间 UI 的按钮回调（`gameModeRBtn` / `teamModeLBtn` 那一堆）。

这次改成搜韩文关键词（`레벨` / `미션` / `퀘스트` / `선택할 수 없습니다`），
一次命中 `0x66a7fc = '레벨이 낮아서 퀘스트를 선택할 수 없습니다'`，
全镜像**唯一**引用 `0x4682d6`。

### 2. 真凶：读的是房主座位里的 u16 等级（→ FINDINGS §77）

```asm
00468242  mov edi, [esi+0x34]              ; LobbyStage+0x34 = 房主座位号
00468256  call 0x404d42                    ; -> 座位指针（+0x40 + idx*0x3c）
00468272  call 0x464848                    ; -> 关卡要求等级 = [关卡记录+0x28]
00468277  movzx ecx, word ptr [edi+0x10]   ; ★ 座位里的等级
0046827b  cmp ecx, eax
0046827d  jge 0x468316                     ; 够 -> 通过
```

和 `gspRepLogin` 下发、存在 `[0x72e338]` 的账号等级**完全无关**，
所以 §75「等级 30 照样弹」是必然的。

同一个校验函数 `0x468176` 还会返回另外三个错误码（地图人数超、难度太高、
随机图不可用），闯关房都能过。

### 3. 补上 `0x0300` 房间座位快照（→ FINDINGS §78/§79，D033）

- `SessionSlot` 线格式逐字段解出（12 个字段）。两个容易踩的坑：
  `+0x08` 是 **1 字节**（`0x5d5942`）不是 4；`+0x01` 是**「关闭」**不是「占用」，
  所以实机 `0x0302` 报 `free_slots=6` 而座位 0 已占用是对的。
- `0x0300` 包体 = `int32 房主座位号 + int32 ? + SessionSlot × 6`。
- 顺序约束：**必须排在 `0x0201` 之后** —— `0x54f815` 会把座位 0 的角色 id 清零。

`server/gameserver.py` 新增 `build_session_slot()` / `build_session_members()` /
`Conn.send_session_members()`；`server/account_store.py` 新增 `display_name()`。
测试从 32 项加到 **37 项**，全部通过。

### 4. 实机验收 ✅

`0x0303`(空图名) → `0x0201`(ok) → `0x0300`(座位 0 = testuser/Lv1) 之后：

- 玩家列表出现 **`testuser` +「房主」徽标 + Lv.1**（此前是空的「等待」）
  —— 截图 `logs/shot_s09_room.png`
- 「人物选择」栏出现三个角色头像（此前全空）
- 点「F5 游戏开始」**不再弹任何提示框**，客户端直接发 `0x0402`，
  走完 `0x0402 → 0x0401 → 0x0402 → 0x0402 + 0x0412`

### 5. 顺手更正 §72（→ FINDINGS §80）

闯关房点 F5 发的是 **`0x0402`**，不是 `0x0203`。
`0x0203` 是**离开房间/取消**（发送函数 `0x406191`，调用点在离开逻辑和连接清理里，
同一函数还会弹「倒计时中不能离开房间」）。

### 6. 用户线索：大厅点「对战」弹「不符合等级要求，无法连接」（→ FINDINGS §83）

判定在 `0x440b08`：`[0x72e338] == 1` **且** 目标频道 == `[this+0xd4]` 才拦
（是 `== 1`，不是 `< 2`，属于 1 级新号的引导性拦截）。

**这条现象反证了 §77**：账号等级确实下发并被客户端用上了，
只是「等级太低，无法选择任务」那个框根本不看它。两套判定连等级来源都不同。

### 7. 中途的崩溃与它的真正原因（→ FINDINGS §82 / §84 / §85）

补上座位数据后，F5 能进开局握手了，但 `0x0412` 一发出客户端就在渲染路径
空指针崩溃（`C0000005 @ 0x50a368`），`[LobbyStage+0x1d0+我的座位*4]` 是 NULL。

**新工具 `tools/probe_room_seats.py`**（轮询 6 个座位 + 每座位的角色对象指针）
一次采样就定案：

```text
[00:20:42.698] 座位0 ... 对象=0x3d1c8038     ← 0x0300 建的
[00:20:52.535] 座位0 ... 对象=0x0            ← 切 stage 时拆除
[00:20:54.142] 座位0 ... 对象=0x3d1c8038     ← 加载流程又重建了（同地址）
```

所以「变 NULL」是**正常过渡态**，错的是我们发包的时机。真正的机制是：

- `0x0400 gspPrepareGame` 的处理器最后 `push 6 / call 0x40e47f` → **切 stage 6**（加载）
- `0x0402` 的处理器最后 `push 7 / jmp 0x40e47f` → **切 stage 7**（游戏）
- `0x0412` 在 `0x54e036` 的跳表里映射到 `0x54e546` = **未处理**，发了白发

我们原先一口气回 `0x0402` + `0x0412`，等于跳过 stage 6 直接把客户端踢进 stage 7。

### 8. 修正后的开局链 → 进游戏 ✅

```text
C→S 0x0402  → S→C 0x0401 result=0
C→S 0x0402  → S→C 0x0400 seed=0     ★ 切 stage 6，客户端开始加载关卡
C→S 0x0403  → S→C 0x0402            ★ 加载 100% 后的轮询，这时才切 stage 7
```

`0x0403` 是客户端加载完之后**每 5.02 秒一发**的空包轮询，等的就是服务端放行。

### 9. 用户实测反馈 + 根因定位（→ FINDINGS §86）

用户玩了一局，报了两个现象：**血量归零人物不死站着不动**、
**倒计时归零关卡不结束**。日志里一局的包全都在，根因就是服务端没接：

```text
00:40:04.089  C→S 0x040f gcpEndQuest  (载荷 0)     ← 12:30 倒计时归零那一刻
00:40:04.095  C→S 0x0417 gcpMarkQuestSuccess(0)
              服务端一个都没回
```

从 RTTI vftable 反查 `0x54e036` 分发树，确认了两个应答 opcode：

- **`0x0419` = `gspRespawnCharacter`**（vft `0x6916b0`，处理器 `0x553ecc`）
  —— 线格式已完全读出：4 个 int32 `id, X, Y, ?`，X/Y 在线上是整数
- **`0x0411` = `gspEndGame`**（vft `0x691874`，处理器 `0x551804`）
  —— 线格式只读到开头，`0x54cea3` 还没读到 `ret`

---

### 10. 实现两个战斗应答（→ FINDINGS §87）

- **`0x0411 gspEndGame`** = 14 个 4 字节字段（`0x54cea3` 数到 `ret`）：
  座位号、成功 bool32、12 个业务值。**`+0x1c` 在客户端是 `[0x72e330] +=`**，
  所以未查明语义前必须填 0，否则每结算一次玩家数据就涨一次。
  接线：收到 `0x040f gcpEndQuest` 就回。
- **`0x0419 gspRespawnCharacter`** = 4 个 int32 `id, X, Y, ?`。
  **坐标在线上是整数**，客户端 `fild` 转 float。

重生的触发条件只能靠推断：死亡时客户端**什么包都不发**
（上一局实测静默了整整 11 分钟），所以用「战斗中静默 8 秒」当死亡信号
（`Conn.maybe_respawn()` + `sock.settimeout(1.0)`）。

实机：进关卡后剧情演出期间就误触发了一次 ——

```text
[00:57:03.165] 战斗中静默 8.1s，判定角色死亡卡住 (第 1 次)
[00:57:03.167] ← 回 gspRespawnCharacter(id=0, x=3225, y=635)
```

**客户端没崩，之后正常进入战斗**（持续发 `0x0408`/`0x0410`），
说明包格式被接受了。但误触发本身不干净，见下面的遗留。

测试 41 → **45 项全通过**。

### 11. 用户再次反馈：重生包把游戏搞坏了（→ FINDINGS §88）

用户报「提示『15秒内没有向前移动将强制退出』，15 秒后没真退出，
但会被传送到边缘位置无法移动」。**这是我引入的问题**，日志里有铁证：

```text
01:04:51.534  服务端：静默 8.1s → 发 gspRespawnCharacter(x=3225, y=635)
01:04:51.557  客户端：★ 0x0106 gcpReportHack —— 仅 23 毫秒之后
```

因果链：静默误判 → 传送到上一场景的坐标（本场景非法）→ 角色卡在地图边缘
→ 无法向前 → 触发闯关的反挂机警告 → 客户端报 hack；
而强制退出流程也要服务端配合，我们没接，所以 15 秒后并不会真退出。

两条重要教训：

1. **`0x0106 gcpReportHack` 是免费的正确性检查器**，比截图快、比「没崩」严格。
2. **闯关有强制推进机制，「挂机等 12:30」这条测试路线走不通** ——
   这也是本会话最终没能实机验证 `0x0411` 的原因。

处置：`RESPAWN_IDLE_SECONDS` 默认改 0（关闭），加 `--respawn-idle` 开关。

**另一个自己踩的坑**：服务端是 00:53 启动的，01:01 改的默认值没生效，
用户又多踩了一轮。**改完 `gameserver.py` 必须重启服务端进程。**

## 遗留 / 下个会话从这里接

0. **`0x0411 gspEndGame` 实机未验证**。要验证得真把关打完/打输，
   不能挂机等超时（§88）。
1. **重生的触发条件要做扎实**。「静默 8 秒」会被剧情演出误触发。
   入手点：`0x0408`（18 字节，疑似开火/命中）的服务端方向处理器 `0x551e44`，
   看能不能反推出伤害/血量结构，让服务端自己算死亡。
2. **结算之后怎么回房间**：`0x0403` 的**服务端**方向处理器 `0x5518fb` 是
   `mov [LobbyStage+4], 2` + `push 5 / call 0x40e47f` = 切回 stage 5（RoomStage）。
3. **`gspEndGame` 那 12 个业务值的语义**：已知 `+0x1c` 累加进 `[0x72e330]`，
   `+0x10/+0x14/+0x18` 分别落到 `[0x72e33c]/[0x72e344]/[0x72e340]`。
   13 个 dword 整体进结算 UI `0x4a4096`，从那里能反推每格显示什么。
   `0x0410` 报的累计分数（4→12→…→64）大概率要回填。

四条仍然有效的禁忌：不发 `0x0409`（§76）、不发 `0x0412`（§84）、
不在客户端报 `0x0403` 之前发 `0x0402`（§85）、
不回显 `0x0406`/`0x040f`/`0x0410`/`0x0415`（服务端方向全是未处理，§86）。
