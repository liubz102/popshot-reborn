## §6 ★★★★ 「一个角色」由什么构成（🔍静态 + ✅离线核对）

- **模型**：`Models/Characters/chNN/chNN<类><4位设计号>.msh` + 同名 `.dds`；
  `chNN@<动作>.mtn` + 可选 `.evn`。
  类字母（`0x505cee` 的跳转表）：`0`=头发/头 `H`=脸 `B`=上衣 `G`=手套 `L`=下装 `S`=鞋
  `^C`=头饰 `^N`=? `^T`=尾巴 `^W`=翅膀 `T`=套装 `W`=手持武器 `D`=弹体 `J`=?
  路径模板 `Models/Characters/Ch%02d/%s` + `ch%02d%s%04d.msh`（`%02d` 是最小宽度，100→`ch100`）。
  **最低必需动作集 = 15 个角色目录的交集 = 73 个**。
- **数据**：`ChrProps.ini`（`ChrIndex=` 才是真 id，节号只是下标；`WeaponIdxBase=1e6+id×1000`）、
  `weapon.ini` 的 `[chNN-dash/-01/-02/-03]`、`NewMutu.ini` 10 节、`Chinese.ini`（**韩文原串当 key**）、
  2D 弹体还要 `default.amf` 里的条目。
- **图集**：小头像 2 帧 + 大头像 2 帧（灰 / 彩），见 §3。
- **音效**：`Sounds/FX/char/KR/char/chNN/`、`…/voice/chNN/`、`FX/wp/chNN/`、
  `Sounds/CharacterChanger/ChNNN.ogg`。
- ★ **战斗内 HUD 立绘不是图集**：`Images/Ui/Portrait.png` 那 35 帧在 exe 里**没有任何引用**，
  HUD 立绘是把模型实时渲染到名为 `Game/Portrait` 的贴图上
  （`ChrProps` 的 `PortraitScale` / `PortraitXOffset` 就是给它用的）。**加角色不用管它。**

## §7 ★★★★ `.msh` / `.mtn` / `.evn` / `.dds` 格式（够用的部分）（🔍静态 + ✅离线核对）

- **`.msh`**：`u32 版本=3` + 4×4 矩阵 + `+0x6c` 顶点数 + `+0x70` 索引数 + 顶点 32 B +
  索引 u16 + 材质块（含 **`u32 码元数 + UTF-16LE 贴图名`**，如 `len=13 + "ch01B0000.dds"`，
  同一文件可能出现 2 次）+ `u32 骨骼数`，每根 `u32 长度 + UTF-16 骨骼名 + u32 n +
  n×索引 + n×权重 + 16 float`。
  ⚠ **偏移 `0x4c` 还有一个长度前缀串是挂接特效路径**（`ArmorSpakle\Efx\CH01_*.efx` 等，
  ch01 有 8 个文件带）—— **含 `/` 或 `\` 的串一律不能当贴图名改**。
- **`.mtn`**：`u32 版本=3 + u32 长度 + UTF-16 "AnimationSet0"` + 骨骼名表。
  ch01 的 86 个 `.mtn` 内部 **0 处** `chNN` 串 ⇒ 克隆时**一个字节都不用改**。
- **`.evn`**：明文 XML，CP949，声明 `encoding="ks_c_5601-1987"`，逐帧事件（`PlaySound` /
  `RenderEffect` + `ResourcePath`）。⚠ ch01 有 **2 个 `.evn` 引用别的角色**
  （`Mutu-DamagedFly`→ch00、`MutuStand-P00`→ch02），**无差别替换会改错**。
- **`.dds`**：128 字节头 + 像素区。ch01 的 268 张里
  **117 张 64×64 R5G6B5（8320 B）、122 张 64×64 A8R8G8B8（16512 B）、
  17 张 128×128 R5G6B5（32896 B）、只有 8 张 DXT1/DXT3** ⇒ **绝大多数是未压缩的**，
  改像素时**把 128 字节头原样保留**即可，别用 `PIL.Image.save(*.dds)`（它不保证吐出同样的头）。
- ★ **骨骼必须同源**：V0.3商店 §50 记过「骨骼按名字在角色骨架里找，找不到返 NULL，
  喂进矩阵乘直接崩」。ch02 有 `Bone_Spine_01`/`Bone_Pelvis_01` 而 ch00/ch01 没有。
  爱琳 ChrProps 点名的 `Bip01_R_Finger1` / `Bone_Wp00_02` / `Bone_Wp00_11` **在 ch01 骨架里全有**。

## §11 ★★★★ `.msh` 的**完整**布局（✅ 257/257 round-trip 逐字节一致）

§7 只写了「够用的部分」。`tools/mshtool.py` 把整个格式吃透了，按顺序：

```
u32 版本=3 | 4x4 矩阵 | 0x44 处 4B 标志 | 0x48 处挂接特效数 + 每条(wstr + 4B)
| 32B 零块 | u32 顶点数 | u32 索引数 | 顶点(32B) | 索引(u16)
| 材质块（★ 45 个头发件有 **2 个**材质，不是一个）
| u32 子集数 + n×4×u32
| 骨骼块（u32 骨骼数，每根 wstr + u32 n + n×索引 + n×权重 + 16 float）
| ★ 末尾还有**模板阴影用的邻接表**：u32 面数 + 每面 40B
  （面号 / 邻居数 / 3×u16 邻居面 / 3×2×u16 共享边 / 14B 零）
```

- `ch0300011.msh` 的邻接表后面还挂着 **676 B 残片**，引擎只读前 n 面 —— 原样保留即可。
- ⇒ 改顶点坐标是安全的（只动 xyz，拓扑/骨骼/权重/邻接表一个字节不碰）；
  **追加三角形要同时改索引、子集面数、邻接表**，是完全不同的风险等级。

## §14 ★★★★ `.mtn` 格式全解 + 绑定姿态的三条坑（✅ 86 个文件复现，工具 `tools/mtntool.py`）

```
u32 3 | wstr "AnimationSet0" | f64 3600(tick/s) | f64 时长 | u32 229 | u32 0
| 骨架树 | u32 轨道数 | 轨道…
```

- **骨架树按 D3DXFRAME 序列化**：每节点 = 名字 + 16 f32；有子节点写 `1` 递归首子、
  有兄弟写 `2` 递归兄弟、收尾写 `3`。ch03 是 **229 个节点**（173 有子、55 有兄弟）。
- 轨道 = 名字 + 旋转 `(t, qx qy qz qw)×n` + 平移 `(t, xyz)×n` + 缩放×n，**帧距 120 tick**。
- **86 个文件的骨架树完全一致**；`Crouch-Start.mtn` 轨道后有 35602 B 垃圾残片（引擎不读）。
- **103 根骨没有轨道**，用树里的静态矩阵。

三条坑：

1. `.msh` 骨骼块尾部那 16 float 是**绑定姿态世界矩阵的逆**（网格单位）。
2. **默认件顶点是「场景单位 ÷ 2.8791」**（`0x04` 的世界矩阵就是这个缩放），
   另有 185 个文件用场景单位或轴置换。
   补缺骨的公式：`bind(子) = 局部(Stand00, t=0, 场景单位) · bind(父)`，
   ★ **平移不要再除 2.8791**。
3. **绑定姿态 ≠ 任何一帧动画**（Stand00 第 0 帧头在 y=69.2，绑定姿态 70.96）；
   而且**不同套装的手臂骨绑定姿态不同**（`B0014` 的 Clavicle 差 13）——
   从别的件借 offset 前必须逐骨核对共同骨。

## §15 ★★★ 邻接表和绕向的规则（✅ 256 个文件复现 213 个）

- 位置**逐位相等**焊接后找共边，每条共边**只记在面号小的那面**；
  条目 = `u32 面号, u32 邻居数, 3×u16 邻居(补 0xFFFF), 3×2×u16 本面该边顶点号, 14 B 零`。
- 面绕向 `cross(b-a, c-a)` = 外法线（98%+），**引擎开背面剔除** ——
  要做双面片（花瓣、蝴蝶结）就得像 `ch01B0006` 那样放 15 组反向重复面。
- **每顶点最多 3 根骨**；双材质只出现在头发类（39 个件）。

## §17 ★★★★★ 「裙子上有网格线」的根因：邻接表把双面薄片的**正面和反面配成了邻居**，不是贴图 / UV（✅离线复现，⏳等实机）

**结论**：`.msh` 末尾的邻接表是给**模板阴影**抽轮廓边用的（一对邻居面一朝光一背光 ⇒ 这条边挤出阴影体）。
`geometry.py` 的花瓣是双面薄片（正面 F/F2 + 反绕向副本 F'/F2'，每条内部边上 4 个面），
`mshtool.build_adjacency` 的旧规则「取第一个面号更大的面当邻居」写出了 `F2→F'`（正面配反面）——
正反面永远一朝光一背光 ⇒ 花瓣的**每条内部边都成了轮廓边**，阴影体沿三角形的边落回裙面，就是那些暗线。

- 贴图 / UV 排除：每片花瓣独占一块连续渐变区，缝只在花瓣外沿，画不出花瓣**内部**的格子（`tools/ch03_skin/compare_D_skirt.png` 左）。
- 原版 `ch01B0006`（蝴蝶结，15 组反绕向重复面）的表：内部边记 `(F,F2)`+`(F',F2')`，**只有边界边**才记 `(F,F')`
  ⇒ 导出工具的规则是「每条边上的面按面号排序后**两两配对**」。换成这条规则后 ch01 256 个文件复现 213 → **235** 个，无退步。
- 用 `mshtool.silhouette_edges` 按同一光向模拟：旧表在 `ch03B0000` 上抽出 508 条轮廓边（花瓣内部全是），新表 220 条（只剩外沿）；
  新表里法线相反的邻居对 128 个，**全部落在只有 2 个面的边界边上**，和 B0006 同构。
- 修法：只改 `build_adjacency` 规则重跑 `geometry.py`，顶点 / 索引 / 骨骼逐字节不动（`ch03B0000` 去掉 309 对、`ch0300000` 去掉 28 对）。
- ⚠ 🤔 exe 里没搜到 `stencil` 字样（只有 `Shadow=` 这个 ini 键和 `NpcBossShadow.png`），「引擎拿这张表做模板阴影」是从

## §30 ★★★ 管理页日志下载：审计行是**发完结束块之后**才写的（✅两套运行时实测）

`web/admin.py::_admin_logs_download` 的顺序是：`body.finish()` 把 chunked 结束块写进
socket → **然后**才写 `eventlog.online(…)` 那一行审计。而 `wfile` 不带缓冲

## §42 ★★★★★ `WeaponTable::Load` 的调用时机**不等于开局**；弹匣容量进图时就被快照走了（✅两份日志对齐 + 🔍逐指令）

**结论一：D27 的前提是错的。** `Load` 挂在**场景对象构造**上，而客户端会复用场景对象。
2026-09-19 实测（`bshook_20260919_102009` × `server.out` 逐条对齐）：

- 11:30:40 第 1 局**闯关开局**时模式还是【对战】，`Load(4A3B81)` 到 **11:32:07**
  （第 1 局打完 15 秒后）才跑 ⇒ **第一局闯关用的是 PVP 那套值**；
- 11:37:07 建 PvP 房、11:37:33 开局，**一次 `Load` 都没有**（也没有「⚠ 不认识的地方」那条日志）
  ⇒ 模式卡在【任务】，后面两局对战全按 PVE 的数值打。

⇒ 模式只能由**建房的那一方**说 —— 服务端（D32）。`0x0F01` 格式 1 → 2，头上多一个模式字节。

**结论二：弹匣容量是快照，局内改不动。**

- `[持枪器+0x48]`（弹匣容量）和 `[持枪器+0x54]`（当前弹药）都是 **4 格 vector**，内容由
  `0x48b96e`（`0x517233`，角色装备武器时）**一次性灌进去**；换弹 `0x48bc2a` 抄的是这份快照
  （`ammo[i] = maxAmmo[i]`），`0x48bc76` 是「四格全填」的版本（`cmp eax,0x10` 钉死 4 格）。

  （不在表里就用默认那张）。⇒ 局内改记录：**图标立刻变、实际弹匣不变**，两边必然对不上。
- ⇒ ① 开局那一发推送必须排在 `0x0400`（客户端切 stage 6 开始加载关卡）**之前**，
  这一局的快照才是新值；② 局内干脆**不写内存**，数值改动统一「下一局生效」（D32）。
