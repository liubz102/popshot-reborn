## 查的过程

1. `grenades.py`（scratchpad）：解 `server.out` 里 bot 的 `rpFire` / `rpExplode`（inner 0x0002 / 0x0003，发送方座位 1）+
   客户端 `PROJ+` / `PROJ.` 逐帧轨迹，按「局 + 句柄」配对。碎片从服务端炸点重生 ⇒ 玩家看到的就是「雷瞬移到别处炸」。
2. `replay2.py`：主雷原字节喂服务端 `_shell_step`，鲤鱼时钟 = 锚点 + 偏移 + 32 ms × 格；**破坏物按日志还原**
   （「破坏物碎了 … N 秒后长回来」）—— 不还原的话 (822,652) 那块 20 s 的会造出一组 500~700 px 的假分叉。
   - 锚「hook 报告 + 墙钟外推」：服务端实炸点大多 0 px 复现（= 服务端当时的时钟），但 47 颗里 25 颗偏离客户端 >20 px。
   - 逐颗扫偏移（10 s 周期）：客户端的鱼比服务端晚 ≈ 加载等待（局 0 ≈ −8.4 s、局 1 ≈ −6.2 s）⇒ 客户端从开打算起。
   - 锚「`0x0402` − 45 ms」：只剩 13 颗；200087（破坏物顶反弹角）/ 200154（真人交互）/ 200132（擦鱼边）与起点无关。
3. 逆向：全镜像「`call 0x40a01e` 紧跟 `mov [r32+0x90], eax`」只有两处 —— `0x511d97`（LinkPath）和 **`0x476463`**；
   后者在 World `0x476435` 里，唯一调用者 `0x491388` 在 `GameContext::StartGame`（虚表 +0xc = `0x491244`），
   23 个 GameContext 子类的 +0xc 都是它或 call 它 ⇒ 所有模式开打都重取起点。
4. 「同步为什么没纠正」：`Timer()` 的 `[[0x72e2b4]+8]` 是 Desktop 的**当前 Stage**（`Stage::Tick` 0x42b548 存 now 到 +0xe0），
   stage 6 / 7 是两个 new 出来的对象（工厂 `0x40bcab` / `0x40bd19`）⇒ hook 的 `gc != g_mover_gc` 门在开打后拦掉全部发包；
   而且就算发，报的也是记表时缓存的 t0。World `[0x72e2d4]` 是单例（两局同一个），按 World 去重的日志整个进程只打一行。
